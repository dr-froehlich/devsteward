## Context

The REQ-047 trunk-based pivot (landed across REQ-048…051) collapsed the team-scale git
topology — feature branches, worktrees, engine-initiated branch switching — into a single
dev-only model. A migration of that size leaves residue, and this REQ is the disciplined
sweep that pays it down. Two kinds:

- **Code residue.** Stale segments survive a large overhaul: dead code paths, an
  architecture still *bent* toward the removed topology, legacy structure that still shapes
  parts of the code even though the reason for it is gone.
- **Skill residue.** The shipped skills still carry guidance that only made sense under the
  old model. The canonical case Peter caught mid-migration was language like *"we commit to
  dev, not to a feature branch, because the governance is not to always commit to dev."* In
  a tool that lives only on `dev` and never commits anywhere else, that is a single, stable
  invariant — re-justifying it at every turn points at a legacy that is gone, and is at best
  superfluous and at worst distracting. The skills should read concisely as the *current*
  tool.

This REQ is scoped to **code review** and **skill review**. The process-resilience question
raised in the same idea stub — does every red step have a clear, available path forward, and
do the `recover`/`rework` verbs map onto the real "rework vs repeat" choice — is a separate
concern with its own acceptance; it lives in REQ-053.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | The durable deliverable is a written review report in `docs/reports/`, plus the clearly-safe fixes applied inline. | A review's honest oracle is a human reading the findings; this matches existing practice (`docs/reports/` already holds the 2026-06-10 assessment and the postmortems). Low-risk subtractions land in the same sweep. |
| 2 | Fix only what is **feasible and low-risk**; raise everything else as a recommendation or a named follow-on REQ — never an unreviewed inline rewrite. | Honors "prefer subtraction / add machinery only on present need." A cleanup review must not smuggle in a risky refactor. |
| 3 | Skill review targets the **production (shipped) skills and their hardlinked templates**; the two legacy consumers (DevSteward dogfooding, FlowSteward) are handled, but **not at the production-skill level**. | Production skills must read as the current state of the tool; consumer-specific or dogfooding residue must not pollute them. Repo `.claude/skills/<name>/SKILL.md` and the stamped template are one inode (edit once, never double-edit). |
| 4 | The audit's verdict is **human** (`manual`); the inline fixes are guarded by the full suite staying green (`regression`). | No artifact-less green: a review can only be certified by its reader. The regression AC exists solely so subtraction does not break the build — it does not certify the review. |

## Requirement

### Code review

Look for stale code paths, architecture bent by the removed topology, and legacy structure
that no longer has a live reason. Fix the feasible, low-risk ones inline; raise the rest in
the report with a concrete recommendation (or a named follow-on REQ).

### Skill review

Remove the superfluous legacy-justification language from the shipped skills (and their
hardlinked templates) so each reads concisely as the current dev-only tool. Anything that
concerns DevSteward's own dogfooding or FlowSteward specifically is handled outside the
production skill, not inlined into it.

### Deliverable

A review report at `docs/reports/2026-06-19-req047-migration-review.md` covers **both** the
code review and the skill review. For every finding it states the residue and its
disposition: *fixed inline* (with the fix named), *recommendation* (with how to address it),
or *spun out* as a named follow-on REQ. After the inline fixes, the full test suite is green.
