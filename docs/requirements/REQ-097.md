## Context

Sixteen projects on the development box are stamped under the engine, and each one answers
"where does it stand" only from inside its own directory: `steward status` for the cursor,
`git status` and `git log` for the tree, `steward backlog-list` for the needs. Knowing the
state of everything means sixteen directory changes and three commands each. Nothing shows
the whole estate, and nothing shows what is waiting on the *operator* — a parked decision
here, a validation to sign off there, a failed step in a project not touched for a week.

REQ-093 named this tool as its follow-on: "The status server — a small web surface showing
projects, their state, and backlog items with a way to tick them off — is a separate
objective and a separate REQ; Decision 4 is the constraint this REQ owes it." Decision 4 made
the acceptance verdict a standalone command precisely so "a future status server must be
able to record one". That constraint is honoured here and extended to the rest of the
backlog surface: the dashboard is where the owner reads, authors, edits and rules on needs
across every project, not per project.

The owner's needs are recorded in this project's own backlog (`docs/BACKLOG.md`, created for
this intake — the first time devsteward has had a user-need queue of its own) with their
acceptance criteria in his words; this REQ takes seven of them up. Two boundaries came from
the interview and are hard: the tool **never runs a Claude session** — it changes state the
way the CLI does and leaves the run itself to a shell — and it **never edits a REQ**. The
eighth item, `simpler-state-changes`, is deliberately *not* taken up: it asks to revisit a
recorded choice (REQ-055 Decision 2, "red-only, symmetric to rework — Peter's choice") and
deserves its own intake; this dashboard mirrors whatever state changes the CLI offers at
the time, so the two are independent in either order.

Deployment was interviewed as a need, not a mechanism. A 24/7 LAN server with pulled clones
was rejected: the tool *writes* into project state (verdicts, ledger flips, items), those
writes land uncommitted in the working tree and ride the next checkpoint, so it must operate
on the working copies the sessions use — and nine of the seventeen project folders have no
remote at all, so a mirror could never be complete. Docker on WSL2 was rejected for adding a
second engine install inside an image (against "pipx editable, and nothing else") with no
isolation need to justify it. What remains is the simplest option: a plain local process,
started on demand, bound to loopback, viewed in the box's own browser.

## Requirement

### The verb

`steward dashboard [--root DIR] [--port N]` serves a local web application on `127.0.0.1`
and prints the URL. Without the `dashboard` extra installed it exits non-zero with the exact
install command (`pipx install --editable '.[dashboard]'` for this repo, `pipx inject
devsteward flask` for an existing install). It runs until interrupted. It never spawns a
Claude session and never invokes `steward run`, `advance` or `validate`.

### Discovery and the overview

The overview lists every stamped project under the root with its **steward status** (the
ledger cursor, eligible and blocked steps, parked decisions, stamped-artifact drift — what
`steward status` reports) and its **git facts** (Decision 8), and lists unstamped folders
separately for information. A **needs-me** strip aggregates, across all projects, what waits
on the operator: parked decisions, validate steps awaiting a human sign-off, and FAILED steps.

### The project page

One project's status and git facts in full; its backlog with each item's derived state, its
attempt record (which REQ took it up, succeeded, is still running, or was attempted and
denied with the reason) and its acceptance criteria; and its requirements index. Each REQ
opens as a read-only rendered page.

### Backlog authoring

From the project page the operator can add an item, edit an item's need, origin and
acceptance criteria (Decision 6), and record a verdict — accept, deny with reason, hold with
reason, retire with reason — each through the same function the corresponding CLI verb calls,
writing the same file and appending the same event.

### Error resolution

For any step the page offers exactly the state-changing verbs the CLI offers for that step —
`rework`, `revalidate`, `repeat`, `reland`, `activate`, `decision-answer` — through the same
lifecycle functions, with the same preconditions and the same refusal messages. After a
change the page shows the new state. The run itself remains a shell command.

### Out of scope

Running any Claude session or batch verb from the UI (may be revisited later). Editing REQ
content. Authentication, remote access, multi-user use, a service unit, Docker. The
retrospective and per-project governance loop REQ-093 named. Revisiting the state machine —
that is `simpler-state-changes`, its own future intake.

## Notes

**The UI's own criteria arrive after the freeze (Decision 2).** AC1–AC7 prove the mechanism
and can be written today. What the pages must show — layout, what is one glance and what is
one click — cannot be honestly specified before the operator has looked at a prototype. The
concept session builds it, iterates attended until the owner freezes it in the concept
bundle, names the bundle in `concept_refs`, and then appends the target ACs it has earned to
the block above before `steward checkpoint`. No downstream REQ carries them.

**Required environment (REQ-064).** AC6 and AC7 import Flask. They are `regression`, not
`live`: the resource is an installed package, not a service, and a missing package is a hard
red (an import error), never a silent skip. The develop session installs the extra into the
tooling `.venv` (`.venv/bin/pip install flask` — the *package* itself is never installed
there, per CLAUDE.md) and into the pipx engine (`pipx inject devsteward flask`), and records
both in the plan.

**The owner's acceptance is separate.** The seven items' criteria in `docs/BACKLOG.md` are
the owner's verdict surface (`steward backlog-accept`/`-deny`), recorded after living with
the result; none of them is an AC here (REQ-093 Decision 2).

**Attended develop.** `process.concept: true` makes the develop step attended; batch parks it.
Start it with `/advance REQ-097 develop`.
