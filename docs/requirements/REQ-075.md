## Context

`steward revalidate` (REQ-055) treats a red validation as an all-or-nothing unit: it flips
the whole `:validate` step back to PENDING and the next validation run re-captures **every**
AC from scratch. FlowSteward REQ-080 showed why that is wrong for mixed-check REQs. Its
validation carried one repeatable observation (AC2, a health-watermark window) alongside
two expensive attended one-offs (AC3, a human-signed bulk-move rehearsal; AC4, a pg_dump
restore into a scratch database). When AC2 went red, revalidate forced the one-offs to be
re-performed — hours of attended work whose evidence already existed, was already graded
green, and was already committed to git. Worse, the re-run AC4 restore saturated the
database host's I/O *during* AC2's fresh observation window and pushed the tick durations
over their threshold: the full re-run **contaminated the very measurement it was retrying**,
manufacturing another red and another revalidate round. Per the REQ-068 taxonomy, `artifact`
and `manual` checks are one-time validations, not regression members — re-performing a green
one-off on every retry contradicts the engine's own classification.

The same incident exposed a second, independent gap: **the engine never tells the grading
tests where the evidence is.** The engine creates `.devsteward/evidence/REQ-NNN/<stamp>/`,
names it in the guided session's prompt, and runs each `artifact` AC's test itself — but
injects nothing into that test's environment. Consumers filled the void with an ambient
convention (FlowSteward's `FLOWSTEWARD_EVIDENCE_DIR`, exported by whatever shell captured
last). An export from one REQ's capture outlived its session, rode process inheritance
through `steward validate` into the grading pytest, and made REQ-080's tests grade
REQ-081's directory — three identical red rounds whose cause was invisible from the
failure text. The engine holds the authoritative path at grading time and drops it on the
floor; the leak is the predictable result.

Required environment: none beyond a clean checkout — all acceptance is headless
fixture-ledger testing of engine logic.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Red-only re-open is the engine **default** of `revalidate` — no `--ac` flag, no session discretion | The engine owns certification (REQ-001 D3); the last validation event already records per-AC results, so the engine can scope mechanically. A human-typed AC list invites re-certifying a red AC by omission; a session-level convention puts a certification decision outside the engine. |
| 2 | Green one-off evidence is carried forward **automatically, with provenance** | Running `revalidate` already asserts "the develop stands; the cause was external" — that assertion covers reuse. The engine copies the green ACs' artifacts into the new evidence dir and records their origin (source evidence path + original validation event) in the new validation event; no extra interactive stop. |
| 3 | The engine injects `DEVSTEWARD_EVIDENCE_DIR` into each `artifact` grading command, per-subprocess, unconditionally | Gives the grading side the defined channel it never had. Set fresh from the path the engine holds, it lives only for that one command (nothing to leak) and **overrides** any stale inherited value, killing the ambient-export failure class for every consumer. Documented in STEWARD.md as part of the black-box contract. |
| 4 | Grade-only retry (re-grade an existing capture without a new System-Test session) is **out of scope** — a named non-goal | Its motivating case was the ambient-var poisoning, which Decision 3 eliminates at the root. If a distinct grade-only need recurs, it gets its own REQ; see Notes. |
| 5 | Acceptance is `regression` only — no manual live proof | Operator's deliberate call at intake (2026-07-05): the engine logic is fully exercisable against a fixture ledger, and the validate-pending queue cost of another attended sign-off outweighs a supervised first run. The first real exercise happens in a consumer; treat any surprise there as a postmortem input. |

## Requirement

When a validation records mixed per-AC results and the operator runs `steward revalidate
REQ-NNN`, the subsequent validation run re-observes **only what was red** and re-certifies
the whole REQ from the union of fresh and carried evidence:

1. **Scoping.** `revalidate` reads the step's most recent validation event. ACs that were
   red (or unrecorded) are re-opened for capture; ACs that were green keep their standing.
   The scoped set is recorded on the revalidate event. Degenerate cases collapse to today's
   behavior: no per-AC results available, or every AC red → full re-run.
2. **Scoped capture.** The guided System-Test session is told, in its prompt, exactly which
   ACs to capture — a green one-off (`artifact` or `manual`) is not re-performed.
3. **Carry-forward with provenance.** Before grading, the engine copies each carried
   `artifact` AC's files from the source evidence dir into the new run's evidence dir, and
   carries a green `manual` AC's recorded sign-off; the new validation event names, per
   carried AC, the source evidence path and the originating validation event. The "no
   artifact captured → hard red" rule still applies to the fresh ACs' output.
4. **Evidence handoff.** Whenever the engine runs an `artifact` AC's test command — on any
   validation, not just a revalidate — it sets `DEVSTEWARD_EVIDENCE_DIR` to the current
   run's evidence dir in that subprocess's environment, overriding any inherited value.
   STEWARD.md documents the variable as the supported way for a consumer's grading test to
   locate its evidence.

## Notes

- **Out of scope (named non-goal, per Decision 4):** grade-only retry — re-running the
  grading tests against an already-captured evidence dir without a new System-Test session.
  The env-poisoning incident that motivated it is root-fixed by Decision 3; if a genuine
  grade-only case recurs (capture good, grading infrastructure broken), file a new REQ
  rather than widening this one.
- **Consumer migration (FlowSteward):** its artifact tests switch to reading
  `DEVSTEWARD_EVIDENCE_DIR` (briefly falling back to `FLOWSTEWARD_EVIDENCE_DIR`, then the
  old name and every `export` convention in its runbooks dies). That migration is
  FlowSteward's own REQ, not this one.
- **Origin:** FlowSteward REQ-080's validation loop, 2026-07-05 — three env-poisoned red
  rounds plus one self-contaminated re-run (restore I/O during the health-observation
  window), all forced through full re-capture.
- Carry-forward interacts with `reland` (REQ-065) and `validate-on-done` (REQ-073) only
  through the validation event schema; the new provenance fields are additive.
