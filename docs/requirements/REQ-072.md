## Context

The **capture gate** (REQ-050 → made non-destructive by REQ-063: the pre-commit
`_capture_gap` → `_green_gap_at`) re-runs a develop step's named acceptance tests against a
clean `git archive` extract of the staged tree, to prove the recorded commit reproduces its
own green. The extract holds **only tracked content** — by design, it strips the gitignored
`.env`. But the consumer's test bootstrap *reads* that `.env` from the working directory (now
the throwaway extract dir) to resolve its environment. So the capture gate runs the same tests
the develop gate just passed, **in a different environment than the develop gate used**.

**The concrete loss (FlowSteward).** FlowSteward declares its registry database engine in a
gitignored `.env` (`FLOWSTEWARD_DB_ENGINE=postgres` + `FLOWSTEWARD_DB_*`). The develop gate
runs in the operator's repo root, the test reads `.env`, resolves Postgres, and goes green.
The capture-gate extract has no `.env`, the bootstrap falls back to the hermetic SQLite
default, and the Postgres-only DB-integration tests **fail** there — e.g. a JSONField
`__contains` lookup SQLite can't compile. A green, paid-for develop checkpoint fails *its own*
capture gate for environment reasons alone, with no code regression. The operator's only
recovery today is to hand-`export` the DB vars into the shell and `steward repeat` — a manual
patch for an **engine-introduced asymmetry**: the engine changes the environment between the
gate that *passes* a step and the gate that *re-verifies* it. This violates the consumer's
stated invariant that develop and both validation modes must refer to the **same** environment.

**This is the fail-side complement to REQ-063.** REQ-063 ruled that an environment *skip* in
the bare extract is not a capture gap — but it could only address skips, because it had no way
to *carry* the environment in. When the missing environment makes a test **fail** (not skip) —
as a Postgres-only lookup does on SQLite — REQ-063's skip exemption doesn't apply, and the gate
(now non-destructively, per REQ-063) withholds certification anyway. The right fix is upstream
of the skip-vs-fail distinction: **reproduce the develop gate's green in the same *declared*
environment, not a stripped one.** With the declared env carried in, the test that passed
verify passes the capture check too — no skip-classification needed.

**The diagnosis is also a red herring.** On a withheld certification `_capture_gap_message`
asserts a single cause — "an uncaptured source/test file the commit can't hold — track it / fix
.gitignore." When *every* file is in the commit and the real cause is a dropped environment,
this sends the operator hunting for a missing file that does not exist. The message must frame
the gap honestly: the named test did not reproduce; the cause may be source/test **or**
environment — never *only* "a file you forgot to track."

**Honor-when-present, not require.** The clean-checkout property must not regress: a repo with
no env-file declared/present still runs the hermetic unit subset against the bare extract on the
SQLite default. The fix is "carry a declared env when one exists," never "demand one."

**Secrets.** The env-file carries credentials, so the carry must not leak them. The extract is
an `0700` `TemporaryDirectory` that is deleted after the run; the env-file is copied **into**
it (so a bootstrap that reads the file directly finds it) and `os.environ` is inherited as it
already is — but the file's *contents* must never reach a surfaced message, the event log, or
any persisted artifact. Copying into the ephemeral extract is the minimal carry that works for
both file-reading (`dotenv`) and `os.environ`-reading bootstraps without adding a config
allowlist the operator must maintain.

## Requirement

- Before the capture check runs the named acceptance tests against the tree extract, the engine
  **carries the operator's declared environment** into the extract: it resolves the env-file
  (`verify.env_file`, default `.env`), and **if that file exists in the repo root, copies it
  into the extract directory**; `os.environ` continues to be inherited by the test subprocess.
- A develop green whose named test passes **only because** a gitignored env-file is present in
  the operator's repo (its oracle reads a value the env-file declares) **reproduces green in the
  capture extract** and the land **certifies** — with **no** shell exports and no
  `steward repeat`.
- **Honor-when-present:** a repo with **no** env-file declared/present runs the capture check
  against the bare extract unchanged — a self-sufficient green certifies, and a genuine
  source/test gap (fail / error / zero-collection) is still refused (REQ-063's guarantee, intact).
- A project that declares a **non-default** env-file via `verify.env_file` has *that* file
  carried into the extract; the default `.env` is used when `verify.env_file` is unset.
- On a withheld certification, the surfaced diagnosis **does not assert** "an uncaptured
  source/test file" as the only cause: it names the preserved work-commit SHA and frames the
  cause as source/test **or** environment, pointing at the env-file carry — and **never**
  instructs committing a gitignored secret.
- **Secrets do not leak:** the env-file is copied only into the ephemeral extract dir (deleted
  after the run); its contents never appear in a surfaced message, the event log, or any
  persisted artifact.
- The Claude-targeted `steward` black-box manual and the handbook note the env-file carry
  (`verify.env_file`), the "same declared environment" guarantee, and the honest recovery path.

## Notes

- **Why all `regression`, no lab (mirrors REQ-063).** The engine behaviour — *the declared
  env-file is carried into the extract; the hermetic path is preserved; the diagnosis is honest;
  secrets don't leak* — is fully provable with synthetic fixtures: a throwaway git repo whose
  named test reads a value from a copied env-file (the coupled stand-in for
  `FLOWSTEWARD_DB_ENGINE`). No real Postgres is needed to prove the *carry*; "DB engine" is one
  instance of "a declared environment." The real Postgres end-to-end (FlowSteward's AC suite
  passing its capture gate with only `.env` present) is the **consumer's** live proof, owned by
  FlowSteward — out of scope here, exactly as REQ-063 deferred its FlowSteward-side Defect 1.
- **`os.environ` was already inherited.** `subprocess.run` in `_reproduces_green` /
  `_pytest_outcome` inherits the parent environment by default; this REQ does not change that.
  The load-bearing addition is copying the *file* into the extract CWD, because the consumer's
  bootstrap reads `.env` from CWD (via `dotenv`) — the operator's shell does not carry the
  declared vars, which is why the manual recovery is to `export` them.
- **Not the validate land.** This stays a *develop*-land invariant; the validate phase remains
  exempt (`_capture_gap` early-returns for `phase == "validate"`).
- **Out of scope:** the FlowSteward-side real-Postgres validation (theirs), a declared
  env-key allowlist (rejected at intake in favour of copying the whole file into the ephemeral
  extract — least operator friction; revisit only if a leak surface appears), and any
  intake/taxonomy change.
