## Context

Onboarding an existing project (plan [0005-memzy-onboarding](../plans/0005-memzy-onboarding.md),
Piece 3) hits a wall the engine was never built for: `steward init` (`cli.py:322`,
`Ledger.init`) creates an **empty** ledger, and the REQ profile's step source yields
`REQ-NNN:{design,build,land}` steps for every REQ it finds. memzy arrives with 23 REQs that
are **already terminal** — built and verified by memzy's own process. Point `steward` at that
corpus with an empty ledger and the engine sees 69 pending steps and tries to *re-Design built
work*. The ledger is a cursor over reality; for an already-finished project the cursor must
start at the end.

There is **no `steward import-ledger`** today. The gap is small but real: something must mark
each historic REQ's three phase-steps `done` and leave a provenance trail, so that
`steward status` reports an all-done corpus and `advance`/`run` is a correct no-op until the
next `/intake` produces genuinely new work.

The key realization — settled in intake — is that **this tool is dialect-independent and
therefore generic**. It runs *after* the per-project converter ([[REQ-010]]) has already
produced schema-valid REQ files. It reads only the converted frontmatter (`id`, `status`),
never the source dialect. So the identical command seeds memzy, ExamEngineer ([[REQ-017]]), or
any future onboarding — which is exactly why it belongs in the installable package as a
first-class `steward` subcommand, not as a per-project script. The *conversion* is bespoke (a
script per dialect); the *seeding* is uniform (one command over the normalized result). That
boundary is the whole reason this is a command and [[REQ-010]] is a script.

This is **not** a re-adjudication of history — the same archivist boundary [[REQ-010]] drew.
The seeder trusts the converted `status: done`; it does not re-run historic suites (infeasible
against historic SHAs) and the verification gate ([[REQ-015]]) never fires, because seeding a
finished record is not landing fresh work.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | A first-class `steward seed-ledger` subcommand in the package, not a `scripts/` tool | It operates only on already-converted, schema-valid REQs (`id` + `status`), so it is dialect-independent and reusable for every onboarding. [[REQ-010]] Decision 6 keeps the *converter* a per-project script precisely because conversion is bespoke; seeding is uniform, so it earns package status |
| 2 | Seed only **terminal** REQs (`done`/`dropped`/`superseded`): set their `design`/`build`/`land` steps to `done`. Leave **active** and **draft** REQs untouched | Active/draft REQs are genuine pending work the engine *should* drive; only finished history needs the cursor advanced. This yields the correct outcome: a fully-terminal corpus produces an empty work queue, a mixed corpus leaves exactly the unfinished REQs eligible |
| 3 | Append one synthetic provenance event per seeded REQ to `events.jsonl` (e.g. `ledger_seed` with the REQ id), distinct from real checkpoint events | The ledger's event log is the audit trail; a seeded `done` must be honestly distinguishable from one the engine actually drove. No new state schema — reuse `append_event` |
| 4 | **Idempotent** — re-running seeds nothing already `done` and never duplicates events or errors | A migration step must be safe to re-run; the onboarding skill ([[REQ-024]]) may invoke it more than once while iterating |
| 5 | Operates on an **already-initialized** ledger (`_load_or_die` like other subcommands); errors cleanly if none exists | Keeps `init` and `seed` orthogonal and composable: the skill runs `steward init` then `steward seed-ledger`. No hidden ledger creation |
| 6 | Step ids and `depends_on` edges are handled **opaquely**, so lettered ids ([[REQ-021]]) seed correctly | memzy ships `REQ-028p`; the seeder derives `REQ-028p:{design,build,land}` via the same opaque path [[REQ-021]] guards. Pinned by a test, not assumed |

## Requirement

A `steward seed-ledger` command that, given an initialized ledger and a converted
schema-valid REQ corpus, advances the cursor to reflect already-finished history: every
terminal REQ's phase-steps become `done` with a provenance event, every active/draft REQ is
left for the normal engine, and the operation is idempotent.

### Behaviour

- For each REQ with a **terminal** status (`done`, `dropped`, `superseded`), set its
  `design`, `build`, and `land` steps to `done` via `Ledger.set_status`.
- For each REQ with an **active** (`open`/`in-progress`/`blocked`) or `draft` status, do
  nothing — its steps remain pending so the engine still drives it.
- Append one `ledger_seed` event per newly-seeded REQ (carrying its id) to `events.jsonl`.
- Re-running seeds only REQs not already seeded; no duplicate events, no error.
- After seeding a fully-terminal corpus, `steward status` reports all-done and `advance`/`run`
  is a no-op.
- Error cleanly (`ProjectNotFound`/clear message) when run with no initialized ledger.

### Out of scope

- **Conversion** of any dialect into the schema — that is [[REQ-010]] (memzy) / [[REQ-017]]
  (prose); `seed-ledger` runs strictly on already-converted output.
- **Re-verification** of historic REQs — the verdict travels from the converted `status`; no
  historic test is re-run (the [[REQ-015]] gate does not fire on seeding).
- **The full onboarding pipeline** (stamp, CLAUDE.md reconcile, running it against memzy live)
  → [[REQ-024]] orchestrates; this REQ ships only the command + its tests.

## Notes

- **Why a command and not a script.** The operator's test: would the *identical* tool serve
  ExamEngineer despite its divergent source format? Yes — because it consumes the converter's
  normalized output, not the source. The divergence is fully absorbed by the per-project
  converter upstream; the seeder sees only schema. That is the line between [[REQ-010]] (script,
  bespoke) and this (command, generic).
- **The empty queue is the correct outcome, not a bug.** A seeded done-corpus *should* leave
  `advance` idle — the engine has nothing to land. Work resumes the moment `/intake` adds an
  active REQ, which the seeder deliberately never touches.
- **Generalization path.** [[REQ-024]] (the onboard skill) chains `convert_reqs.py` →
  `seed-ledger` → scaffold stamp; [[REQ-023]] makes the index splice non-destructive so the
  convert step is safe to run in place.
