## Context

Every project stamped by `steward new` gets a REQ-001 north star from
`templates/docs/requirements/REQ-001.md.tmpl`. That template ships `status: open`, and the
REQ profile derives a `:develop` step for every **active** requirement
(`profiles/req/reqfile.py:41` — `ACTIVE_STATUSES = {"open", "in-progress", "blocked"}`).
So the north star becomes a permanently-eligible work item that `/bootstrap` never
resolves. `steward status` advertises it as the next thing to do, for the life of the
project, in every consumer.

It is not merely cosmetic noise, because the step is *nonsense to run*. REQ-001 is a
compass — a frozen statement of what the project is for. There is no code it asks for. A
develop session pointed at it finds nothing to build and does the only reasonable thing:
it forks. That is exactly what happened in DocSteward on 2026-08-05, when a "quick session
to turn it green" (`steward run REQ-001`) became a parked decision at 23:33, an answered
decision at 23:45 ("land it green"), and then a *failed* follow-up develop step at 23:51 —
an hour spent where the owner expected one minute.

The failure at the end is the second half of the trap, and it is independent of the first.
The template's AC1 test is `{{TEST_COMMAND}}` — **the entire suite**. REQ-063's capture
check re-runs each named acceptance test from a bare `git archive` extract of the staged
tree, to prove the green was really captured in the commit. A whole-suite command is the
most fragile thing the engine can be handed there: the extract has no `.venv/`, nothing
installed, and none of the project's gitignored local environment. DocSteward's ledger
records the two lines side by side —

```
23:51:30  verify       REQ-001:develop  [0] python -m pytest → 517 passed
23:51:31  capture_gap  REQ-001:develop  'python -m pytest' no longer passes from the
                                        recorded commit (0 failed, 1 errors of 1)
```

— and reproducing it by hand (`git archive HEAD | tar -x` into a temp dir, then pytest)
gives 36 collection errors: `ModuleNotFoundError: No module named 'docsteward'` and
`No module named 'pypdf'`, because the src-layout package is only importable through the
gitignored `.venv`, and `/config/*` — the project's whole local-environment layer — is
gitignored by design. That AC can never pass from an extract, in any project with real
dependencies. It was never a check; it was a delayed failure.

There is a third defect underneath both: **the template ships no `tests/` directory at
all.** A freshly stamped skeleton has zero tests, so even on day one the AC1 command
collects nothing and pytest exits 5. The north star has never been passable in any
consumer, at any moment in its life.

DevSteward's own REQ-001 is *not* a usable precedent here, and the owner said so
explicitly when this was interrogated. It carries `status: done` with acceptance criteria
still `status: pending` and no `check:` field, and it has no ledger step in
`.devsteward/state.yaml` — it was hand-declared done during dogfooding, before the
machinery it now describes existed. Copying that shape into the template would propagate a
status nobody earned. The bar the owner set instead: *an honest assurance that project
initialization has been accomplished should turn this green and done.*

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | REQ-001's acceptance becomes a **scaffolding-invariant** check, not a functional one | The north star claims the project is *initialized*, not that it works. Asserting scaffolding coherence is the honest reading of that claim, and it is the only claim provable on day one — before any code exists |
| 2 | The check ships as a real committed test, `tests/test_project_initialized.py`, stamped by `steward new` | An assurance that lives in a skill's prose is asserted; one that lives in a committed test is earned, re-runnable, and visible to the engine. It also gives every stamped project a non-empty `tests/` directory, fixing the exit-5 defect |
| 3 | That test uses **stdlib + pytest only** — no YAML library, no project imports | It must pass from a bare `git archive` extract with nothing installed (Decision 1's whole point). It reads the two or three scalar keys it needs from `.devsteward/config.yaml` with a small line scanner. Parsing a fraction of YAML by hand is the lesser evil against re-creating the DocSteward capture gap in every consumer |
| 4 | `/bootstrap` closes by running `steward checkpoint`, letting the **engine** land REQ-001 | The status flip is then certified by the same machinery every other REQ uses — verified, capture-checked, and committed under same-commit discipline (REQ-077) — instead of being written by a skill. This is the owner's "mini session": ~1 minute, no special case, and REQ-001 leaves the eligible set because it is genuinely `done` |
| 5 | `steward checkpoint`, never `steward run`, from inside the bootstrap session | `checkpoint` is the non-spawning verb. `run` launches Claude, and a Claude session must never spawn Claude (REQ-034 D6) |
| 6 | The template REQ-001 keeps `status: open` and is **not** pre-declared done | Decision 4 earns the flip. Shipping `done` would reproduce the very thing the owner rejected about this project's own REQ-001 |
| 7 | No lint rule, no migration command, no `/onboard` audit in this REQ | The affected population is projects stamped before this fix — DocSteward and possibly nothing else. Machinery for an N≈1 population is exactly the accretion the design principles forbid; the retrofit is done by hand, once (see Requirement) |
| 8 | The DocSteward retrofit is a **develop-session obligation**, not an acceptance criterion | It is the live proof that the new shape settles a real, already-broken consumer — and it needs a fixing loop, so it belongs in the attended develop session, not deferred to a fixless System-Test phase. A DevSteward regression test asserting another repo's state would also be unrunnable for anyone else and would rot ([[regression-tests-must-be-executable]]) |

## Requirement

A project stamped by `steward new` and brought to life by `/bootstrap` ends that session
with REQ-001 **done in the ledger, verified by the engine**, and with no eligible step
remaining — so the operator's next move is `/intake`, never a nonsense develop session
pointed at the compass.

**The shipped initialization check.** `steward new` stamps
`tests/test_project_initialized.py`. It asserts, using only the standard library and
pytest, that project initialization is genuinely accomplished:

- the requirements scaffolding is coherent — REQ-001 exists in the configured
  `requirements_dir`, carries the required frontmatter fields, and its status agrees with
  its row in the index;
- the ledger is initialized — `.devsteward/config.yaml` and `.devsteward/state.yaml` are
  present and readable, and the state names a profile;
- no `{{PLACEHOLDER}}` token survives anywhere in the stamped scaffolding — an unfilled
  placeholder means bootstrap did not finish.

The test locates the project root relative to its own file, honors `requirements_dir` from
`.devsteward/config.yaml` (REQ-084), and passes from a bare `git archive` extract of the
committed skeleton with no virtualenv and no project dependencies installed.

**The template's acceptance.** `REQ-001.md.tmpl`'s AC1 names that test —
`python -m pytest tests/test_project_initialized.py`, `check: regression`. The
`{{TEST_COMMAND}}` whole-suite acceptance is removed; the real build/test commands remain
what the interview captures for `.devsteward/config.yaml`, where the develop gate's
`verify.full_suite` uses them.

**The bootstrap close.** `/bootstrap`'s final act, after the first commit on `dev`, is
`steward checkpoint`. The engine verifies AC1, runs the capture check, and commits the
status flip plus the index `DONE` sync in one commit. The skill then reports the landed
step and names the next move as `/intake "<first real idea>"`. The skill file and its
stamped twin are one inode ([[skills-hardlinked-to-templates]]) — edited once.

**The DocSteward retrofit (develop-session obligation, per Decision 8).** DocSteward is
currently stuck: `REQ-001:develop` is `failed`, the cursor is pinned to it, and REQ-007 —
the real next work — sits behind it. During this REQ's develop session, DocSteward
receives the same cure: the shipped initialization test, REQ-001's AC1 narrowed to it, and
then `steward repeat` / `steward checkpoint` so the engine lands it for real. Settling it
by the normal path is simultaneously the live proof that the new shape works on an
already-stamped consumer whose extract is genuinely hostile. The already-committed
`0d288a6` (develop work) and `bfdc95c` (ledger close — capture gap) stay in history; this
does not rewrite them.

## Notes

**Why not simply exclude `kind: spec` from step derivation.** That was considered and
rejected: it keeps REQ-001 legitimately `open` forever and adds a second, invisible reason
a requirement can have no step. It is an engine change in service of a template defect,
and it cuts against *minimal topology / prefer subtraction*. The chosen fix touches no
engine code.

**Why not have `/bootstrap` write `status: done` itself.** Also rejected — it is the shape
the owner objected to in DevSteward's own REQ-001: a status asserted by a skill rather than
certified by the engine. Decision 4 costs one extra command in the skill and buys a real
ledger entry.

**Expect these tests to join the flake family.** AC2 and AC3 drive `steward checkpoint`
over a temp repo, which is exactly the profile of the known intermittent
`land left N path(s) uncommitted after the code commit` failure
([[clean-tree-assert-flaky-test]]). If one of them reds in isolation while the rest of the
suite is green, re-run before diagnosing.

**Out of scope, deliberately:** a `steward lint` rule for an `open` north star; any
migration or repair command; an audit of `/onboard`'s handling of an arriving open north
star. If a second already-stamped consumer turns up with this trap, revisit the lint rule
then — with a real population instead of a hypothetical one.

**Not deferred silently:** the DocSteward settlement is a known, currently-broken state and
is homed in this REQ's develop session by Decision 8, not scoped out.
