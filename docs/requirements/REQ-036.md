## Context

`steward new` stamps the bundled `.claude/skills/` into a consumer project **once**; the
engine (`steward`) is then upgraded independently (`pipx install …@vX.Y.Z`) while the
stamped skills stay frozen at stamp time. The two drift, and there is **no refresh path and
no signal** — so a consumer silently runs stale skill behavior against a current engine.

This is REQ-034's live-AC6 **Finding 50**, caught on FlowSteward: its stamped
`.claude/skills/system-test/SKILL.md` predated REQ-034, so the engine's new `--guided`
human-validation half **silently no-opped in the consumer** — the human got the old bare
`y/N`, the exact "present + record" asymmetry REQ-034 set out to kill, reproduced in a real
consumer while every engine mechanic (guard, bring-up, gate, verdict-record) passed. The
green-but-hollow shape REQ-027 exists to prevent, at the template↔consumer seam.

DevSteward already hardlinks the repo skill ↔ the template skill so they cannot drift
*internally* (see the house note on hardlinked skills); there is **no equivalent guarantee
between the template and a consumer's stamped copy**, and no way to even detect the gap.
This REQ closes that seam: a provenance manifest so drift is *detectable* (and tellable
apart from intentional customization), a `steward status` signal so it is *visible*, and a
`steward sync-skills` verb so it is *fixable*.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | **Scope: the bundled engine-owned skills only** (`.claude/skills/{advance,bootstrap,intake,system-test}`). CLAUDE.md, settings, and other consumer-customized scaffolding are *not* synced. | The bundled skills are pure engine *behavior* meant to track the engine; they are exactly what drifts harmfully (Finding 50). CLAUDE.md/settings are filled per-project by `/bootstrap` — overwriting them would clobber the consumer's own content, the opposite of safe. |
| 2 | **A provenance manifest `.devsteward/skills.lock` records the template content-hash each bundled skill was stamped/synced from.** Detection then yields three honest buckets: *in-sync* (stamped == lock == template), *stale* (stamped == lock, template moved), *customized* (stamped != lock). | Without recorded provenance you cannot tell "stale, safe to refresh" from "the consumer deliberately edited this" — a plain content compare conflates them and either nags about intentional edits or clobbers them. The lock is the third reference point that disambiguates. |
| 3 | **The drift signal lives in `steward status` — informational, never blocking.** A stale/customized skill shows as a warning line pointing at `steward sync-skills`; it does not fail any gate. | `steward lint` is a *spec* validator (REQ-002/028) and must stay decoupled from machine install-state; a stale stamped file is a local-environment fact, not a spec defect. Visibility is the fix for "silent"; a hard block would couple unrelated work to install hygiene. |
| 4 | **`sync-skills` refreshes *stale* skills and updates the lock; it never silently clobbers a *customized* skill.** A customized skill is refused without `--force`; `--force` backs the local copy up (`.orig`) before refreshing and re-records the lock hash. No 3-way prose merge. | A refresh of an untouched-but-stale skill is safe and is the common case (Finding 50). A consumer who edited a bundled skill made a deliberate choice; the engine surfaces it and requires an explicit `--force` (with a backup) rather than destroying it. Merging skill prose is out of scope (and unreliable). |
| 5 | **`steward new` seeds the lock at stamp time.** Every freshly-stamped project starts *in-sync* with a populated `.devsteward/skills.lock`, so drift is measured from a known baseline rather than guessed. | Drift detection needs a baseline; the only honest one is "the template hash this copy was actually stamped from," which only `steward new` can record truthfully. |

## Requirement

Give DevSteward a first-class way to keep a consumer's bundled skills current with the
installed engine, and to surface when they are not:

- `steward new` stamps the bundled skills **and** writes `.devsteward/skills.lock` mapping
  each bundled skill to the content-hash of the template copy it was stamped from.
- Drift detection compares, per bundled skill, three hashes — the stamped file, the lock
  record, and the installed template — and classifies each as **in-sync**, **stale**, or
  **customized** (Decision 2).
- `steward status` reports any non-in-sync bundled skill as an informational warning line
  naming the bucket and pointing at `steward sync-skills`; it never blocks (Decision 3).
- `steward sync-skills` refreshes every **stale** bundled skill to byte-match the installed
  template and updates the lock; a **customized** skill is left untouched and reported
  unless `--force` is given, in which case its current content is backed up (`.orig`) before
  the refresh and the lock is re-recorded (Decision 4).
- The bundled skill set and the manifest are engine-derived (no hand-maintained list that
  can fall out of step with what the template actually ships).

## Notes

- **Out of scope:** syncing CLAUDE.md / settings / non-skill scaffolding (Decision 1); a
  3-way prose merge of a customized skill (Decision 4 — `--force` + backup instead); an
  auto-sync on every command or a hard `steward lint` block (Decision 3 — `status` only);
  re-verifying that a refreshed guided session *actually guides* the human — that is
  REQ-034 AC6's job, this REQ only proves the drift is detected and the file brought
  current.
- **Relationship to REQ-034:** this is the spun-out fourth finding of REQ-034's live AC6
  (the other three — async-validate ledger on dev — were the REQ-034 rework). REQ-034 AC6
  re-validation may need FlowSteward's stamped skill refreshed *by hand* until this REQ
  lands; once it lands, `steward sync-skills` is the supported path.
- **Process declarations:** defaults — fused develop, no concept phase. **No devsteward lab**
  (`lab: []`): AC5 re-uses FlowSteward, a real consumer repo (the REQ-030 AC8 / REQ-034 AC6
  precedent — consumer-repo reality, not a DevSteward-owned lab asset). AC1–AC4 run headless
  on synthetic stamped projects in a temp dir.
- **Localization:** engine/CLI/skill text is technical English; no user-facing localized
  strings.
- **Hashing:** content-hash is the existing evidence-style sha256 of file bytes; the lock is
  a small JSON/YAML map `{skill-name: sha256}` under `.devsteward/` (committed — it is
  registry provenance, like the ledger).
