## Context

REQ-037 moved the live ledger onto the integration branch (`dev`), bound through a linked
worktree, so feature branches carry pure code. The **write** paths were updated to bind
(`advance`, `run`, `checkpoint`, `validate` all call `_bind_ledger`). The **read** path was
not: `steward status` reads `ex.ledger` unbound, and the `/advance` skill's step-1
orientation still says *"Read `.devsteward/state.yaml`"* — both of which, on a feature
branch, return the **branch-cut snapshot**, not the live cursor/status.

This is the 2026-06-15 dogfood incident (postmortem
`docs/reports/2026-06-15-req037-ledger-on-dev-orientation-and-double-checkpoint-postmortem.md`).
Orienting a fresh `/advance REQ-036` from the feature branch read the stale snapshot
(cursor frozen at `REQ-037:develop`, no REQ-036 step), led to a wrong "checkpoint never
ran" diagnosis, and a re-run of `steward checkpoint` appended a duplicate
`develop_committed` (with `commit: null`) plus a redundant ledger commit on `dev` —
because `steward checkpoint` has **no guard** against re-checkpointing an already-`done`
step. REQ-037's topology worked end-to-end; what it left broken is the *read/orientation*
surface and the bookkeeper's idempotency. This REQ closes both.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | **Bind the ledger on the read path too.** `steward status` (and the executor read accessor it uses) calls `_bind_ledger`, so every read resolves the live integration-branch ledger from anywhere — including a feature branch. | REQ-037 bound only the write paths; an unbound read on a feature branch returns a stale branch-cut snapshot. The live cursor/status must be the same from any branch, or orientation is unreliable — the exact footgun that caused the double-checkpoint. |
| 2 | **`/advance` orientation reads the live ledger via `steward status`, never a direct file read.** The skill's step-1 instruction is corrected accordingly. | The `/advance` skill *is* DevSteward; its "Read `.devsteward/state.yaml`" instruction is now wrong on a feature branch. No operator (human or agent) should hand-read a branch-local ledger snapshot; the binding command is the one sanctioned read. |
| 3 | **`steward checkpoint` hard-refuses an already-`done` step** — a `ClickException`, zero ledger writes (no flip, no `develop_committed`, no commit, no cursor move). | The bookkeeper must be idempotent; re-running it should be safe. A refusal is consistent with how `checkpoint` already refuses a validate step and a red gate, and it turns a mis-diagnosed re-run into a clear signal instead of a duplicate write. |

## Requirement

Make the engine's read path branch-agnostic and the checkpoint idempotent:

- `steward status` resolves and reports the **live integration-branch ledger** (cursor,
  step statuses, parked decisions) regardless of the current branch — binding the ledger
  the same way the write paths do.
- The `/advance` skill orients from `steward status` (a binding read), not from a direct
  `.devsteward/state.yaml` read.
- `steward checkpoint REQ-NNN <phase>` on a step already at `status: done` **refuses**
  with an actionable message and performs **no** ledger writes.
- The fixes are proven against a real-git fixture where the feature branch's snapshot and
  the integration-branch ledger genuinely diverge (the REQ-037 real-git-teeth precedent).

## Notes

- **Real-git teeth (the REQ-037 lesson):** all ACs run against a real `git init` repo with
  the real `GitCli` and a real integration worktree; only `claude -p` and any interactive
  bring-up are faked. A unit fake that keeps one in-memory ledger cannot certify "which
  branch's ledger did the read resolve" — the precise gap that hid this bug.
- **Out of scope:** changing the REQ-037 *write* topology (it is correct); a `steward where`
  / `steward cursor` command (binding `status` is enough — revisit only if a leaner
  cursor-only read is wanted later); reformatting `status` output beyond making it live.
- **Relationship to REQ-037 / REQ-018:** this is the read-side and idempotency follow-up to
  REQ-037's write-side topology, and it hardens the REQ-018 `steward checkpoint` bookkeeper.
- **Process declarations:** defaults — fused develop, no concept phase, **no lab**
  (`lab: []`): the ACs run on synthetic real-git repos in a temp dir; no consumer repo or
  human oracle is needed (the defect is reproducible headless), so there is **no validate
  phase**.
- **Localization:** engine/CLI/skill text is technical English; no user-facing localized
  strings.
