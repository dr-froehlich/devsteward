## Context

"Git with teeth" is the right instinct — strong guidelines, no false greens. But a tool that
drives real work must also be a **reliable, stable, resilient** partner: at every step that
goes **red**, there must be a clear and *available* path forward. The REQ-047 pivot made
engine state un-divergeable and un-strandable; this REQ asks the next question — now that
state can't fork, is the **forward path out of every red/failed/parked state always available
and clearly named**?

Peter's framing: at a red step there are fundamentally two options, and which is right depends
on the **root cause**:

- **Repeat** — the step failed for a reason *external* to the work itself: Claude crashed with
  a rate-limit error or an API timeout, or a manual validation hit a setup issue the human has
  since fixed. The prior work was sound; the right move is to run the step again.
- **Rework** — the prior development was genuinely *insufficient*; it must be redone.

The open question is whether today's verbs map onto that. The engine has `steward recover`
(REQ-026 — flip a FAILED step so `/advance` reassesses) and `steward rework` (REQ-033 — the
V-model return edge from a red validation back to develop), plus `decision answer` for parked
forks. Peter is "not sure if `rework` and `recover` match the two options" and suspects
**`repeat`** is a clearer name than `recover` for the run-it-again case. A critical wrinkle:
the root-cause fix often lies **outside the tool's management** (a rate limit that resets on
its own, an account swap, a lab/host setup the human repairs) — the tool cannot fix it, but it
must still offer a **stable path to adopt the external fix and continue**.

Per the intake decision, this REQ is **audit-and-recommend**: it produces the model and the
gap list; implementing any rename or new recovery verb is a named follow-on. This keeps with
"assess the process before changing the mechanism" — the most critical aspect of the migration
to get right, so we name it explicitly before we move code.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | This REQ is an **assessment**, not an implementation: the deliverable is a written audit + recommendation report in `docs/reports/`. | Peter chose audit-and-recommend at intake. The verb model and the forward-path completeness must be agreed before a rename or new verb is built — a string of fixes that each *add* recovery machinery is exactly the smell the design principles warn against. |
| 2 | The audit **enumerates every terminal red/failed/parked state** in the V-model flow (develop red, repair-budget exhausted, validate red, declined human verdict, parked async validation, parked fork, and externally-caused failure) and maps each to its currently-available forward verb — or flags it as a dead-end. | "Available path forward" is only provable by walking the whole state space; a dead-end (the unrecoverable half-state REQ-043/044 were patching) is the exact failure mode to surface. |
| 3 | The report evaluates the **rework / repeat** model against the current `recover` / `rework` / `decision answer` verbs and recommends the naming + any missing verb, **distinguishing internal-cause (rework) from external-cause (repeat)** and naming the stable path to adopt an out-of-tool fix and continue. | This is the core question Peter raised; the recommendation must be concrete enough that a follow-on REQ can implement it without re-litigating the model. |
| 4 | The verdict is **human** (`manual`): Peter reads the report and signs off that every red state has a named forward verb or a flagged gap with a recommendation. | An audit's only honest oracle is its reader; there is no code change here to gate with regression. |

## Requirement

Produce a process-resilience audit report at
`docs/reports/2026-06-19-process-resilience-forward-path-audit.md` that:

- Enumerates every red / failed / parked terminal state a REQ can reach in the current
  (post-REQ-047) flow, and for each names the **available** forward verb that adopts a fix and
  continues — or flags it as a dead-end with no available path.
- Classifies the two recovery intents — **repeat** (external root cause; the work was sound)
  and **rework** (internal root cause; the work was insufficient) — and assesses whether the
  current `recover` / `rework` / `decision answer` verbs map cleanly onto them, recommending
  the naming (including whether `recover` should become `repeat`) and any missing verb.
- Explicitly covers the **out-of-tool root cause** case (rate limit, API timeout, account
  swap, lab/host setup the human fixes) and names the stable path by which the tool adopts that
  external fix and continues.
- Spins out a named follow-on REQ for each recommended implementation change.

## Notes

- **Why audit-first, not patch-first.** The recovery surface already accreted verbs
  (`recover`, `rework`, `decision answer`) and dead-end fixes (REQ-043/044). Adding another
  verb before the model is agreed risks repeating the REQ-047 anti-pattern of patching a
  premise instead of naming it. The model comes first; the mechanism follows in a scoped REQ.
- **Relationship to existing REQs:** assesses the surface from REQ-026 (`recover`), REQ-033
  (`rework`), and REQ-005 (park-and-surface); builds on the un-divergeable state model of
  REQ-047. None are hard prerequisites beyond REQ-047 — the audit reports on whatever exists.
- **Split from REQ-052:** this was the third strand of the REQ-052 idea stub, separated at
  intake because it is a process redesign with its own acceptance, not a cleanup sweep.
- **Process declarations:** defaults — fused develop, no concept phase, no lab. The report is
  the validation surface; no owned lab asset is needed, so the `process:` block is omitted.
- **Localization:** report and any technical text is English; no user-facing localized strings.
