## Context

The owner's need, in the owner's words (backlog item `non-governed-joint-tasks`): *"The
joint-project-task works for DevSteward governed projects only. I want my custom, non-DevSteward
governed repository to interact with any of the governed projects in a comparable way."* The
item's acceptance criteria were authored at this intake, before any design, and live in
`docs/BACKLOG.md`. On what *comparable* means, the owner: *"I have a command or skill that
stands in for these DevSteward skills. For the other project it should make no difference
which impacts their interaction with the steward tool, I don't want that every target project
has to learn how to deal with system-admin. On the system-admin side we're flexible to
accommodate what the others need."*

**The repository is system-admin.** It records the owner's machines. Its documents hold rules
and dated state, and its rationale goes in an append-only `log/`. Its unit of work is an **open
item** (`OPEN-NNNN · owner`, with a *Closes when* and a *Filed as*) in the document that owns
the subject. Its own tool, `open/open.py`, writes a handover file per receiving project and
reads the receivers' backlogs and `backlog_refs` to learn what each item was filed under. It
has no REQs, no backlog and no ledger. Twice now its nature has been found at odds with the REQ
workflow: REQ-101 (*"I'd rather you design for DevSteward and then we design how we could bring
on system-admin"*), and REQ-099's scoped-out question of stamping only its `tools/` subfolder,
which REQ-079's whole-tree commit makes unsafe. Its handover traffic is the real traffic REQ-101
was built for. In about two weeks its handover folder accumulated sixteen commits across four
receivers, and sarah sent five reply files back, all carried between sessions by the owner.

**What a bare `.devsteward/` already does (probed at intake).** A folder holding only
`.devsteward/config.yaml`, beside a stamped sibling, can already run every joint verb, and the
sibling sees its threads. Four things are wrong with it:

- **`steward status` asks to sync.** It asks to `steward sync` the REQ skills, STEWARD.md and
  the REQ template, which would stamp the REQ workflow into a repository that must not have it.
  The existing `generic` profile does the same.
- **`steward lint` is red:** *"requirements dir not found"*.
- **The dashboard lists it as a stamped project.**
- **Take-up has nowhere to live.** Without a backlog, every request to it stays a *request to
  take up* forever, and the sibling's `joint-show` reports *"not filed in … backlog yet"*
  forever. system-admin's equivalent of filing is an open item and its *Filed as*.

## Requirement

### The joint-only participant

`profile: joint` in `.devsteward/config.yaml` declares a joint-only participant. In such a
folder:

- the joint verbs (`joint-send`, `joint-ack`, `joint-list`, `joint-show`) work exactly as in a
  governed project, writing only the folder's own `.devsteward/joint.jsonl`;
- `steward status` prints that this is a joint-only participant, and no sync or drift line;
- `steward lint` passes with nothing to lint;
- `steward sync` stamps nothing and records nothing;
- every REQ-workflow verb refuses with one line naming the profile and changes nothing.

`steward new TARGET --profile joint` writes `.devsteward/config.yaml` with `profile: joint`
and nothing else. It works in a non-empty folder without `--force` and leaves every existing
byte untouched. It refuses when `TARGET/.devsteward/` exists.

### Seen from everywhere else

- **Discovery.** A joint-only participant is a sibling like any other. `--to` addresses it by
  folder name, case-insensitively (REQ-101).
- **The dashboard** lists it with its git facts, marked as a joint-only participant. It has no
  steward status, backlog, requirements or actions, and adds nothing to the needs-me strip.

### Take-up recorded by acknowledgement

- `steward joint-ack <thread> <ref> --filed-as <reference>` records the reference on the
  receiver's own `ack` line as `filed_as`. It is refused, writing nothing, when `<ref>` is not
  the thread's `action`. An existing acknowledgement can never be changed (REQ-101 Decision 4),
  so a request already acknowledged without one is refused the same way.
- **The take-up `joint-show` prints** follows Decision 4's order. A governed addressee shows what
  its backlog derives, as before; a joint-only addressee shows *"filed as <reference>"*.
- **A request stops being a candidate** in the receiver's `joint-list` once its handle is an
  item in the receiver's backlog **or** the receiver's acknowledgement of it carries a
  `filed_as`.

### Live proof (develop obligation, Decision 7)

1. **Join.** With the owner's go, run `steward new <system-admin> --profile joint`, then check
   that `steward status`, `steward lint` and the dashboard behave as above, in system-admin
   itself.
2. **Adoption.** devsteward opens the *adopt joint tasks* thread to system-admin. A system-admin
   session the owner opens there takes it up as an open item, acknowledges it with
   `--filed-as`, builds its stand-in command and the `open.py handover` change under its own
   rules. devsteward's `joint-show` shows the `filed as OPEN-NNNN` take-up. Whatever the real
   sessions turn up on devsteward's side is fixed in place. The two `done`s follow when that open
   item closes on a real request (Decision 8). The thread stays open in both projects until then.
3. **First real traffic.** One real system-admin → sarah request is sent with the new handover
   (for example one of the items OPEN-0165 or OPEN-0178, still open at intake). sarah's
   `/intake` takes it up unchanged, after the owner has run `steward sync` in sarah. system-admin's
   `joint-show` shows sarah's take-up. This thread does not have to reach `done` within develop:
   it is a real job of sarah's.

## Notes

**Out of scope, on purpose.**
- Two non-governed repositories talking to each other (system-admin ↔ Espressomuehle). The owner's
  need is about a non-governed repository and the governed projects.
- A generic participant skill shipped by devsteward (Decision 6).
- Running the REQ workflow on part of a repository: REQ-099's `tools/` question, still a separate
  discussion.
- Showing joint threads on the dashboard (REQ-101 Decision 8 stands).
- system-admin's own changes (its stand-in command, `open.py`, its CLAUDE.md and log). These are
  system-admin's work, taken up through the adoption thread under its own rules (Decision 7).
- Retiring `open.py`'s handover files for receivers that are not stamped (Espressomuehle). That is
  system-admin's call.

**Develop obligations.**
- **The live proof** (Requirement, *Live proof*): it needs the owner's go before
  `steward new <system-admin> --profile joint`, and the owner's attended system-admin and sarah
  sessions.
- **The manual and the handbook** in the same commit as the code (REQ-094). The shipped skills do
  not change (Decision 5).

**Risks.**
- **system-admin's side may take more than one sitting.** Its rules ask for a tool specification
  with requirement ids, a log entry and tests. The develop step then stays open, attended, until
  the adoption thread reaches both `done`s.
- **A governed project's dashboard view of system-admin** shows no joint threads. That is the
  owner's REQ-101 choice, unchanged here.
- **sarah's skills come from its next `steward sync`.** Until it runs there, sarah's `/intake`
  lacks REQ-101's take-up step. At intake, sarah also had uncommitted changes from an earlier sync.
