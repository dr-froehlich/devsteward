## Context

`process.concept: true` exists (REQ-027) but carries **zero in-session semantics**. It is
a batch-ineligibility flag and nothing more: the REQ profile sets `attended=True` on the
single develop step (`source.py:104`) and the executor parks it in batch
(`executor.py:356`). There is no concept step, no concept-aware session, no deliverable, no
gate — mechanically it does the *identical* thing as `develop: split`. So a REQ that
declared a concept phase, run interactively, gets an ordinary fused develop checkpoint:
plan → build → green. The concept intent lives only in the REQ text and the human's head.

FlowSteward surfaced this on its first concept phase: *"there's no `steward concept`
command — the concept step is driven by the develop skill parking at the approval fork. If
`/advance` doesn't naturally produce the mockups-first behavior, that's a DevSteward engine
gap."* It is a real gap. `/advance` never reads `process.concept`; its fork-park fires only
on an unresolvable ambiguity, not a planned concept→build sign-off. The declaration is
correct; the execution side is empty.

The concept phase is the **left-arm counterpart** of the System-Test (validate) phase
(REQ-030). Validate is a conditional *trailing* step with its own interactive session
(REQ-034), its own skill, and an engine-recorded sign-off, on the **back** of the V. Concept
is the conditional *leading* step on the **front** of the V — but it is a different altitude
from develop, not the same thing earlier: it is **architectural** (architecture, risk
buy-down via spikes/prototypes, choosing among design paths), *above* Claude's implementation
plan. `develop: fused|split` decides whether the *implementation plan* is reviewed before
coding; `concept` decides whether an *architecture/exploration* round runs before we even get
to implementation planning. The two are orthogonal — a risky REQ could declare both.

One inversion from validate matters: the System Tester's whole value is **decoupling** from
the builder. Concept is the opposite — its output exists to **feed** develop. So this REQ
reuses validate's *bring-up mechanism* (a script that launches an interactive guided Claude
session with a dedicated skill, two-phase start/record bookkeeping, the `CLAUDECODE` nesting
guard, the engine-owned sign-off) and **none** of its decoupling: no no-see-the-diff rule
(there is no diff yet), no `.devsteward/evidence/` capture, no engine-run artifact gate.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | A REQ with `process.concept: true` gets exactly one **`REQ-NNN:concept`** step *before* `REQ-NNN:develop`; develop `depends_on` it. REQs without the flag get none. | The left-arm symmetry of REQ-030's conditional trailing `validate` step — the declaration is the router, on the front of the V. |
| 2 | The concept step is **interactive-only** — never a headless pass. In batch it is ineligible / parks naming the attended need (it is `attended`). Unlike validate there is no unattended concept execution path. | Exploration, prototyping, and choosing a design path are irreducibly human-in-the-loop; a headless "concept" would be theatre. |
| 3 | **Bring-up mirrors `steward validate`; semantics do not.** `steward concept REQ-NNN` is the single entry point: it brings up an interactive `/concept` guided session through the same two-phase start/record bookkeeping (REQ-034) and refuses to nest inside a Claude session (`CLAUDECODE`). But the session is **coupled by design** — it carries none of the System Tester's no-see-the-diff rules, no evidence-dir capture, and no engine-run artifact gate. | Reuse the proven bring-up plumbing; drop the decoupling that only makes sense for independent validation. Concept feeds develop — coupling is the point, not the hazard. |
| 4 | **Deliverable = a concept document** at `docs/concepts/REQ-NNN.md` (architecture, the design path chosen + alternatives rejected, spike findings), recorded in the REQ's existing `concept_refs:` frontmatter. The engine refuses to complete the concept step without it. | The same artifact-discipline as develop's `docs/plans/` rule, at a higher altitude: the implementation plan is later written *against* the approved concept. Gives the currently-dead `concept_refs:` field a real purpose. |
| 5 | **Spikes/prototypes are throwaway** — run to learn, then discarded, never committed. Only the architectural conclusion survives, in the concept doc (what was prototyped, what it proved/ruled out, the chosen path + why). | A spike is disposable by definition; keeping the repo clean beats carrying exploration code that the implementation will not use. |
| 6 | **The gate is a human sign-off, engine-recorded** (the REQ-030 D4 / REQ-034 convention): approve → the engine records the sign-off as a ledger event, marks concept done, and unblocks develop; defer → async park (clean tree, resumable with `steward concept REQ-NNN`); decline → records the verdict and routes to a decision/rework (no auto-advance to develop). The human supplies the verdict + one-line scope; the engine composes the provenance; the session never writes its own verdict. | No runnable oracle exists upstream of code, so the gate is necessarily the human's. Same self-certification firewall as every other gate (north star D3): the session cannot assert its own pass. |
| 7 | The concept phase **runs on the integration branch** (`dev`); its deliverable, sign-off, and ledger writes commit there. The implementation feature branch is created only when `develop` begins. | Concept is declaration/architecture-level and gates whether implementation happens at all — a decline may mean no implementation branch is ever cut. Mirrors "declaration lives on `dev`" + REQ-037's ledger-on-dev. |
| 8 | **The e2e proof is a `manual` AC** (REQ-030 D10 / REQ-029 D10 precedent): one scratch concept REQ driven by the real engine through concept → develop → land. The first **real** consumer — FlowSteward's concept re-drive, the trigger for this REQ — is a named follow-on, exactly as REQ-031 followed REQ-030. | A phase going `done` without ever being observed running once is the hollow-green shape; the scratch REQ proves the machinery, the real lab consumer stays its own REQ. |

## Requirement

Add the conditional **Concept** phase to the REQ profile's step model, on the front of the
V, symmetric to REQ-030's trailing validate phase:

- A REQ with `process.concept: true` gets exactly one **`concept`** step *before* develop;
  `develop` depends on it. REQs without the flag are untouched (Decision 1).
- The concept step is **interactive-only**: `steward concept REQ-NNN` is the single entry
  point, bringing up an interactive `/concept` guided session through the two-phase
  start/record bookkeeping, refusing to nest inside a Claude session (`CLAUDECODE`). In
  batch the step is ineligible / parks naming the attended need; there is no headless pass
  (Decisions 2, 3).
- The `/concept` session is **coupled by design** — it produces the architecture that feeds
  develop and therefore carries none of the System Tester's decoupling rules, no evidence
  capture, and no engine-run artifact gate (Decision 3).
- The session produces a **concept document** at `docs/concepts/REQ-NNN.md`; the engine
  refuses to complete the concept step without it and records it in `concept_refs:`. Spikes
  and prototypes are throwaway — only the architectural conclusion in the doc survives
  (Decisions 4, 5).
- The concept step **lands on a human sign-off** the engine records: approve unblocks
  develop, defer parks as async (resumable), decline routes to a decision/rework. The
  session never writes the verdict; the engine composes the provenance (Decision 6).
- The phase runs on the **integration branch**; the implementation feature branch is cut
  only at develop (Decision 7).

## Notes

- **Out of scope (own REQs / elsewhere):** the first **real** concept consumer —
  FlowSteward's concept re-drive (the trigger for this REQ) — is a named follow-on, exactly
  as REQ-031 (first lab) followed REQ-030 (validate machinery). The release-gate handling of
  concept docs, and any "concept staleness" detection, are not in scope (mirrors REQ-030's
  no-auto-staleness stance).
- **`develop: split` is untouched.** Concept and split are orthogonal altitudes (architecture
  vs implementation-plan review), not overlapping tiers; this REQ adds the concept phase
  alongside split and changes neither its behaviour nor its name.
- **Localization:** engine/skill/handbook text is technical English; no user-facing localized
  strings.
- **Surfaces (expected):** `devsteward/profiles/req/source.py` (leading concept-step
  emission, develop→concept dependency, attended/interactive-only), a concept routine
  symmetric to `validate.py` (e.g. `devsteward/profiles/req/concept.py` — two-phase
  start/record, sign-off recording, async-defer park, concept-doc artifact rule),
  `devsteward/core/executor.py` (concept-runner seam, branch placement on integration),
  `devsteward/cli.py` (`steward concept`), the **`/concept`** skill (repo `.claude/skills/`
  + stamped `devsteward/templates/.claude/skills/`, kept identical/hardlinked), the
  `/advance` skill (read the approved concept doc and write the implementation plan against
  it), the `/intake` skill + handbook (concept now spawns a real interactive phase with a
  `docs/concepts/` deliverable, not just an attended-park flag), `docs/concepts/` as a new
  home for concept docs.
