## Context

`process.concept: true` exists (REQ-027) but carries **zero in-session semantics**. It is
a batch-ineligibility flag and nothing more: the REQ profile sets `attended=True` on the
single develop step (`source.py:104`) and the executor parks it in batch
(`executor.py:356`). There is no concept step, no concept-aware session, no deliverable, no
gate — mechanically it does the *identical* thing as `develop: split`. So a REQ that
declared a concept phase, run interactively, gets an ordinary fused develop checkpoint:
plan → build → green. The concept intent lives only in the REQ text and the human's head.

FlowSteward surfaced this on its first concept phase: *"there's no `steward concept`
command — the concept step is driven by the develop skill parking at the approval fork. If
`/advance` doesn't naturally produce the mockups-first behavior, that's a DevSteward engine
gap."* It is a real gap. `/advance` never reads `process.concept`; its fork-park fires only
on an unresolvable ambiguity, not a planned concept→build sign-off. The declaration is
correct; the execution side is empty.

The concept phase is the **left-arm counterpart** of the System-Test (validate) phase
(REQ-030). Validate is a conditional *trailing* step with its own interactive session
(REQ-034), its own skill, and an engine-recorded sign-off, on the **back** of the V. Concept
is the conditional *leading* step on the **front** of the V — but it is a different altitude
from develop, not the same thing earlier: it is **architectural** (architecture, risk
buy-down via spikes/prototypes, choosing among design paths), *above* Claude's implementation
plan. `develop: fused|split` decides whether the *implementation plan* is reviewed before
coding; `concept` decides whether an *architecture/exploration* round runs before we even get
to implementation planning. The two are orthogonal — a risky REQ could declare both.

But the symmetry stops at altitude — it must **not** be paid in machinery. The System Tester
carries a heavy bring-up (a dedicated `steward validate` verb, a `/system-test` skill, a
`validate.py` routine, two-phase start/record, the `CLAUDECODE` guard, an engine-recorded
sign-off) for exactly one reason: **decoupling** — the validation session must run fresh and
never see the builder's diff. Concept is the opposite — its output exists to **feed** develop,
so it carries *none* of that decoupling. A coupled concept session is just the human and Claude
thinking together about architecture, which is precisely what an interactive `/advance` session
already is. Building a parallel `steward concept` verb + `/concept` skill + concept routine to
re-create that would add a second bring-up path for no isolation gain — against the engine's
"minimal topology / prefer subtraction / surface unnecessary complexity" principles (CLAUDE.md).

**Resolution (owner decision, interactive, 2026-06-21): the lightweight doc-gate.**
`process.concept: true` keeps its existing semantics — it makes the single `develop` step
*attended*, so a batch run parks it naming the attended need. No new step, CLI verb, skill, or
routine. The concept session *is* that attended develop session: the human and Claude do the
architecture/spike work and capture the conclusion in a **concept document** at
`docs/concepts/REQ-NNN.md`, then write the implementation plan against it and build. The
engine's firewall is a develop **land-gate** that exactly mirrors the existing `docs/plans/`
plan-artifact gate (REQ-029 D6), one altitude up. (This re-scopes the original heavy spec,
which also still leaned on the pre-REQ-047 feature-branch model that no longer exists.)

## Requirement

Give `process.concept: true` real in-session teeth as a **lightweight, gate-enforced concept
phase** on the front of the V — without adding a separate step, CLI verb, skill, or routine:

- `process.concept: true` keeps making the single `develop` step **attended**, so a batch run
  finds it ineligible and parks naming the attended need; the concept session *is* that
  attended develop session (Decision 1). A REQ without the flag is untouched.
- The session produces a **concept document** at `docs/concepts/REQ-NNN.md` (architecture, the
  chosen design path + rejected alternatives, spike findings), referenced from the REQ's
  `concept_refs:`. Spikes/prototypes are throwaway — only the architectural conclusion in the
  doc survives (Decisions 2, 4).
- The engine's develop **land-gate** refuses to land a `process.concept: true` REQ unless
  `docs/concepts/REQ-NNN.md` exists **and** the REQ's `concept_refs:` reference it — mirroring
  the `docs/plans/` plan-artifact gate, conditioned on the flag, on the same REQ-056
  land-refusal path. A REQ without the flag is never subject to it (Decision 3).
- Everything commits on `dev`; there are no feature branches (Decision 5). All acceptance
  criteria are `regression`; the REQ has no validate phase (Decision 6).

## Notes

- **Decision 4 amended by REQ-067 (2026-06-26):** D4's "spikes/prototypes are throwaway — never
  committed" is **no longer absolute**. A `concept: true` REQ MAY keep a **durable, committed,
  frozen prototype** as its deliverable (the build wires it) when the bought-down risk is
  *empirical* — e.g. operator consent to a concrete UI, unanswerable by a REQ or wireframe; the
  throwaway spike stays a valid choice for architectural/feasibility risk. The author decides per
  REQ; the engine enforces no criterion. REQ-067 also widened this REQ's land-gate to accept a
  concept **bundle directory** `docs/concepts/REQ-NNN/` (not only the flat `REQ-NNN.md`).
- **Re-scope note:** this REQ was intaken 2026-06-14 as a full symmetric phase (a `concept`
  step, `steward concept`, a `/concept` skill, a `concept.py` routine, an engine-recorded
  sign-off, defer/decline routing) built on the pre-REQ-047 feature-branch model. That spec is
  both stale (no feature branches exist post-REQ-047/048) and over-built for a coupled session
  that needs none of validate's decoupling. Re-scoped interactively to the lightweight doc-gate
  (owner decision, 2026-06-21). The dropped machinery is deliberately *not* built.
- **Out of scope (own REQs / elsewhere):** the first **real** concept consumer —
  FlowSteward's concept re-drive (the trigger for this REQ) — is a named follow-on, exactly
  as REQ-031 (first lab) followed REQ-030 (validate machinery). The release-gate handling of
  concept docs, and any "concept staleness" detection, are not in scope (mirrors REQ-030's
  no-auto-staleness stance).
- **`develop: split` is untouched.** Concept and split are orthogonal altitudes (architecture
  vs implementation-plan review), not overlapping tiers; this REQ changes neither.
- **Localization:** engine/skill/handbook text is technical English; no user-facing localized
  strings.
- **Surfaces (actual):** `devsteward/profiles/req/reqfile.py` (a `concept_refs` accessor on
  `ReqFile`), `devsteward/config.py` (`concepts_dir` → `docs/concepts/`),
  `devsteward/profiles/req/checkpoint.py` (`ConceptArtifactGate` + a small `CompositeLandGate`),
  `devsteward/build.py` (compose the plan + concept gates), `tests/test_concept_phase.py` and
  `tests/conftest.py` (a `concept_refs` arg on `write_req`), the `/advance` and `/intake` skills
  + handbook (`_01-format`, `_02-engine`, `_03-workflow`) + `STEWARD.md` (the concept gate
  described alongside the plan gate). `source.py`'s existing attended-park for `concept` is
  reused unchanged. (`/advance` & `/intake` skills are hardlinked to their stamped templates.)
