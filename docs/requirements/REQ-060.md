## Context

On clauder (every REQ `done` or `draft`, nothing active) the engine presents a
self-contradictory state and then refuses every action, with no signal that the project is
simply finished:

```
$ steward status
profile: req    cursor: REQ-005:develop
no active steps (all requirements done, draft, or none defined).
$ steward checkpoint REQ-005
Error: REQ-005:develop is not a derivable step — is REQ-005 active (not draft/done) and is the phase 'develop'?
$ steward activate REQ-005
Error: REQ-005 is done — a finished requirement is never reopened. ...
```

The `cursor: REQ-005:develop` line names a **done** step that the engine itself will not
derive — `steps()` yields steps only for *active* REQs (`source.py:80`), and the persisted
cursor is *"last step touched, never reset"*: `set_cursor(step.id)` is written when a step
starts (`executor.py:269`) and again when it lands (`:454,:474`), but nothing ever clears
it. So after the final REQ lands, the cursor stays pinned to that done step forever. A user
reads the cursor as pending work and is refused by every verb — and `steward checkpoint`'s
message poses the diagnosis as a question (*"is REQ-005 active (not draft/done)…?"*)
instead of naming the actual state (**done**), directly contradicting the cursor line
above it.

It is not a crash — `steward run` cleanly says *"Nothing eligible to run."* — but a
**cognitive dead-end**: the engine implies work remains, refuses every move to act on it,
and never says the one true, useful thing: *you are caught up; there is nothing to do; add
the next REQ with `/intake`.*

The fix is honest display, not new machinery. The persisted cursor stays (its real
consumer is the no-arg `steward checkpoint` resolution of the in-flight step), but it is
**never surfaced when it names a non-derivable step**, and the all-caught-up state gets a
positive terminal line. This is the [[REQ-056]] principle — a state must name its forward
path — applied to the *done* terminal: the forward path out of "all done" is `/intake`.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | **`steward status` shows the cursor only when it is still derivable; otherwise it prints a positive terminal line.** When `steps()` is empty (every REQ done/draft) and no step is eligible, status does not print a `cursor: …` that names a done/non-derivable step; it prints *"all requirements done — nothing to do; add the next with `/intake`."* (when there are draft-but-no-active REQs, it still points at activation). | The cursor's job is to orient — *where are we headed* — not to echo the last finished step. A cursor naming a step the engine won't derive is strictly misleading. Computing the displayed position from current state (eligible / in-flight), and otherwise affirming the terminal, removes the contradiction at the display layer without changing cursor semantics. |
| 2 | **A `checkpoint` whose target resolves to a done (or otherwise non-derivable) step names that reason plainly and points at supersede.** `steward checkpoint REQ-NNN` on a done REQ fails with *"REQ-NNN is done — nothing to checkpoint; supersede it to change direction"* rather than the *"is it active?"* question. | The message must tell, not interrogate. The done case is the common one behind this error and has a clear next action (supersede); the generic question made the user re-derive a diagnosis the engine already knows. |
| 3 | **No-arg `steward checkpoint` with nothing in flight says so.** When the resolved cursor names a done/non-derivable step (or is unset), `steward checkpoint` (no args) reports *"nothing in flight to checkpoint"* instead of pushing the stale cursor into the "not a derivable step" error. | A stale cursor must not be silently turned into a confusing failure. "Nothing in flight" is the honest state and matches the no-cursor message already in `cli.py:530`. |
| 4 | **The persisted cursor and its semantics are unchanged — display only.** No reset-on-completion, no clearing write, no removal of the `cursor` field. | Subtraction-minded but bounded: resetting/removing the cursor touches every checkpoint site and the interactive no-arg `checkpoint` resolution (larger blast radius) to fix a problem that is purely presentational. Fixing the *display* is the minimal change that kills the contradiction; the deeper "should the cursor exist at all" question is left for a future REQ if it ever earns its keep. |

## Requirement

A fully-caught-up project reports an honest, non-contradictory terminal state, and no
command refuses a done REQ with a message that fails to name *done*.

- **Honest terminal display.** When every REQ is done (or done/draft) and no step is
  eligible, `steward status` does **not** print a cursor line naming a done/non-derivable
  step; it prints a clear terminal line stating the project is caught up and pointing at
  `/intake` (or, when draft REQs exist, at `steward activate`). The cursor is shown only
  while it names a step the engine still derives.
- **`checkpoint` on a done REQ names done.** `steward checkpoint REQ-NNN` where `REQ-NNN`
  is `done` fails with a message that states it is done and points at supersede — not the
  generic "is it active (not draft/done)…?" question.
- **No-arg `checkpoint` with nothing in flight.** `steward checkpoint` (no args) whose
  cursor names a done/non-derivable step (or is unset) reports "nothing in flight to
  checkpoint", not the "not a derivable step" error.
- **No behavioural change to the cursor itself.** The persisted cursor, its write sites,
  and the interactive no-arg resolution of an *in-flight* develop step are unchanged; this
  REQ only changes what is displayed and how a non-derivable target is reported.

## Notes

- **Sibling, not parent, of [[REQ-059]].** That REQ closes the *runtime* stalemate (a step
  stranded mid-flight in `RUNNING`); this one closes the *terminal-state* confusion (a done
  project whose cursor lies). Different states, different code paths — split deliberately
  per the owner's "unrelated → fix both" steer.
- **Deliberately not done here: resetting or removing the persisted cursor.** Two heavier
  alternatives were weighed — advancing the cursor to `next_eligible` (None when caught up)
  on each land, and deleting the persisted cursor entirely (deriving in-flight live for
  no-arg `checkpoint`). Both touch every checkpoint site / the interactive resolution for a
  purely presentational defect, so they are out of scope; if the persisted cursor proves to
  earn no keep, that is a separate subtractive REQ.
- **`steward validate` on a done REQ is correct as-is.** The clauder trace also shows
  `validate REQ-005` recording *"fresh evidence … status and verified_by both frozen"* —
  that is the intended re-validation policy (REQ-035) and is **not** in scope.
- **Process declarations:** defaults — fused develop, no concept phase, no lab. All ACs are
  `regression` (CliRunner over the engine's own status/checkpoint surface, coupled oracle),
  so there is no System-Test phase; the `process:` block is omitted.
- **Localization:** all messages are operator-facing CLI/technical English; no localized UI
  strings.
