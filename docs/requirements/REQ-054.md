## Context

REQ-053's forward-path audit (`docs/reports/2026-06-19-process-resilience-forward-path-audit.md`,
recommendation #1) found that `steward recover` is **misnamed for its dominant use**. The verb
re-arms a `FAILED` develop step so the next run attempts it again. In the common case the work
was *sound* and the failure was external — `claude` crashed, an API timed out, an account swap
or a `PATH` glitch — and the right action is simply: **run the step again**. "Recover" frames
that as climbing out of a broken state; **`repeat`** names the action honestly. It also reads
correctly for the gate-red case (the resuming session judges sound-vs-insufficient from the
tree), so the verb does not need to be split by cause — the engine cannot reliably pre-classify
the cause, and the forward *action* is identical either way.

This is Peter's framing in REQ-053: at a red step there are two intents — **repeat** (external
cause, work sound, run again) and **rework** (internal cause, work insufficient, redo). `rework`
is already correctly named (REQ-033, the V-model return edge). Renaming `recover → repeat`
completes the pair so the operator vocabulary matches the mental model.

The user-facing recovery vocabulary is the verb **and** the `--recover` resume flag that the
executor appends to a re-armed step's command — the flag the `/advance` skill branches on to
assess the tree instead of starting clean. Both are things the operator types or reads, so both
rename together. The runnable status symbol (`StepStatus.RECOVER`) and the `step_recover` ledger
event are *not* user-facing — `steward status` renders the status as an icon (`↻`), never as the
string, and the event is append-only history no command reads programmatically — so they stay
unchanged (renaming them would fork ledger-history continuity for no user benefit; REQ-029's
"old ledgers are reinterpreted, never rewritten").

This is a deliberate rename, not new machinery — the smallest possible change that makes the
name honest, with no behavioural change to recovery itself.

## Requirement

Rename the run-it-again recovery verb and its resume flag from `recover` to `repeat`, with no
change to recovery behaviour, internal status symbols, or ledger event names.

- `steward repeat REQ` re-arms a `FAILED` develop step exactly as `steward recover` did: it
  flips the REQ's `FAILED` ledger step(s) to `RECOVER`, records the event, leaves the working
  tree as the failed attempt left it, and refuses (non-zero) when the REQ has no failed step. It
  runs regardless of HEAD inside the same atomic transaction as the other recovery verbs.
- `steward recover` is no longer a registered command — there is no alias.
- A step re-armed for a repeat is launched with `--repeat` (not `--recover`) appended to its
  command, and the `advance` skill reads `--repeat` as its assess-the-tree resume signal.
- Operator-facing CLI help and messages — the `repeat` success line and the `rework` refusal's
  cross-reference — name `steward repeat`, not `steward recover`.
- Internal symbols are untouched: `StepStatus.RECOVER` and the `step_recover` event keep their
  names.

## Notes

- **Why a rename and not a split.** The audit settled this: the forward *action* (re-arm the
  failed step → run again, hand the session the tree + the resume brief) is identical whether the
  cause was external (sound work) or a red gate (insufficient work); the engine cannot reliably
  pre-classify, and the resuming session judges from the tree. One honest name — `repeat` — beats
  two verbs the operator would have to choose between blind.
- **Relationship to siblings.** REQ-055 (`revalidate`) is independent and does **not** depend on
  this rename — it uses today's verb names. The audit also *names* (does not yet intake) a
  resume-signal-through-dirty-parks change and a docs item; the handbook + skill-prose updates for
  this rename fold into that docs REQ.
- **Process declarations:** defaults — fused develop, no concept phase, no lab. All ACs are
  `regression` (module/CLI scope, coupled oracle); no artifact/manual check, so no System-Test
  phase. The `process:` block is omitted.
- **Localization:** all strings are operator-facing CLI/technical English; no localized UI.
