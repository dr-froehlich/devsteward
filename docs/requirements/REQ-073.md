## Context

From the 2026-07-03 intake brief
(`docs/reports/2026-07-03-ledger-lost-update-and-decision-recovery-gap.md`), surfaced live
in FlowSteward. Two coupled defects: the first loses data, the second removes every path
back.

**D1 — lost update.** `Ledger.save()` (`core/ledger.py`) is a blind whole-file write of an
in-memory dict: no reload-before-save, no version/sequence guard, no mtime check. Any
process holding an older snapshot that saves after a newer commit wins by last-write. The
attended `steward validate` flow makes this reachable by a *single operator*: the parent
process loads the ledger in `start()`, blocks for the whole interactive session, and its
`record()` half saves at the end — so its snapshot can be hours stale. In FlowSteward
(2026-07-02), a correct, committed land (`REQ-069:validate = done`, `DEC-044 = answered`,
commit `5b574e1`) was silently rewound hours later by a stale snapshot's save: `state.yaml`
went back to `pending`/`open` while the append-only `events.jsonl` kept the truth — cursor
and event log **diverged**, and the REQ's frontmatter (`done`) contradicted its cursor
entry. The exact clobbering invocation is not pinned and does not need to be: the
structural defect is proven by the divergence, and the fix must assume overlap can occur.

**This revises the 2026-07-02 process review §5.** The review parked multi-writer
concurrency as ceremony to revisit "*if* a second contributor ever appears." D1 shows the
hazard is **temporal, not multi-user**: one operator's long-lived process overlapping later
invocations already fired it. It must **not** be conflated with the review's §4.6
`_park_red` no-dedupe gap — that mints multiple *genuine* decisions for repeated reds; this
is **one** decision that **was answered**, whose answer was **lost**. The §4.6 dedupe fix
would do nothing here.

**D2 — no recovery path.** Once `state.yaml` says `DEC-044 = open` while the REQ is
`done`, no CLI verb can close it. `steward validate` on a `done` REQ routes to
`revalidate`, which is non-mutating by design — every re-approval appends fresh evidence
and leaves the decision open (the "advertised remedy that does nothing"). `steward
decision answer` refuses a `:validate` decision (the REQ-057 guard) and redirects back to
`steward validate`. The two remedies point at each other; unsticking the operator required
hand-editing `state.yaml` — the one thing STEWARD.md forbids. The "never hand-edit
`state.yaml`" rule needs a sanctioned recovery behind it, or it is unenforceable exactly
when the ledger self-inconsistency arises.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | **D1 root fix: a monotonic `seq` guard on `save()`, not just a reload-before-terminal-save.** `state.yaml` carries a monotonic sequence number bumped on every save; `save()` compares the on-disk `seq` against the one this process loaded, and on a mismatch **refuses the blind write** — it reloads and re-applies this process's specific mutation, or fails loudly. | The reload-before-terminal-save variant only closes the one known overlap shape (the long-lived validate parent); any future long-lived path re-opens the hole. The seq guard closes the lost-update *class*. It is a check, **not a lock** — no multi-writer locking subsystem for a single-operator tool (intake brief guardrail; per-invocation overlap is temporal, not multi-user). Aligns with the event log already being the append-only source of truth. |
| 2 | **On a stale-save detection, reconcile narrow mutations and refuse broad ones — never silently lose either side.** The mutating methods (`set_status`, `park_decision`, `answer_decision`, `set_cursor`) are small, targeted writes; on conflict the guard reloads the newer state and re-applies just this mutation. A write that cannot be expressed as a targeted re-application fails loudly with both states preserved on disk/log. | The failure mode being cured is *silent* loss. A correct merge is best; a loud, recoverable error is acceptable; a silent rewind is the only forbidden outcome. |
| 2a | **Loud failure is a defect signal, never a regular-operation outcome — and it tells the operator what to do** (Peter, intake 2026-07-03). Every mutation the engine performs in normal operation goes through the targeted-mutation methods, so reconciliation always succeeds for real workflows — the known overlap shapes (long-lived attended validate, an overlapping `steward run`) resolve silently and correctly. The refusal path is reachable only by an engine code path that bypassed the targeted API with a broad blind write — i.e. an engine bug. When it fires, the message states that **nothing was lost**, names both preserved sides (the newer on-disk `state.yaml` and the append-only event log), and instructs: re-run the command; if it recurs, report it as an engine defect — never hand-edit `state.yaml`. | Peter's constraint: "failing loudly is the outcome of a defect, not regular operations" — and the operator at the message is the least-context reader; a refusal without a next action would recreate the exact stranded feeling this REQ exists to cure. |
| 3 | **D2 recovery: targeted, not a general `steward reconcile` verb.** `steward validate` on a `done` REQ (the revalidate route) additionally reconciles any lingering **open** `:validate` decision for that step: a `done` REQ with an open validation hold is self-evidently resolvable — the land already happened and is in the event log (`latest_validation` / `decision_answered`). No new verb. | Subtraction: start targeted unless a second divergence shape is already known (intake brief §6.2, house principle). The general event-log-replay verb is machinery for a class Decision 1 makes impossible going forward; it stays a *named rejected alternative* to re-intake only if a second divergence shape ever appears. This closes exactly the dead end that occurred, on the exact verb the park message already advertises. |
| 4 | **The REQ-057 `decision answer` guard stands unchanged.** A `:validate` decision keeps refusing free-text answers and redirecting to `steward validate` — but the redirect target now actually resolves the diverged state (Decision 3), so the two remedies no longer point at each other. | The guard was right (a validation hold is not a fork to answer); the dead end was the redirect landing on a non-mutating path. Fix the target, keep the guard. |
| 5 | **REQ-035's provenance freeze is preserved.** Closing a stale open decision on a `done` REQ touches only the decision record (and appends an event); `verified_by`, `status`, and the frozen landing provenance stay untouched. | Decision 3 is a *reconciliation* of the cursor with the event log, not a re-validation outcome; REQ-035 ruled a done re-validation must not clobber provenance. |
| 6 | **Back-compat: a `seq`-less `state.yaml` loads unchanged and acquires `seq` on its first save.** No migration step, no consumer action. | Every existing consumer ledger (FlowSteward, devsteward's own) predates the field; the guard must not turn their first post-upgrade save into an error. |
| 7 | **Engine-only; fused develop; no lab; regression-only ACs.** Ledger behaviour is fully provable with synthetic ledgers in temp dirs. The black-box manual/handbook note the recovery path (a done REQ with a lingering validation hold: run `steward validate REQ-NNN`). | The oracle is the engine's own state files — coupled, hermetic, no service/secret/network beyond a temp git repo. No decoupled observable exists to justify an artifact/manual check; the FlowSteward incident is the motivating postmortem, not a lab. |

## Requirement

- `state.yaml` carries a monotonic sequence number; every `Ledger.save()` bumps it, and
  `Ledger.reload()` picks it up.
- A `save()` from a process whose loaded `seq` is older than the on-disk `seq` **never
  blind-overwrites**: it reconciles (reload + re-apply this process's specific mutation)
  or fails loudly with both the on-disk state and the event log intact. A committed newer
  fact — an answered decision, a `done` status, an advanced cursor — is never silently
  rewound by a stale snapshot's save.
- **Reconciliation succeeds for every mutation the engine performs in regular operation**
  (all engine writes route through the targeted-mutation methods), so the loud-failure
  path is reachable only via an engine defect — and its message is actionable: it states
  that nothing was lost, names the preserved on-disk state and event log, and instructs
  re-run / report-if-recurring — never a hand-edit of `state.yaml`.
- The FlowSteward overlap shape specifically survives: a long-lived process loads the
  ledger, a second invocation lands a step (status → `done`, decision → `answered`) and
  saves, then the first process saves — the land's facts are still on disk afterwards.
- `steward validate REQ-NNN` on a `done` REQ also closes any lingering **open** `:validate`
  decision for that step (reconciling from the event log), appends a reconciliation event,
  and `steward status` stops surfacing the decision. `verified_by`/`status` stay frozen
  (REQ-035).
- `steward decision answer` on a `:validate` decision still refuses and redirects
  (REQ-057) — and the redirected-to verb now resolves the diverged state, so no
  mutually-pointing dead end remains.
- A legacy `state.yaml` without a `seq` field loads without error and is upgraded on its
  first save.
- The Claude-targeted black-box manual and the handbook name the recovery: a `done` REQ
  still surfacing a parked validation decision is closed by `steward validate REQ-NNN`,
  never by hand-editing `state.yaml`.

## Notes

- **Source:** `docs/reports/2026-07-03-ledger-lost-update-and-decision-recovery-gap.md`
  (D1 + D2 + the relation to the 2026-07-02 process review). FlowSteward's ledger was
  already hand-reconciled (its commit `089af9a`) — nothing to repair there; this REQ cures
  the engine.
- **Scope split (intake decision):** the `steward decision` UX strand of the same brief
  (§3 — missing context, free-text-not-a-choice, no useful effect) is deliberately **not**
  in this REQ; it is the separable premise question drafted as REQ-074. D1 and D2 travel
  together because D2 is the recovery for exactly D1's failure mode.
- **Rejected alternatives:** (a) reload-before-terminal-save only — closes one shape, not
  the class (Decision 1); (b) a general `steward reconcile` event-log-replay verb — new
  machinery for a class the seq guard removes; re-intake only if a second divergence shape
  appears (Decision 3); (c) rethinking the long-lived attended-validate process shape
  (load late, right before recording) — a larger refactor of the session flow that still
  would not guard other overlaps; the seq guard subsumes its benefit.
- **Not a lock:** the guard is a compare-on-save check. Do not grow it into a general
  multi-writer locking subsystem (house principle: minimal topology / prefer subtraction).
- **Environment note (REQ-064 screen):** all ACs are hermetic — synthetic ledgers and
  temp git repos, no service/secret/network. Nothing env-bound.
- **Intake forks answered by Peter (2026-07-03, second interview round):** two-REQ split
  and targeted recovery confirmed; on D1 he set the constraint captured as Decision 2a
  ("failing loudly is the outcome of a defect, not regular operations" + the failure must
  tell the operator what to do). The first interview round had timed out and been
  defaulted — the re-ask is the binding one.
