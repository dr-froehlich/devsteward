## Context

When more than one REQ is eligible, the human running the workflow often wants to steer
*which one* advances next. The capability already exists — REQ-026 shipped
`steward advance --only REQ-NNN` and `steward run --only REQ-NNN`, backed by
`eligible_steps(only=…)` and the `only_ineligibility_reason()` messages — but it is
undiscoverable and the *natural* gesture is rejected. A user reaches for the obvious form:

```
$ steward activate REQ-027
activated REQ-027 (draft -> open).
$ steward advance
✗ refusing to reuse feature branch 'req-019-retention-engine' — it has diverged from 'dev' …
$ steward advance REQ-027
Error: Got unexpected extra argument (REQ-027)
```

Two failures compound here. First, plain `advance` silently selected the lowest-id
eligible step (a stale REQ-019 in-progress branch) instead of the REQ the human had just
activated — there was no signal that a choice was even being made, nor that it could be
steered. Second, when the human did the obvious thing and *named* the REQ positionally,
click rejected it, because the steering knob is spelled `--only` and is invisible unless
you read `--help`. The cost is a daily papercut: the human knows exactly which REQ they
mean, the engine already supports targeting it, and yet the two don't meet. `checkpoint`
and `validate` already take a positional `REQ_ID`; `advance`/`run` are the inconsistent
pair.

This REQ closes the gap as pure ergonomics on top of the existing `--only` machinery: no
new resolution logic, just the natural surface plus a nudge toward it. The diverged
feature-branch refusal in the trace above is a *separate* concern (stale-branch
reconciliation) and is explicitly out of scope — but note that scoping to one REQ
naturally sidesteps it, since only the named REQ's branch is then consulted.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | `advance` and `run` accept an optional positional `REQ_ID` that maps onto the existing `--only` resolution (`eligible_steps(only=…)`) | The natural gesture (`steward advance REQ-027`) should just work; reuse the proven machinery rather than add a parallel path. Both batch siblings get it, matching their existing `--only` and the positional `checkpoint`/`validate` already carry. |
| 2 | The positional and `--only` are mutually exclusive — supplying both errors | Two spellings for one target is ambiguous; fail loudly rather than silently prefer one. `--only` stays for back-compat and scripts. |
| 3 | A named-but-ineligible REQ (draft, done, or dep-blocked) reuses `only_ineligibility_reason()` verbatim and exits non-zero — no auto-activation of a draft | Naming a REQ is a target, not a lifecycle command; activation stays an explicit, deliberate step (`steward activate`). The existing message already names *why* and points to `activate`. |
| 4 | Plain `advance`/`run` with >1 eligible step keeps picking the lowest id, but now prints the eligible REQ ids and the `steward advance REQ-NNN` steer syntax | Non-breaking (unattended auto-drive still works), but the silent choice becomes visible and teaches the steering gesture at the exact moment it's useful. |

## Requirement

`steward advance` and `steward run` accept an optional positional `REQ_ID`. When present
it scopes step resolution to that REQ exactly as `--only REQ_ID` does today; the positional
and `--only` may not both be given. Naming a REQ with no eligible step fails with the
existing reason message. When no target is named and more than one step is eligible, the
chosen step is still the lowest id, but the eligible set and the steer syntax are surfaced.

## Notes

- Out of scope: the diverged/stale feature-branch reconciliation refusal seen in the
  motivating trace — that is its own concern; this REQ only adds targeting.
- Out of scope: auto-activating a draft when named (Decision 3).
- The `/advance` skill already lets a human name the REQ; this aligns the CLI so the skill
  and the bare CLI offer the same gesture.
