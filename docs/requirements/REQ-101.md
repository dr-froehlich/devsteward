## Context

The owner's need, in the owner's words (backlog item `joint-project-tasks`): *"Handover between
projects works like this: from sarah I ran `steward backlog-add --origin proposed --handle
sysadmin-open-0177 "…"`. I want this to become fully automated. My DevSteward projects shall be
able to hand over tasks without many manual involvment. Once a joint task has been initiated, a
bidirectional communication channel shall remain open until the job has finished, which should
be acknowledged from both sides."* The item's acceptance criteria were authored at this intake,
before any design, and live in `docs/BACKLOG.md`.

**How a handover works today.** The live case is sarah and system-admin, two projects on the
development box. system-admin keeps its open items in its own documents, and its own tool writes
a self-contained handover file per receiving project. The file holds the items, the reasoning
they cite, and a ready `steward backlog-add --handle sysadmin-open-NNNN` command for each. The
owner then opens a sarah session and points it at that file. sarah files the item and intakes it
(OPEN-0177 became sarah REQ-052). When it has questions back, it writes a reply file into its own
`docs/handover/` folder. The owner carries that reply back to a system-admin session. system-admin
reads sarah's backlog and requirements directly to learn what each item was filed under. Each
side expires its files by hand once everything in them is filed or closed. sarah's folder holds
five such replies, and system-admin's handover folder has sixteen commits behind it.

So the engine already supplies a stable cross-reference (the backlog handle) and derived take-up
state (`steward backlog-list`). What it does not supply is delivery, replies, or any notion of the
job being finished on both sides. **The owner is the courier in both directions**, carrying files
and paths between sessions and telling each session where to look.

**What was settled at intake, and why.**

- **Only stamped projects.** system-admin is not a DevSteward project. It has no ledger, and its
  open-item tool is its own. The owner: *"It's only system-admin, we now determined twice that the
  nature of its work is in conflict with the DevSteward patterns. We could still stamp it with a
  .devsteward folder, to offer the same 'interface'. I'd rather you design for DevSteward and then
  we design how we could bring on system-admin."*
- **Each project writes only into its own repo.** REQ-079 commits a project's whole working tree
  at every checkpoint, and REQ-077 Decision 3 makes a land fail when *"anything left dirty beyond
  the pre-boundary/concurrent set"* remains: it *"fails loudly and rolls back"*. A file one project
  writes into another project's tree while a session runs there is therefore swept into that
  session's REQ commit. If it arrives mid-checkpoint, it rolls the land back. Writing only into
  one's own repo is also what sarah and system-admin already do by hand. The owner accepted the
  consequence that each repo's history holds only what that project authored: *"split history, I
  only have what I author … it looks clean to me."*
- **The receiver finds the sender without being told.** All of the owner's projects are siblings
  in one parent folder. The dashboard already finds every stamped project there without a
  configured path (REQ-097 Decision 7). The owner's criterion says the target project *"finds it,
  presents me with the possible candidates"*, so the owner names no project, folder or file.
- **Only `/advance` and `/intake` look.** REQ-034 Decision 6 stands: *"Never spawn Claude from
  within Claude (Peter, firm)"*. Nothing starts a session when a message arrives. The owner, on how
  far the check reaches: *"only advance and intake see it, of course."*
- **What travels.** The owner: *"Requests for action, request for feedback / information /
  decision, push information to the other, finished job handshake."* On finishing: *"Both sessions
  assess the job as finished. It is the session responsibility to determine with the user / me
  how. It could be in a develop session, a successful validation or something else."*

## Requirement

### The joint log

Each participating project keeps `.devsteward/joint.jsonl`, created on its first send. Each
line is one JSON object, and lines are only ever appended. Every entry carries:

- `seq`: 1, 2, 3, … within this log;
- `at`: ISO 8601 with offset;
- `thread`: the thread handle;
- `kind`: `action`, `ask`, `tell`, `done` or `ack`.

A message's reference is `<author project>#<seq>`. The kinds add these fields:

- **`action`**: `to` (the addressee's project name), `need` (one line, folded exactly as a
  backlog need is folded, REQ-100, because it becomes the receiver's backlog text word for word)
  and `body` (Markdown, possibly empty: the reasoning, which today's handover files inline).
- **`ask`, `tell`, `done`**: `body`, plus an optional `reply_to` (a message reference). The
  addressee is implicitly the other party of the thread.
- **`ack`**: `ref`, the reference of the acknowledged message.

### Addressing and discovery

The projects are the stamped children of the parent folder of the enclosing project, found by
the dashboard's discovery (REQ-097 Decision 7), shared rather than copied. `--to` matches a
project's folder name case-insensitively. Each of these is refused with a non-zero exit, a
message listing the addressable project names, and nothing written:

- an unknown name;
- an unstamped folder;
- the sending project itself;
- a name matching two folders that differ only by case.

A minted handle is `<sender>-<slug>` in the backlog-handle grammar. A handle that already names
a thread in either party's log, or an item in the addressee's backlog, is refused.

### The verbs

- **`steward joint-send`** opens a thread with an `action` to a project, or sends an `ask`, a
  `tell` or a `done` into an existing thread. A long body is accepted from a file or stdin.
  These sends are refused:
  - by a project that is not a party of the thread;
  - into a closed thread;
  - with a `reply_to` that names no message of the thread.
- **`steward joint-ack`** records that this project handled a message addressed to it.
- **`steward joint-list`**, in the current project, lists every open thread it is a party of,
  marking what waits for it: messages addressed to it that it has neither acknowledged nor
  replied to. It also lists the **candidates**: incoming `action`s whose handle is not an item in
  this project's backlog.
- **`steward joint-show <handle>`** prints one thread with both halves merged in time order. Each
  message shows its author, kind, reference and reply-to, and whether it was handled. The
  addressee's take-up is shown as `steward backlog-list` derives it in that project (e.g. taken up
  by REQ-052, and that REQ's status). It works on closed threads too.

The exact option spelling is the develop session's, documented in STEWARD.md.

### Lifecycle

A thread opens with its `action` and closes once both parties have sent `done`. A party that has
sent `done` may still answer while the thread is open. Closed threads leave `joint-list` and stay
readable through `joint-show`.

### Where sessions look

- **`/intake`.** When the operator asks it to take up another project's request, it runs `steward
  joint-list` and presents the candidates. On the operator's pick, it files the request with
  `steward backlog-add --handle <thread> --origin proposed "<need>"`, acknowledges the `action`,
  and continues the normal intake (§2d) from that item.
- **`/advance`.** At orientation it runs `steward joint-list`. If anything waits, it works through
  it with the operator:
  - it answers an `ask` with a `tell`, putting a decision to the operator;
  - it acknowledges a `tell` once it has read it and acted on it;
  - it points an incoming `action` to `/intake`.

  It skips this step when `DEVSTEWARD_UNATTENDED=1`.

## Notes

**Out of scope, on purpose.**
- system-admin and any other unstamped project (Decision 1). The item stays open for them.
- Projects outside the shared parent folder, or on another machine.
- Renaming a project folder while threads that address it are open.
- Any session starting by itself (REQ-034 Decision 6).
- Showing joint messages in `steward status` or the dashboard.
- Processing messages in headless runs.
- Attachments other than the Markdown body.
- A verb that commits.
- The `backlog-commit-ui-changes` and `prose-converter-fidelity` items, which are separate needs.

**Develop obligations.**
- **The live proof** (Decision 11): one complete real thread between two stamped projects, with
  attended `/intake` and `/advance` sessions on both sides. The pair is chosen with the owner
  then. Whatever the real sessions turn up (a skill step they skip, an output they misread) is
  fixed in place.
- **The manual and the skills** (Decision 12): STEWARD.md, `/intake` and `/advance` change in the
  same commit as the code. Each skill is inode-shared with its template, so edit one path, never
  both. Consumers receive the skills and the manual at their next `steward sync`.
- **One discovery** (Decision 3): the scan the joint verbs use is the dashboard's, moved wherever
  both can import it without the optional `dashboard` extra, never copied.

**Risks.**
- **Retraction.** Readers see a sibling's working tree (Decision 9). If the sending session
  discards uncommitted work, a message the receiver has already acknowledged can vanish from the
  sender's log. AC4's dangling-reference handling keeps that visible instead of fatal.
- **Session compliance.** "Process automatically" rests on `/intake` and `/advance` following
  their skill text. That is what the live proof is for. A plain session started without either
  skill sees nothing, by the owner's choice (Decision 8).
- **Folder rename.** It silently orphans the threads that address the old name (out of scope).
