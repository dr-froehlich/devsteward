## Context

A live session in a consumer project **refused to push during a develop step**, and was right
to by the letter of the doctrine it was reading. `/advance` §4 tells the interactive close:

> Do **not** commit separately … `checkpoint` is the committer … **The one sanctioned exception:
> mid-phase commits during an *empirical* `concept: true` phase.**

That project builds its arm64 image in CI and deploys to a remote host — so *pushing is a
precondition for the code existing anywhere it can be run at all*. Taken literally, the rule
makes the live proof unreachable during develop, and the only remaining home for it is the
System-Test phase. That is the worst possible destination: the System Tester runs in a **fresh
session that never sees the diff and cannot fix anything** (REQ-030), so a deploy proof routed
there has **no repair loop** — every red bounces back as rework a whole session later. The
operator's summary was exact: the escape hatch assumes deployment is pushed to a teethless
validation session, which is utterly wrong.

Pulling that thread surfaced three more defects on the same seam. This REQ owns all four,
because they are one workflow: *get code onto a remote host, prove it there, and fix what the
proof finds without paying for the proof twice.*

### 1. The doctrine contradicts itself

`/intake` §2b anticipates precisely this misreading and disclaims it:

> the empirical-concept-phase deploy permission is **a grant, not a restriction** that **only**
> concept phases may reach the live system.

and its live-proof-in-develop screen says the opposite of what `/advance` enforces: *don't defer
the critical proof to the validator* — make the live proof a develop-session obligation,
performed and iterated attended, **fixable in place**.

So the correct rule is already written down. It is simply written in the file a session reads at
**intake**, while the file it obeys during **develop** states an absolute with a single
enumerated exception. Normative text beats a disclaimer in another document every time.

**This is a regression of scope, not a new bug.** The same shape was reported in the FlowSteward
REQ-081 postmortem (`docs/reports/2026-07-05-…-postmortem.md`): *"Producing that deliverable is
inherently a multi-commit, multi-deploy effort … That frame is wrong for this shape of work, and
there is no mid-phase commit/push verb."* It cost real work — while the session held its output
uncommitted, a concurrent `steward validate` swept those files into a commit labelled for a
**different REQ** (`ce1c9ef` "REQ-090:validate"), violating same-commit discipline and drifting
the ledger. Refusing to commit mid-phase is not the safe default it looks like; long-lived
uncommitted work is itself a hazard. [[REQ-071]] then codified the fix but bound the grant to
`concept: true` — the narrowest reading of the evidence, since the FlowSteward case *happened*
to be a concept phase. **Enumerating exceptions guarantees the next unlisted-but-legitimate case
fails**, and it did.

### 2. There is no way to see the gate before committing

Investigated 2026-08-06: there is **no instruction anywhere to run `steward checkpoint`
mid-development**, and **no mid-phase commit or push verb** at all. What exists is permission to
make plain **git** commits mid-phase (fenced to `concept: true`) and the clause that the
*terminal* checkpoint is "sanctioned over an already-clean tree". A session hunting for the
sanctioned way to commit mid-phase finds nothing and concludes there isn't one.

The operator's instinct was a mid-phase checkpoint that runs the gates but does not close the
ledger, so a push only happens on green. **The gating half is rejected** (Decision 4): in the
deploy case the dependency runs the other way — you push *so that* CI builds the image, *so that*
it deploys, *so that* the proof can run at all. Requiring green before pushing inverts that and
deadlocks the exact case this REQ exists to unblock. What survives is the useful half: today the
land-grade gate is reachable **only by attempting a land**, so a session cannot see where it
stands without trying to close.

### 3. `rework` throws away sign-offs it does not need to

The operator's real workflow: a deployment is pushed to the validation phase, validation pauses,
a develop session fixes the issue, then the *same* validation resumes — because validation is
often a long manual walkthrough nobody wants to repeat. The unsanctioned alternative is copying
evidence between sessions by hand.

That workflow falls in the gap **between** two verbs:

| verb | develop re-opened? | carry written? |
|------|--------------------|----------------|
| `steward rework` (REQ-033) | yes → `RECOVER` | **no** |
| `steward revalidate` (REQ-055/075) | no — stays `DONE` | yes |

`revalidate` (`lifecycle.py:328`) calls `_scope_revalidation` and carries green one-off evidence
plus recorded `manual` sign-offs forward with provenance — but it is the **external-cause** edge
and leaves develop at `DONE`, so a code fix never passes a develop gate. `rework`
(`lifecycle.py:~285`) is the right route for a code fix but never calls `_scope_revalidation` at
all: no `scope`, no `carried`. The consumption side then goes quiet — `_pending_revalidate`
(`validate.py:145`) matches only `event == "revalidate"` **with** a `scope`, its result becomes
`ctx.reval`, and `validate.py:526` gates the *entire* `_carry_forward` call on `if reval is not
None`. So after a rework every `artifact` and `manual` AC is re-walked from scratch.

The carry machinery is already built and proven (REQ-075). `rework` simply does not use it, and
`_pending_revalidate` would not read it if it did.

### 4. Two verbs the CLI cannot show you

`steward decision list|answer` is a real click group — discoverable under `steward decision
--help`, though absent from `steward --help`. `steward validate start|record` is **not a group at
all**: `cli.py:742` declares

```python
@click.argument("words", nargs=-1, required=True, metavar="[start|record] REQ_ID")
```

a variadic argument parsed by hand, so the verbs are invisible to click's own introspection —
walking the command tree prints only `steward validate <words>`. The `[start|record]` in the help
output is a hand-written `metavar` string. `steward validate start` is the one command in the
whole CLI designed to be invoked *mid-phase*, and it is the least discoverable thing in it.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | The mid-phase commit/push permission is keyed on **attended** (`DEVSTEWARD_UNATTENDED` unset), not on `concept: true`. Batch never commits. | A human is present, owns the consequences, and can repair in place. Batch genuinely must not commit — the engine is the committer there and a headless commit would double-commit — so *attended* is the axis that actually carries the distinction the old rule was groping for. |
| 2 | The skill names the legitimate **trigger**: work that cannot be proven without a round-trip through external infrastructure (CI building an image, a remote host, a deploy target). | Keeps the grant honest without inviting casual mid-develop commits. | 3 | State it as a **principle**, not a longer list of exceptions: *the one-checkpoint frame bounds the bookkeeping, not the round-trips.* Mid-phase commits are **plain git commits by the session**; `steward checkpoint` stays terminal-only. | The enumerated-exception framing *is* the defect; adding "…and deploy" as a second entry moves the failure to the third unlisted case. Naming the mechanism explicitly is what stops the next reader concluding no sanctioned path exists. |
| 4 | **Reject** the gated mid-phase checkpoint. Ship instead a **read-only `steward gate`** that previews the verdict and touches nothing. | Gating a push on green inverts the deploy dependency and deadlocks the case this REQ unblocks; mid-develop the named tests may not exist yet, and for deploy-shaped work they cannot pass from a bare extract by construction. Separating "am I green?" from "commit" gets the confidence without the half-transaction. |

| 11 | `develop: fused` (the default), despite the four workstreams. | Operator's call, taken over a recommendation to split for an attended design review of the carry semantics and the migration shape. `/advance`'s plan-first step still forces a written approach before code. |

## Requirement

### A. Doctrine — one coherent rule across four surfaces

An attended develop session may commit, push and deploy mid-phase when the work requires a
round-trip through external infrastructure; a batch session never commits; `steward checkpoint`
remains the terminal bookkeeping act.

1. `/advance` §4 no longer says "the one sanctioned exception … `concept: true`". It states the
   attended grant with its trigger, names plain git commits as the mechanism, and keeps
   `steward checkpoint` terminal.
2. `/advance` §2's iterate-until-frozen clause is generalized **off** `concept: true` — the
   concept phase becomes one instance of the pattern, not its licence.
3. The batch prohibition is untouched and stays absolute.
4. `/advance` §2 tells a session whose proof needs a deploy that the proof belongs **in this
   session**, fixable in place — not deferred to the System-Test phase. `/intake`'s
   live-proof-in-develop screen names the deploy-shaped case explicitly and keeps its "grant, not
   a restriction" clause, which now agrees with `/advance` instead of compensating for it.
5. `STEWARD.md`'s "(One exception: an *empirical* `concept: true` phase may commit mid-phase…)"
   and handbook rule 4 are both restated on the attended axis.

### B. `steward gate` — see the verdict without committing

6. `steward gate [REQ-NNN] [PHASE]` runs the step's named acceptance tests exactly as the develop
   gate will (resolved interpreter, `check:`-routed selection, `verify.env_file` carry) and prints
   the verdict plus each failing test.
7. It is **read-only**: `HEAD`, the working tree, the git index, `.devsteward/state.yaml`,
   `.devsteward/events.jsonl` and the REQ file are all byte-identical afterwards. It records no
   event, mints no evidence dir, and never lands.
8. Its output states that it is the *verify* gate, not REQ-063's capture check — a green `gate`
   is not a promise that `steward checkpoint` will land.

### C. `steward rework` carries prior sign-offs

9. `rework` computes `scope` + `carried` via `_scope_revalidation` from the red validation's
   per-AC results and writes them onto its `rework` event, alongside the existing evidence path
   and failure brief. Develop still goes to `RECOVER`.
10. `_pending_revalidate` treats a scope-bearing **`rework`** event as pending scope exactly as it
    treats `revalidate`, so `ctx.reval` is populated and `_carry_forward` runs.
11. The resumed validation therefore re-opens only the ACs the red validation left red or
    unrecorded; carried `artifact` evidence is copied into the fresh evidence dir; a carried
    `manual` green replays its recorded sign-off **without** a new decision stop; and the
    validation event records each carried AC's `source_evidence` and `source_event`.
12. The degenerate cases are unchanged: no per-AC results, or nothing green → full re-run.

### D. A flat, discoverable CLI

13. `validate-start`, `validate-record`, `decision-list`, `decision-answer` replace the two-word
    forms. `steward validate REQ-NNN` is unchanged. The hand-parsed variadic `words` argument is
    gone — every command's arguments are declared and introspectable.
14. `steward --help` lists every invocable command; nothing requires a second `--help` to discover.
15. No DevSteward-owned surface (stamped skills, `STEWARD.md`, handbook, `docs/`) still names a
    two-word form.

## Notes

- **Accepted hazard — the stale carried sign-off (Decision 7).** `revalidate` carries safely
  because the code did **not** change; `rework` exists precisely because it **did**, so a carried
  `manual` green is an observation of code that no longer exists. It replays with no decision
  stop, so a stale sign-off lands silently. The operator chose the unconditional carry over a
  recommendation for a per-AC opt-out; the mitigation is provenance (`source_evidence` +
  `source_event` on every carried AC) and the `scoped re-run (REQ-075): …` announcement the
  resumed session prints *before* the walkthrough starts, so what is not being re-walked is
  visible in advance. **If this bites — a carried green that the fix invalidated — the home is a
  follow-on REQ adding per-AC carry control, not a silent tightening here.**
- **Blast radius of the hard rename (Decision 9).** All consumers (FlowSteward, memzy, THermo)
  run whatever branch the one shared pipx editable `steward` has checked out, so the rename
  reaches them the moment this lands on `dev` — not when they choose to upgrade. Consumer-side
  runbooks, notes and muscle memory still typing `steward validate start` will break with a
  no-such-command error. Rewriting DevSteward-owned surfaces (AC6) does not reach consumer-owned
  documents; those are the consumer's to fix, and this REQ does not track them.
- **Lineage.** REQ-064 (intake screens env-bound `regression` ACs) → REQ-068 (the `check:` lanes)
  → REQ-071 (concept-phase & wiring-gap doctrine) → this. Each codified a downstream lesson into
  the doctrine surfaces. This one corrects REQ-071's scope: right rule, wrong axis.
- **The skills are hardlinked** (`.claude/skills/<name>/SKILL.md` and the stamped template are one
  inode) and repo-root `STEWARD.md` is a **symlink** to `devsteward/templates/STEWARD.md`. Edit
  once. The tests read the template paths deliberately — those are what `steward new`/`sync` stamp.
- **Considered and rejected:** a mid-phase checkpoint gated on green (Decision 4 — inverts the
  deploy dependency, deadlocks the case this REQ unblocks); a `process.deploys: true` frontmatter
  declaration (moves the enumerate-the-exceptions trap into schema); an engine guard refusing
  headless mid-step commits (the batch lane cannot reach that path — the engine is the committer);
  permanent aliases for the two-word forms (Decision 9).
- **Out of scope:** the `check:` taxonomy; REQ-030's System-Test phase design (the fixless
  validator is correct *as a validator* — the defect is routing deploy proofs to it); any schema
  or lint change; consumer-owned documentation.
- **Not a licence to skip the gate.** The attended grant covers committing and pushing during
  develop. The session still never writes `status:` or edits the index row, the engine still owns
  the flip, and `steward checkpoint` still re-runs the acceptance tests through the land-grade
  gate and refuses to land on red. `steward gate` is a preview and certifies nothing.
- **Residual risk.** Pushing mid-develop puts un-checkpointed work on the remote `dev`; if the
  session is abandoned the remote carries code the ledger does not know landed. Recovery is
  `steward repeat`, which reads the tree as it finds it. Acceptable — `dev` is the integration
  branch, consumers pin release tags cut on `main`, and this exposure already exists via the
  concept-phase grant.
