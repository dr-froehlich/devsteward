## Context

A live session in a consumer project **refused to push during a develop step**, and was right to
by the letter of the doctrine it was reading. `/advance` §4 tells the interactive close:

> Do **not** commit separately … `checkpoint` is the committer … **The one sanctioned exception:
> mid-phase commits during an *empirical* `concept: true` phase.**

That project builds its arm64 image in CI and deploys to a remote host — so *pushing is a
precondition for the code existing anywhere it can be run at all*. Taken literally, the rule
makes the live proof unreachable during develop, and the only remaining home for it is the
System-Test phase. That is the worst possible destination: the System Tester runs in a **fresh
session that never sees the diff and cannot fix anything** (REQ-030), so a deploy proof routed
there has **no repair loop** — every red bounces back as rework a whole session later. The
operator's summary was exact: the escape hatch assumes deployment is pushed to a teethless
validation session, which is utterly wrong.

### The doctrine already contradicts itself

`/intake` §2b anticipates precisely this misreading and disclaims it:

> the empirical-concept-phase deploy permission is **a grant, not a restriction** that **only**
> concept phases may reach the live system.

and its live-proof-in-develop screen says the opposite of what `/advance` enforces: *don't defer
the critical proof to the validator* — make the live proof a develop-session obligation,
performed and iterated attended, **fixable in place**.

So the correct rule is already written down. It is simply written in the file a session reads at
**intake**, while the file it obeys during **develop** states an absolute with a single
enumerated exception. Normative text beats a disclaimer in another document every time.

### This is a regression of scope, not a new bug

The same shape was reported nine months earlier in the **FlowSteward REQ-081 postmortem**
(`docs/reports/2026-07-05-flowsteward-req081-concept-phase-scope-and-worktree-sweep-postmortem.md`):

> Producing that deliverable is inherently a **multi-commit, multi-deploy** effort — build
> tooling → commit → push → deploy to the prod box → run the reader *inside the container* →
> capture → iterate … But the `/advance` skill frames the session as "do exactly one checkpoint
> and stop; leave the tree dirty" … **That frame is wrong for this shape of work, there is no
> mid-phase commit/push verb** …

and it cost real work: while the session held its output uncommitted, a concurrent
`steward validate` swept those files into a commit labelled for a **different REQ**
(`ce1c9ef` "REQ-090:validate") — same-commit discipline silently violated, the ledger drifted.
So refusing to commit mid-phase is not the safe default it looks like; long-lived uncommitted
work is itself a hazard.

[[REQ-071]] then codified the fix — but bound the grant to `concept: true`. That was the narrowest
reading of the evidence available at the time (the FlowSteward case *happened* to be a concept
phase), and it is why the next legitimate case — deploy-shaped develop work that is not a
concept phase — fails identically. **Enumerating exceptions guarantees the next unlisted-but-
legitimate case fails.**

### What does not exist (investigated, 2026-08-06)

There is **no instruction anywhere to run `steward checkpoint` mid-development**, and **no
mid-phase commit or push verb** at all. What exists is:

- permission to make plain **git** commits mid-phase, fenced to `concept: true`
  (`/advance` §4; `STEWARD.md`'s "One exception: an *empirical* `concept: true` phase may commit
  mid-phase"); and
- the clause that the **terminal** `steward checkpoint` is "sanctioned over an already-clean
  tree" and "records the step over an effectively no-op commit" ([[REQ-071]] Context, observed
  live 2026-07-05).

That second clause is the load-bearing one — it is what makes committing before the close work
at all — but it describes the *terminal* act tolerating prior commits, not a mid-development
checkpoint. The absence of any named verb is part of why the rule reads as a prohibition: a
session looking for the sanctioned way to commit mid-phase finds nothing, and concludes there
isn't one.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | The permission is keyed on **attended** (`DEVSTEWARD_UNATTENDED` unset), not on `concept: true`. Batch never commits. | A human is present, owns the consequences, and can repair in place. Batch genuinely must not commit — the engine is the committer there and a headless commit would double-commit — so *attended* is the axis that actually carries the distinction the old rule was groping for. |
| 2 | The skill names the legitimate **trigger**: work that cannot be proven without a round-trip through external infrastructure (CI building an image, a remote host, a deploy target). | Keeps the grant honest without inviting casual mid-develop commits. "Attended, full stop" would demote "checkpoint is the terminal act" from a rule to a convention. |
| 3 | State it as a **principle**, not a longer list of exceptions: *the one-checkpoint frame bounds the bookkeeping, not the round-trips.* | The enumerated-exception framing is the actual defect; adding "…and deploy" as a second entry would just move the failure to the third unlisted case. The clause already exists in `/advance` §2 — it is fenced to concept phases and needs to be the general rule. |
| 4 | Mid-phase commits are **plain git commits made by the session**. `steward checkpoint` stays **terminal-only**; no new verb, no `steward save`. | The engine already tolerates this (REQ-071 Context; the terminal checkpoint records a no-op commit over a clean tree). Adding a verb would be machinery for a prose defect — the REQ-039 lesson. Naming the mechanism explicitly is what stops the next reader concluding no sanctioned path exists. |
| 5 | Doctrine only: `/advance`, `/intake`, `STEWARD.md`, handbook `_00-method.qmd`. **No engine change**, no new `process:` field, no lint rule. | Nothing in the engine forbids a mid-develop commit today — the prohibition is entirely prose, and the session that refused was obeying prose. A `process:` declaration would re-create the enumerate-the-exceptions trap one level up, in schema. |
| 6 | Both halves are fixed together: the commit rule **and** the deploy-proof routing. | They are two faces of one defect. Fixing only the commit rule leaves `/advance` silent on where a deploy proof belongs, and the fixless-validator default stands. |
| 7 | All four surfaces are edited, and the test asserts the **stale absolute wording is gone**, not merely that new wording was added. | REQ-071's AC1 exists because leaving one surface unwired *was* the failure mode. And an additive-only test would pass while the contradicting sentence still sits in the file a develop session actually reads. |
| 8 | Accepted consequence: when a session commits mid-phase, the authoritative `steward checkpoint` commit may carry **only the `done` flip**. | Not new — REQ-063's capture-gap path and the develop-then-validate `develop_committed` path both already commit pure code ahead of the flip. Same-commit discipline's teeth are "never flip status without the code", not "code must never precede the flip". |

## Requirement

The doctrine states one coherent rule across all four surfaces: **an attended develop session
may commit, push and deploy mid-phase when the work requires a round-trip through external
infrastructure; a batch session never commits; `steward checkpoint` remains the terminal
bookkeeping act.**

### `/advance` (`devsteward/templates/.claude/skills/advance/SKILL.md`)

1. §4's interactive close no longer says "the one sanctioned exception … `concept: true`". It
   states the attended grant with its trigger (Decisions 1–2), names the mechanism as plain git
   commits (Decision 4), and keeps `steward checkpoint` as the terminal act that closes the step
   whether or not the tree is already clean.
2. §2's iterate-until-frozen clause is **generalized off** `concept: true`: the one-checkpoint
   frame bounds the bookkeeping, not the round-trips (Decision 3). The concept phase remains one
   instance of the pattern, not its licence.
3. The batch prohibition is untouched and stays absolute — *(batch)* never commits, never
   branches.
4. §2 tells a session whose proof needs a deploy that the proof belongs **in this session**,
   fixable in place — not deferred to the System-Test phase.

### `/intake` (`devsteward/templates/.claude/skills/intake/SKILL.md`)

5. The live-proof-in-develop screen names the **deploy-shaped** case explicitly: a criterion whose
   proof requires the code to be pushed and deployed before it can be observed is a
   develop-session obligation, not an `artifact`/`manual` deferral — and the REQ says so in its
   Requirement plus a Decision.
6. The existing "grant, not a restriction" disclaimer stays and now agrees with `/advance` rather
   than compensating for it.

### `STEWARD.md` and the handbook (`devsteward/handbook/_00-method.qmd`)

7. `STEWARD.md`'s "(One exception: an *empirical* `concept: true` phase may commit mid-phase…)"
   is replaced by the attended rule, and its concept-phase section stops presenting
   iterate-until-frozen as a concept-phase privilege.
8. Handbook rule 4 is restated on the attended axis, with the concept phase as an example rather
   than the boundary.

## Notes

- **Lineage.** REQ-064 (intake screens env-bound `regression` ACs) → REQ-068 (the `check:` lanes)
  → REQ-071 (concept-phase & wiring-gap doctrine) → this. Each codified a downstream lesson into
  the doctrine surfaces. This one corrects REQ-071's scope: right rule, wrong axis.
- **The skills are hardlinked** (`.claude/skills/<name>/SKILL.md` and the stamped template are one
  inode) and `STEWARD.md` at the repo root is a **symlink** to `devsteward/templates/STEWARD.md`.
  Edit once; the acceptance test reads the template paths deliberately, since those are what
  `steward new` / `steward sync` stamp into consumers.
- **Considered and rejected:** a `steward save` / mid-phase commit verb (Decision 4 — machinery
  for a prose defect); a `process.deploys: true` frontmatter declaration (Decision 5 — moves the
  enumerate-the-exceptions trap into schema); an engine guard refusing headless mid-step commits
  (the batch lane cannot reach that path — the engine is the committer there).
- **Out of scope:** the `check:` taxonomy itself; REQ-030's System-Test phase design (the fixless
  validator is correct *as a validator* — the defect is routing deploy proofs to it); any engine,
  schema or lint change; consumer-side adoption (a consumer picks this up via `steward sync`).
- **Not a licence to skip the gate.** The grant covers committing and pushing during develop. It
  does **not** loosen: the session still never writes `status:` or edits the index row, the
  engine still owns the flip, and `steward checkpoint` still re-runs the acceptance tests through
  the land-grade gate and refuses to land on red.
- **Residual risk.** Pushing mid-develop puts un-checkpointed work on the remote `dev`. If the
  session is abandoned, the remote carries code the ledger does not know landed; recovery is
  `steward repeat`, which reads the tree as it finds it. Acceptable — `dev` is the integration
  branch and consumers pin release tags cut on `main`, and this exposure already exists via the
  concept-phase grant.
