## Context

`steward run REQ-040` was issued on FlowSteward while both cswap accounts were saturated.
`run_step` set `REQ-040:develop → RUNNING`, wrote a `step_started` event, then **blocked
inside the runner** waiting out the quota window. The operator `Ctrl-C`'d. The next
`steward run REQ-040` failed with *"REQ-040 has no eligible step — it is blocked on an
unfinished dependency."* — a **provably false** diagnosis: all five of REQ-040's
dependencies are `done`. The REQ was wedged with no CLI verb to recover it; the only fix
was hand-editing `.devsteward/state.yaml`. (Full writeup:
`docs/reports/2026-06-20-stranded-running-step-misdiagnosed-as-dependency-block.md`.)

Two independent defects compound — this is the runtime stalemate this REQ closes:

- **The interrupt window leaves the step `RUNNING` with no terminal event.**
  `run_step` (`executor.py:267-304`) only compensates the `RUNNING` status back to
  `PENDING`/`RECOVER` on two paths: an up-front `precheck()` failure (`:280`) or a clean
  `USAGE_LIMIT` return (`:301`). When saturation manifests as the runner *blocking* (the
  quota-wait, REQ-025) rather than returning, a `SIGINT` during that block kills the
  process between the `step_started` event (`:272`) and any terminal event. The `RUNNING`
  status set at `:270` is already persisted; the compensating requeue never runs. Nothing
  later reconciles it — there is **no stale-`RUNNING` sweep** anywhere — so the
  inconsistency is permanent until hand-fixed. (A second step, `REQ-019:develop`, was
  stranded the same way the same morning — not a one-off.)

- **`only_ineligibility_reason` fabricates a dependency cause.** `eligible_steps` treats
  only `PENDING`/`RECOVER` as runnable (`executor.py:199,213`), so a `RUNNING` step is
  silently skipped. When `--only REQ-040` then selects nothing,
  `only_ineligibility_reason` (`:226-240`) ends in an **unconditional else** that returns
  *"blocked on an unfinished dependency"* without ever checking whether a dependency is in
  fact not `done`. Any non-runnable, non-`DONE` status (`RUNNING` here; also a `BLOCKED`
  parked step) falls through to a confident, false cause that points debugging at the
  wrong layer.

This is the REQ-053 lineage — *every state must have an available, clearly-named forward
path*. A stranded `RUNNING` step had none. The owner chose the subtractive fix over a new
recovery verb (the report's suggestion #3): the engine **reconciles its own ledger** at
the start of every run/advance, so the wedge self-heals and the sanctioned recovery is
simply re-running `steward run` — no widened `repeat`, no new verb. The diagnosis path is
fixed to branch on the *actual* statuses so it can never again invent a dependency cause.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | **Startup sweep, self-healing — not a finally/SIGINT guard, not a new verb.** At the start of `run`/`advance` (after `check_invariants`, before step selection), reconcile every step the ledger holds in `RUNNING`: requeue it (`PENDING`, or `RECOVER` if its prior attempt was recovering) and append an `interrupted` event. | A startup sweep catches **every** death mode — `SIGINT`, `SIGKILL`, crash, power loss — that a `finally`/`SIGINT` guard inside `run_step` cannot. The engine is single-process and synchronous over one ledger (trunk-based, single-writer), so a `RUNNING` status observed at the start of a fresh top-level command provably has no live owner: it is stranded by construction. This makes the wedge self-healing — re-run `steward run` and it proceeds — so no recovery verb is needed (subtraction over the report's suggestion #3). |
| 2 | **The requeue preserves the recovery signal.** A step stranded out of `RECOVER` (a `steward repeat` re-arm that was interrupted) requeues to `RECOVER`, not `PENDING`, so the `--repeat` resume brief survives the interrupt. | Mirrors the existing line-280/301 compensation (`requeue = RECOVER if recovering else PENDING`); the sweep is that same compensation applied at load instead of inline, so it must not silently downgrade a recovering step to a clean restart and throw away the partial work. |
| 3 | **`only_ineligibility_reason` branches on the actual statuses; it never fabricates a dependency cause.** When `--only REQ` selects nothing it names the real obstruction: a stranded `RUNNING` step explicitly (and, post-sweep, this case no longer arises), a `BLOCKED` parked step as parked, and *"blocked on an unfinished dependency"* **only** after confirming a `depends_on` entry is in fact not `DONE` — naming the offending dependency. | The unconditional else actively misled the operator to debug a non-existent dependency problem. Diagnosis must be computed from state, not assumed. Defense in depth: the sweep removes the `RUNNING` strand, but other non-runnable states (`BLOCKED`) reach this code, and a correct, specific message is the whole point. |
| 4 | **No new machinery beyond the sweep + the message fix.** `repeat`/`rework`/`revalidate` are untouched; `park_decision`/`answer_decision` are untouched; no `state.yaml` schema change. | Prefer subtraction. The stranded-`RUNNING` class is fully covered by self-reconciliation; adding a verb or a schema field would be machinery layered on a state the sweep already heals. |

## Requirement

An interrupted run leaves no permanently inconsistent ledger, and a `--only` miss never
states a false cause.

- **Self-healing sweep.** Starting `steward run` (or `steward advance`) first reconciles
  every step the ledger holds in `RUNNING`: it sets the step back to `PENDING` (or
  `RECOVER` when the interrupted attempt was itself a recovery), appends an `interrupted`
  event naming the step, and only then selects the next eligible step — so a step stranded
  `RUNNING` by a prior `SIGINT`/crash becomes eligible again and the run proceeds with no
  hand-editing of `state.yaml`.
- **Recovery signal preserved.** A step stranded out of `RECOVER` requeues to `RECOVER`,
  so the next driven run still issues its develop command with the `--repeat` resume
  signal.
- **Honest ineligibility diagnosis.** When `steward run REQ`/`advance REQ` (or `--only`)
  selects nothing, the reason names the real obstruction — and *"blocked on an unfinished
  dependency"* is returned **only** when a `depends_on` entry is genuinely not `DONE`,
  naming that dependency. A step that is merely non-runnable for another reason (e.g.
  `BLOCKED`) is never reported as a dependency block.
- **No new verb.** The sanctioned recovery for an interrupted run is re-running
  `steward run`; `repeat`/`rework`/`revalidate` and the decision surface are unchanged.

## Notes

- **Reframes the report's suggestion #3.** The report
  (`docs/reports/2026-06-20-stranded-running-step-misdiagnosed-as-dependency-block.md`)
  offered (1) a sweep *or* a `finally` guard, (2) the diagnosis fix, and (3) giving
  `repeat`/a new verb authority over a stranded `RUNNING`. The owner took the sweep as the
  *authoritative* reconciliation (it dominates the `finally` guard — it catches `SIGKILL`,
  crash, and power loss the guard cannot) and **dropped #3**: a self-healing sweep makes a
  recovery verb redundant. A `finally`/`SIGINT` guard is explicitly **not** added — it
  would be a second, weaker reconciliation path for a state the sweep already owns.
- **The sweep mirrors existing compensation, not new transaction machinery.** It is the
  line-280/301 requeue (`set_status` + `save` + `append_event`) applied at load; it adds no
  commit/merge and no `state.yaml` schema change. The pre-step `check_invariants`
  (REQ-049) still runs first.
- **Out of scope: the quota-wait interruptibility itself.** That a saturated cswap blocks
  *inside* the runner (rather than returning `USAGE_LIMIT`) is REQ-025's surface; this REQ
  makes the *consequence* recoverable, it does not change how the quota wait is
  interrupted. A separate REQ owns making the wait return cleanly if that proves worth it.
- **Sibling, not parent, of REQ-060.** The all-done stale-cursor confusion (the clauder
  trace) is an unrelated terminal-state display defect handled by [[REQ-060]]; this REQ is
  the *runtime* stalemate (a stranded mid-flight step). They share only the theme that the
  engine must present an honest state with a forward path.
- **Process declarations:** defaults — fused develop, no concept phase, no lab. All ACs are
  `regression` (module-scope, coupled oracle over the engine's own executor/ledger), so
  there is no System-Test phase; the `process:` block is omitted.
- **Localization:** all messages are operator-facing CLI/technical English; no localized
  UI strings.
