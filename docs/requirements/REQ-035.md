## Context

Re-validating a `done` REQ is a sanctioned path: REQ-030 Decision 5 lets `steward validate
REQ-NNN` re-run a done REQ's validation on demand and **append** a fresh evidence event
"without touching status" — the CLI even prints *"fresh evidence recorded for REQ-NNN
(status untouched)."* The 2026-06-12 postmortem (Finding 3,
`docs/reports/2026-06-12-req013-deferred-validate-and-human-oracle-postmortem.md`) caught
that this non-mutating promise is half-true: the re-run silently **overwrites the REQ's
`verified_by`** with whatever the casual re-check happened to say, destroying the original
landing provenance. On REQ-033 a substantive note ("AC4's live case … was actually carried
out") was downgraded to a hollow line ("was already validated, nothing changed") by a no-op
poke.

The mechanism is small and localized:

- `reqfile.py` `set_frontmatter_verified_by` does an unconditional in-place rewrite
  (`subn(…, count=1)`) — it has no leave/append mode.
- `validate.py` `_validate` calls `_write_verified_by` in the green branch **before** the
  `if not in_flight: return` early-out, so the done re-validation path (`revalidate`,
  `in_flight=False`) hits the writer on its way through.
- `cli.py` prints *"(status untouched)"* — the *cursor* is untouched, but the REQ file's
  provenance line is rewritten in place.

The contradiction: REQ-030 D5 advertises a done re-validation as a safe, non-mutating check,
but the mechanism rewrites the one field that records *why* the REQ is trusted. This is a
focused defect fix that clarifies D5 (does not weaken it): the events.jsonl event D5 already
appends *is* the durable, dated re-validation record, so the provenance field need not grow —
it should stay the frozen landing provenance ("done is never weakened" — REQ-001).

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | **On a done re-validation (`revalidate`, `in_flight=False`), `verified_by` is not rewritten — it stays the frozen landing provenance.** The fresh re-check is the appended evidence event in `events.jsonl` (REQ-030 D3). | "Done is never weakened" (REQ-001); the event log is already the dated re-validation record, so the provenance field needn't grow. Leave-untouched honors D5's non-mutating promise in full. |
| 2 | **The in-flight paths are unchanged:** the first validation of an in-flight REQ (and a rework re-validation) still composes and writes `verified_by` — that is the landing provenance being *established*, not a re-check. The guard is scoped strictly to the done re-validation path. | Do not over-correct: `verified_by` must be written when the REQ actually lands; only the done re-run is destructive. |
| 3 | **The CLI message is honest:** a done re-validation reports that it recorded fresh evidence and changed nothing else — status *and* `verified_by` unchanged. | Postmortem rec 3: the operator must know the durable fields are frozen, and (with Decision 1) they genuinely are. |
| 4 | **This clarifies REQ-030 D5 (does not weaken it):** D5's "status untouched" extends to "the REQ file is untouched — status and `verified_by` both frozen on a done re-validation." | The REQ-033 precedent of clarifying a done REQ's decision via a new REQ; the provenance convention survives, only the clobber is removed. |

## Requirement

- Re-validating a `done` REQ (`steward validate` on a done REQ → `revalidate`) records a
  fresh dated evidence event (REQ-030 D3) and **leaves the REQ file untouched**:
  `verified_by` and `status` are both unchanged (Decisions 1, 4).
- The first validation of an in-flight REQ — and a rework re-validation — still composes and
  writes `verified_by` as the landing provenance; the fix is scoped to the done re-validation
  path only (Decision 2).
- The CLI accurately reports that nothing but the evidence record changed (Decision 3).

## Notes

- **Why leave-untouched over append:** the `events.jsonl` validation event is the durable,
  dated re-validation record (REQ-030 D3), so growing `verified_by` on every casual re-check
  only bloats the provenance line and risks a hollow note overwriting a substantive one.
  Leave-untouched makes the postmortem's rec 2 (reject empty/"nothing changed" overwrites)
  moot for the done case — nothing is overwritten.
- **All criteria are honest `regression`:** the oracle is real REQ-file + `events.jsonl`
  state in a fixture (the existing validate-test pattern), decoupled from any external system.
  No lab, no `manual`, no System-Test phase — a focused fix.
- **Out of scope:** committing the re-validation's event/evidence on the done path (the
  `revalidate` CLI path leaving `events.jsonl`/evidence uncommitted is REQ-032/REQ-034's
  clean-tree invariant, not this REQ); what an *in-flight* validation writes (unchanged); a
  **red** on a done re-validation (REQ-030 D5 / REQ-033 D3 — supersede, not rework).
- **Process declarations:** defaults — fused develop, no concept phase, no lab.
- **Localization:** engine/CLI text is technical English; no user-facing localized strings.
- **Surfaces (expected):** `devsteward/profiles/req/validate.py` (`_validate`/`revalidate` —
  skip `_write_verified_by` when `in_flight=False`), `devsteward/cli.py` (the done
  re-validation message), and a regression test (`tests/test_revalidate_provenance.py`).
