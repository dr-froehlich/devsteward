## Context

REQ-011 and REQ-019 drew the branching map but left the human to walk it. REQ-011 made the
engine *refuse* to commit on production; REQ-019 added the symmetric refusal for `build`/`land`
on the integration branch, encoding the rule "declaration on `dev`, only implementation
branches." Both were deliberately **guard-only** — REQ-011 Decision 1 and REQ-019's *Out of
scope* both state plainly: *"the engine guards, it does not manage git topology."*

That left a real, recurring gap. After REQ-019, the standard cycle — `intake → design`
(on `dev`) `→ build → land` (on a feature branch) `→ merge to dev` — has **two manual,
error-prone git steps bracketing every REQ**: create the feature branch before `build`, and
merge it back after `land`. This is not an exception path; it is *every* REQ. It was just
hit live on REQ-010: the engine landed and committed, then stopped, leaving the human to
(a) commit a trailing ledger write the engine made *after* its land commit, and (b) perform
the merge by hand — a dance with enough sharp edges (amend-vs-follow-up because the
`checkpoint` event records the land commit hash; `--ff-only` erroring when `dev` moved;
the temptation to `git stash` the ledger, which would carry it back off `dev`) that it
warranted a whole interactive session to get right. A manual step repeated on every REQ,
with that many ways to get it subtly wrong, belongs in the engine.

The wish is to automate the create→merge dance again — but **correctly** this time. The
over-eager auto-branching that REQ-019 stopped branched on *declaration* (a feature branch
spun up merely to write a REQ). The new automation is safe precisely where the old one was
not: it is gated strictly on `step.phase ∈ {build, land}` and never on declaration/intake.
REQ-019 disciplined *what* may branch; this REQ automates the branching of exactly that
disciplined set.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | **Deliberately reverse REQ-011 D1 / REQ-019 Out-of-scope**: the executor now *manages* feature-branch topology for implementation steps, not merely guards it | The guard-only stance solved the *declaration* problem (don't branch to write a REQ) but left the *implementation* dance manual on every REQ. Managing topology is acceptable now because REQ-019 already fixed which steps may branch; automation is safe where it is gated on `phase ∈ {build, land}`, never on declaration — the exact difference that made the old auto-branching harmful |
| 2 | **Replace the REQ-019 integration-branch refusal** for `build`/`land` with management — no opt-out flag | REQ-011 Decision 4's lesson: a disable switch is the first thing a tired run reaches for. The refusal was a placeholder for "the human must branch"; now the engine branches, so the refusal is obsolete for those steps. The **production-branch guard (REQ-011) is untouched** — the engine still never commits to `main` |
| 3 | **Lazy creation on the first eligible `build`/`land` on the integration branch** | Mirrors the existing per-step guard seam (`step_branch_guard`) exactly — same hook point, opposite action (create+switch instead of refuse). A `design` step still runs on the integration branch (declaration; plans may live on `dev`). No eager creation: the branch appears exactly when behavior first changes |
| 4 | **Auto-merge only on a green `land`; `--no-ff` with the co-author trailer** | A merge commit records an auditable REQ boundary, succeeds even if `dev` advanced (where `--ff-only` would hard-error and force a fallback path), and gives a natural home for the trailer the engine already writes everywhere. CLAUDE.md's "plain local merge" means *no PR*, not *fast-forward* — `--no-ff` is compatible |
| 5 | **No merge on a failed or parked `land`** — the branch stays checked out and unmerged for inspection | Merging an unverified or parked-decision state would defeat the verification gate (REQ-006/015) and bury a fork. The branch is left exactly where a human (or a resumed run) can inspect and continue |
| 6 | **The merge reconciles the trailing ledger** so `dev` is clean at rest (REQ-019 Decision 4) | The engine writes the final cursor state (`status: done` + the `checkpoint` event) into the working tree *after* its land commit. Auto-merge must commit that trailing write so the "ledger current on `dev` at rest" invariant holds without a human. This is the minimal in-REQ reconcile; it does **not** depend on `steward checkpoint` ([[REQ-018]]) |
| 7 | **Idempotent resume**: reuse an existing feature branch rather than erroring; surface a *diverged* branch instead of silently merging | A partial prior run (interrupted before merge) must resume, not crash. But a branch that has diverged from what the engine expects is a real conflict — surface it, do not auto-merge over it |
| 8 | **Branch names derive from the REQ id + slug**, config-driven, extending REQ-011's `git` section | One legible convention (`req-<nnn>-<slug>`, e.g. `req-010-memzy-converter` as already used), overridable in `.devsteward/config.yaml` so consumer repos can adjust. No new config file |

## Requirement

The executor manages the implementation feature branch for a REQ end-to-end: it creates and
switches to the branch when implementation first begins on the integration branch, and merges
it back after a verified land — replacing the REQ-019 refusal with management, while the
REQ-011 production guard and the `dev → main` PR rule stay untouched.

### Behavior

1. **Lazy create+switch.** When a `build` or `land` step is eligible and HEAD is the
   configured integration branch, the executor creates a feature branch named from the REQ
   (config-driven, default `req-<nnn>-<slug>`), switches to it, and proceeds with the step —
   instead of refusing (REQ-019). A `design` step on the integration branch still proceeds
   there with no branch created.
2. **Auto-merge on green land.** After a `land` step verifies green and commits, the executor
   commits any trailing ledger write, switches to the integration branch, and merges the
   feature branch with `--no-ff` and the co-author trailer. The integration branch's working
   tree and ledger are clean at rest.
3. **No merge on failure/park.** If `land` fails verification or parks a decision
   (`DEVSTEWARD_UNATTENDED=1`), no merge occurs; the feature branch stays checked out for
   inspection.
4. **Resume.** If the feature branch already exists, the executor reuses it; a diverged branch
   is surfaced, not silently merged.
5. **Guards preserved.** The production-branch refusal (REQ-011) is unchanged; no PR automation
   is introduced (`dev → main` stays a PR, REQ-019).

## Notes

- **Relationship to [[REQ-018]] (`steward checkpoint`).** Both touch ledger reconciliation at
  the feature↔`dev` seam. REQ-020 does the *minimal* reconcile needed to merge cleanly
  (commit the trailing cursor write) and deliberately does **not** depend on REQ-018; if
  `steward checkpoint` later lands, the merge step can delegate to it, but REQ-020 must not
  block on it.
- **Why this is not the over-eager branching REQ-019 stopped.** The harmful behavior branched
  on *declaration*. This branches only on `phase ∈ {build, land}`. The discipline REQ-019
  established (which steps may branch) is the precondition that makes the automation safe.
- **Out of scope.** PR automation of any kind (`dev → main` stays a human PR, REQ-019);
  concurrent implementation of two REQs against one ledger (single cursor, REQ-019 D4); any
  remote/push operations; auto-deletion of the merged feature branch (a later refinement may
  add it behind config).
- Seam: `Executor.step_branch_guard` (executor.py:139) is the existing hook the create+switch
  replaces; the auto-merge attaches to the land-step completion path.
