## Context

A consumer project — **memzy** — now wants to come under the `steward` engine, and that
forces the question REQ-010 was parked for: how does an *existing* project's requirement
corpus cross into DevSteward's machine-readable format without a hand rewrite of every
file?

When this REQ was first drafted it assumed the legacy projects held REQs in a **prose**
format (`### REQ-NNN:` headers with `- **Status:**` lines). Reality check against memzy's
repo: that is **no longer true**. All 20 of memzy's REQs already carry YAML frontmatter —
memzy crossed the frontmatter threshold on its own. So the work here is **not** a prose
parser; it is a **dialect normalizer**. memzy's frontmatter is *close to* DevSteward's
schema but diverges in named, enumerable ways (`steward lint` is the oracle):

| Gap | memzy today | DevSteward schema / linter wants | Converter must |
|-----|-------------|----------------------------------|----------------|
| `kind` | absent on all 20 | **required** field (enum) | infer & inject |
| Acceptance | `## Acceptance criteria` prose `- [x]`/`- [ ]` checkboxes; any test name is embedded inline in backticks, often absent (manual / guided e2e verification) | a single ```` ```yaml acceptance ```` block, each entry `id` + `text` + `test` + `status` | transcode the checkboxes, preserving each verdict |
| `supersedes` | `[]` (list); one file carries an unknown `superseded_by:` | a single `REQ-NNN` string or `null` | normalize; drop the unknown key |
| Index rows | lowercase + annotations (`superseded *(by REQ-020)*`) that the linter's row regex won't match | rows matched by `_INDEX_ROW_RE`, status in sync with the REQ | rewrite the rows |
| status values | `draft`/`open`/`in-progress`/`done`/`superseded` | same enum | no change |

The governing principle — settled during intake — is that **the converter is an
archivist, not a judge of historic governance.** memzy was verified by its own process
(pytest, manual, guided end-to-end testing); its `[x]` means *met*. The converter records
*met* and does not retroactively demand DevSteward-shaped proof. This is the same boundary
the engine already respects in the other direction (REQ-015: it will not *land* a fresh
REQ on a marker — but migrating a finished record is not landing).

This REQ targets **memzy only**. The legacy-**prose** converter (for ExamEngineer, once
its "upscale" evolution concludes) is preserved as a separate backlog draft, [[REQ-017]],
which builds on this converter's core.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Normalize the observed **frontmatter dialect**, not a prose format | memzy has no prose-header REQs left; design against the real input. Prose stays REQ-017's job |
| 2 | The converter is **faithful, never a judge**: `[x]` → `passed`, `[ ]` → `pending`, criterion text verbatim | A format migration preserves the source's verdict; it does not re-adjudicate another project's governance. Re-verification, if ever wanted, is a separate opt-in act (reopen the REQ) |
| 3 | A runnable `test:` is **best-effort, not required on import** | memzy verified much of its work manually / guided-e2e — many criteria have no test id and never did. Copy an embedded `test_*` when present (handy for future re-runs); leave it empty otherwise. The verdict does not depend on it |
| 4 | Relax `steward lint` so a test id is required only on **active** REQs (`open`/`in-progress`/`blocked`), exempting **terminal** ones as drafts already are | The test-id rule exists so the verification gate has something to run *before landing*. A record imported as already-complete has nothing to land, so the rule is meaningless for it. Reopen an imported REQ and lint asks for a test again — exactly when one is needed |
| 5 | Provenance lives in REQ-level `verified_by`, not a new per-criterion field | memzy's `verified_by` ("pytest", a manual date) already carries *how it was proven*. A first-class per-criterion `verified:` method field is richer but touches schema/parser/verifier/template — deferred, not in scope here |
| 6 | Ship as a **standalone script** with importable functions; tested against captured memzy **fixtures** | Matches the "a converter per project" model; running it on memzy's live repo is a separate act the operator triggers, not part of landing this REQ. Fixtures keep the test hermetic |
| 7 | **Idempotent and non-destructive** — prose (Context/Decisions/Requirement/Notes) is byte-preserved; a second run is a no-op | A migration must be safe to re-run and must not silently rewrite a maintainer's reasoning |

## Requirement

A standalone converter that reads memzy's frontmatter-dialect requirement corpus and emits
DevSteward-schema-valid REQ files plus a synchronized index, **preserving every verdict and
all prose**, and a one-line relaxation of `steward lint` so the result is green.

### Converter (the script)

Importable functions (so the acceptance tests can drive them directly), invoked by a thin
`scripts/convert_reqs.py` entry point that reads a source `docs/requirements/` and writes a
normalized copy:

1. **`kind` injection** — every output REQ gains a schema-valid `kind`, inferred (default
   `feature`; the north star → `spec`; a light tag/title heuristic otherwise). Existing
   frontmatter (`status`, `depends_on`, dates, `tags`, …) is otherwise carried unchanged.
2. **Acceptance transcode** — the `## Acceptance criteria` checkbox list becomes a single
   ```` ```yaml acceptance ```` block parseable by the REQ profile's parser, with
   sequential `AC1…ACn` ids, the checkbox text as `text` **verbatim**, `status: passed` for
   `[x]` and `status: pending` for `[ ]`, and `test:` set to an embedded `test_*` name when
   one is present, empty otherwise.
3. **`supersedes` normalization** — `[]` → `null`; `[REQ-NNN]` → `"REQ-NNN"`; an unknown
   `superseded_by:` key is dropped (its information, if any, is preserved in prose/notes,
   not invented into a schema field).
4. **Index rewrite** — emit `REQUIREMENTS_INDEX.md` rows that `lint._index_rows` matches,
   each row's status in sync with its REQ's frontmatter.
5. **Idempotent & non-destructive** — running the converter on its own output is a no-op;
   the prose sections are byte-for-byte preserved.

### Linter relaxation

`lint.py` rule 5 requires a non-empty `test:` on every acceptance criterion of a non-draft
REQ. Narrow it so it fires only on **active** statuses (`open`/`in-progress`/`blocked`) —
terminal REQs (`done`/`dropped`/`superseded`) are exempt, like `draft` already is. Active
REQs still require an empty-block check and a test id, so the engine never lands one blind.

### Out of scope

- The legacy **prose** format (`### REQ-`/`- **Status:**`) and the ExamEngineer migration
  → [[REQ-017]].
- Converting memzy's **scenarios** (`SCN-*`), `ROADMAP.md`, or any non-REQ doc.
- Mutating memzy's **live** repo — this REQ ships the tool + fixtures; the operator runs it.
- A per-criterion `verified:` method field (Decision 5).

## Notes

- **Why this is the honest design.** Two intake rounds corrected an over-application of
  marker-distrust: the engine refuses to *land* on a marker (REQ-015), but a converter that
  *imports a finished record* is not landing — demanding test ids or re-running history
  would be imposing DevSteward's governance on a project that had its own (and would mean
  checking out historic SHAs to rerun historic suites — infeasible and fruitless). The
  verdict travels; the proof's provenance travels in `verified_by`.
- **The linter relaxation generalizes the model**, it doesn't special-case import: a
  runnable test is required exactly where the engine is on the hook to run it (active
  REQs). Native DevSteward done-REQs already carry their test ids, so they are unaffected.
- **Generalization path:** [[REQ-017]] reuses this converter's core to add a legacy-prose
  front-end for ExamEngineer once its upscale evolution concludes. The "a converter per
  project" shape (Decision 6) is deliberate.
