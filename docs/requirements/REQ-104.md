## Context

**The owner's need, in the owner's words** (backlog item `backlog-commit-ui-changes`). It
quotes a consumer session: *"Uncommitted backlog changes. docs/BACKLOG.md is modified and
.devsteward/backlog.jsonl (the new verdict log holding your two accepts) is untracked. The
ledger is meant to be committed. If they stay dirty, the next checkpoint sweeps them into the
next REQ's commit."* The owner adds: *"The need is to commit backlog changes from the UI in safe
way. Safe means: If the operation is accepted and performed it does not disturb a running
session or cause issues because of the repo's current state."* These are the item's acceptance
criteria, authored at this intake before the design:

- A backlog change I make, in the dashboard or with the CLI, gets a commit of its own instead of
  riding in the commit of whatever REQ is being developed.
- Reverting a REQ's develop or land commit leaves my backlog changes and verdicts in place.
- Committing my backlog changes does not disturb a running session. If it cannot be done, my
  changes stay as they were.
- A session no longer stops to warn me about my uncommitted backlog changes.

**It happened here too.** This item's own row was swept into REQ-098's develop commit
(`4db7478`, `docs/BACKLOG.md` +1). `git revert 4db7478` would delete the need along with
REQ-098's code. At this intake, `git log -S` named `REQ-098:develop` as the row's origin, which
is false.

**Why it happens.** The operator verbs never commit, and that is a recorded choice:

- `activate`: *"Declaration is committed deliberately by the operator/skill, often batched with
  other intake edits; auto-committing would surprise and fragment history"* (REQ-026
  Decision 3).
- The dashboard's writes *"ride the next checkpoint"* (REQ-097 Context), and *"the dashboard
  never runs a mutating git command"* (REQ-097 Decision 8).
- The joint verbs stay consistent with the backlog verbs (REQ-101 Decision 9).

The engine's code commit stages the whole tree *except* `.devsteward/` (REQ-079,
`GitCli._stage_code`). So the backlog file rides the next REQ's code commit, while the verdict
log (`.devsteward/backlog.jsonl`) and the joint log ride the trailing ledger commit.

**What a commit is worth, as discussed with the owner at intake.** The owner's words: *"the core
purpose is being able to revert a change / restore historic elements, therefore committing a
trivial ledger change has no value to me personally."*

- For reverting, what matters is that a commit holds only things one would undo together.
  Smallness doesn't matter.
  - An activation riding *its own* REQ's develop commit belongs there: reverting that develop
    step returns the REQ to draft.
  - A backlog row inside an unrelated REQ's commit does not belong there.
- For restoring, granularity barely matters. Being committed at all is what counts.
- As documentation for a Claude session, a granular commit is worth close to nothing.
  - Sessions orient through `steward status`, the REQ files, `steward backlog-list` (derived
    from the file, `backlog_refs:` and the dated verdict log) and the joint logs. None of them
    read git history.
  - Where history does reach a session (`git log`, `git blame` while diagnosing), a swept row
    misleads it.

**The item's own wording, a commit from the UI, was considered and rejected.**

- It would reverse REQ-097 Decision 8, REQ-026 Decision 3 and REQ-101 Decision 9. Under the
  owner's `error-resolution` criterion ("what the CLI offers is what the UI shows"), the CLI
  would need a commit verb as well.
- It would add a second committer to a repo whose safety rests on one. One session at a time is
  *"doctrine, not something the engine locks or detects"* (REQ-079 Decision 3), and the dashboard
  exists to be used while sessions run.
  - `steward checkpoint` runs its gate, which takes minutes, inside a transaction that records
    `HEAD` at entry. A UI commit in that window moves `HEAD`.
  - A colliding git failure (`index.lock`) then rolls the land back to entry, and today that
    rollback also erases the session's uncommitted work (REQ-105).
- "Safe" would require detecting a running attended session, which the engine cannot do. Only
  headless steps mark themselves `RUNNING`.

The owner's decision: *"one committer only, checkpoint separation."*

**The related activation complaint.** Consumer sessions keep flagging an uncommitted
`steward activate` as about to be swept into the develop checkpoint. The owner: *"to me the mere
activation is not a project change worth committing as it is a mere ledger change and, in my
opinion, should ride with the checkpoint when possible."* That is the recorded design (REQ-026
Decision 3). The complaint comes from the manual:

- STEWARD.md's hard rule warns that a parallel session's edits *"would be swept into the other
  REQ's commit"*.
- Its `activate` row says only *"Leaves the change uncommitted."*
- No text tells a session which uncommitted files are expected.

The owner's decision: *"activation needs only a manual change"*. It is folded in here, because it
is the same manual passage.

**A sentence of the item that became no criterion.** The item's *"We only commit to dev in
DevSteward"* was first drafted as a criterion ("nothing is committed anywhere but dev"). The
owner questioned the global "never". It is false today: `main` receives the release merge and
permitted hotfixes, and INV-2 refuses only the production branch, not every branch other than
`dev` (`devsteward/core/invariants.py:65-74`). With one committer it guards nothing either, so it
was dropped. Decision 6 states the relative version instead.

## Requirement

### The backlog changes get a commit of their own

Whenever the engine is about to commit, through the code commit or the ledger commit, on any
path (an attended `steward checkpoint`, a headless step, a validation land, `repeat`'s land
replay, a ledger close), it first checks the backlog file and the verdict log:

- If either has uncommitted changes, both changed paths are committed first as one commit whose
  message begins with `backlog:`. It contains nothing else.
- The commit that follows (the REQ's develop commit, its land commit, or a ledger commit)
  contains neither path.
- If neither has changes, no `backlog:` commit is made, and the commit sequence is exactly as
  it is today.
- A command that refuses before committing commits nothing, the `backlog:` commit included.
- If a later part of the same command fails, the backlog file and the verdict log hold exactly
  the owner's content afterwards (REQ-105).

After a develop or land commit, `git revert` of that commit leaves the backlog row and its
verdicts in place.

### What does not change

The dashboard runs no mutating git command. The backlog verbs and the joint verbs do not
commit. `activate` does not commit. The joint log keeps riding the ledger commit.

### The manual says which uncommitted files to expect

STEWARD.md states Decision 9 where it warns about sweeping a parallel session's edits, and in
the rows of `activate`, `backlog-add`, `backlog-edit` and the four verdict verbs. The handbook
says the same wherever it describes what a checkpoint commits.

## Notes

**Out of scope, on purpose.**
- A commit verb or a commit button: the item's wording, rejected (Context, Decision 1).
- Committing the joint log separately: it never rides a REQ's code commit, and no item asks for
  it.
- Committing an activation separately: the owner ruled it rides.
- An intake's own commit, which by design carries the item criteria authored in it together with
  its REQ: the `/intake` skill commits by hand, and its commit is the intake's work, not a sweep.
- Detecting a running session: the doctrine stays (REQ-079 Decision 3).

**Develop obligations.**
- STEWARD.md and the handbook change in the same commit as the code (Decision 9, REQ-094).
- Consumers receive the manual at their next `steward sync`. No consumer document repeats the
  changed wording, so no sweep by hand is owed.
- Correct the docstrings of `GitCli._stage_code` and `commit_code`, which say the code commit
  stages the whole dirty tree, so that they name the backlog exception.

**Risks.**
1. **The capture gate (REQ-063)** certifies the tree it builds with `write_code_tree` before the
   commit. The `backlog:` commit must not change what the code commit then lands. The develop
   session checks that the gate's tree and the landed tree still agree, and records how.
2. **REQ-077's leftover guard** runs after the code commit. A backlog path left uncommitted by a
   mis-scoped `backlog:` commit would trip it. AC1 and AC2 assert a clean tree.
3. **A develop REQ that edits the project's own backlog file** has that edit split off
   (Decision 8).
