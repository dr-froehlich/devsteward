## Context

The first live onboarding ([[REQ-062]], memzy, 2026-08-01) worked — memzy is a caught-up steward
project on commit `a00444e` — but the run surfaced three defects in the machinery that were
**deliberately not patched inside the proof** (REQ-062's out-of-scope rule: a surfaced defect
routes back to the machinery REQ, it is not fixed inside the run). They have had no home since.
This REQ is that home.

They are filed together because they are one theme — *the onboarding pipeline works but lies to
its operator at three points* — and because the second onboarding is imminent. Every one of them
will be hit again, by hand, in [[REQ-085]] unless it is fixed first.

**Finding 1 — the gate goes red at a point where red is correct.** `steward lint` was green after
the conversion and **red** after `seed-ledger`, on two memzy REQs:

```
✗ REQ-018: ledger develop step is 'done' but the committed marker lags —
           HEAD frontmatter 'superseded', index row 'ABSENT'
✗ REQ-039: ... HEAD frontmatter 'done', index row 'ABSENT'
```

This is not a corpus defect. [[REQ-077]]'s symmetric HEAD-reading lint compares seeded `done`
steps against the **committed** markers, and HEAD still held the *pre-conversion* index whose
rows carry annotations the row regex rejects (`superseded *(by REQ-020)*`, `done *(2026-07-26)*`)
— precisely the rows the converter had just normalized **in the working tree**. The rule can only
fire after seeding, because before that the ledger has no `done` steps to compare against. It
resolved deterministically on the onboarding commit, with no other change.

The problem is procedural, not diagnostic. `/onboard` instructs: *stop on any red verification
gate — onboarding must never declare success on an unlinted corpus.* Followed literally, a
**correct** onboarding halts here, and the operator's only way forward is to decide, unaided,
that this particular red is benign — exactly the judgement call the gate exists to remove. The
skill's §2 gate and REQ-077's HEAD-marker rule carry an **unstated ordering dependency**: the
converted corpus must be *committed* before a HEAD-comparison means anything.

**Finding 2 — `steward sync` does not seed `_templates/`, but the `/intake` it stamps requires
it.** `/onboard` §3 lists `_templates/` among what the stamp must bring in, and the stamped
`/intake` skill writes new REQs *from* `_templates/req.md` — but `sync` seeds only the skills and
`STEWARD.md` ([[REQ-066]]). A project onboarded by the skill as written therefore receives an
`/intake` that references a file it does not have, and **its very next intake breaks**. memzy's
copy was made by hand during the run; nothing in the machinery would have made it.

**Finding 3 — the converter drops unknown frontmatter keys silently.** memzy's REQ-039 carried
`amends: [REQ-013]`, a relation its author recorded deliberately ("recording it as an amendment
— not silently — is the point"). The converter dropped it without a word, the same code path as
the known-and-intended `superseded_by` drop. Across 31 files exactly two keys were dropped, and
in this instance the fact survived elsewhere (REQ-039's prose and its `depends_on`), so nothing
was actually lost. But [[REQ-010]]'s non-destructive guarantee is asserted for **prose**, not for
frontmatter, and a migration that quietly discards a maintainer's typed relation is a failure
mode that only ever surfaces later, in a repo the engine no longer touches.

## Requirement

Three independent repairs to the onboarding pipeline, each disconfirmable in this repo's suite:

### 1. `/onboard` commits the converted corpus before seeding the ledger

The `onboard` skill's step sequence orders **convert → commit → seed-ledger → gate**, and says
*why*: [[REQ-077]]'s HEAD-marker rule compares seeded `done` steps against **committed** markers,
so a lint run between `seed-ledger` and the conversion commit is comparing against a
pre-conversion HEAD and is meaningless. With the commit first, the §2 gate means what it claims
at every point in the sequence and the operator is never asked to wave a red gate through.

### 2. `steward sync` seeds `_templates/`

`sync` treats `<requirements_dir>/_templates/req.md` as an engine-owned stamped artifact
alongside the skills and `STEWARD.md`: it seeds it when absent, leaves a customized copy alone
(the same refusal semantics as the rest), and reports what it did. A project that has been
`sync`ed can run `/intake` without a hand-copied file.

### 3. The converter reports dropped non-schema frontmatter keys

`scripts/convert_reqs.py` lists, per file, every non-schema frontmatter key it drops, so the
operator can judge whether a deliberate relation is being discarded. The keys are still dropped —
the output schema does not grow — and the report goes to the same operator-facing channel as the
converter's other reports (title conflicts, status demotions).

### Out of scope

- **Preserving** dropped frontmatter keys, or adding schema fields for them (Decision 5).
- Changing [[REQ-077]]'s HEAD-marker lint rule in any way (Decision 2).
- Re-running the memzy onboarding. memzy is already correctly onboarded at `a00444e`; these
  repairs make the *next* one clean and are not retroactive to it.
- The THermo retrofit itself — that is [[REQ-085]], which depends on this.

## Notes

**On AC1's oracle, stated plainly.** AC1 asserts over the *text* of a skill — a coupled oracle,
authored alongside the change, that can confirm only what its author already believed (the
[[REQ-017]] Decision 8 framing). It is worth having because it makes the ordering a thing that
cannot silently regress, and it is the strongest oracle available in this repo: "the operator was
never asked to override a red gate" is an observation about a **live migration**, not a property
of a file. The decoupled proof is [[REQ-085]]'s THermo run, one REQ downstream, where the gate
either stays green through the sequence or it does not. This is the honest split, not a gap.

**All five criteria are `check: regression` and hermetic** — temp projects and captured fixtures,
no service, secret, network or foreign checkout (the §2b environment-bound screen is clean). Per
[[REQ-068]] every command is authored as `python -m pytest …`.

**`process:` is omitted** — every value is the default (`develop: fused`, `concept: false`,
`lab: []`). No concept phase: all three defects were *observed live* with diagnosis and candidate
cures already written down in the REQ-062 report, so there is no risk left to buy down and the
acceptance criteria are writable today.

**Hardlink warning, repeated because it bites here.** `.claude/skills/onboard/SKILL.md` and
`devsteward/templates/.claude/skills/onboard/SKILL.md` are one inode. Edit once. A second
"matching" edit to the other path reverts the first.
