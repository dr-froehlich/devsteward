## Context

REQ-030 built one `validate` step over two oracles. The **engine oracle** (`artifact`
ACs) gets a whole prepared System-Tester session — REQ-030 D2 says "spend the orientation
tax here gladly" — that brings the lab up, drives the procedure, and captures artifacts
before the engine runs the named test. The **human oracle** (`manual` ACs) was modeled by
REQ-030 **D4** as *"present the AC and record the sign-off"*: a bare `y/N`, on the
assumption the runbook would carry the human. The asymmetry is the defect — the human, the
least-context reader in the system, got the *end* of validation (the checkbox) with none of
the *beginning* (preparation, guidance, the ability to ask).

The 2026-06-12 postmortem (`docs/reports/2026-06-12-req013-deferred-validate-and-human-oracle-postmortem.md`)
records this failing four ways, all one consequence of D4's asymmetry:

- **Cryptic / missing instructions, no preparation** (Finding 2). D4 leaned entirely on a
  runbook that is routinely absent, imprecise, or names an operator entrypoint nobody built
  (`runserver`, `provision`, "bring up the page" — REQ-017 AC6, REQ-018 AC4).
- **No session to guide or answer questions.** The diff-free session runs *only for
  `artifact` ACs* and is a one-shot `claude -p` whose output the human merely watches; for a
  pure-`manual` AC no session runs at all. There is no one to ask.
- **Can't run from inside Claude / silent gate** (Finding 4). Run from within a Claude Code
  session, the spawn forks the ambient session and wedges a pty; from a plain shell there is
  no Claude at all. Guidance is structurally impossible: it either wedges or it is a bare
  prompt.
- **Only a `y/N`.** The checkbox is the last step of validation, presented as if it were the
  whole thing.

And the deeper modeling error, named by Peter (2026-06-13): **a real lab/acceptance test
does not stall the project.** Today a pending human validation freezes the REQ on a dangling
feature branch — `steward validate` parking attended never commits its ledger (it bypasses
the REQ-032 `_drive_step` close), leaves HEAD on the feature branch, and a later `steward
run` trips over it (the diverged-branch refusal of Finding 1). The model conflates "waiting
for a human" with "the pipeline is stuck." In a V-model, acceptance testing is asynchronous
QA: other work proceeds, the human runs the test when available, the verdict is integrated
on return.

This REQ reworks the human-validation phase to match: a guided interactive session that pays
the human the same orientation tax the engine oracle already gets, and a **QA-ticket** park
that never freezes the project and is cleanly re-enterable. It **amends REQ-030 D4** (the
REQ-033 precedent — D4 was likewise amended, not weakened): the human remains the sole
oracle and the engine still records, never simulates, the sign-off.

## Requirement

Rework the `manual`-AC half of the System-Test phase (REQ-030) so a human validation is a
guided, asynchronous activity:

- A `manual` AC is validated through an **interactive** session (the System Tester in
  attended mode) that prepares the lab/surfaces and operator entrypoint, walks the human
  through the documented procedure, and answers questions. The **verdict is recorded by the
  engine** from the human's checkbox; the engine-run gate + human verdict mean the session
  can never turn the gate green (Decisions 1–2).
- Validation bookkeeping is a **two-phase script** (start / end-record) and Claude is
  **never spawned from within Claude** (Decision 6): from a **plain shell**, `steward
  validate REQ-NNN` does start → brings up an interactive Claude attached to the terminal
  (the editor pattern) → end; **mid-session**, a running session's skill calls the start and
  end-record halves itself. The bring-up path refuses when run inside a Claude session,
  pointing to a plain terminal.
- A **pending** human validation parks as an async QA-ticket (Decision 3): clean working
  tree, HEAD back on the integration branch, the feature branch intact and unmerged; a
  subsequent `steward run` advances other eligible REQs. The branch is never merged on a
  park (Decision 4).
- `steward validate REQ-NNN` **cleanly resumes** a parked validation at any later time,
  reconciling the feature branch from current `dev` rather than erroring when it is
  behind-but-merged (Decision 5); a green verdict then fires the deferred mechanical land.
- The three terminal outcomes route correctly — green → land, declined → red park pointing
  at `steward rework`, pending → async park — each leaving a clean tree (Decision 7).

## Notes

- **Amends, does not weaken, REQ-030 D4** (the REQ-033 D4 precedent): the human is still the
  sole oracle and the engine records, never simulates, the sign-off — D4's "a human oracle is
  validation" survives; only "present + record" is replaced by "prepare + guide + record."
- **Finding 2 is addressed at runtime, not by lint.** The guided session brings up the
  surface and walks the procedure live, so a cryptic/absent runbook hurts less. The *static*
  safety net the postmortem also recommends — `steward lint` verifying a `manual` AC's
  runbook anchor resolves (rec 4) and that an action it names (`provision`, `freeze`, "bring
  up the page") maps to a real operator command (rec 5) — was considered and **deliberately
  dropped** (2026-06-13): static lint can only prove a string *resolves*, not that the runbook
  is correct or the entrypoint actually works (the green-but-hollow shape REQ-027 keeps lint
  away from), and the guided session catches the real failure against reality. The authoring
  lesson — a `manual` AC must name its **observation surface**, its **operator entrypoint**,
  and an explicit **pass/fail** — moved to the `/intake` skill (§2b), where it belongs, not a
  lint rule.
- **Out of scope:** the manual-AC runbook **lint** discipline (postmortem recs 4/5) —
  **dropped**, subsumed by the guided session (see the Finding-2 note above) with the authoring
  lesson moved to `/intake`; **Finding 3** — re-validating a `done` REQ clobbering
  `verified_by` — is its own focused fix, **REQ-035**; any engine auto-looping on red (REQ-030
  D8 stands — a declined verdict routes to `steward rework`, REQ-033).
- **Verdict authorship (REQ-030 D4 / REQ-018 close-out convention survives):** the human
  supplies only the verdict + an optional one-line scope; the engine composes the dense
  `verified_by` / evidence provenance mechanically.
- **Process declarations:** defaults — fused develop, no concept phase, no lab. This intake
  interview served as the design review; no owned lab is needed — AC6 re-drives FlowSteward's
  existing parked REQ-024 (consumer-repo reality, not a DevSteward lab asset), the REQ-030 AC8
  precedent. **No concept spike is warranted:** Finding 4 is dissolved by design — Claude is
  never spawned from within Claude (Decision 6), so the only new spawn is the standard
  foreground editor pattern from a shell; the reality-boundary risk that would have justified
  a spike is gone.
- **Localization:** engine/skill/handbook text is technical English; no user-facing localized
  strings. The guided session's prompts to the human are technical English.
- **Surfaces (expected):** `devsteward/profiles/req/validate.py` (interactive guided session,
  engine-owned verdict, async park, reconcile-on-resume, terminal-outcome routing),
  `devsteward/core/executor.py` (return-to-integration on park; complete the REQ-032 close at
  the interactive seam), `devsteward/core/claude.py` (foreground interactive spawn — editor
  pattern, TTY inherited, no detach; a `CLAUDECODE` nesting-refusal guard), `devsteward/cli.py`
  (`steward validate` start→bring-up→end flow + the two-phase start / end-record entry points
  the skill calls), the System Tester skill (attended/guided mode; repo `.claude/skills/` + stamped
  `devsteward/templates/.claude/skills/`, kept identical), handbook 02/03 (human validation as
  guided async QA).
