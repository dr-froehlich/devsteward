## Context

Every test in the suite drives the executor through a `FakeRunner` (`tests/conftest.py`)
or a fake `claude` (`tests/test_claude_stream.py`). The harness logic — ledger,
eligibility DAG, park-and-surface, the verify gate, commit/advance — is genuinely well
covered, **but no test has ever driven a real `claude -p` end to end.** The code and its
tests were generated from the same mental model, so they agree with each other and not
necessarily with reality. `tests/test_accounts.py` even *asserts* a `cswap` interface that
does not exist (`cswap exec … --use`), so a green suite measured self-consistency, not
fitness.

The dogfooding trail in `.devsteward/events.jsonl` shows the consequence: the engine has
never once successfully driven a real Claude to produce REQ work — every attempt was an
`error` (the fictional `cswap exec`), a retracted no-op (`/advance` skill unresolvable, so
claude did nothing while the engine committed empty bookkeeping and marked the step DONE
under "marker trust"), or a `usage_limit` stop. Three independent defects live exactly
where the clean code meets an external reality it guessed at:

1. the `cswap` provider speaks a fictional CLI (REQ-012);
2. the headless `claude -p` invocation passes **no permission mode**, so a real session
   cannot Edit/Write/Bash — there is nobody to approve (not yet captured in a REQ);
3. the verify guarantee is real only at `land`-with-tests; `design`/`build` always pass
   via marker-trust, which is how an empty no-op reached DONE.

This REQ builds the missing instrument: a real end-to-end gate. It does **not** fix the
three defects — it makes their absence measurable, so subsequent repair work has a red
test to turn green instead of more mocks that agree with the bug.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | The gate drives the *production* path (`build_executor` → real `claude -p`), not a special mode | A reality check that reuses the mock-free production wiring is the only kind that can't lie |
| 2 | Opt-in via `DEVSTEWARD_REALITY=1`; skip (don't error) when unset or when `claude` is absent | Keeps the default `pytest` run hermetic, fast, and offline; the real run is a deliberate, billable act |
| 3 | The throwaway project is itself asserted lint-clean with exactly one eligible step (a hermetic meta-test) | So a red real-run indicts the engine, never the fixture — the failure mode stays unambiguous |
| 4 | Smallest observable task: produce `greeting.txt` containing `hello`, checked by a plain shell acceptance `test:` | Proves the *chain* (executor → claude → edit → verify → commit), not a task; the verifier re-runs the same check independently |
| 5 | Provider pinned to `single` in the gate's project | The cswap rotation has its own acceptance (REQ-012); pinning isolates this gate's failure to the core loop |
| 6 | The real run is expected RED until REQ-014 (permission mode) and REQ-012 (cswap) land; that red *is* the deliverable's value | The gate's job is to expose the gap and stay as the standing trust check, not to be green on day one |

## Requirement

`tests/test_reality_harness.py` provides an opt-in end-to-end gate plus the hermetic
meta-tests that guard it:

- `reality_skip_reason()` returns a non-`None` reason (naming `DEVSTEWARD_REALITY`) when
  the flag is unset, and a reason naming `claude` when the flag is set but `claude` is not
  on PATH; otherwise `None` (run).
- `scaffold_reality_project()` stamps a real project (bundled skills + one minimal,
  checkable REQ) that `steward lint` passes and that exposes exactly one eligible step.
- `test_real_claude_end_to_end` (gated) drives the production executor over the real
  `claude -p`, then asserts a real file edit, an independently-green acceptance check, the
  land step at `DONE`, and a real commit beyond the initial one.

Henceforth a checkpoint of the engine's own loop is trusted only after the real gate has
been run green at least once — recorded as the project's process rule, not just code.

```yaml acceptance
- id: AC1
  text: With DEVSTEWARD_REALITY unset, the gate skips (reason names the env var), so the default pytest run stays hermetic.
  test: "python -m pytest tests/test_reality_harness.py::test_gate_is_opt_in_by_default"
  status: pending
- id: AC2
  text: With the gate enabled but claude absent from PATH, reality_skip_reason degrades to a skip naming claude (never a hard error).
  test: "python -m pytest tests/test_reality_harness.py::test_gate_skips_without_claude"
  status: pending
- id: AC3
  text: scaffold_reality_project builds a project that lints green and yields exactly one eligible step (REQ-001:design), so a red real-run indicts the engine, not the fixture.
  test: "python -m pytest tests/test_reality_harness.py::test_fixture_project_is_lintable_and_has_one_eligible_step"
  status: pending
```

## Notes

- The real gate itself (`test_real_claude_end_to_end`) is intentionally **not** an
  acceptance criterion: it skips in hermetic runs and is expected red against today's
  engine, so auto-verifying it would enshrine a false signal. It is run by hand
  (`DEVSTEWARD_REALITY=1 python -m pytest tests/test_reality_harness.py -k real -s`).
- Dependents that turn the real gate green: REQ-014 (pass a permission mode to headless
  `claude -p`) and REQ-012 (real cswap CLI). They are out of scope here.
- Full assessment and the repair sequence: `docs/plans/0002-reality-harness-and-engine-repair.md`.
