## Context

REQ-001 promises *"tech-agnostic scaffolding"*. Since 2026-10-04 `CLAUDE.md` also carries the
**Avoid waste** principle. Everything DevSteward puts into a consumer project falls into one of
four Lean quadrants: keep what adds value and is needed; keep what is only needed for
DevSteward's internal workings, at minimal cost to the consumer; make optional what adds value
but is not needed; remove what is neither. The owner drew the line at intake. DevSteward may
depend on pytest *as a dependency of the tool itself*. But when pytest moves into an embedded
C++ project *"only to fulfill a mechanical dependency without actually providing any ongoing
service to the project, then its placement in the project is wrong as it creates a dependency
and thus cost without providing value — the definition of waste."*

Today three things put pytest into every project, whatever its stack.

**1. The stamped starter test.** REQ-087 (Decisions 2–3) ships
`tests/test_project_initialized.py` as REQ-001's acceptance criterion. It checks three things:
REQ-001 and its index row agree, the ledger is initialized, and no `{{PLACEHOLDER}}` is left.
It earns its keep once, at bootstrap. After that it runs in every full suite for the life of the
project, and it ties Python and pytest to the project for good. A survey of `~/projects` on
2026-10-04 found it in 7 consumers. In 4 of them (MobileSteward, churchsteward,
esp-terminal-bridge, silverbullet-companion) it is the *only* pytest file.

**2. The gate's entry check.** `ReqVerifier.verify` resolves a pytest-capable interpreter
*before running anything*. It does this even when every acceptance command and the full suite
are something like `pio run` or `cargo test`. REQ-028 Decision 4 introduced the resolution to
fix FlowSteward's `127 pytest: not found`, a Python project. No recorded rationale extends it
to commands that do not use pytest. The engine's pipx install has no pytest: pytest is the
`dev` extra only. So DriveSteward (2026-08-06) and esp-terminal-bridge (2026-09-11) both failed
`REQ-001:develop` with `no usable test environment: no interpreter can import pytest among:
…/pipx/venvs/devsteward/bin/python`. Both worked around it with
`verify.python: /usr/bin/python3`. esp-terminal-bridge now carries three pieces for one test
file, the starter test: that `verify.python` line, `full_suite: python -m pytest`, and a
`pytest.ini` written at bootstrap.

**3. The full-suite default.** When `verify.full_suite` is unset, the land gate runs
`python -m pytest`. REQ-087 Decision 2 relied on the starter test to keep that default green:
it *"gives every stamped project a non-empty `tests/` directory, fixing the exit-5 defect"*.
`/bootstrap` interviews for the project's test command but writes it only into `CLAUDE.md`
(`{{TEST_COMMAND}}`), never into `verify.full_suite`. Its §2 still says the token is needed
*"so REQ-001's acceptance test actually runs"*, which has been stale since REQ-087 moved
REQ-001's criterion to the starter test.

**Sorting these by the quadrants:**

- The starter test adds no value after bootstrap. It is also not needed: `steward lint` already
  checks REQ frontmatter against the schema, the index ↔ frontmatter pair, the north-star
  compass and the ledger markers. Only the placeholder scan is missing from lint. → remove.
- The entry check is needed only when a command actually runs pytest. → remove it everywhere
  else.
- A full-suite command adds value and is needed, but it must be the project's own command, not
  a Python assumption. → keep, written by the interview.

Pytest in the engine's install would have been allowed, but after Decision 3 nothing in the
engine needs it. So the engine gains no dependency.

## Requirement

**What a stamped project contains.** `steward new` stamps no file whose only purpose is to
satisfy an engine mechanism. In particular it stamps no `tests/` directory and no Python file.
The template REQ-001's acceptance criterion is `steward lint`.

**Lint's placeholder scan.** `steward lint` reports every `{{UPPER_CASE}}` token that survives
in a file the scaffold stamps with placeholders, naming the file and the token, and exits
non-zero. The set of files is derived from the packaged templates and resolved through the
configured document paths. It excludes the bundled skills and never includes the project's own
content.

**The gate's interpreter rule.** The develop gate and the capture check look for a
pytest-capable interpreter only when a command they are about to run uses pytest or starts with
`python`/`python3`. A project whose acceptance commands and full suite use no Python lands
without any Python interpreter able to import pytest.

**Bootstrap.** `/bootstrap` writes the interviewed test command into
`.devsteward/config.yaml` as `verify.full_suite`, or `null` when the project has no suite yet.
Its instructions no longer mention the starter test. The skill and its stamped template share
one inode, so the edit is made once.

**The consumer sweep (develop-session obligation, Decision 5).**

- In each consumer carrying `tests/test_project_initialized.py` (DriveSteward, docsteward,
  heroes-pantheon, MobileSteward, churchsteward, esp-terminal-bridge, silverbullet-companion):
  delete the file.
- Where that file was the only pytest file, set `verify.full_suite` to the project's real test
  command, or `null` when it has none.
- Remove config lines that existed only for the starter test, such as a `verify.python`
  workaround. Judge this per project, and keep anything the project's real tests use.
- Leave the done REQ-001's AC text as history. Lint checks only active REQs, so a dangling
  node-id in a done REQ is legal.
- Commit on each consumer's `dev`, with the attribution trailer, and leave it unpushed. No other
  session may be running in that repo (REQ-079 Decision 3).
- Then run the new `steward lint` in **every** consumer and report the result. Two are known to
  go red because they were never bootstrapped: Wandthermostat and devsteward-test-lab, whose
  REQ-001 still carries its placeholders. Report them to the owner and do not fix them;
  bootstrapping is the owner's interview.

**Manual and config text (Decision 7).** `devsteward/templates/STEWARD.md` and the stamped
`config.yaml.tmpl` comments state the interpreter rule, what `verify.python` now means, and
lint's placeholder check.

## Notes

**Out of scope, deliberately.**
- Sorting the *other* stamped artifacts by the quadrants. The owner set the scope to the pytest
  assumptions only. The scenario stencils (`scenarios/README.md`, `_templates/scn.md`) might be
  quadrant 4 (optional), but how much consumers use them has not been checked, and no backlog
  item has been filed.
- Pytest in the engine's install. It was allowed, but after Decision 3 nothing needs it.
- Bootstrapping Wandthermostat and devsteward-test-lab. The sweep only reports them.
- Running DevSteward on part of a repo (the system-admin `tools/` question). That is a separate
  discussion.

**Risks.**
1. **`steward lint` has become a capture-checked acceptance command.** REQ-063 re-runs it from
   a bare `git archive` extract, so `steward` must be on the gate shell's PATH, and lint must
   pass outside a git repository. Its HEAD-reading guard only runs when a real repo is present,
   but no test has yet run lint as REQ-001's AC end to end. AC2 runs it once.
2. **The adapted REQ-087 tests now run `steward lint` through the gate.** They must stay
   hermetic and must not depend on whichever `steward` the box has on PATH. Develop decides how.
3. **The new scan turns lint red** in any consumer that still has unfilled placeholders. That
   is the intent; the two known cases are reported, not fixed.
4. **A configured `verify.python` that cannot import pytest is no longer an error** when no
   command needs it (Decision 3). This is deliberate: no command was skipped.
