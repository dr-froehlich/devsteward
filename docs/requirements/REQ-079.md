## Context

REQ-076 replaced the engine's proven whole-tree code stage (`git add -A -- ':(exclude).devsteward'`)
with a boundary-delta heuristic: snapshot `dirty_paths()` at the transaction boundary and commit
only `dirty_paths() − baseline`, on the premise that *anything already dirty at the boundary
belongs to someone else* (a concurrent session). That premise is structurally false, and it has
now misfiled three categories of the step's own work:

1. **The engine's own bookkeeping** — the REQ frontmatter flip and the shared
   `REQUIREMENTS_INDEX.md` row are written by *every* land; once the index is baseline-dirty the
   flip is subtracted out and the drift cascades (FlowSteward REQ-098/099, 2026-07-09). REQ-077
   patched exactly this slot with an `include` force-stage.
2. **The step's own previous failed attempt** — the `steward repeat` / RECOVER path. The engine's
   documented recovery contract (`executor.py`, `run_step`) says a `--repeat` session "assesses
   the failed attempt's partial edits *(already in the tree)* instead of starting clean" — the
   RECOVER path *deliberately* builds on boundary-dirty files, while REQ-076 *deliberately*
   refuses to commit boundary-dirty files. Two intentional features, mutually contradictory.
   This destroyed FlowSteward REQ-103 (2026-07-10): three engine invocations (error → repeat →
   repeat), each re-snapshotting the baseline over the previous attempt's work; attempt 3 went
   verify-green against the full working tree (event 978) but commit `6e5a6ab` captured **1 of
   10 files** (302 of 1,597 lines) — the rest, dirtied by attempts 1–2, was classified as a
   concurrent stranger's and left uncommitted. ~9 hours of paid session time; hand-recovered in
   `4de8678`; a fourth run hit a second capture gap from the scoped staged tree (event 981) and
   the step is still `failed`.
3. **The motivating incident itself was out of the model's jurisdiction** — the REQ-081→REQ-090
   sweep happened because *two sessions ran in parallel on one repo*. That is an operator-regime
   violation, not an engine-solvable condition: with commits scoped, a parallel session's files
   are not swept but still collide in the working tree, still race the ledger, and still confound
   verify (which runs against the whole tree — REQ-103's green verified files the commit then
   dropped). Scoping treated one symptom of a forbidden situation and broke the sanctioned one.

Each fix *added* structure onto the same premise (REQ-076 → REQ-077's `include` → a third patch
would be the RECOVER slot). Per the house design principles, a string of additive fixes is the
smell that the premise is wrong: subtract it. The one thing REQ-076's era proved sound is the
guard layer — REQ-063's capture gate caught every hollow commit before a silent false-done
reached the ledger, and REQ-077's clean-tree assertion and symmetric lint are scoping-independent
invariants worth keeping.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | **Remove the boundary-delta scoping entirely** — `_session_commit_scope` / `_commit_baseline`, the `baseline` parameter threading through `commit_code` / `_stage_code` / `write_code_tree` / `_capture_gap` / `_stage_and_write_tree`, and REQ-077's `include` force-stage (dead code once nothing subtracts). Every code commit stages the whole dirty tree, `.devsteward/` excluded — the pre-REQ-076 regime (whole-tree `add -A`, which covers untracked files; note this is *not* literal `commit -a`, which would miss them). | The heuristic's premise is false for the engine's own writes and for the RECOVER path, and its motivating case is an operator error the engine cannot own. Subtraction, not a third patch. |
| 2 | **Keep REQ-077's guards**: the post-land clean-tree assertion (simplified — with whole-tree staging nothing is "allowed dirt"; any tracked/untracked leftover after the code commit fails loudly) and the symmetric HEAD-reading marker↔ledger lint rule. | They are invariant checks, not scoping; under whole-tree staging they become strictly cheaper and would loudly catch any *future* staging defect. REQ-077 is amended, not reverted. |
| 3 | **One-session-at-a-time is doctrine, not machinery** — state in STEWARD.md and the handbook that exactly one engine session (interactive or headless) may run against a repo at a time; parallel sessions are operator error with undefined results. No lock, no worktree, no dirty-tree refusal gate. | The REQ-047 principle: don't solve an information-flow/coordination problem with git topology or new machinery. Decided with the owner at intake. |
| 4 | **Delete the tests that encode the reverted behaviour** — `tests/test_commit_scoping.py` (REQ-076's ACs) and REQ-077's scoped-staging test (AC2); adapt the retained guard tests to the removed seams. Supersede REQ-076; annotate REQ-077's AC2 as superseded by this REQ. | A test asserting subtraction-of-boundary-dirt now asserts the defect (REQ-052 doctrine: no misclassified/obsolete suite members). |
| 5 | FlowSteward REQ-103's consumer-side recovery is **fully out of scope**. | Owner decision at intake; handled in the consumer repo. |

## Requirement

When the engine makes a code commit — headless (`steward advance` / `run`, the deferred and
validate commit paths) or interactive (`steward checkpoint`) — it stages the **entire dirty
tree**: modified tracked files *and* untracked new files, with only `.devsteward/` excluded.
There is no boundary snapshot, no baseline subtraction, and no force-include list; a file
dirtied by a previous failed attempt of the same step (the `steward repeat` path) lands in the
commit exactly like a file the current session authored. The capture-gate mirror serializes the
same whole staged tree the commit lands (REQ-063 unchanged in role, unscoped in input).

The REQ-077 guards remain in force: after a landing commit the working tree is clean (any
leftover fails loudly, never a silent DONE with dirt), and `steward lint`'s marker↔ledger
reconciliation stays symmetric and HEAD-reading.

STEWARD.md and the handbook state the concurrency doctrine: one engine session per repo at a
time; running two in parallel is operator error and its results are undefined.

## Notes

- **Oracle / env (REQ-064):** every AC is `check: regression` — the oracle is git itself over
  temp repos the tests create; no service, secret, or network; nothing environment-bound. No
  `artifact`/`manual` check, so no System-Test phase.
- **What is deliberately kept:** REQ-063/072's capture gate (it caught every incident here —
  the guard layer is the proven part), REQ-073's ledger seq-guard, REQ-077's clean-tree
  assertion and symmetric lint. REQ-077 is *amended* (its Decision 1 `include` mechanism and
  AC2 test are superseded by this REQ), not reverted.
- **Known residual, named not silent (REQ-071):** with whole-tree staging, a genuinely
  concurrent session's dirty files would again be swept into another REQ's commit — accepted,
  because parallel sessions are forbidden by doctrine (Decision 3) and every observed sweep
  traces to that violated regime; the engine does not add machinery for a forbidden state.
  If concurrency is ever *wanted*, that is a new REQ with its own design, not a revival of
  boundary scoping.
- **Out of scope:** FlowSteward REQ-103 recovery (Decision 5); `commit_ledger` and the
  transaction rollback (unchanged, as in REQ-076); any lock/worktree/refusal gate.
- Source evidence: FlowSteward `.devsteward/events.jsonl` events 971–981 (REQ-103), commits
  `6e5a6ab` (1-file scoped commit) and `4de8678` (hand recovery); devsteward
  `executor.py` `run_step` recovery contract vs `_session_commit_scope`. Related:
  `[[trunk-based-pivot-req047]]` (prefer subtraction), REQ-052 (test-suite honesty).
