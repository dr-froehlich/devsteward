## Context

The need came from system-admin as the joint task `sysadmin-open-0201` (its OPEN-0201), and was
filed here under the thread's handle. In its words: *"A joint task wakes no one: a session sees a
new thread entry only when it runs `steward joint-list`. Sessions working in parallel on one
machine therefore reach for Claude Code's own cross-session messages, which leave no trace in
either repository; on 2026-10-12 the requests and answers between system-admin and sarah around
REQ-055 (the broker grant, the live check, a worktree that blocked a checkpoint) went partly that
way."* The item's acceptance criteria are in `docs/BACKLOG.md`, written from the owner's words
that the request quotes.

The owner, 2026-10-12, quoted in the request: direct messages work only while both sessions run
on the same machine, leave no auditable trace in a repository, and need no interaction from him,
which suits parallel work. The joint threads are more general and can later reach other machines
over ssh. *"The logical path seems to be a hybrid approach, direct messaging to get the reaction,
the DevSteward way to carry the content, but I am not sure if the seam is static or if direct
messaging should also carry content if it makes sense."* system-admin proposed that the seam be a
test rather than a fixed rule, and the owner confirmed that at this intake: *"if it is something
that a future session won't need, it can travel directly, if it is something valuable to have on
record, it should go via file."*

**This changes a decision on record.** REQ-101 Decision 8: *"Only `/intake` and `/advance` look
for messages … REQ-034 Decision 6 stands: no session is ever started by an arrival."* A bell to a
session that is already running starts nothing, so REQ-034 Decision 6 (*"Never spawn Claude from
within Claude"*) holds. But a running session that gets a bell looks at the thread outside
`/intake` and `/advance`, so the first sentence of REQ-101 Decision 8 no longer holds. This REQ
replaces that sentence and nothing else. Nothing appears in `steward status` or on the dashboard.

**What a direct message is, as seen from this machine at intake.** Claude Code lists the
other sessions running on the machine and lets a session send one of them a message. A session's
listed name starts with its project's folder name in lower case: the session in
`THermo-single-controller` was listed as `thermo-single-controller-47`, the one in `system-admin`
as `system-admin-7c`. Each is marked `interactive` or not. system-admin reported two ways a
message fails silently: the other session is not running, or it holds the message until its owner
approves it.

## Requirement

### The thread is the record

Everything a later session needs to understand, audit or act on about a joint task is in the
thread, written with the joint verbs. A direct message adds no such content.

### Ringing (the sender)

After every `steward joint-send`, the sending session:

1. lists the sessions running on this machine and picks the addressee's interactive ones, whose
   names start with the addressee's folder name in lower case;
2. sends each of them the single line `steward joint-show <handle>`;
3. rings nobody when none is running, and does not retry or wait.

### Answering a bell (the receiver)

An interactive session that receives `steward joint-show <handle>` runs it and works what waits
for its project in that thread, with the owner, the way `/advance`'s joint step does. A batch
session ignores it, and the entry waits for the next `/advance` or `/intake`.

### The seam

- What a later session needs to understand, audit or act on goes on the thread.
- Coordination nobody will read later may go as a direct message alone.
- The owner's approval never travels by direct message. A peer's report of the owner's decision
  is not the approval.

### A bell that fails

A bell that is lost, because no session is running or the receiver holds it for its owner,
changes nothing. The entry is on the thread and the receiver's next `/advance` or `/intake` finds
it (REQ-101, unchanged).

### Where it is written

- **STEWARD.md**, joint-tasks section: how a message reaches a running session (Ringing,
  Answering a bell), the seam, the approval rule and the failure case. REQ-101's *Where sessions
  look* bullet changes to match Decision 3.
- **The handbook**, `_01-format.qmd`'s joint-tasks section: the same, in short.
- **`/advance`** joint step and **`/intake`** take-up step: ring after each `joint-send` they
  issue, and point to STEWARD.md for the rest.

### Live proof (develop obligation)

1. After the develop commit, the develop session sends a `tell` on `sysadmin-open-0201` that
   names the commit and rings system-admin's running session. With the owner, system-admin's
   session reads the entry through the bell.
2. When system-admin answers on the thread and rings back, devsteward's running session reacts
   to the bell. Whether and how system-admin rings is system-admin's own work, done under its
   own rules.
3. The two `done`s on `sysadmin-open-0201` follow on each side with its owner. system-admin's
   item closes when STEWARD.md states how a message reaches a running session and where the seam
   lies.

## Notes

**Out of scope, on purpose.**
- **Bells to other machines.** Direct messages reach sessions on this machine only. The thread
  stays the general path. Reaching other machines over ssh is a later need.
- **A ring from the engine** (Decision 6).
- **Joint threads in `steward status` or on the dashboard** (REQ-101 Decision 8, unchanged
  there).
- **system-admin's adoption:** its joint-tasks skill and `open.py` ringing and answering bells.
  That is system-admin's work, done under its own rules. It reads the rule from this thread and
  from STEWARD.md.
- **Retrying or confirming a bell.** The thread already gives a confirmation that does not
  depend on the bell: the answer on the thread.

**Develop obligations.**
- **The live proof** needs the owner's attended system-admin session.
- **Consumers** get the new manual and skills at their next `steward sync`.

**Risks.**
- **The session list is Claude Code's, and may change.** The manual names what the session looks
  for: a running interactive session whose name starts with the folder name. If the harness
  changes, a bell may stop arriving. Nothing is lost, because the thread carries everything
  (Decision 1).
- **A held bell is not seen until the receiver's owner approves it.** In parallel work that
  delays the reaction but loses nothing.
