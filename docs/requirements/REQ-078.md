## Context

The observed friction is a live-session one, interactive `/advance` only — Peter has no
observation of `steward advance` from a shell misbehaving. The loop is:

1. `/intake` produces a fresh draft REQ and Claude closes by suggesting a bare "now run
   advance to start development".
2. The operator runs `/advance` with **no target**. Per the skill's §1 orient step, the
   skill self-orients from `steward status` and works whatever step is *eligible* on the
   ledger cursor — which is frequently **not** the just-intook REQ's develop step but some
   **`REQ-NNN:validate`** (System-Test) step left pending from earlier work.
3. `/advance` then tries to prepare/run that validation inside the current Claude session.
   But a System-Test validation must run as a **fresh `steward validate REQ-NNN` shell
   session** — the guided path refuses to run inside a live Claude/CLAUDECODE session by
   design (REQ-064/REQ-034). So the session cannot actually *close* the validation; it
   degrades into a validation-**preparation** session, which is not what the operator asked
   for and burns a paid-for session without landing a checkpoint.

Two root causes compound: (a) the closing suggestion is a **bare** "run advance", so the
operator never names the REQ they mean; and (b) `/advance` has no rule that a
validate/System-Test step is **out of its scope**, so it happily adopts one as a target.

`/advance` is, and should stay, the **fused develop checkpoint** skill. Validations belong
to `/system-test` (engine-dispatched via `steward validate`), never to `/advance`. The fix
is method-only — two skill files — and adds no engine, lint, or schema surface.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Interactive `/advance` with **no explicit REQ target**: if a REQ is freshly in the session context (e.g. just intook this session), **ask** whether to target that REQ's develop step; on decline, or when nothing is in context, auto-select the next eligible step. | Fix #1. The just-intook REQ is almost always what the operator means; asking removes the cursor-roulette that lands on an unrelated pending validation. Batch mode is unaffected — it always carries an explicit `REQ-NNN develop` target. |
| 2 | When auto-selecting a target, `/advance` **skips any eligible validate/System-Test step** and advances the next **develop**-eligible step. Validations are out of scope for `/advance`. | Fix #2. `/advance` is the develop-checkpoint skill; a validate step is `/system-test`'s job, run only via `steward validate` in a plain shell. |
| 3 | If **no** develop step is eligible (only validations pending), `/advance` **surfaces** the pending validation(s) with the exact `steward validate REQ-NNN` shell command and **stops** — it never runs a validation in-session. | Honest terminal state (mirrors REQ-060): don't silently do nothing and don't drift into validation-prep; hand the operator the one correct next command. |
| 4 | `/intake`'s closing report suggests the **precise** next command `/advance REQ-NNN develop` naming the just-intook REQ — never a bare "run advance". | Kills the ambiguity at the source (Decision 1's other half): an explicit target can never be diverted onto a pending validation. |
| 5 | Method-only: edit `.claude/skills/advance/SKILL.md` and `.claude/skills/intake/SKILL.md` (each hardlinked to its `devsteward/templates/.claude/skills/…` twin — one inode, edit once). No engine, CLI, lint, or schema change. | The defect is a skill-instruction gap, not an engine behaviour; `steward advance` from a shell already dispatches validate steps to `/system-test`, so there is nothing to fix in code. |

## Requirement

When this is done, interactive `/advance` never turns into a validation-prep session, and
the intake→advance handoff names its target:

1. **In-context targeting (interactive, no explicit target).** `/advance` SKILL.md instructs
   that when the command carries no `REQ-NNN develop` target and a REQ is fresh in the
   session context, the skill asks (via `AskUserQuestion`) whether to advance that REQ's
   develop step; on decline or empty context it auto-selects the next eligible step.
2. **Validations are out of scope.** `/advance` SKILL.md instructs that auto-selection
   **skips** any eligible validate/System-Test step and advances the next develop-eligible
   step instead; if none is eligible, it surfaces the pending validation(s) with the exact
   `steward validate REQ-NNN` command and stops. The skill never runs a validation session.
3. **Precise handoff.** `/intake` SKILL.md's emit/close (§3) instructs the closing suggestion
   to be `/advance REQ-NNN develop` naming the just-intook REQ, not a bare "run advance".
4. Both edits land on the hardlinked template twins in the same commit; `steward lint` stays
   green; no engine/lint/schema surface is touched.
