## Context

Onboarding **recipes** (a fork of the upstream Tandoor recipe manager) exposed two gaps in
the same surface: what the engine forces into a consumer's tree.

**1. The doc-layout seam is half-built.** recipes publishes `docs/` with mkdocs — everything
under it is built and deployed by a docs workflow — so the DevSteward corpus must live
*outside* `docs/`. `requirements_dir`/`index_file` are configurable, so recipes set
`requirements_dir: requirements` and its REQ corpus landed correctly at the repo top level.
`plans_dir` and `concepts_dir` are **not**: they are hardcoded properties
(`config.py:136-146`, `root/"docs"/"plans"` and `root/"docs"/"concepts"`) with no config
key. The consequences are concrete and already visible in recipes: `steward new` (run by
`/onboard` step 3) stamped `docs/plans/README.md` straight into the mkdocs tree, and the two
land gates — `PlanArtifactGate` and `ConceptArtifactGate` — can only ever look at
`docs/plans`/`docs/concepts`, so a plan written where this project keeps its plans would be
refused. The stamped skills make it worse: `/intake`, `/advance`, `/bootstrap` and
`STEWARD.md` instruct sessions to write literal `docs/plans/NNNN-*.md` and
`docs/concepts/REQ-NNN.md`, so even after the config key existed, a consumer session would
keep writing into the wrong tree and the gate would keep refusing. Half a seam is worse than
none: it looks configurable, and silently isn't.

**2. `steward sync` ships an operator tool to consumers.** `skillsync`'s tracked set is
engine-derived — whatever skill directories `templates/.claude/skills/` ships (REQ-036/066,
deliberately, so no hand-maintained list can fall out of step). `onboard` sits in that
directory, so every stamped project receives `/onboard` and every `steward sync` keeps it
current — while the skill's own first paragraph says it "is an **operator tool**: run by the
person performing the migration … *not* shipped to consumers (a stamped project is already
onboarded and never runs this)." Doctrine and machinery contradict each other; the machinery
wins, and consumers carry a skill that can only mislead a session (it orchestrates migrating
a project that is, by construction, already migrated).

Both are the same class of defect and are fixed together in one REQ: the engine deciding a
consumer's tree from the engine's own conventions rather than from the consumer's config.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | **Add the two seams (symmetry), don't subtract the existing ones.** `plans_dir` and `concepts_dir` become `config.yaml` keys defaulting to `docs/plans`/`docs/concepts`, loaded exactly like `requirements_dir`. | REQ-083 retired `roadmap_file` because nothing read it; these two are read by live land gates and a real consumer (recipes) needs to relocate them. The asymmetry — three of five doc paths configurable — is the defect, and symmetry is the smaller change than de-configuring `requirements_dir` and breaking recipes. |
| 2 | **`steward new` honors an existing `.devsteward/config.yaml`.** When the target already carries a config (the retrofit case `/onboard` creates), the stamp maps its template `docs/requirements/…`, `docs/plans/…` subtrees onto the configured paths. Greenfield (no config yet) stamps the defaults, unchanged. | The pollution in recipes came through `/onboard`'s `steward new --force`, not through greenfield use. Onboard already writes the config before stamping, so the information is present at stamp time; making the stamp *read* it is a smaller and more honest fix than teaching the skill to move files afterwards (a post-hoc `mv` that must stay in step with the template tree forever). |
| 3 | **The stamped prose reads the config, never a literal path.** `/intake`, `/advance`, `/bootstrap` and `STEWARD.md` name "the configured plans/concepts dir" and how to find it, instead of `docs/plans/`. The handbook chapters follow. | Without this the seam is half-wired in a new way: the engine would look in the right place while every session writes to the wrong one. The gate's refusal is the only thing that would catch it — a paid session lost to a documented-wrong path. |
| 4 | **The gates' refusal names the configured relative path**, not `Path.name`. | With `plans_dir: requirements/plans`, today's message would say "no file in `plans/`" — ambiguous exactly when the layout is unconventional, i.e. exactly when the operator needs to be told where the engine actually looked. |
| 5 | **`onboard` leaves `templates/` entirely** — it survives only as the engine repo's own `.claude/skills/onboard/`. No `audience:` marker, no exclusion constant. | Pure subtraction over a new classifier: an artifact that is not a template cannot be stamped, tracked, or synced, and there is no second mechanism to keep in step. It deliberately breaks the skills-are-hardlinked-to-templates pairing for this one skill — that pairing exists for skills that ship, and `onboard` is the one that must not. |
| 6 | **Already-stamped consumers keep their stray copy; sync just stops tracking it.** The engine never deletes a consumer file. `drift`/`steward status` stay silent about it (it is no longer engine-owned), and the next `sync` writes a lock containing only tracked artifacts, so the dead `onboard` key is pruned. | Owner's call. Giving `sync` delete-power over consumer files to retire one skill is machinery bought for a one-off; the three known consumers (FlowSteward, memzy, recipes) delete the directory by hand whenever they next touch `.claude/`. |
| 7 | **Legacy configs stay loadable by construction** — the new keys are read with `data.get(...)` defaults, so every existing consumer config keeps working with no migration verb. | Same lenient-parsing contract as REQ-083 decision 2. |

## Requirement

1. **Config seam.** `Config` carries `plans_dir: str = "docs/plans"` and
   `concepts_dir: str = "docs/concepts"` as loaded fields (both read from `config.yaml`
   via `load_config`), with root-resolved path properties preserving today's names
   (`cfg.plans_dir`, `cfg.concepts_dir` return `Path`s under the repo root, so their
   existing call sites in `build.py` are untouched). Absent keys resolve to the current
   defaults. The stamped `config.yaml.tmpl` documents both keys alongside
   `requirements_dir`, naming the mkdocs-style case they exist for.

2. **Gates.** `PlanArtifactGate` and `ConceptArtifactGate` operate over the configured
   directories, and every refusal message quotes the configured path **relative to the
   repo root** (e.g. `requirements/plans/`), not just the final path segment.

3. **Stamp.** `steward new` reads `<target>/.devsteward/config.yaml` when it exists and
   maps the template's `docs/requirements/**` and `docs/plans/**` onto the configured
   `requirements_dir`/`plans_dir`; nothing is written under `docs/` unless the config says
   so. With no pre-existing config the stamped tree is byte-for-byte what it is today.
   Engine-owned artifacts (`.claude/skills/**`, `STEWARD.md`) keep their fixed relative
   paths — they are engine behaviour, not project docs.

4. **Stamped prose.** No stamped surface hardcodes a doc-tree path: the shipped
   `/intake`, `/advance`, `/bootstrap` skills and `STEWARD.md` refer to the configured
   requirements/plans/concepts directories and tell the reader where to find them
   (`.devsteward/config.yaml`). DevSteward's own handbook chapters (`_01`, `_02`, `_03`)
   are updated the same way; the conventional `docs/…` layout may be named as the
   *default*, never as the location.

5. **Onboard leaves the stamped set.** `devsteward/templates/.claude/skills/onboard/` no
   longer exists; the engine repo keeps `.claude/skills/onboard/SKILL.md` as the operator's
   copy (and its prose is updated per requirement 4, including that it must set the doc-path
   keys in the config it writes *before* stamping). `steward new` therefore cannot stamp it,
   and `tracked_artifacts` cannot track it.

6. **Stray copies are inert.** For a consumer that already holds `.claude/skills/onboard/`
   and an `onboard` entry in `.devsteward/stamped.lock`: the file is left untouched,
   `drift()`/`steward status` report nothing about it, and the next `sync` writes a lock
   whose keys are exactly the tracked artifacts (the dead key pruned).

## Notes

- **Why no artifact/manual check.** Both halves are pure-Python and fully observable
  headless — config loading, gate refusal text, the stamped tree, the tracked set. The
  recipes repo is the motivating case, not the oracle; re-stamping it is an operator chore
  once this lands, not this REQ's proof. (Owner's call at intake: regression only.)
- **recipes' own cleanup is consumer-side and out of scope:** setting `plans_dir` in its
  config, deleting the stray `docs/plans/README.md` from the mkdocs tree, and removing its
  stamped `/onboard` copy are chores in that repo. Same for FlowSteward and memzy's stray
  `/onboard` (decision 6).
- **Hardlink care at build time:** the engine repo's `.claude/skills/*/SKILL.md` are
  hardlinked to their `templates/` twins (one inode, edited once). Removing the template
  copy of `onboard` must leave the repo copy's content intact — `git rm` the template path
  only, then verify `.claude/skills/onboard/SKILL.md` still reads correctly.
- **Out of scope (genuine non-goals):** a `docs_dir`-style single base key that
  requirements/plans/concepts hang off (three explicit keys keep each path independently
  placeable, which is what a fork with a pre-existing tree needs); any `audience:`/skill
  visibility classifier (decision 5); any sync power to delete consumer files (decision 6);
  and any migration verb for legacy configs (decision 7).
- **Doctrine touched:** this is the "minimal topology / prefer subtraction" principle cutting
  both ways in one REQ — the seam is *added* because a live gate reads it and a real consumer
  needs it, while the operator skill is *subtracted* from the stamped set rather than gated by
  a new classifier.
