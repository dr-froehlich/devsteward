## Context

[[REQ-010]] converts a project's REQ corpus, [[REQ-023]] makes that conversion safe in place,
[[REQ-022]] seeds the ledger, and [[REQ-007]] stamps the scaffold — but **nobody drives them in
order**. Plan [0005-memzy-onboarding](../plans/0005-memzy-onboarding.md) decomposes a full
onboarding into five pieces (schema relaxation → corpus conversion → ledger seed → scaffold
stamp → CLAUDE.md reconciliation); pieces 2–5 are a *sequence with verification gates between
them*, and that sequence is currently tribal knowledge living only in the plan document.
Without the skill, every future onboarding would re-derive that sequence from scratch.

The orchestration is **judgement-laden, not mechanical** — which is why it is a skill, not a
command. It must: choose `kind` inferences sanity-checked against the project, decide
merge-vs-overwrite when the target already has a `.claude/` and an 8 KB CLAUDE.md, reconcile
house conventions into the target's domain guidance without flattening it, and verify each step
with `steward lint` / `steward status` before moving on. Those are interview-and-judge tasks the
bundled skills already model (`bootstrap` is the analog for a *fresh* project; `onboard` is the
analog for an *existing* one).

The skill is an **operator tool**, like this repo's `intake`/`advance`/`bootstrap` skills — it
is run by the person performing a migration, pointing at the project being migrated. It is
**not** consumer scaffolding: a freshly `steward new`-ed project is already under the engine and
will never run `onboard`. So it lives in DevSteward's own `.claude/skills/onboard/`, not in the
stamped templates.

memzy is the **first project retrofitted** under the engine with this skill — chosen as the lead
because it is recent and low-stakes (the operator's call), **not** ExamEngineer, which stays a
trusted pre-DevSteward reference and migrates later (via [[REQ-017]]), if at all. The plan was
already validated against memzy's live corpus (23 REQs convert clean, lint down to the one
[[REQ-021]] divergence, since resolved). Driving memzy end-to-end is the proof before any heavier
project is considered.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Ship an `onboard` **skill** (`.claude/skills/onboard/SKILL.md`), not a command | The pipeline needs per-project judgement (kind inference, .claude/ merge, CLAUDE.md reconciliation) that a deterministic command can't own. The model-driven seams stay in the skill; the mechanical seams are the commands/scripts it calls |
| 2 | Lives in DevSteward's **own** `.claude/skills/`, not in `templates/` | It onboards *external* projects; a stamped consumer is already onboarded and never needs it. Bundling it would ship dead scaffolding. Same home as the operator `intake`/`advance` skills |
| 3 | The skill **orchestrates existing tools**, owning no migration logic itself: `convert_reqs.py` ([[REQ-010]]/[[REQ-023]]) → `steward init` + `steward seed-ledger` ([[REQ-022]]) → `steward new`/stamp ([[REQ-007]]) → CLAUDE.md reconcile | Single source of truth: logic lives in tested code; the skill is the *procedure and judgement* over them. Keeps the skill thin and the tools independently verifiable |
| 4 | Each step is **gated by verification** — `steward lint` after conversion, `steward status` after seeding — and the skill stops on a red gate | The engine owns verification (the ledger contract); onboarding must not declare success on an unlinted corpus. Mirrors the park-and-surface discipline of the other skills |
| 5 | **Merge, never overwrite**, when the target has an existing `.claude/`, `CLAUDE.md`, or `ROADMAP.md`: check skill-name/settings collisions, fold house conventions into the target's domain guidance, keep the target's richer artifacts | Onboarding an *existing* project must preserve its accumulated knowledge (memzy's Django/py-fsrs guidance, no-PII invariant); a stamp that clobbers them would be a regression, not a migration |
| 6 | Carry the [[REQ-005]] **park-and-surface** contract (honour `DEVSTEWARD_UNATTENDED=1`) like the bundled skills | Consistency: an onboarding fork (e.g. an ambiguous `kind`, a CLAUDE.md conflict) parks rather than guesses when unattended |
| 7 | **Scenarios (`SCN-*`) and ROADMAP conversion are out of scope** — left as living docs | Same boundary as [[REQ-010]] and the plan 0005 scope decision; the skill onboards the REQ corpus + ledger, not every doc |

## Requirement

An `onboard` operator skill that drives an existing project under the engine by orchestrating
the conversion, seeding, and scaffold tools in order, with a verification gate between steps and
merge-not-overwrite handling of the target's existing artifacts, validated against memzy.

### The pipeline the skill documents and drives

1. **Convert** the REQ corpus in place with `convert_reqs.py` ([[REQ-010]] + the [[REQ-023]]
   index splice), then **gate** on `steward lint` being clean.
2. **Seed** the ledger: `steward init` then `steward seed-ledger` ([[REQ-022]]); **gate** on
   `steward status` showing the finished corpus all-done and the work queue empty.
3. **Stamp** the scaffold ([[REQ-007]]): schema copy (widened, [[REQ-021]]), `_templates/`,
   `.gitignore` additions, config with the project's real branch names — **merging** into any
   existing `.claude/`/settings rather than overwriting.
4. **Reconcile CLAUDE.md**: fold the house conventions (same-commit discipline, the ledger
   contract, the branching model, the co-author trailer) into the target's existing CLAUDE.md
   without discarding its domain guidance.
5. Carry the park-and-surface contract; stop on any red gate.

### Acceptance shape (skill-content + tool-availability)

A skill's guarantee is its documented procedure and the existence of the tools it names — the
honest test is a content assertion plus a tool-availability check (the same posture as
[[REQ-021]] Decision 5 / [[REQ-009]]), not an end-to-end pytest that re-migrates a project.

### Out of scope

- Re-implementing conversion/seeding logic in the skill (Decision 3) — it only orchestrates.
- Scenario/ROADMAP conversion (Decision 7).
- Mutating memzy's live repo as part of *landing* this REQ — this REQ ships the skill + its
  content tests; the live memzy migration is driven and verified under its own tracked REQ
  ([[REQ-062]], the proof run), not here.

## Notes

- **Why a skill and not `steward onboard`.** The mechanical seams are already commands/scripts;
  what is left is judgement (kind inference, merge conflicts, CLAUDE.md reconciliation) that a
  deterministic command would have to either refuse or guess. A skill interviews and decides,
  then calls the tested tools. This is the same split as `bootstrap` (judgement) over `steward
  init` (mechanism).
- **memzy is the first onboarding, not the deliverable.** Landing this REQ ships the skill and
  its content tests; the live memzy run (plan 0005 pieces 2–5) is its own tracked proof REQ
  ([[REQ-062]]), with a `manual` AC a human signs off — symmetric to [[REQ-031]] (first lab)
  after [[REQ-030]]. Each onboarding is gated by `steward lint`/`status`.
- **Generalization path (ExamEngineer is later, not first).** Once — and only if — ExamEngineer's
  upscale concludes, [[REQ-017]] adds a legacy-prose converter front-end and the same `onboard`
  skill drives it unchanged: only step 1's converter differs; seed, stamp, and reconcile are
  uniform. memzy proves the path first.
