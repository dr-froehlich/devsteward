## Context

A red validation today costs the operator the whole guided session. Shape A (`steward
validate REQ-NNN` from a plain shell) takes the human verdict *after* the guided session
exits — the editor pattern (`_interactive_signoff`, `cli.py`) — so by the time the red is
recorded, the oriented System-Tester session is gone. The rework then runs in a second
session, and the re-validation brings up a *third* session that pays the full orientation
tax again (lab bring-up, REQ reading, procedure walk-through). Every red→rework→revalidate
loop burns two session orientations that the design never demanded.

Shape B — the in-session two-phase path (start half → guided work → record half, REQ-034
Decision 6) — was designed exactly for this and is already pointed at by the engine's own
CLAUDECODE refusal message ("drive the validation in this session via the /system-test
skill's start/record steps") and by the skill text. But it has **no CLI entrypoint**: the
start/record halves exist only as Python routine methods (`validate.py` `start()` /
`record()`), so no session can actually call them. The refusal message points at a door
that isn't there.

Meanwhile the rework side already has everything it needs: the red flag is set by the
record half (`_park_red` self-commits the ledger close), `steward rework`/`revalidate`
gate only on that recorded red (`_resolve_red_validation`), and neither verb has a
CLAUDECODE guard. Nothing about rework requires the validation session to *end* — only
shape A's post-exit verdict does. This REQ finishes shape B so the session can stay warm.

**Decision trail from intake (2026-07-17), recorded because two alternatives were
seriously considered and rejected:**

- *Subagent-driven rework from the warm session* (option A): rejected. Claude Code
  subagents cannot use `AskUserQuestion` (it depends on the main conversation's UI —
  confirmed against the docs), so the rework interview the house rules demand cannot
  happen inside one; and repair orchestrated from the System Tester's context re-couples
  the oracle the validate phase exists to keep blind.
- *Verdict via the `!`-prefix channel* (interactive `click.prompt` inside
  `! steward validate record …`): rejected **empirically** — a live test on 2026-07-17
  showed the `!` channel provides no stdin (`input()` → immediate `EOFError`).
- *Verdict as CLI flags* (`--verdict d` typed by the operator): rejected in favor of the
  second shell — it would make a flag-carried verdict a parallel verdict channel and
  weaken the self-certification firewall, for no gain since the operator needs the second
  shell for the rework anyway.

## Decisions

|---|----------|-----------|
| 1 | Shape B becomes two first-class CLI verbs: `steward validate start REQ-NNN` and `steward validate record REQ-NNN`; bare `steward validate REQ-NNN` (shape A) is unchanged | The halves already exist as routine methods; the REQ-034 design is finished, not re-invented. The engine's CLAUDECODE refusal message finally points at commands that exist. |
| 2 | `start` is callable from inside a Claude session — no CLAUDECODE refusal | It spawns nothing (the running session *is* the System Tester); the guard exists to prevent Claude-from-Claude, which start does not do. The `!` channel cannot host the prompt (no stdin, tested), and the operator has the second shell open anyway for the rework. |
| 4 | Full warm cycle in scope: after the second shell runs `steward rework`/`revalidate`, the **same warm session** re-runs `start` on the now-PENDING step; REQ-075's red-only scoping and green-evidence carry-forward ride through unchanged | Half the loop (record-only) would still force a session restart to revalidate, defeating the goal. | 5 | No new guards, no locks: `rework`/`revalidate` keep having no CLAUDECODE guard (operator decision at intake), and one-session-at-a-time (REQ-079) stays doctrine — the warm session sits idle while the second shell works | The recorded-red precondition is already the mandate that matters. | 6 | The cross-process start→record handoff is carried by the ledger + filesystem, not a new state file | `step_started` and the RUNNING status are already recorded; the evidence dir is the REQ's latest dated dir (or its path recorded on the start event). No second cursor to drift. |
| 7 | REQ-081's own System-Test phase analyzes the **ledger evidence of a real out-of-band warm cycle** — it does not nest a second validation run | Operator decision at intake: the proof rides a genuine pending validation driven warm for real; REQ-081's validation session then reads `.devsteward/events.jsonl` and the evidence dirs and records that analysis. No staged lab, no validation-inside-validation. |

## Requirement

A red validation no longer ends the System-Tester session. The two halves of the REQ-034
guided flow are real CLI verbs: the warm session (or the operator) runs `steward validate
start REQ-NNN` to open the step and ready the evidence dir, the guided work and capture
happen in the warm session, and the operator records the verdict from a second plain
shell with `steward validate record REQ-NNN` — the engine's interactive sign-off, artifact
gate, and three-outcome routing (green → mechanical land; decline → red park naming
`steward rework`; defer → pending park) all unchanged in substance, now reachable without
killing the session. After a red, the operator runs the rework from that same second
shell; when `steward rework`/`revalidate` flips the step back to PENDING, the still-warm
session re-runs `start` and the cycle repeats, scoped per REQ-075. Shape A stays intact
for the cold-start case.

## Notes

- **Out of scope:** any CLAUDECODE guard on `steward rework`/`revalidate` (explicitly
  declined at intake — the recorded-red precondition is the mandate); any lock or
  session-identity detection for the one-session doctrine (REQ-079: the rule is the
  operator's); subagent-driven rework (rejected, see Context); changes to `steward
  rework`/`revalidate`/`reland` themselves — they already work from any shell.
- **Doctrine surfaces to update in develop:** the system-test skill's guided-mode step 4
  ("End the session") becomes "hand off to the operator's second shell: `steward validate
  record REQ-NNN`; the session stays warm", plus the warm-cycle description; the
  handbook's workflow chapter; the `cli.py` CLAUDECODE refusal message. Skills are
  hardlinked to their templates and `STEWARD.md` is a symlink — edit once, never
  double-edit.
- **One-session discipline during the cycle:** while the second shell records, reworks,
  or checkpoints, the warm session must sit idle (no tree or ledger writes). This is the
  existing REQ-079 doctrine applied to a new rhythm, not a new rule.
- All regression oracles are engine-internal (CliRunner/subprocess over a temp repo,
  fake session seams); the suite is self-contained in a clean checkout. AC6 grades the
  captured event-log excerpt via `DEVSTEWARD_EVIDENCE_DIR` (REQ-075). `-k` selectors
  chosen not to collide with the module name (REQ-080's lesson).
- Empirical basis for Decision 3: `! python3 -c "print(input('Verdict: '))"` →
  `EOFError: EOF when reading a line` (2026-07-17, this repo's session).
