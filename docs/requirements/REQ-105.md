## Context

Found on 2026-10-16 during the intake of REQ-104, while weighing what happens when two writers
commit into one repo. The owner asked for it to be intaken as its own REQ. It is a defect
repair and takes up no backlog item.

**What the rollback does.** Every mutating `steward` command runs its body inside
`transaction()` (`devsteward/core/transaction.py`, REQ-049). On entry it records `HEAD`. If an
untyped exception escapes the body, it runs `git reset --hard <that HEAD>` and raises a
`RecoverableError` whose recovery line says *"nothing was half-applied … re-run the command"*.
The docstrings of `transaction()` and `GitCli.reset_hard` both claim this restores the
pre-command state "byte-identically".

**Why that is false here.** It holds only for a clean tree, and in this workflow a command
rarely starts on one. A develop session leaves its whole work uncommitted for the checkpoint
by design (`/advance`: *"leave the working tree dirty for the engine"*; REQ-079). The operator
verbs leave their writes uncommitted on purpose: `activate` (REQ-026 Decision 3), the
dashboard and the backlog verbs (REQ-097), and the joint verbs (REQ-101 Decision 9). `git reset
--hard` treats all of that as the command's own mess.

**Probed against the real `transaction()` and `GitCli` in a scratch repo:**

1. A tracked file modified before the command, and a body that raises. Afterwards the file is
   back at its committed content.
2. Add a new, untracked file, and a body that runs `git add -A` (what the land's whole-tree
   stage, `GitCli._stage_code`, does before its commit) and then raises. Afterwards the
   modified file is reverted **and the new file is deleted**.

`steward checkpoint` runs its gate and its commit inside one transaction
(`devsteward/core/executor.py:740`). So a git failure at the land's commit erases the
session's entire develop work, modified and new files alike, and only ignored files survive.
Once the stage has run, the staged blobs are still in the object store, so forensic recovery
(`git fsck --lost-found`) may be possible. The engine names none of that, and its message says
nothing was lost.

**What sets it off:**
- A commit hook that fails. None of the 23 stamped projects on this box has one (checked
  2026-10-16), but nothing prevents adding one.
- A second git writer holding `index.lock`.
- Any failing git command (disk, permissions).
- REQ-077's leftover guard (`_assert_committed_clean`), which raises on purpose to trigger
  exactly this rollback. REQ-088 removed one cause of it firing. When it fires, the code
  commit has already been made, so the work survives only in the reflog.

This is rare today, but when it happens the cost is the whole session. REQ-104 adds one more
commit to the land path, and so one more git command inside the window.

**This defect has happened before.** REQ-063 removed a `reset --hard` that discarded a green
session's work on a capture gap (the FlowSteward REQ-043 postmortem). It cured that one path
and left the generic rollback as it was. REQ-049 Decision 4 already knew the hazard. It
exempts graceful refusals from the rollback *"since those verbs deliberately leave
uncommitted work the rollback would destroy"*, but a real failure still destroys that work.

**Every caller is affected:**
- `activate`, `repeat` (including the land replay), `rework` and `decision-answer`
  (`devsteward/verbs.py`);
- `checkpoint` and the headless step (`executor.py`);
- the stale-validation reconcile, `validate` and `decide` (`cli.py`);
- the validation routine (`profiles/req/validate.py`).

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | **Keep the rollback, and change what it restores to: the state at entry**, meaning `HEAD`, the index and the working tree. | Owner's choice at intake. REQ-049's INV-3 ("a mutation is fully applied or fully rolled back") stays true, and "rolled back" now means *back to how it was*. One function changes and every caller benefits. |
| 2 | **Removing the rollback (subtraction) was considered and not taken now.** | REQ-049's recorded reason, *"never the half-state stalemate the firefighting loop kept producing"*, was written while work still ran on feature branches (REQ-047 Stage C). Whether those half-states are gone under trunk-based work is unproven, and proving it is its own analysis. Nothing prevents a later REQ from making that case. |
| 3 | **What the command itself did is still undone.** Its commits leave the branch, and the tracked files it wrote go back to their entry content (which may itself be uncommitted content). Files the command created that did not exist at entry are left as today. Ignored files are untouched, as today. | The guarantee is about the operator's and the session's work, which is what exists at entry. Leaving a mid-command file visible rather than mistaking it for applied state is REQ-049's existing rule. |
| 4 | **Taking the snapshot touches nothing.** It writes no ref and does not change the index or the working tree, so a command that succeeds behaves exactly as today. The mechanism is the develop session's choice; for example, `git stash create`, or a write-tree of the working tree through a temporary index. | A snapshot that disturbs the tree, such as `git stash push`, would itself be a mutation outside the transaction. Untracked files must be covered (probe 2), and `git stash create` alone does not cover them. |
| 5 | **If the restore itself fails, the error names the object that holds the entry state** and how to get the work back from it. | The operator's work must never depend on the restore succeeding silently. The snapshot exists as an object either way, so naming it costs nothing. |
| 6 | **The recovery message tells the truth.** It says that the tree was restored to how it was when the command started, and it no longer says "nothing was half-applied" unless that is so. | The message is the only thing the operator reads at that moment. Today it reassures them at the moment their work is gone. |
| 7 | **Graceful refusals are unchanged.** `PreconditionError`, `RecoverableError` and a caller's `pass_through` types still propagate without any rollback (REQ-049 Decision 4). | They mutate nothing, so there is nothing to restore. |
| 8 | **No change to the manual.** | Neither STEWARD.md nor the handbook describes the rollback (searched at intake). The behaviour a consumer agent observes, the recovery message, carries the truth itself (Decision 6). |
| 9 | **No concept phase, no System-Test phase, no lab. Every criterion is `regression`.** | Every criterion runs headless in temp git repos, with a real git failure injected through a commit hook. That is a decoupled oracle: git itself refuses, and no mock decides. |

## Requirement

### The rollback restores the state at entry

For every command that runs inside `transaction()`, when an exception that is not a graceful
refusal escapes the body:

- `HEAD` is the entry `HEAD`. Any commit the body made has left the branch.
- Every path that held uncommitted content at entry has exactly its entry content afterwards:
  a modified tracked file, a file with staged changes, and an untracked file that is not
  ignored. The index stages exactly what it staged at entry, so a file that was untracked at
  entry is untracked again.
- Tracked files the body wrote have their entry content.
- Files the body created that did not exist at entry, and ignored files, are treated as today
  (Decision 3).
- A `RecoverableError` is raised, and its message says truthfully what was restored
  (Decision 6).
- If restoring the entry state fails, the error names the object holding the entry state and
  how to recover from it (Decision 5).

A command that succeeds, or that refuses gracefully, behaves exactly as today.

### Through the real land

A `steward checkpoint` whose code commit fails leaves the session's develop work exactly as it
was before the checkpoint, both modified files and new ones. Once the cause is removed,
re-running the same `steward checkpoint` lands that work.

## Notes

**Out of scope.** Whether the rollback should exist at all (Decision 2). Detecting or locking
against a second writer: one session at a time stays doctrine (REQ-079 Decision 3).
Recovering work already lost to this defect in the past: no loss is on record.

**Build order.** REQ-104 depends on this REQ. A failure of the code commit after REQ-104's
`backlog:` commit must leave the owner's backlog changes as they were, which is this REQ's
guarantee. Build this REQ first.

**Develop obligations.** Correct the docstrings of `transaction()` and `GitCli.reset_hard`,
which claim a byte-identical restore. Any caller whose comments repeat that claim is corrected
in the same commit.

**Risks.**
1. Restoring the index exactly, including a staged change with a further unstaged change on
   top, is the fiddly part. AC1's file B exists to prove it.
2. A snapshot taken from a very large untracked tree costs time on every mutating command. A
   develop session that measures a noticeable delay records it in the plan, rather than
   narrowing the guarantee on its own.
