## Context

Three gaps surfaced while driving DevSteward by hand. All three are missing *verbs* — the
engine can run the queue but gives the operator no first-class way to shape it.

**1. Activating a REQ is a manual two-file edit.** `/intake` emits a REQ as `status: draft`,
which is invisible to the executor — only `open`/`in-progress`/`blocked` produce steps
(`reqfile.py:ACTIVE_STATUSES`). To enqueue it you must hand-edit the REQ frontmatter *and*
the matching `REQUIREMENTS_INDEX.md` row in lockstep (the same-commit discipline; `steward
lint` fails if they drift). That is fiddly and error-prone for what is one logical action.

**2. A failed step is a dead end.** When a `build`/`land` step fails (a hard error or a red
verify), the executor marks the ledger step `FAILED` and `run` stops. `FAILED` is not
`PENDING`, so it is not eligible — the next `run`/`advance` will *not* retry it. The only
way back today is hand-editing `state.yaml`. There is no operator verb to say "I looked,
re-attempt this," and no signal to the skill that it is resuming over its own partial work
(the failed step left the tree dirty — the executor only commits on success).

**3. `run`/`advance` cannot target one REQ.** They always take the lowest-id eligible step
across *all* active REQs. With several REQs `open` at once there is no way to drive a single
one full-circle (design→build→land) without first parking the others back to `draft` — as
just discovered when trying to run REQ-025 alone past the already-open REQ-022/023.

These are small, cohesive CLI additions that operate on REQ status and the ledger. This REQ
adds the three verbs. It deliberately does **not** introduce a "repair" skill or any extra
`claude` invocation: recovery is a status flip the *existing* `/advance` skill picks up and
assesses on its next run (which it does anyway), keeping the engine's run-lifecycle ownership
intact.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | `steward activate REQ-NNN` flips the REQ to `open`, editing the frontmatter `status:` **and** the `REQUIREMENTS_INDEX.md` row in sync so `steward lint` stays green. | One verb for one logical action; preserves the index↔REQ same-commit invariant (REQ-002). |
| 2 | `activate` accepts `draft → open` and `dropped → open` (reconsidered); it **refuses** `done`/`superseded` (pointing to supersede) and is a no-op on an already-active status. | REQ-001: never weaken a finished requirement — change direction by superseding, not reopening. `dropped` is the one terminal that legitimately reverses. |
| 3 | `activate` edits the two files and leaves them **uncommitted** on the current (integration) branch; it does not auto-commit. | Declaration is committed deliberately by the operator/skill, often batched with other intake edits; auto-committing would surprise and fragment history. |
| 4 | Recovery introduces a new **ledger-level step status `RECOVER`** (a `StepStatus`, *not* a REQ-frontmatter status — no schema change). `steward recover REQ-NNN` flips that REQ's `FAILED` step(s) to `RECOVER`; it refuses when there is no failed step. | The user-chosen mechanism: a distinct status the skill can see, kept strictly at the ledger/cursor layer where step state lives — the REQ stays `open`. |
| 5 | The executor treats `RECOVER` as **eligible** (alongside `PENDING`) and drives the step with a recovery signal in its command so the `/advance` skill knows it is resuming and must assess prior partial work; on success it advances to `DONE`, on a second failure back to `FAILED`. | Makes `run`/`advance` pick recovery up with no new skill; the dirty tree from the failed attempt is left in place for the skill to reconcile. |
| 6 | `recover` does **not** clean the working tree; it leaves the failed step's partial edits for the skill to assess. | The whole point of recovery is to build on / fix what the failed step left, not to discard it. |
| 7 | `--only REQ-NNN` on `run` and `advance` restricts step selection to steps whose `req` is `REQ-NNN`; everything else (dependency order within the REQ, the production-branch guard, park-and-surface) is unchanged. | A pure filter on the existing eligibility set — minimal surface, no new policy. |
| 8 | `--only REQ-NNN` **fails** (non-zero, with a reason) when that REQ has no eligible step — naming why (not active, blocked on an unfinished dependency, or already done). | "Fails if not eligible, obviously" — explicit over a silent no-op or accidentally running another REQ. |

## Requirement

`steward activate REQ-NNN`:

- Flips the REQ from `draft` or `dropped` to `open`, writing both the frontmatter `status:`
  and the index row so they stay in sync and `steward lint` passes; leaves the edits
  uncommitted.
- Refuses with a clear message on `done`/`superseded` (suggest superseding) and on an
  unknown id; reports a no-op when the REQ is already active.

`steward recover REQ-NNN`:

- Flips that REQ's `FAILED` ledger step(s) to the new `RECOVER` status and records a ledger
  event; refuses (non-zero) when the REQ has no failed step.
- Leaves the working tree as the failed attempt left it.

A `RECOVER` step is eligible: the next `steward run`/`advance` re-attempts it, invoking the
skill with a recovery signal in the step command so the skill assesses existing state before
acting. Success advances it to `DONE`; a further failure returns it to `FAILED`.

`steward run --only REQ-NNN` / `steward advance --only REQ-NNN`:

- Operate exclusively on `REQ-NNN`'s steps — `run` drives them to landing ignoring every
  other eligible REQ; `advance` does `REQ-NNN`'s next eligible step even when a lower-id REQ
  is eligible.
- Exit non-zero with a reason when `REQ-NNN` has no eligible step.

## Notes

- **Out of scope:** a dedicated "repair" skill or any extra `claude` invocation for
  recovery (recovery reuses the existing `/advance` skill via the status flip); a `deactivate`
  / `drop` verb; reopening `done` REQs with a ledger reset (superseding is the sanctioned path).
- **Status-layer clarity:** `RECOVER` is a `StepStatus` in the ledger, distinct from the REQ
  *frontmatter* status set (`draft|open|in-progress|blocked|done|dropped|superseded`). The
  REQ stays `open` while a step recovers — no `req.schema.json` change.
- **REQ-020 interaction:** when a failed `build`/`land` step is recovered, the re-run resumes
  on the REQ's existing feature branch (REQ-020's `prepare_branch` reuses it) — recovery does
  not re-cut or merge a branch.
- **Localization:** all command output is operational/technical English; no user-facing
  German strings introduced.
- Surfaces touched: `cli.py` (the three verbs/flags), `core/model.py` (`StepStatus.RECOVER`),
  `core/executor.py` (eligibility + `--only` filter + recovery signal), `core/ledger.py` and
  the index writer (status flips), and the `/advance` skill prompt (recovery awareness).
