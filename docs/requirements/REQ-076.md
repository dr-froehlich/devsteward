## Context

The engine stages every dirty path in the worktree when it commits. `GitCli.commit_code`
(`devsteward/core/git.py`) runs `git add -A -- :(exclude).devsteward` and its capture-gate
mirror `Executor._stage_and_write_tree` (`devsteward/core/executor.py`) does the same to
build the tree the REQ-063 gate checks. So a code commit for REQ-X sweeps in **any** file
that happens to be dirty in the shared `dev` worktree — including a concurrent session's
in-progress work for a different REQ.

This bit hard in FlowSteward's REQ-081 postmortem (2026-07-05): while an interactive concept
session was still building REQ-081's files, a background `steward validate` run for REQ-090
committed them into `ce1c9ef` labelled `REQ-090:validate`. Same-commit discipline was
silently violated (REQ-081's implementation lives in a commit named for REQ-090) and the
ledger drifted. The blanket stage means same-commit discipline is only as strong as "nobody
else is editing the tree."

The house doctrine (REQ-047, `[[trunk-based-pivot-req047]]`) forbids the postmortem's other
suggested fix — a per-run worktree or lock — because that solves an information-flow problem
with git topology. The subtractive fix is to **scope the commit**: stage only what the
command itself authored, not whatever else was already dirty.

The engine already has the signal. Every mutating command runs inside `transaction`
(`devsteward/core/transaction.py`), which snapshots `HEAD` at entry — *before* the command
does any work. The headless authoring commands (`advance` / `run`, and the deferred/validate
commit path) invoke `claude -p` **after** that boundary, so at the boundary the tree is at
its pre-command state: anything already dirty there belongs to someone else, and everything
the session dirties afterward is this command's work. Recording the set of dirty paths at the
boundary and committing only the delta excludes a concurrent run's files — exactly what would
have prevented the REQ-081 sweep (its files were already dirty when REQ-090's validate ran).

**One case does not fit and is deliberately left out.** `steward checkpoint` runs **no**
`claude` invocation (`Executor.checkpoint`) — the interactive `/advance` leaves the tree dirty
*before* the command starts, so checkpoint's own work is dirty-at-the-boundary and cannot be
distinguished from pre-existing dirt by a boundary snapshot. Scoping it by the same rule would
stage nothing. Checkpoint is attended (a human is present to curate the tree) and concurrency
isolation is explicitly out of scope here, so checkpoint keeps its whole-tree stage. This is a
known, documented residual, not a silent deferral (REQ-071): its home is the human's own
tree-curation before checkpoint, recorded in Notes.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Scope only the **clean-at-entry** commit path: `commit_code` gains an optional boundary baseline (the dirty-path set at the transaction boundary); when supplied it stages only paths changed after the baseline, when omitted it stages the whole tree as today. | The headless authoring commands (`advance`/`run`, deferred/validate) are the ones that swept a concurrent REQ; they have a clean boundary before `claude -p`. `checkpoint` passes no baseline and keeps today's behaviour. |
| 2 | The capture-gate mirror `_stage_and_write_tree` applies the **same** baseline. | The REQ-063 gate must check exactly the tree that `commit_code` will commit — if the two diverge, the gate certifies a different tree than lands. |
| 3 | Leave `commit_ledger` (`.devsteward/`-scoped, seq-guarded by REQ-073) and the `transaction` rollback `reset_hard` **unchanged** — out of scope. | Tightest fix that kills the observed cross-REQ sweep; `commit_ledger`'s `-A` is confined to `.devsteward/` and the rollback hazard is a distinct (mirror-image) concern worth its own REQ if it ever bites. |
| 4 | No worktree, no lock, no per-REQ path manifest, no session self-report. | Concurrency isolation via topology is the REQ-047 anti-pattern; scoping the commit by the boundary the engine already snapshots is the minimal, coordination-free fix. |

## Requirement

When a headless authoring command (`steward advance` / `steward run`, and the deferred /
validate commit path) makes its code commit, the commit contains **only** the files that
command authored after its transaction boundary. A file that was already dirty in the worktree
when the command began — e.g. a concurrent session's in-progress work for a different REQ — is
**not** staged into the commit, and same-commit discipline holds (REQ-X's implementation lands
in a commit named for REQ-X).

The capture-gate check (REQ-063) runs against the same scoped tree, so what the gate certifies
and what the commit lands are byte-identical.

`steward checkpoint` (no `claude`, dirty-at-entry) is unchanged: it stages the whole dirty tree
as before. `commit_ledger` and the transaction rollback are unchanged.

## Notes

- **Oracle / env (REQ-064):** every AC is `check: regression` with a coupled oracle — a
  temp git repo created by the test asserting staged/committed path sets. No service, secret,
  or network is needed, so none of these greens is environment-bound; nothing to route to
  `artifact` or a lab.
- **Out of scope (explicit, not silent):**
  - `steward checkpoint`'s whole-tree stage. Its work is dirty-at-boundary and a boundary
    snapshot cannot separate it from pre-existing dirt (see Context). Checkpoint is attended;
    the human curates the dirty tree before checkpointing. If a mechanical checkpoint-scoping
    is ever wanted it needs its own signal (an `/advance`-recorded start marker) — a named
    follow-on, not this REQ.
  - `commit_ledger` (`.devsteward/`-scoped, REQ-073 seq-guarded) and the `transaction`
    rollback `reset_hard` (the mirror-image worktree-wide hazard). Left unchanged by
    Decision 3; either earns its own REQ if it ever bites.
