## Context

`/advance` is one skill run two ways (the batch/interactive contract in
`handbook/03-workflow.md`). The batch path is whole: `steward advance`/`run` drive
`claude -p`, and the **executor** owns the bookkeeping — it sets the cursor, marks the step
done, and appends the `checkpoint` event (`core/executor.py` is the *sole* writer of
`.devsteward/state.yaml` + `events.jsonl`).

The **interactive** path is not whole. When a human runs `/advance` in a live session, the
skill does the thinking and (per SKILL §4) commits the work — but **nothing advances the
ledger.** The executor isn't in the loop, and the only commands that move the cursor
(`advance`/`run`) re-invoke `claude`, which is the opposite of what an already-done
interactive checkpoint needs. The result: the cursor stays pointed at the step you just
finished, so the next `steward advance` **redoes** it. Today the only fix is to hand-edit
`state.yaml`/`events.jsonl` — undocumented and error-prone.

This is the unclosed half of the conceptual fork already named in `ROADMAP.md` under
*Repair* ("make `advance`/`run` batch-only; separate interactive `/advance`"). Closing it
makes interactive mode a first-class peer of batch: do the work and commit live, then record
the checkpoint authoritatively — **without** pretending an engine verified it.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | A new `steward checkpoint` command that advances the ledger for already-committed work, **without invoking `claude`** | The interactive checkpoint is *done*; the gap is purely bookkeeping. Re-running `claude` (what `advance` does) would redo the work |
| 2 | **No verification re-run** — `checkpoint` does not run the acceptance tests | In interactive mode the human is the guarantee (the two-mode contract). The engine's teeth (REQ-015) stay exclusive to batch; this command must not impersonate them |
| 3 | **Honest provenance** — the recorded event marks the checkpoint as human-attested, not engine-verified | The ledger must not blur who certified a step. An interactive checkpoint and an engine one should be distinguishable in `events.jsonl` |
| 4 | Operates on the **current cursor step** by default; `--commit` defaults to `HEAD` | The common case is "I just committed the step I was on." Explicit `STEP`/`--commit` args cover the rest |
| 5 | **Refuse, don't guess** — error cleanly when there is no eligible cursor step or no commit to point at | Same discipline as the branch guard: a precondition failure is a clear refusal, not a silent half-write |

## Requirement

Add `steward checkpoint [STEP] [--commit SHA]` that records a completed **interactive**
checkpoint in the ledger without driving `claude` and without re-running verification:

1. Resolve the target step (default: the current cursor step) and the commit (default
   `HEAD`).
2. Mark the step `done`, append a `checkpoint` event carrying the commit sha **and a marker
   that this was human-attested** (e.g. `verified: interactive`), and advance the cursor to
   the next eligible step — the same ledger transition the executor makes, minus the
   `claude` invocation and the verification gate.
3. Refuse with a clear message if there is no eligible step to checkpoint or no commit to
   reference; write nothing in that case.
4. SKILL §4 (interactive close) and `handbook/03-workflow.md` reference this command as the
   ledger-advance step, replacing the hand-edit.

### Out of scope

- Any change to the **batch** path or the executor's verification teeth (REQ-006/REQ-015).
- Auto-committing the work — `checkpoint` records an *existing* commit; the skill/human
  still makes it.
- Re-running or trusting acceptance tests (Decision 2).

## Notes

- **Why a command and not just docs:** the doc patch (this session) tells a human *what* to
  hand-edit; this REQ removes the hand-edit. Until it lands, the documented manual step is
  the stopgap.
- **Provenance keeps the trust model honest (Decision 3):** the whole point of the
  batch/interactive split is *who certifies done*. A `checkpoint` event that looked identical
  to an engine checkpoint would erase that distinction — so it carries its own marker. A
  reader (or a future audit) can always tell a human-attested step from an engine-verified
  one.
- Formalizes the ROADMAP *Repair* item "make `advance`/`run` batch-only; separate
  interactive `/advance`."
