> **Revised 2026-06-10** per the strategic assessment
> (`docs/reports/2026-06-10-strategic-assessment-process-and-token-economics.md`, §5) and
> plan 0011 step 3. The original draft made `checkpoint` a *non-verifying recorder*
> ("in interactive mode the human is the guarantee"). That trust model is reversed here:
> **the engine is the verifying bookkeeper always; only the driver varies.**

## Context

`/advance` is one skill run two ways. The batch path is whole: `steward advance`/`run`
drive `claude -p`, and the executor owns the bookkeeping — cursor, step status,
`checkpoint` event (`core/executor.py` is the sole writer of `.devsteward/state.yaml` +
`events.jsonl`). The interactive path was not: when a human ran `/advance` in a live
session, the skill did the thinking and committed the work, but nothing advanced the
ledger, and — worse — nothing *verified*. The handbook still says interactive mode has
"no engine guarantees," which the assessment identified as backwards: interactive is the
**default** driving mode for a single developer, so it is precisely the mode that must
carry the guarantees. The false-`done` of FlowSteward REQ-003a is impossible in either
mode only once the bookkeeper — verifier included — is shared.

REQ-029 already built most of the machinery while constructing the shared land:
`Executor.checkpoint()` (branch guard → REQ-028 verify → shared `mechanical_land`), the
`steward checkpoint REQ-NNN [PHASE]` CLI command, and the `/advance` close via
`steward checkpoint` (repo + stamped template). What this REQ finishes, settled at the
flesh-out interview (2026-06-10): the **full topology close-out** (the interactive path
currently stops after the land commit, leaving the trailing ledger write dirty and the
merge manual — exactly the hand surgery this REQ exists to remove), **driver provenance**
on the checkpoint event, the **handbook flip** to interactive-first, and dedicated
acceptance tests plus a human-reviewed proof run.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | `steward checkpoint` **verifies before it records**: it runs the same REQ-028-toothed gate as a batch land (named ACs, skip ≠ green, zero-collection ≠ green, full suite, project venv). Red ⇒ report and refuse the land. | A checkpoint that records without verifying re-opens the hand-stamped-`done` hole. The gate cannot be talked into green; that property must not depend on who drove. |
| 2 | On green, `checkpoint` performs the **same mechanical bookkeeping as REQ-029's land** — status flip, index `DONE`-sync, commit, ledger advance — via the shared `mechanical_land`. One bookkeeper, two drivers. | Two divergent bookkeeping paths would drift. REQ-029 built the routine; this command is its second caller. |
| 3 | **Red bookkeeping (interview, revising the stub's "nothing is written"):** a red gate records the red `verify` event and marks the step `FAILED` — an honest trail of failed attempts — but performs **zero land-side writes**: no frontmatter flip, no index touch, no commit, no cursor move, no `checkpoint` event. Re-running `checkpoint` after a fix needs no `recover`. | Erasing failed attempts weakens the audit trail the ledger exists to keep; the invariant that matters is that nothing *lands* on red, not that nothing is remembered. |
| 4 | **Full topology close-out (interview):** on green, `checkpoint` finishes like batch — the trailing ledger write is committed as a follow-up and the feature branch is `--no-ff`-merged into the integration branch via the shared REQ-020 routine (`_merge_after_land`), with the `branch_merged` event. On the integration branch itself, no merge is attempted. | One bookkeeper means the whole transaction. Stopping at the land commit leaves `state.yaml`/`events.jsonl` dirty and the merge manual — the last undocumented hand step. |
| 5 | Provenance records the **driver** (`interactive` vs `headless`) on the checkpoint event; certification is the engine's in both modes. | The audit question changes from "who certified?" (always the engine) to "who did the cognition?" — still worth recording, no longer a trust boundary. |
| 6 | The handbook is repositioned **interactive-first**: interactive driving with `steward checkpoint` is the default; `steward run` is the overnight batch lane for queues of well-specified, low-fork REQs; the "no engine guarantees" / "the human is the guarantee" framing is removed everywhere (00-method, 02-engine, 03-workflow, 04-skills). Also document the standing rule that engine REQs originate from consumer postmortems. | The guarantees, not the autonomy, are the product (assessment §5). |
| 7 | `/advance` (repo + stamped template, kept identical) ends its interactive close with `steward checkpoint` — already shipped with REQ-029; this REQ owns asserting it stays true. | Removes the last documented hand-edit of `state.yaml`/`events.jsonl`. |
| 8 | **Refuse, don't guess — revised (interview):** refusals are the wrong branch (production guard) and a non-derivable/ineligible step. The *dirty tree is the expected input* — `checkpoint` is the committer of the interactive session's work, so the stub's dirty-tree refusal is dropped; a re-run on an already-landed step is a safe no-op (idempotent flip). | The original sketch assumed the human committed first (`--commit SHA`); REQ-029's reality made the engine the committer, which is strictly safer — committing first would let a red land in history. |
| 9 | **REQ-030 seam (interview):** REQ-018 lands first, with **no dependency** on REQ-030. When REQ-030 inserts the validate step that gates the land, `checkpoint` inherits it for free through the shared `mechanical_land` — no checkpoint-specific validate logic here. | Plan-0011 order (step 3 before step 4) holds; one shared tail means the gate reshapes both drivers at once instead of being taught twice. |

## Requirement

`steward checkpoint [REQ-NNN] [PHASE]` closes an interactively-driven step: resolve the
target step (default: the current cursor step; `PHASE` defaults to `develop`), run the
land-grade REQ-028 verification gate, and on green perform the shared mechanical
bookkeeping (Decision 2) **plus the topology close-out** (Decision 4), appending a
checkpoint event that carries the commit sha and `driver: interactive` (Decision 5). On
red, record the red verify event, mark the step `FAILED`, print the gate's evidence, and
exit non-zero with zero land-side writes (Decision 3). Handbook + `/advance` per
Decisions 6–7.

## Notes

- **What changed vs the 2026-06-08 draft:** Decisions 2–3 of the original ("no
  verification re-run", "human-attested provenance") are dropped — the evidence
  (FlowSteward postmortems, assessment §1.2) showed the human-as-guarantee model is
  exactly the hole the engine exists to close. The flesh-out interview (2026-06-10)
  further revised the stub: red refusal now *records* the failure (Decision 3), the
  dirty-tree refusal is dropped because the engine is the committer (Decision 8), and
  the close-out gains the merge (Decision 4).
- **Already shipped by REQ-029** (this REQ's tests pin them, its build fills the gaps):
  `Executor.checkpoint()`, the `steward checkpoint` CLI command, the `/advance` close.
  Open gaps: no `_merge_after_land` on the interactive path, no `driver` field, the
  handbook still batch-first, no `tests/test_checkpoint.py`.
- **Out of scope:** the validate step and `steward validate` (REQ-030 — Decision 9 keeps
  this REQ free of validate logic); concept-phase mechanics; re-earning batch mode
  (plan 0011 step 6).
- **AC7 interim convention:** REQ-018 lands before REQ-030's decision-stop machinery, so
  the manual sign-off uses the REQ-027 D12 interim hand-flip with its provenance
  convention (date, reviewer, scope in `verified_by`) — the REQ-029 AC8 precedent.
- **Process declarations:** defaults — fused develop, no concept phase, no lab (the
  proof run needs only this repo or a scratch stamp); the `process:` block is omitted.
- **Localization:** engine/handbook text is technical English; no user-facing localized
  strings.
- **Surfaces (expected):** `devsteward/core/executor.py` (close-out on the checkpoint
  path, `driver` on the event), `devsteward/cli.py` (cursor-default argument),
  `devsteward/handbook/00-method.md`/`02-engine.md`/`03-workflow.md`/`04-skills.md`,
  `tests/test_checkpoint.py`.
- After this REQ lands, the plan-0011 migration REQs themselves regain proper ledger
  records (the migration is driven interactively; see plan 0011, "How this migration
  itself is driven").
