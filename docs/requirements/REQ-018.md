## Context

`/advance` is one skill run two ways. The batch path is whole: `steward advance`/`run`
drive `claude -p`, and the executor owns the bookkeeping — cursor, step status,
`checkpoint` event (`core/executor.py` is the sole writer of `.devsteward/state.yaml` +
`events.jsonl`). The interactive path is not: when a human runs `/advance` in a live
session, the skill does the thinking and commits the work, but nothing advances the
ledger, and — worse — nothing *verifies*. The handbook currently says interactive mode has
"no engine guarantees," which the assessment identified as backwards: interactive is the
**default** driving mode for a single developer, so it is precisely the mode that must
carry the guarantees. The false-`done` of FlowSteward REQ-003a is impossible in either
mode only once the bookkeeper — verifier included — is shared.

## Direction (provisional decisions)

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | `steward checkpoint` **verifies before it records**: it runs the same REQ-028-toothed gate as a batch land (named ACs, skip ≠ green, zero-collection ≠ green, full suite, project venv). Red ⇒ report and refuse; **nothing is written**. | A checkpoint that records without verifying re-opens the hand-stamped-`done` hole. The gate cannot be talked into green; that property must not depend on who drove. |
| 2 | On green, `checkpoint` performs the **same mechanical bookkeeping as REQ-029's land** — status flip, index `DONE`-sync, commit, ledger advance — via shared engine code. One bookkeeper, two drivers. | Two divergent bookkeeping paths would drift. REQ-029 builds the mechanical-land routine; this command is its second caller. |
| 3 | Provenance records the **driver** (`interactive` vs `headless`) on the checkpoint event; certification is the engine's in both modes. | The audit question changes from "who certified?" (always the engine) to "who did the cognition?" — still worth recording, no longer a trust boundary. |
| 4 | The handbook is repositioned **interactive-first**: interactive driving with `steward checkpoint` is the default; `steward run` is the overnight batch lane for queues of well-specified, low-fork REQs; the "no engine guarantees" framing is removed. Also document the standing rule that engine REQs originate from consumer postmortems. | The guarantees, not the autonomy, are the product (assessment §5). |
| 5 | `/advance` (repo + stamped template) ends its interactive close with `steward checkpoint`, replacing the documented hand-edit of `state.yaml`/`events.jsonl`. | Removes the last undocumented manual ledger surgery. |
| 6 | Refuse, don't guess: no eligible cursor step, no commit to reference, or a dirty tree ⇒ clean refusal, zero writes. | Same discipline as the branch guard. |

## Requirement (sketch)

`steward checkpoint [STEP] [--commit SHA]` closes an interactively-driven step: resolve
the target step (default: current cursor step), run the land-grade verification gate, and
on green perform the shared mechanical bookkeeping (Decision 2), appending a checkpoint
event that carries the commit sha and `driver: interactive`. On red, print the gate's
evidence and exit non-zero without touching the ledger. Handbook + `/advance` updates per
Decisions 4–5.

## Notes

- **What changed vs the 2026-06-08 draft:** Decisions 2–3 of the original ("no
  verification re-run", "human-attested provenance") are dropped. The evidence
  (FlowSteward postmortems, assessment §1.2) showed the human-as-guarantee model is
  exactly the hole the engine exists to close.
- **Dependency on REQ-029:** the mechanical-land routine (verify → flip → sync → commit →
  advance) is built there; this REQ wires it to a second entry point. If REQ-029 slips,
  the flesh-out session may invert the build order — the shared routine can be born here
  instead.
- After this REQ lands, the plan-0011 migration REQs themselves regain proper ledger
  records (the migration is driven interactively; see plan 0011, "How this migration
  itself is driven").
