## Context

REQ-006 made the engine — not the skill — re-run a step's named acceptance tests before it
advances the ledger. But the REQ profile only attaches tests to the `:land` step
(`profiles/req/source.py`): `design` and `build` get `verify=()`, and
`core/verify.py` then marker-trusts an empty `verify` (`return True, "marker trust"`). So
**every** design/build step auto-passed, and a REQ that declared no acceptance tests at all
auto-passed even at land — which is how an empty no-op once reached `DONE` and was committed
(then retracted in the event log). The architecture's headline promise, "unattended
automation can't be talked into a false done" (`handbook/02-engine.md`), held only by
accident: it was real solely at *land-with-tests*, and nothing guaranteed land had tests.

This is the third reality-boundary defect from the 2026-06-07 assessment
(`docs/plans/0002-reality-harness-and-engine-repair.md`), after REQ-012 (cswap) and
REQ-013/REQ-014 (reality harness + permission mode).

A per-phase "did the working tree change" gate was considered and rejected: the `advance`
skill's `design` phase legitimately produces no file change for a trivial REQ (it captures a
plan only "if non-trivial"), so such a gate would fail honest designs and break the standing
reality gate. The robust place for teeth is where the work is *delivered* — land.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Concentrate the guarantee at **land**: a `land` step with no acceptance tests is *refused*, not trusted | A REQ is delivered at land; a no-op build is then caught there when its acceptance tests fail. Closes the false-done for the "done" that matters |
| 2 | Keep `design`/`build` marker-trust (they only advance the cursor) | They carry no per-phase tests by construction; gating them on file changes would fail honest trivial phases and the reality gate |
| 3 | Put the rule in a REQ-profile `ReqVerifier` wrapping the generic `CommandVerifier`, not in core | "land" is a REQ-workflow concept; the content-agnostic core must not know it. `build_executor` wires `ReqVerifier` for the req profile, plain `CommandVerifier` for generic |
| 4 | No new lint rule | Lint already requires every active REQ to declare ≥1 acceptance criterion with a test id; the engine now also enforces it at runtime (defense in depth, self-contained) |

## Requirement

The engine refuses to mark a `land` step `DONE` unless it re-runs at least one named
acceptance test and sees it green:

- `ReqVerifier.verify` returns `(False, …)` for a `land` step whose `verify` is empty — no
  marker-trust at land.
- A `land` step with tests has them re-run for real (green ⇒ pass, red ⇒ fail), exactly as
  `CommandVerifier` does today.
- `design`/`build` steps with no per-phase tests still pass on marker-trust; the guarantee
  is enforced at land, where the REQ is delivered.
- `build_executor` wires `ReqVerifier` for the REQ profile so the guarantee holds end to end.

```yaml acceptance
- id: AC1
  text: ReqVerifier refuses a land step that declares no acceptance tests (no marker-trust at land).
  test: "python -m pytest tests/test_verify_teeth.py::test_land_without_tests_fails"
  status: pass
- id: AC2
  text: ReqVerifier re-runs a land step's named tests (green passes, red fails) while design/build with no per-phase tests still pass on marker-trust.
  test: "python -m pytest tests/test_verify_teeth.py::test_land_runs_tests_designbuild_pass"
  status: pass
- id: AC3
  text: End to end, the executor + ReqVerifier mark a land step with no tests FAILED and never commit it.
  test: "python -m pytest tests/test_verify_teeth.py::test_executor_refuses_land_without_tests"
  status: pass
```
