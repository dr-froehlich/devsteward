## Context

From the FlowSteward REQ-022 post-mortem
(`flowsteward/docs/postmortems/2026-06-26-req-022-fixture-pdf-poison-feed-and-test-roles.md`,
§"The process gap (DevSteward)") and the live incident that followed it: a paid develop
checkpoint for FlowSteward REQ-054 went green on its own work but **tripped over a test it
did not own** — REQ-053's live System-Test choreography ran inside REQ-054's develop
full-suite gate and flaked on lab-state ordering. The hand-fix was to set
`verify.full_suite: python -m pytest -m "not live"`, which works but is a band-aid: it
excludes **all** live tests from the gate, collapsing two distinct things the owner wants to
keep apart. Peter's stated model is three tiers:

1. **module regression** — hermetic, fast, every gate forever.
2. **a few end-to-end live tests run *as* regression** — the cheapest standing integration
   proofs, kept running continuously.
3. **validation tests — run once, on demand only**, never auto-run by later REQs.

The engine already has a role axis — the REQ-027 `check:` field — and it already knows every
acceptance test's lane from frontmatter. But the three-value enum (`regression | artifact |
manual`) has **no honest home for tier 2**: an end-to-end live test has a *system scope and a
decoupled oracle* (so by REQ-027's own definition it is not `regression`, which is
module-scope / coupled), yet it must run as a **standing** gate member (so it is not a
one-time `artifact`, which runs once in its REQ's System-Test phase). The missing cell is
*system-scope × standing*. With no value for it, authors either mislabel an e2e as
`regression` (a lie the taxonomy exists to kill) or hide it behind the `live` pytest marker —
which then also catches the tier-3 one-time validations, the exact conflation that produced
the REQ-054 flake.

Worse, the develop full-suite gate runs the **whole** pytest suite (`verify.full_suite`,
default `python -m pytest`), so a *one-time* `artifact`/`manual` validation test of an
already-done REQ is re-executed in every later REQ's develop gate — tier 3 leaking into the
standing gate. That leak, not the fixture, is the engine-side root of the incident.

The post-mortem surfaced a **second** recurring pattern in the same family ("pytest is often
the wrong one"): an acceptance `test:` string authored as a bare `pytest …` runs the console
script via `shell=True` — wrong interpreter, and **no repo root on `sys.path`** — so a
`from tests.<helper> import …` that resolves fine under `python -m pytest` explodes under
bare `pytest`. The engine's `_resolve_interpreter` rebinds a leading `python`/`python3` to a
pytest-capable venv interpreter, but a leading `pytest` slips past unrebound. This is the
run-time twin of the lane problem: a test should never run in a different *flavor* depending
on how a human happened to type the string, any more than it should run in a different *lane*
depending on a hand-edited marker expression.

The unifying thesis: **the engine — not ambient state, not a marker string, not authoring
whim — decides how an acceptance test runs (which lane, which flavor), and a resource a
declared test requires being absent is a hard red, never a silent skip.** This is the
left-shift/runtime completion of REQ-027 (the `check:` axis), REQ-028 (skip≠green at the
named-test gate), REQ-063 (the engine tolerates the *unknown* skip without destroying work),
and REQ-064 (intake screens env-bound regressions). It extends the **one** existing axis
rather than adding a parallel "test-role" axis the post-mortem first sketched — house style:
make the field you already have load-bearing, do not grow a second one.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | **`check:` gains a fourth value: `live`** — system scope, decoupled oracle, but a **standing** gate member (runs continuously like a regression, not once-on-demand like an artifact). Enum becomes `regression \| live \| artifact \| manual`. | Fills the missing matrix cell (system-scope × standing) that forced authors to mislabel an e2e as `regression` or hide it behind a marker. Extends the single role axis the engine already owns — no parallel "role" attribute, no consumer marker convention to keep honest. |
| 2 | **The develop gate routes by `check:`, deterministically.** It runs the REQ's `regression` + `live` lane tests as named tests, runs the hermetic full suite, and **excludes every `artifact`/`manual` AC test node-id project-wide** from that suite — a one-time validation never gates a later REQ's develop. The engine derives the exclusion set from frontmatter it already parses; no hand-edited `-m "not live"`. | The incident root: the full suite ran another REQ's one-time live System-Test. The lane a test belongs to is *declared*, so the engine decides gate membership — not a fragile marker expression that collapses tier 2 into tier 3. |
| 3 | **A declared-lane test whose required resource is absent is a HARD RED, not a tolerated skip.** A `check: live` (or any named lane) test that reports `skipped` in the develop gate fails it. This is the deliberate-declaration counterpart to REQ-064's screen and the counterweight to REQ-063. | "Tests running in different flavors depending on ambient state" is the frustration this kills: a test the engine *knows* must run cannot quietly not-run. REQ-063 still governs that a red **withholds the land without destroying the work commit** and still tolerates the *unknown* skip; this only sharpens the gate verdict for tests the engine knows must run. The release valve when a live lab stops paying its keep is Decision 5 (degrade), not a silent skip. |
| 4 | **One flavor: every pytest acceptance command runs as `python -m pytest` under the one engine-resolved interpreter.** A leading bare `pytest` token is normalized to `<resolved interpreter> -m pytest …` (so the repo root is importable), the same rebind `_resolve_interpreter` already applies to a leading `python`/`python3`. Non-pytest commands keep exit-code semantics (gated on `_is_pytest_command`). | The run-time twin of Decision 2: neither the lane nor the flavor should depend on how a human typed the string. Fixes the `from tests.<helper>` import break (FlowSteward REQ-052/053) without re-landing those REQs. Consistent with the engine's existing pytest-awareness (JUnit XML, the `python` rebind); the fallback stays tech-agnostic. |
| 5 | **Degrade is re-classification, not a new verb.** When a newer live proof subsumes an older one, the older AC's `check:` flips `live → artifact` (it leaves the standing gate by Decision 2, stays re-runnable via `steward revalidate`) and the superseding test/REQ is recorded in the AC text / Notes. Lint accepts the degraded form. | The lifecycle the owner wants ("a live regression is degraded once a successor takes its role") falls out of Decisions 1+2 for free — degrade needs no `steward degrade` verb and no successor frontmatter field. House style: add machinery only on a concrete present need; here there is none beyond the reclassification the model already supports. |
| 6 | **Dogfood + intake/handbook/manual.** Mostly hermetic `regression` ACs over the engine gate / lint / interpreter with fake projects (the `test_verify_teeth` family); one `manual` AC where a human confirms the deterministic behaviour on a seeded multi-lane scenario and that the docs explain the model well enough to code against. `/intake`, the handbook taxonomy, and the `STEWARD.md` black-box manual document the four lanes, the routing, fail-hard, the one-flavor rule, and degrade. | Mirrors REQ-027 D8 / REQ-064 D4: prove the behaviour with honest tests and seed the house style where a human is present. The "FlowSteward (and I) didn't know how to code it — improve the manual or specify it" gap is closed on both the engine and the documentation side. |

## Requirement

- The acceptance `check:` enum is **`regression | live | artifact | manual`**; `steward lint`
  accepts `live` on an active REQ and rejects an out-of-enum value, exactly as for the other
  three (presence/enum only — REQ-027 Decision 5).
- The **develop gate** runs the REQ's `regression` and `live` lane tests as named tests, runs
  the hermetic full suite, and **excludes every `artifact`/`manual` acceptance test (across
  all REQs)** from the full-suite run, so a one-time validation never executes in a later
  REQ's develop gate.
- A `check: live` named test that reports **skipped** in the develop gate is a **hard red**
  (Decision 3). An *unknown* test skipping in the full suite stays tolerated (REQ-063); the
  fail-hard applies only to tests the engine knows must run from a declared lane. A red
  withholds the land without destroying the work commit (REQ-063 unchanged).
- Every pytest acceptance command runs as **`python -m pytest`** under the engine-resolved
  interpreter: a leading bare `pytest` is normalized (repo root importable); a leading
  `python`/`python3` keeps its existing rebind; a non-pytest command is unchanged.
- A `live` AC re-classified to `artifact` (**degrade**) leaves the standing develop gate and
  remains re-runnable via `steward revalidate`; lint accepts the degraded form.
- `/intake`, the handbook taxonomy, and `STEWARD.md` document the four lanes, the develop-gate
  routing, fail-hard-on-a-missing-declared-resource, the one-flavor `python -m pytest` rule,
  and the degrade (`live → artifact` + successor) lifecycle.

## Notes

- **Reconciling with REQ-063 (no contradiction).** REQ-063 has two facets: certification is
  atomic and the work commit is durable + surfaced; and an env-skip is not a *capture* gap.
  Decision 3 changes neither — it sharpens the develop **gate verdict** (a *declared* live
  test that skips → the gate is red), which only *withholds* the land; REQ-063 still ensures
  that red does not `reset --hard` the paid-for work. The tolerate-the-skip rule survives for
  **unknown** suite members; fail-hard is scoped to the lanes the engine knows must run.
- **Why not a separate "test-role" axis (the post-mortem's first sketch).** Two axes
  (`check:` intent + a pytest `live` marker) is exactly what conflated tier 2 and tier 3.
  One axis the engine reads end-to-end removes the second, fragile, consumer-owned degree of
  freedom. Subtraction over addition.
- **Degrade has no present second instance yet** — it is delivered as the *reclassification
  convention* (Decision 5) that Decisions 1+2 already make work, not as a `steward degrade`
  verb. If a real need for a recorded successor field or a one-shot verb ever appears, that is
  a named follow-on; do not build it speculatively.
- **Tech-agnostic posture.** The pytest-specific bits (project-wide node-id deselection, the
  `pytest → -m pytest` normalization) gate on `_is_pytest_command`; a non-pytest acceptance
  command keeps exit-code semantics, as today. This extends the engine's *existing* pytest
  awareness (JUnit XML parsing, the `python` rebind), it does not introduce a new violation —
  and it stays out of `steward lint`'s static reach for env-binding (REQ-064 Decision 1).
- **Out of scope:** the System-Test/validate phase mechanics (the artifact gate stays as
  REQ-030/051 built it); any `steward degrade` verb or successor frontmatter field (Decision
  5); FlowSteward's own consumer-side fixes (the REQ-022 fixture, the feed dead-letter REQ) —
  those are FlowSteward's; branch/topology (trunk-based, unchanged).
- **Localization:** all schema/lint/engine/skill/handbook/manual text is technical English;
  no user-facing localized strings introduced.
- **Surfaces touched (to confirm at design):** the `check` enum in `devsteward/lint.py`
  (`CHECK_VALUES`) and `devsteward/core/model.py` (`AcceptanceCheck.check`); the develop-gate
  routing (`devsteward/core/executor.py` + `devsteward/profiles/req/verify.py` `ReqVerifier`,
  which must learn the project-wide artifact/manual node-id exclusion and run `live` as named
  tests with skip=red); the interpreter normalization in `devsteward/core/verify.py`
  (`_PY_PREFIX`/`_resolve_interpreter` extended to a leading `pytest`); the `/intake` SKILL.md
  (repo `.claude/skills/intake/` and stamped `devsteward/templates/.claude/skills/intake/`,
  kept identical); the handbook (`devsteward/handbook/_01-format.qmd` / `_03-workflow.qmd`);
  and the stamped `STEWARD.md` (`devsteward/templates/STEWARD.md`).
