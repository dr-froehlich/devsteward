## Context

REQ-051 made the System Tester's prohibition absolute: a missing lab fixture is a **hard
red**, the Tester **never improvises**, and committing the fixture upstream is *"a human's
call"* — the REQ's own closing line states it *"does not author fixtures for anyone."* That
built one jaw of a pincer. The other jaw was never built: **no rule obliges the builder to
produce the fixture.** The `/advance` Build step (skill §2) says only *"write the code **and**
the acceptance tests named in the REQ's `yaml acceptance` block"* — the `test:` *commands* —
and is silent on the **starting state** those commands run against: the seeded sample project,
the captured fixture, the lab setup that an `artifact`/`manual` acceptance criterion's
validation procedure rests on.

So a `manual`/`artifact` AC that needs a seeded fixture has **no owner under a duty to create
it.** REQ-051 punts it to a human, but no step prompts that human at the one moment it is cheap
(during Build). The gap stays invisible until the System-Test phase, where it detonates: the
only person present (the decoupled Tester) is *forbidden* to fix it, and the validation
deadlocks — a hard red that no step of the workflow can clear; only a human stepping outside
it can.

This was surfaced by **dogfooding REQ-068**: its AC6 specified a *seeded multi-lane fixture
project* (one hermetic `regression`, one `live`, one one-time `artifact` test) for a human to
drive a develop checkpoint against. REQ-068's Build never created it; the guided System-Test
session for REQ-068 AC6 came up, found no committed fixture, and correctly stopped — it may not
author one (REQ-051). The deadlock is not REQ-068-specific: it is structural, and it ships to
consumers, because the `/advance` skill is hardlinked into the stamped consumer template.

The fix is the missing production-side duty that mirrors REQ-051's prohibition-side. It is a
**method correction, not new machinery**: the engine already hard-reds a missing fixture at
validate time (REQ-051); we simply make the Build phase deliver it so validation is not
dead-on-arrival.

**Re-assessment (2026-10-10, amendment).** The REQ was re-read against the repo before
activation:

- **The trigger is closed, the gap is not.** REQ-068 is done: its AC6 was signed off after
  the owner built the seeded fixture by hand, outside this repo. That is the human
  intervention REQ-051 provides for, and it cost one stalled validation session. Nothing in
  the method changed, so the next fixture-needing validation meets the same pincer. The
  `/advance` Build step still says nothing about fixtures, and the handbook still carries
  only REQ-051's prohibition.
- **No recurrence so far.** Across the 21 ledgers under the shared engine on 2026-10-10, no
  REQ declares `process.fixtures`, and REQ-051's missing-fixture and improvised-fixture reds
  have never fired. REQ-068 AC6 is the only observed case.
- **The `/advance` skill now states the same principle for deploys.** REQ-089 added *"A proof
  that needs a deploy belongs in this session"*, because the System Tester *"runs in a fresh
  session that never sees the diff and cannot fix anything (REQ-030), so a deploy proof
  routed there has no repair loop."* The duty this REQ adds applies that reasoning to
  validation fixtures, so it belongs next to that bullet.

## Requirement

- The `/advance` skill **Build** step states that when a REQ carries `artifact` or `manual`
  acceptance criteria, the Develop phase must **build and commit on `dev`** every fixture,
  seeded sample project, and lab starting-state those criteria's validation procedures rest
  on — naming explicitly that the decoupled System Tester may **not** create them (REQ-051),
  so an undelivered fixture is a deadlock the Build phase alone can prevent. The duty sits
  next to the REQ-089 bullet *"A proof that needs a deploy belongs in this session"* in §2.
- The handbook **workflow** section documents the same build-side duty **next to** the REQ-051
  "fixtures are committed upstream; the System Tester never improvises" paragraph, so the
  prohibition and the production duty are read together as the two jaws of one rule.
- The repo `/advance` skill and the stamped template (`devsteward/templates/.claude/skills/
  advance/SKILL.md`) remain one file (inode-shared, REQ-096), so the duty ships to
  consumers.

## Notes

- **Both criteria run once, in validation (Decision 5).** The intake classified them as
  `regression` because the oracle, *"does the doc state the duty"*, is coupled and hermetic.
  The owner overruled that on 2026-10-10. Each one grades a copy the System Tester captures,
  so REQ-069 has a System-Test phase: the green develop gate only commits the work, and the
  REQ lands after `steward validate REQ-069`.
- **Residual + the named follow-on.** An instruction can be ignored, which is exactly how this
  gap arose. If forgetting recurs after this lands, the next step is a *left-shift engine tooth*
  — the develop land-gate refuses to defer a REQ to its System-Test phase while a declared
  validation fixture/lab asset is absent (firing REQ-051's check at develop-land instead of
  validate-time). The declaration surface it reads already exists (`process.fixtures`, REQ-051;
  corrected 2026-10-10, see Decision 3), but the tooth only helps once REQs actually declare
  their fixtures. It is a follow-on REQ, **not** built speculatively now.
- **REQ-068 AC6** was signed off and REQ-068 is done (2026-10-10 amendment). Its fixture was
  built by hand outside this repo, so REQ-069 owes it nothing.
- **The grading tests are new.** Both live in `tests/test_req069_fixture_duty.py` and read
  only the evidence dir (`DEVSTEWARD_EVIDENCE_DIR`). The develop gate deselects them as
  one-time validations.
- **Localization:** all skill/handbook/template text is technical English; no user-facing
  localized strings introduced.
