## Context

The park-and-surface **decision** mechanism exists so a headless `steward run` can raise its
hand at a genuine fork and wait for a human *without losing its place*: it records a question,
marks the step `BLOCKED`, and stops; `steward decision answer DEC` unblocks it on the next run.
That is the right tool for a real **choice** — an attended-session need, a skill-raised
question, the rework-vs-revalidate verdict on a red validation.

But two of the states REQ-053's forward-path audit enumerated are **not** choices — they are
mechanical failures that need a human to fix something out-of-band and then re-run:

- **State D — repair exhausted** (`executor.py:585-601`): develop went red, the engine spawned
  its full repair budget of fresh sessions, still red. It parks a decision *"gate still red
  after N attempts — needs a human."* There is no either/or; the only action is "look, fix, run
  it again."
- **State H — land refused** (`executor.py:434-448`): the develop work is green but no plan
  names the REQ, so the mechanical land gate refuses. It parks a decision *"add a plan."* Again
  no choice — add the file, run it again.

Routing these through *decisions* is exactly what made the mechanism feel like a
stalemate-generator. Answering a decision flips the step back to `PENDING` — a **clean
restart** that abandons the partial work sitting in the tree — so the human answers, the engine
re-runs from scratch, hits the same wall, and re-parks. Round and round, nothing recovered.

The engine already has the honest verb for *"the prior work stands, run the step again and
assess what's in the tree"*: **`steward repeat`** (REQ-026, renamed by REQ-054), which flips a
`FAILED` step to `RECOVER` so the resuming session is handed the dirty tree plus a `--repeat`
brief (`executor.py:264-268`). And a red develop gate with **no** repair budget already does
precisely the right thing — it sets the step `FAILED` and `repeat` recovers it (the audit's
state A, `executor.py:340-343`). **State D is just state A after the budget runs out**, and
state H has the same shape: a mechanical failure that wants a re-run, not a question.

REQ-053's audit recommended *patching* `answer_decision` to carry the resume signal through a
decision-answered D/H re-run. The owner chose the sharper, subtractive move: **take D and H off
the decision mechanism entirely** and let `repeat` carry them. This adds no machinery —
`answer_decision` and `park_decision` are untouched; the parks simply stop *calling* the
decision machinery, set the step `FAILED`, and converge on the path that already works. The
decision surface is then left meaning only *"a human must make a choice or be present,"* which
is what it is good at.

One companion is required so the subtraction does not regress the human's guidance: today
`steward status` shows a `FAILED` step as a bare `✗ … failed` with no forward verb (the
next-action hint used to live in the parked-decision line, `cli.py:317-321`). A `FAILED` step
must now name its own forward path — `steward repeat REQ` — so D, H, and the pre-existing
`FAILED` states (A/B/G) all tell the human what to do.

## Requirement

Take the two non-choice stops — repair-exhausted (D) and land-refused (H) — off the
park-and-surface decision mechanism and route them to the existing `steward repeat` recovery
verb, and have the `FAILED`-step surface name that verb.

- On repair-budget exhaustion with the gate still red, the develop step is set `FAILED` (not
  `BLOCKED`), **no decision is parked** (no `decision_parked` event, no open decision for the
  step), the `repair_exhausted` event is still appended, and the unattended run continues to
  other independent steps rather than hard-stopping — converging on the no-budget red-gate path
  (state A).
- On a land-gate refusal (no plan names the REQ), the step is set `FAILED` (not `BLOCKED`), no
  decision is parked, the `land_refused` event is still appended, the ledger close is still
  committed (clean tree at rest), and the run continues to other REQs.
- `steward repeat REQ` recovers either failure: it flips the `FAILED` develop step to `RECOVER`,
  and the next driven run issues the develop command with the `--repeat` resume signal
  (`step_started` carries `recover: true`) so the resuming session assesses the partial work
  already in the tree instead of restarting clean.
- `steward status` names the forward verb for a `FAILED` step (`steward repeat REQ`); D and H no
  longer appear in `steward decision list`.

## Notes

- **Reframes the audit's recommendation #4.** The audit
  (`docs/reports/2026-06-19-process-resilience-forward-path-audit.md`, REQ-053) recommended
  patching `answer_decision` to carry the `--repeat` signal through a decision-answered re-run
  of D/H. The owner chose the subtractive alternative — take D/H off decisions entirely and
  route to `repeat` — because neither is a genuine fork; the decision mechanism should mean *"a
  human must choose or be present,"* not *"automation gave up / a file is missing."* The
  original working title ("carry the resume signal through decision-answered dirty re-runs") is
  therefore reframed: the signal is carried by `repeat`, which already exists, not by a new path
  through `answer_decision`.
- **State E is out of scope and already correct.** A red validation is a genuine fork — `rework`
  (develop was hollow) vs `revalidate` (the lab was broken; REQ-055) — so it stays on the
  decision mechanism, and `rework`/`revalidate` set `RECOVER` explicitly and already carry
  `--repeat`.
- **Out of scope: a mechanical land-retry.** State H re-runs a full develop session on `repeat`
  even though the work was already green and only the land gate refused. Carrying `--repeat`
  makes that session cheap (assess, don't redo) and matches today's cost, so this REQ does not
  add a "retry the land without re-running cognition" path. If that proves wasteful in practice
  it is a separate, named follow-on.
- **Test harness.** Reuses `test_phase_model.py`'s in-memory git + scripted-claude harness where
  the repair loop and mechanical land are already exercised. The two existing park-asserting
  tests — `test_repair_budget_then_park` (D) and `test_land_requires_plan_artifact` (H) — are
  rewritten to assert the FAILED-not-park behaviour; `test_repeat_resume_flag` is the reference
  for AC3's `--repeat` signal.
- **Process declarations:** defaults — fused develop, no concept phase, no lab. All ACs are
  `regression` (module-scope, coupled oracle — the engine's own ledger/executor/status surface);
  there is no artifact/manual check, so no System-Test phase. The `process:` block is omitted.
- **Localization:** all messages are operator-facing CLI/technical English; no localized UI
  strings.
