## Context

DevSteward's own test suite reds at random, and because `verify.full_suite` defaults to the
whole `python -m pytest` run, **any** random red gates **any** REQ's land. The cost is not
theoretical: a session that trusts the red goes hunting a phantom in unrelated code, and a
session that distrusts it learns to re-run reds until they go green — which is how a real
regression eventually sails through. The standing coping advice ("re-run the checkpoint before
believing a lone red") has been accumulating since 2026-07-17 and has now been written into
REQ-087's Notes and its plan. That is the point at which a workaround has become doctrine, and
the premise needs fixing instead of patching.

Measured on this box (Ubuntu 26.04 / Python 3.14.4) on 2026-08-06 during this intake:

- 8 runs of the three known-member files (`test_req077_atomic_flip.py`, `test_req081_halves.py`,
  `test_commit_integrity.py`) → **2 red**; a further 6-run batch → **2 more red**, one of which
  reddened two nodes at once.
- 5 runs of the **full** suite (366 tests) → **2 red**.

So roughly one run in three fails, and the affected node moves around: seven distinct member
tests have now been observed. Every one of them drives the engine's `advance_once()` /
land / validate machinery over a real temp git repo — which is the actual common factor, not
any property of the individual tests.

Contrary to the earlier working assumption, this is **not one flake**. It is at least two
independent engine defects with a shared symptom.

### Cause A — the evidence-dir mint collides with itself (fully diagnosed)

`validate._now_stamp()` (`devsteward/profiles/req/validate.py:98`) is
`datetime.now(timezone.utc).strftime("%Y%m%dT%H%M%SZ")` — **second** granularity. The two mint
sites (`validate.py:377`, `validate.py:639`) build
`.devsteward/evidence/<REQ>/<stamp>/` and call `mkdir(parents=True, exist_ok=True)`, so a second
validation starting inside the same wall-clock second silently resolves to the **same
directory** as the first. `_carry_forward` (`validate.py:886`) then walks the source evidence
dir and `shutil.copy2(p, dest)`s each file — where `dest` is now `p` itself:

```
SameFileError: PosixPath('…/evidence/REQ-001/20260806T050731Z/capture.txt')
           and PosixPath('…/evidence/REQ-001/20260806T050731Z/capture.txt') are the same file
```

This is deterministic, not racy in any deep sense: it fires exactly when the machine is fast
enough to do two validations inside one second, which a temp-repo test always is and a real
project occasionally is. It is also **already known and papered over** — `tests/test_req081_halves.py`
carries `time.sleep(1.1)  # the dated dir name is second-granular` at **two** sites (lines 139
and 335), and one of the tests it pads is literally named
`test_start_half_reentry_mints_fresh_evidence_dir`. The mint does not mint fresh; the test
sleeps until it does. That sleep both taxes every suite run and destroys the test's ability to
disconfirm the bug sitting next to it.

The blast radius reaches consumers: `steward revalidate` immediately after a `steward validate`
hits the same window, and the failure lands mid-mutation, so it surfaces as a rolled-back
`RecoverableError` rather than a legible error.

### Cause B — the land leaves its own flip uncommitted (undiagnosed)

The other observed shape is REQ-077's post-land guard firing:

```
RuntimeError: REQ-001:develop: land left 2 path(s) uncommitted after the code commit —
docs/requirements/REQ-001.md, docs/requirements/REQUIREMENTS_INDEX.md
```

The guard is doing its job — the concerning part is that it has anything to fire on. In
`_land_checked` (`executor.py:700`) the order is `_capture_gap` (which calls `_stage_code` →
`git add -A`, then `write-tree`, then runs the named acceptance tests against an archive
extract) → `on_verified` (writes the `done` flip into the REQ frontmatter and the index row) →
`_commit` → `commit_code` → `_stage_code` again → `git commit`. The second `git add -A` is
supposed to pick up the flip written moments earlier. Intermittently it does not, and the
commit lands without the flip.

This matters far more than test noise. It is observed in the **control half** of
`test_req077_atomic_flip.py::test_land_asserts_clean_tree_or_fails_loudly` — i.e. in the real
`advance_once()` path over a real git repo with no fakes in play. Same-commit discipline (the
REQ's frontmatter, its index row and the code moving together) is a house invariant; a land
that can drop the flip is a correctness defect in every consumer, and today only REQ-077's
guard stands between it and a silently inconsistent history.

The mechanism is genuinely unknown. The surviving hypothesis is a racy git index — `git add -A`
treating an entry whose stat data was recorded in the same timestamp window as
"racily clean" and declining to re-stage it — but it has never been confirmed, and it must be
proven or killed rather than assumed. Ruled out already: the old machine, the old OS and the
old Python (the flake survived the move to Ubuntu 26.04 / Python 3.14.4 unchanged, and got
*worse*).

### Why one REQ

Both defects present identically to the operator — "the suite randomly reds a land" — and
either one left standing keeps that symptom alive, including in the develop gate that would
have to certify a fix for the other. Splitting them would mean landing one behind a gate the
other can still red at random.

## Requirement

When this is done, the suite is deterministic because the two defects behind its randomness are
gone from the engine.

### Evidence-dir minting (Cause A)

1. Two evidence dirs minted at either mint site (`validate.py:377`, `validate.py:639`) within
   the same wall-clock second resolve to **distinct** paths. The stamp carries sub-second
   precision; no mint ever lands on a directory that already exists.
2. `_carry_forward` never copies a file onto itself. A scoped `steward revalidate` started in
   the same wall-clock second as the validation it carries from completes normally, carrying
   the green one-offs' artifacts into the fresh dir.
3. Evidence paths recorded in existing `events.jsonl` history (second-granular) continue to
   resolve — they are read back literally, never re-derived. No consumer migration.

### The land captures its own flip (Cause B)

4. A green land always commits what it wrote: the REQ frontmatter `done` flip and the index
   `DONE`-sync ride the one code commit, and the working tree is clean afterwards — every time,
   not almost every time. REQ-077's `_assert_committed_clean` remains in place as the guard; it
   simply stops having anything to fire on.
5. The mechanism is **named** (see Notes — confirmed, not hypothesised) and pinned by a
   deterministic test rather than left to the soak. Decision 8's fallback is not taken.
6. The fix only ever **widens** what the commit stages. `force_paths` names paths to re-stage
   content-blind; it can never restrict the commit, so REQ-079's whole-tree guarantee (and its
   standing seam guard) survives intact.

### The workarounds are subtracted

7. `tests/test_req081_halves.py` contains no `time.sleep` — both `1.1s` pads are gone and both
   tests pass without them.
8. The repo carries no active instruction to re-run a red instead of diagnosing it: the
   REQ-087 Notes and the REQ-087 plan surfaces that carry the flake caveat are marked superseded
   by REQ-088.

## Notes

- **Reproduction lever for the develop session.** `for i in $(seq 8); do .venv/bin/python -m
  pytest tests/test_req077_atomic_flip.py tests/test_req081_halves.py
  tests/test_commit_integrity.py -q; done` reds roughly 1 run in 3 on this box. The full-suite
  form (`.venv/bin/python -m pytest -q`, ~47s) reds about 2 in 5 and skews toward Cause A.
- **Observed member tests** (do not treat as a closed list — the common factor is driving
  `advance_once()`/land/validate over a temp repo, not the individual node):
  `test_req077_atomic_flip.py::test_checkpoint_commits_flip_clean_tree`,
  `test_req077_atomic_flip.py::test_land_asserts_clean_tree_or_fails_loudly`,
  `test_req081_halves.py::test_full_cycle_revalidate_scoped_carry`,
  `test_req081_halves.py::test_start_half_reentry_mints_fresh_evidence_dir`,
  `test_commit_integrity.py::test_declared_env_file_is_carried_into_extract`,
  `test_commit_integrity.py::test_no_env_file_keeps_hermetic_capture_path`,
  `test_commit_integrity.py::test_configured_env_file_name_is_honored`.
- **Cause B mechanism — CONFIRMED 2026-08-06, Decision 8's fallback not taken.** The
  racy-git-index hypothesis was right in outline and wrong in detail. Three conditions coincide:
  (1) the flip is **size-preserving** — `status: open` → `status: done` and `| OPEN |` →
  `| DONE |` are 4 bytes either way; (2) it lands in the **same wall-clock second** as the stat
  git cached when the capture gate staged the tree, and git built without `USE_NSEC` (the
  default) compares only seconds + size; (3) git's racy-clean content-check cannot rescue it,
  because that fires only for an entry whose cached mtime is at or after the *index file's* own
  timestamp — and the capture-gate extract pushes the index write seconds past the flip. The
  decisive dump, immediately before the land's `git add -A`:
  `cached entry mtime 1785994308:402866240 size 412` / `worktree mtime 1785994308.680900 size
  412` / `index file mtime 1785994320.336700` / `staged: []`. This is why the naive shell
  reproduction never reproduced — there the index is written in the same second as the file, so
  the entry *is* racy, git smudges it and content-checks it. The 12-second capture-gate gap is
  load-bearing.
- **The soak is the weaker oracle, deliberately.** Measured against a deliberately un-fixed
  engine, the 30-land soak catches the known Cause-B mechanism only about **1 run in 5** — it
  cannot force the wall-clock coincidence. AC5's deterministic test is what actually proves the
  fix; AC4 stands as a bound on the *invariant* (a land never leaves the tree dirty) and so on
  residual causes nobody has diagnosed. Raising the soak size buys little: at 60 lands the cost
  doubles and detection is still well under half. If the standing cost (~23s per develop gate)
  ever stops being worth it, cutting AC4 loses little proof — cutting AC5 would lose all of it.
- **Risk — a fixed clock is not a fixed filesystem.** AC1/AC2 pin the *stamp source*; if the fix
  were ever moved to depend on filesystem mtime resolution instead, the deterministic test would
  stop being deterministic. Keep the mint's uniqueness a property of the stamp.
- **Out of scope:** any change to `verify.full_suite`'s default (the whole-suite develop gate
  stays as-is — insulating the gate was considered and rejected, Decision 1); retry-on-red of any
  kind; REQ-077's clean-tree guard itself, which is correct and stays; the `live`/`artifact`/
  `manual` taxonomy; the general REQ-056 "repeat on a transient failure" doctrine in STEWARD.md
  and handbook `_03-workflow.qmd`, which is about environment/account transients and is not this
  workaround.
- **Operator-side follow-up at land:** the `clean-tree-assert-flaky-test` memory note becomes
  wrong the moment this lands and should be deleted rather than amended — it exists only to
  encode the coping advice Decision 6 retires.
- Sibling to the gating-integrity line: REQ-028 (a skip is not green), REQ-063 (a capture gap
  preserves a paid-for green), REQ-068 (deterministic routing by `check:`), REQ-070 (the gate's
  deselect set is real node-ids only). This one closes the last source of *random* gate verdicts.
