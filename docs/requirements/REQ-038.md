## Context

Surfaced live during REQ-034's dogfood (captured as **Finding 90**,
`.devsteward/evidence/REQ-034/20260614T034201Z/90-FINDING-cross-host-deploy-channel.md`):
a `manual` AC whose observation surface is on **another host** has no sanctioned way to
receive the implementation before land. FlowSteward REQ-024's AC6 — *deploy the stack on the
homelab and verify it serves* — proved it. The deployable artifact lived on exactly one ref
(the local feature branch), reachable by no deploy host; the only clean deploy channel
(`git pull` of a published ref) requires a **land-phase** action (push / branch / merge)
that the workflow defers **until after validation** — but the live-host AC is supposed to
*precede* land. Chicken-and-egg, and the System Tester is explicitly barred from
pushing/branching, so the gap is structural, not operator error.

The premise that *creates* the deadlock is **"deployment must be `git pull` of a ref."** The
standard CD pattern is **build once, promote the artifact**. If the validate phase *emits* a
clean release candidate (a `git archive` of tracked files only — no `.git`, no gitignored
cruft) and ships **that** cross-host, the artifact travels with **no ref published early**
and the ordering tension dissolves. A fix discovered live then returns as a **true `git
diff` patch** through the evidence channel — byte-identical to what was tested, not a lossy
prose re-description — and is applied on the dev host through the rework loop (REQ-033). The
deploy host never commits, never touches `origin`, and never holds the full repository.

Routed (Peter, 2026-06-14): its own REQ, leaning **option A (artifact-export)** over option
B (publish a feature/`rc` ref to `origin`) — B leaves an unvalidated ref on `origin` and
makes the most-exposed host a committer to shared history, the exact divergence that crashed
REQ-024's land. The A-vs-B fidelity worry was resolved: under A the fix still travels as a
real diff (a patch *is* a true code diff), so A loses no fidelity and additionally yields one
clean develop commit instead of live-debug history noise.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | **Deploy by artifact-export, not by publishing a ref (option A, not B).** Validate produces a clean release candidate from the validated ref — tracked files only, no `.git`, no gitignored files — and ships *that* cross-host; the deploy host runs the extracted artifact. No feature/`rc` ref reaches `origin`. | Build-once-promote dissolves the chicken-and-egg (the artifact travels without an early ref publish) and keeps "feature branches stay local." B would put an unvalidated ref on `origin` and make the exposed deploy host a committer to shared history. |
| 2 | **The RC materializes on the deploy host as a thin one-commit git repo** (seed: `git init && git add -A && git commit -m "RC <req> @<sha>"`), not a bare tarball; the deploy host never receives the full repository. | It stays an *artifact* (no branches, no history, no `origin` remote), but a single RC commit gives `git diff` for free — so a live fix produces a clean, faithful patch with zero coupling to the real repo. A full repo on a production box (source + history + push path on the most exposed machine) is the anti-pattern this avoids. |
| 3 | **A live fix returns as a `git diff` patch captured into the validation evidence dir; the dev host applies it through the rework loop (REQ-033) as a develop commit. The deploy host never commits to or pushes the project repo.** | The evidence dir already travels back — reuse it, no new channel. A patch is a true code diff (identical bytes to what was tested green), so fidelity is preserved. Authoring the commit on the dev host keeps the single-writer code plane (REQ-037) and yields one clean commit, not live-debug noise. A change that never reached a tracked file (a hand-edited running container) survives no rebuild and so is out of scope for both A and B. |
| 4 | **The candidate is frozen at the green verdict:** the engine lands the *exact* ref the RC was exported from. A change to the RC after the green verdict invalidates the candidate and requires re-validation. | Build-once-promote: what was validated is what ships. Silently absorbing a post-verdict change would land unvalidated bytes. |
| 5 | **The export/deploy is a first-class engine-owned step inside validate** (the missing publish-for-validation hop), parameterized by source ref: the feature branch for an isolated RC, or `dev` for an integrated build. | Finding 90's gap is precisely that validate has no publish hop. Making the export target any ref also answers "give me a robust way to test the integrated `dev` version," not only the feature branch. |

## Requirement

Give the validate phase a sanctioned cross-host artifact channel that respects the branching
model:

- `steward` exports a clean release candidate from a given ref — tracked files only, no
  `.git`, no gitignored content — equivalent to `git archive` of that ref, and ships it to a
  deploy host where it materializes as a thin one-commit repo. No feature/`rc` ref is pushed
  to `origin`.
- A fix made on the deploy host is captured as a `git diff` patch into the run's evidence
  dir; on the dev host the rework loop applies that patch to the source ref as a develop
  commit. The deploy host never commits to or pushes the project repo.
- On a green verdict the engine lands the exact ref the RC was exported from; an RC modified
  after the verdict is detected and refused (re-validate).
- The export step is owned by the engine within validate and targets any ref (feature branch
  or `dev`).

## Notes

- **Out of scope (own REQs / later):** option B (publishing a feature/`rc` ref for pull) —
  rejected in Decision 1; placing the full repo on the deploy host (Decision 2); a 3-way
  merge of divergent live fixes (Decision 3 — single clean patch via rework); a container
  **image registry** pipeline — Decision 1 ships a `git archive` first; an image-based RC is
  a natural later variant of the same channel, not required here.
- **Relationship to REQ-037:** depends on it. The pure-code feature branch and fetch-first
  atomic merges are what make "land the exact validated ref" and "absorb a live fix" safe;
  without REQ-037 the deploy host as a committer reproduces the original crash.
- **Relationship to REQ-033 / REQ-034:** the rework loop is the return edge that lands the
  live-fix patch; the guided validate session (REQ-034) is where the export/deploy step
  lives and where the operator is walked through the cross-host procedure.
- **Process declarations:** defaults — fused develop, no concept phase. **No devsteward lab**
  (`lab: []`): AC1–AC4 run headless on synthetic real-git repos in a temp dir; AC5 re-uses
  FlowSteward + the homelab (consumer-repo reality, the REQ-030 AC8 / REQ-034 AC6 / REQ-036
  AC5 precedent).
- **Localization:** engine/CLI text is technical English; no user-facing localized strings.
