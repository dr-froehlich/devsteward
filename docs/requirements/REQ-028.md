## Context

A consumer (FlowSteward) drove three requirements in a row at the *same single behaviour* —
"prove the IMAP adapter opens a real socket" — and all three reached green without that
socket ever being part of a gate that can fail. Two post-mortems record the mechanics
(`flowsteward/docs/postmortems/2026-06-09-req-003a-live-test-never-ran.md` and
`…-req-006-live-test-still-not-gated.md`). The engine behaved exactly as written; the holes
are structural, and they are *this* engine's to close.

REQ-015 already gave land **teeth**: a land step cannot pass on marker-trust, and its named
acceptance tests are re-run for real. But REQ-015 equates *exit-0* with *green*, and four
things slip through that equation:

1. **A `pytest.skip` exits 0, so a skip lands as a pass.** FlowSteward REQ-003a's live test
   ran and reported `1 skipped`; the engine recorded `ok: true` and the step landed. A
   "prove X" test that declines to run is indistinguishable from one that proved X.
2. **The named behaviour can live entirely outside the REQ that owns it.** FlowSteward
   REQ-006 ("make the live test run") named only offline loader tests in its own
   acceptance block; the live socket test belonged to a *dependency* and was never invoked
   at REQ-006's land. A REQ certified itself green while delegating its headline proof to a
   test it does not run. A typo'd or non-existent test id would likewise "pass" by
   collecting zero tests.
3. **The verifier doesn't run in the project's real environment.** Both FlowSteward REQs
   first failed land with `[127] pytest: not found` — the verifier shelled into a context
   without the project venv. A `done` must be impossible *because the suite couldn't be
   run*, not waved through later.
4. **Nothing reconciles the REQ marker against the ledger.** FlowSteward REQ-003a's
   frontmatter was hand-edited to `status: done` while the ledger's last land event for it
   was `failed`. `steward lint` checks frontmatter↔index agreement but never cross-checks
   the ledger, so a `done` over a `failed`/absent land is invisible.

REQ-027 (the acceptance-taxonomy + intake seeding REQ) attacks the *upstream* cause — a
self-authored mock as the only oracle — but it explicitly leaves lint blind to test
quality/scope, and its System-Test phase (which would *run* validation checks) is a named
follow-on. This REQ is the **runtime/lint enforcement complement**: regardless of how an AC
is classified, the engine must refuse to call a step done when its named behaviour did not
actually, observably run and pass — and lint must refuse a `done` the ledger contradicts.

A no-network/skippable test is still legitimate (FlowSteward keeps a clean checkout green by
skipping the live test). The rule is narrower: a **skip cannot satisfy a gate**. If the
clean-checkout path must stay green, the skippable test must not be the *only* evidence for
the behaviour — but that is a house-style/intake concern (REQ-027), not something this REQ
lints. This REQ guarantees only that when a named acceptance test runs under a land gate, a
skip, a zero-collection, a missing venv, or a marker the ledger contradicts all read as
**not green**.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | At land, `ReqVerifier` treats a named acceptance test that reports **skipped** as a gate **failure**, not a pass — exit-0 is no longer sufficient; the engine reads the per-test outcome and requires `passed`. | Directly closes the REQ-003a hole: a "prove X" test that doesn't run must not certify X. A skip and a pass stop being the same signal. |
| 2 | At land, a named acceptance test command that **collects zero tests** (typo'd/renamed/unowned id, or an empty selection) is a gate **failure**. | A REQ cannot certify itself by naming a test that does not exist or by delegating its proof to a selection that runs nothing. The named behaviour must actually execute. |
| 3 | At land, in addition to each AC's named tests, the engine runs the project's **full suite**; any `failed`/`error` anywhere marks the land **FAILED**, even when every named AC test is green. | A real, unambiguous failure on the very behaviour under discussion must have a path to turn the status red. A per-AC gate that never runs the rest of the suite lets a known-broken behaviour ship green (FlowSteward REQ-006). |
| 4 | The verifier executes the test command through the **project's configured environment** (venv/interpreter resolved from project config), so `127 pytest: not found` cannot masquerade as "not yet verified". A configured-but-unusable environment is a hard, surfaced error, never a silent skip-ahead. | A `done` must never become reachable *because* the verifier couldn't run the suite. The `[127]` misses in both FlowSteward REQs were environment resolution, not test failures. |
| 5 | `steward lint` gains a **marker↔ledger reconciliation** rule: a REQ whose frontmatter is `status: done` while the ledger's terminal record for it is not a green land (it is `failed`, `open`, or absent) is a hard lint error. | The false `done` was a hand-edit lint never inspected. Frontmatter, index, and ledger must agree; the ledger is the cursor of record. This is the highest-leverage single guard from the first post-mortem. |
| 6 | Scope: this REQ is **runtime/lint enforcement only**. It does not build the System-Test phase, the `check:` taxonomy, or any lab/intake house-style shaping — those are REQ-027 and its follow-ons. It strengthens REQ-006/REQ-015's *implementation*; their specs stand, so `supersedes` is null. | Keep the umbrella to the four gating holes the post-mortems proved. The upstream "what makes a good AC" work lives in REQ-027; this is the floor under it. |

## Requirement

The engine refuses to mark a `land` step `DONE` unless its named behaviour observably ran
and passed, and `steward lint` refuses a `done` the ledger contradicts:

- A named acceptance test that reports **skipped** does not satisfy the land gate — the
  verifier reads per-test outcomes and requires `passed`; an all-skipped run is FAILED.
- A named acceptance test command that **collects zero tests** is FAILED — a REQ cannot pass
  by naming a non-existent, renamed, or unowned test id.
- At land the engine also runs the **full project suite**; any failure/error anywhere marks
  the step FAILED even if every named AC test passed.
- The verifier runs the test command in the **project's configured environment** so a
  missing interpreter/venv is a hard surfaced error, never a pass-through; `127 pytest: not
  found` cannot reach a green land.
- `steward lint` hard-errors when a REQ's frontmatter `status: done` disagrees with the
  ledger's terminal record for that REQ (not a green land).
- The pre-existing guarantees hold unchanged: `design`/`build` still pass on marker-trust
  (REQ-015 Decision 2); a clean checkout that legitimately *skips* a network test stays
  green **as long as that skip is not the sole evidence the land gate runs** — i.e. a land
  whose only named test skipped is now FAILED, not green.

## Notes

- **Relationship to REQ-015:** this extends `ReqVerifier` — REQ-015's spec (no marker-trust
  at land; re-run named tests) stands; AC1–AC3 sharpen "green" to mean *passed*, *collected*,
  and *suite-clean*, not merely exit-0.
- **Relationship to REQ-027:** complementary, not overlapping. REQ-027 shapes *which* ACs a
  REQ should carry (system-level, artifact-bound, classified) at intake; REQ-028 enforces
  that whatever is carried *actually runs and passes* at the gate, and that the marker can't
  outrun the ledger. Neither depends on the other landing first.
- **Skip stays legal, just not load-bearing:** a network/integration test may still skip on a
  clean checkout. AC1 only forbids a skip from being the evidence a *land gate* accepts — so a
  REQ that must prove a runtime behaviour cannot do it with a test that skips in the gate's
  environment. Keeping the clean-checkout suite green while still proving the behaviour
  elsewhere is the intake/house-style job (REQ-027), deliberately out of scope here.
- **Localization:** all engine/lint/handbook text is technical English; no user-facing
  localized strings introduced.
- **Expected surfaces (to confirm at design):** the REQ-profile verifier
  (`devsteward/profiles/req/source.py` / `ReqVerifier`) and the generic command verifier
  (`devsteward/core/verify.py`) for AC1–AC4; the executor wiring for the full-suite land gate
  (AC3); environment/venv resolution used by the verifier (AC4); and `devsteward/lint.py`
  plus the ledger reader for AC5. The handbook (`02-engine.md`) is updated to state the
  sharpened guarantee.
- **Out of scope (own REQs):** the System-Test/validation phase and the `check:` taxonomy
  (REQ-027 and its follow-ons); any per-phase work-evidence gate for design/build (rejected
  in REQ-015); and intake-time house-style shaping of acceptance criteria.
