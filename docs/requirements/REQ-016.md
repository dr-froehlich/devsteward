## Context

`core/claude.py::_classify` decides whether a headless `claude -p` session hit a usage
limit by serializing the **entire** stream — `json.dumps(lines).lower()` — and substring-
matching `_LIMIT_MARKERS` (`"usage limit"`, `"rate limit"`, `"quota"`, `"exceeded your"`,
…) anywhere in that blob. But `lines` includes every `tool_result` event, i.e. the verbatim
contents of every file the session `Read`, and every `assistant` text block. So the detector
fires on *content the session handled*, not on Claude's runtime control signal.

This is self-poisoning: any REQ whose work touches the quota code path trips the quota
detector. On 2026-06-07 `steward run` drove **REQ-011:design**, which had to read
`executor.py` and `claude.py` — files that literally contain the marker table
(`claude.py` *is* `_LIMIT_MARKERS`; `executor.py` carries `"claude usage limit"`). The
design completed correctly and emitted a full advance summary, but `_classify` returned
`USAGE_LIMIT` (twice: 21:05 and 23:08). `run_step` then reset the step to `PENDING`
(`executor.py:158-162`) and the run loop broke (`executor.py:280-282`), discarding a
finished checkpoint. The work was recovered manually (commit `b11181f`); this REQ fixes the
root cause so the engine stops dropping real work.

Fourth reality-boundary defect of the family in
`docs/plans/0002-reality-harness-and-engine-repair.md` (REQ-012 cswap fingerprint,
REQ-013/REQ-014 reality harness, REQ-015 verify teeth): the engine conflates *"Claude's
runtime signalled a limit"* with *"the text Claude read or produced contains the words
'usage limit'."* A real limit is a control-plane fact Claude emits when it stops; it is not
arbitrary text in the transcript.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Classify the limit from the **runtime signal**, not from transcript content | A usage limit is something Claude's runtime reports as it stops; matching it against echoed file contents or assistant prose is the defect itself |
| 2 | Scan only the events that carry the runtime's own verdict — the terminal `result` event (its `subtype`/`is_error`/`result` text) and any `system`/error event — and exclude `tool_result` and `assistant` content from the marker scan | `tool_result` echoes files (which may *be* the marker table); `assistant` prose can legitimately discuss limits. The result/error event is the truthful, content-independent signal |
| 3 | A session that completed normally (terminal `result` with no error/limit subtype) is **OK** even if its transcript quotes limit markers | The exact false positive observed: a clean, finished design whose only marker hits were in source it read |
| 4 | Keep the `_LIMIT_MARKERS` table; only narrow *where* it is applied | The human-readable substrings are still the signal — they must just be read from the runtime verdict, not the whole stream. No behaviour change for a genuine limit |

## Requirement

The engine classifies a usage limit only from Claude's runtime control signal, never from
content the session read or produced.

1. `_classify` determines `USAGE_LIMIT` from the terminal `result` event (and any
   `system`/error event) — not from a blob of the entire stream including `tool_result`
   and `assistant` text.
2. A completed session whose limit-marker occurrences appear **only** inside read/produced
   content (e.g. DevSteward's own `_LIMIT_MARKERS`, or a plan that quotes `"usage limit"`)
   is classified `OK`, not `USAGE_LIMIT`.
3. A genuine usage/rate limit — the runtime's terminal/error event carrying the limit — is
   still classified `USAGE_LIMIT`, so `run_step` still resets the step to `PENDING` and the
   run still stops (no regression of the real degradation path).
4. The executor consequently verifies, commits, and advances a completed step whose output
   merely echoed marker text, instead of dropping it.
