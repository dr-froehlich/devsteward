## Context

The three-session-per-REQ split (design / build / land as separate `claude -p` sessions)
tripled the fixed cost of every requirement while two of the three gates verified nothing.
The FlowSteward run: 29 headless Opus sessions for 8 small REQs, orientation-dominated
(0.5–7 min each), with roughly two thirds being design/build checkpoints the engine
accepted on marker trust. None of the postmortem failures were prevented by the session
boundaries; all are closed by gate semantics (REQ-028) and intake quality (REQ-027). Cost
≈ sessions × (orientation tax + work), and no cache survives across cold `claude -p`
sessions — so the fix is **fewer, larger, verified sessions**, not less tooling.

Fleshed out 2026-06-10 (interview, plan 0011 step 2): the provisional direction is
confirmed and the open mechanics of the stub's row 6 are settled in Decisions 6–10 below.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | The REQ profile's step source emits **one `develop` step** per REQ (replacing design + build). The plan artifact in `docs/plans/` remains **required** — plan-first discipline survives inside the session; only the session boundary is dropped. | The design→build handoff forced build to re-ingest through the plan file what design already held in context. The plan survives as an artifact, the boundary doesn't. |
| 2 | On a green develop gate, **land is engine code** — status flip, index `DONE`-sync, one commit, `--no-ff` merge (REQ-020 machinery). **Zero Claude tokens.** | Keeping a Claude session at land pays Opus to watch pytest run. REQ-028 made the verifier the authority; the flip/commit/merge are deterministic. |
| 3 | On a red gate, the executor spawns a **bounded repair session** — budget **2** attempts (adopted, plan 0011), then the step parks for a human. The repair session inherits land's real historical function (both FlowSteward "failed lands" were environment problems a repair loop would have surfaced immediately). | Full-cost cold retries on every red were a major cost driver; a bounded repair loop with an explicit park is cheaper and honest. |
| 4 | **Per-step-kind model/effort config:** develop defaults Opus-high; repair defaults **Sonnet** (adopted, plan 0011); CLI/config overridable. The validate step kind (REQ-030) inherits the same config surface. | Uniform Opus-high for mechanical work was the third cost driver. |
| 5 | A REQ whose intake declared **split** (REQ-027 `process.develop`) gets an attended design review before develop; fused is the default. | Default fused, exception declared while a human is present. |
| 6 | **Plan gate (interview):** the mechanical land refuses to land a REQ when no file in `docs/plans/` names its REQ id — a grep-shaped existence check at the moment that matters. The engine verifies *existence*, never plan quality. | Skill-discipline-only is the marker-trust failure mode again; a lint rule would fire during the whole develop window before the plan can exist. The land gate is the one place the check is both cheap and load-bearing. |
| 7 | **Ledger migration (interview): reinterpret, no rewrite.** The step source emits only the new step ids; old `design`/`build` entries stay in `state.yaml`/`events.jsonl` as history and are ignored for eligibility. A REQ with a green `land` stays done; a REQ caught mid-flight gets a fresh `develop` step — half-done work survives in git, the cursor restarts cleanly. | The event log is append-only (audit contract); a shim that reads marker-trusted design/build pairs as develop-done would re-extend the exact trust REQ-028 revoked. |
| 8 | **Repair context (interview): fresh session + failure brief.** Each repair is a cold session fed the gate's failure output (failed test ids, verifier detail, REQ id) — no `--resume` of the develop session. | Cross-model resume (Opus develop → Sonnet repair) gets no cache benefit, couples repair to claude-CLI session persistence, and inherits the very context that produced the red. Sonnet makes the cold-start tax cheap. |
| 9 | **Human-presence flags park in batch (interview):** `steward run` treats a REQ declaring `develop: split` *or* `concept: true` as batch-ineligible — it parks a decision naming the attended need ("declared split — needs an attended design review" / "declared a concept phase — needs an attended session") and moves on. One shared rule for both flags. Full concept-phase mechanics stay a future REQ. | Split/concept mean a human chose to be present; batch honors that instead of simulating it or silently skipping. An inert declaration the engine ignores would lie. |
| 10 | **The e2e proof is an acceptance criterion (interview):** one trivial REQ driven green end-to-end by a real `steward run` under the new model, evidenced by `events.jsonl` (develop → mechanical land, zero Claude invocations at land) and the merged commit, reviewed by a human — `check: manual` per REQ-027 D12. REQ-029 stays `in-progress` until that run happens. | Plan 0011 demands this proof before `steward run` is trusted again; a REQ claiming "mechanical land works" that was never observed doing one for real is the hollow-green shape. Human oracle, no owned lab → `manual`, honestly. |

## Requirement

Rework `profiles/req/source.py` and the executor loop:

- One **`develop`** step per REQ replaces design + build. For a REQ with default
  process declarations it is the only Claude session in the happy path.
- On a **green** develop gate (REQ-028 semantics) the engine performs the **mechanical
  land** itself — status flip, index sync, single commit, `--no-ff` merge, ledger
  advance — invoking no Claude. The land refuses when no `docs/plans/` file names the
  REQ id (Decision 6).
- On a **red** gate the executor spawns at most **two** repair sessions (fresh context +
  failure brief, configured model/effort, default Sonnet), then parks the step.
- Model/effort are configurable **per step kind** with documented defaults
  (develop: opus/high, repair: sonnet).
- A REQ declaring `develop: split` or `concept: true` is **batch-ineligible**: `steward
  run` parks it with a decision naming the attended need (Decision 9).
- Existing ledgers are **reinterpreted, never rewritten** (Decision 7).

Do this **before** REQ-030 so the System-Test phase plugs into the final step model.
