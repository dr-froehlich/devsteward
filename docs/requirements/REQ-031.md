## Context

REQ-027 defined the lab: a shared, versioned fixture whose **provenance** — reality-
derived, owned, built by its own REQ — is what gives an `artifact` check trustworthy
decoupling. The canonical anti-pattern it replaces is FlowSteward REQ-003 AC1's "fixture
IMAP server" that was the build agent's own in-memory double, authored in the same step
as the code it certified. This REQ puts the first real lab to work. The lab itself —
tooling, reality-derived seed corpus, provenance notes — was built **in its home repo**
as FlowSteward REQ-008 (landed 2026-06-11): FlowSteward owns the mail domain, the
dedicated test account, and the credentials, and the engine's `process.lab` references
are registry-local, so only a REQ in FlowSteward's registry can gate its future
validations. DevSteward's part is the **pattern and the consumption**: document the
consumer-owned-lab pattern in the handbook, and drive the first end-to-end validation —
a live-socket fetch captured as evidence and graded by the lab's own offline verify,
plus the re-drive of FlowSteward's REQ-003a/006/007 surface, signed off by a human.

This REQ is intentionally the **first consumer** of everything before it: REQ-027's
taxonomy routes it, REQ-029's step model schedules it, REQ-030's phase executes it.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | **No owned test server.** The lab targets the *real internet mail server* — the dedicated external IMAP test account FlowSteward's REQ-003a established (Dovecot, IMAPS; never a production inbox). (Peter, 2026-06-11.) | Provenance does not get more real than production mail infrastructure over a live TLS socket; a containerized double would re-introduce exactly the distance the lab exists to remove. |
| 2 | **The lab lives in FlowSteward** (its REQ-008, `labs/imap/`): stdlib-only `lab.py` + sanitized reality-derived corpus + provenance README. DevSteward ships no domain fixtures. (Peter, 2026-06-11.) | The consumer owns the domain, account, and credentials; `process.lab` is registry-local; consumer labs in DevSteward would make the generic engine a fixture zoo. |
| 3 | The seam is `DEVSTEWARD_LAB_IMAP_ENV` → the FlowSteward checkout's `.env`; the lab tool is `<checkout>/labs/imap/lab.py`, invoked by path with any interpreter. No real paths or secrets committed on either side. | Self-contained oracle, sanitized public repos, one variable locates both credentials and lab. |
| 4 | AC2's artifact gate grades the captured fetch through the **lab's own offline verify** (`lab.py verify --against FILE`, exit code is the contract) — DevSteward holds no copy of the golden manifest. | One owner for the golden expectation; a copied manifest would drift and re-couple the oracle to this repo. |
| 5 | Skip/red semantics at the gate: no evidence at all → skip (clean checkouts stay green; the validate gate counts skip as red); evidence present but lab unreachable/unset seam → **failure**. | The missing-artifact hard red (REQ-030 D3) and the lab-skip-is-red rule, expressed in pytest semantics. |
| 6 | The handbook (03 · workflow) documents the consumer-owned-lab pattern the first lab set: consumer repo, real-system-first, self-contained, hard-failing config, reality-derived versioned corpus. | The pattern is DevSteward's durable deliverable here; the next consumer should not re-derive it. |
| 7 | The re-drive runs FlowSteward's own live e2e surface (`tests/test_req003a_e2e.py`) in the FlowSteward checkout during this REQ's validate phase, output captured verbatim as evidence; the human sign-off (AC3) reviews it against the postmortems. Evidence events in **FlowSteward's own ledger** for its surface are future FlowSteward intake work (REQ-008 is the lab; re-validating 003a/006/007 there needs artifact ACs declared there). | Consumer outcomes measured now, with the engine we have; cross-repo ledger writes are not a thing. |

## Requirement

phase proves the full arc end-to-end against FlowSteward's IMAP lab: the System Tester
brings the lab up through the env seam, captures a live-socket fetch of the seeded
message and a real run of FlowSteward's REQ-003a/006/007 surface as evidence, the engine
grades the fetch through the lab's own offline verify, and a human signs off the
re-drive.

## Validation procedure (for the System Tester)

> **For whoever runs `steward validate REQ-031`:** export `DEVSTEWARD_LAB_IMAP_ENV` in
> *that* shell too — the engine runs AC2's artifact gate in its own environment, not the
> System Tester's session (which sets the variable only for itself). An unset seam with
> evidence present is a deliberate hard red.

1. Set `DEVSTEWARD_LAB_IMAP_ENV` to the FlowSteward checkout's `.env`
   (e.g. `~/projects/flowsteward/.env`); the lab tool is `labs/imap/lab.py` next to it
   (FlowSteward REQ-008 — make sure the checkout has it). Missing → stop, hard red.
2. Bring the lab up and log it: `python <checkout>/labs/imap/lab.py status` then
   `... seed`, output appended to `<evidence>/imap-session.log`.
3. Capture the live fetch: `python <checkout>/labs/imap/lab.py fetch --out
   <evidence>/fetched-seed.eml` (what AC2's engine-run gate grades via the lab's verify).
4. Re-drive FlowSteward: in the FlowSteward checkout run its live e2e surface
   (`.venv/bin/python -m pytest tests/test_req003a_e2e.py -v`) and capture the verbatim
   output to `<evidence>/flowsteward-redrive.txt`. A skip in that run is a finding, not
   a pass — report it.
