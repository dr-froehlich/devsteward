## Context

DevSteward's house style is a two-line branching model: `main` is production (release
tags are cut there; consumers pin them), and an integration branch (`dev`) is the default
working and merge target, with REQ-sized work going on feature branches that merge into
the integration branch with a plain local merge (no PR — PRs are reserved for the
`dev → main` release).

Today that rule is **doc-only**. It is asserted in four consumer-facing places
(`templates/CLAUDE.md.tmpl`, `handbook/00-method.md`, `handbook/03-workflow.md`, the
`bootstrap` skill) but the engine does not enforce it: `Executor._git_commit` runs
`git add -A && git commit` on whatever branch is checked out, so `steward run` on `main`
commits straight to production. Worse, `handbook/00-method.md` claims *"these are not
style preferences; the linter and the engine enforce them"* — which is **false** for
branch-before-main. This REQ closes that doc/reality gap so every future or migrated
consumer project inherits real enforcement, not just prose.

The engine already owns the other governance that automation must not be talked out of
(verification, park-and-surface); branch protection belongs in the same place.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Guard-only, not branch-management | The engine *refuses* to commit to production; it does not create feature branches or open PRs. Smallest surface that closes the gap; git topology stays the human's (and the docs') job |
| 2 | Precheck refusal (not park, not mid-run fail) | Branch is a whole-run precondition (the engine never switches branches), so check once up front before invoking `claude`. Park-and-surface is for *content* forks resolvable by `decision answer` — a wrong branch is an environment precondition, not a fork, and answering a decision can't switch a branch |
| 3 | Protect the production branch only | Block commits on `production_branch`; committing on the integration branch is allowed. Per-REQ feature branches stay encouraged by docs, not enforced by the engine (that would be branch-management, decision 1) |
| 4 | Always enforced, no opt-out flag | A disable switch is the first thing a tired run reaches for; strictness is the point. Migrated repos create an integration branch before running |
| 5 | Branch names are config, with defaults | `git.production_branch` (default `main`) and `git.integration_branch` (default `dev`) live in `.devsteward/config.yaml`, so repos using `master`/`release` and the engine guard agree on what "production" means |

## Requirement

The engine refuses to autocommit onto the configured production branch, and the branching
model is configurable and documented so consumer projects inherit it.

1. `Config` reads a `git` section with `production_branch` (default `main`) and
   `integration_branch` (default `dev`); absent config yields the defaults.
2. Before any step runs, the executor detects the current git branch; if it equals the
   production branch it **refuses** — invokes no `claude`, commits nothing, leaves the
   step `PENDING`, and surfaces a clear message naming the production branch and the fix
   (switch to the integration or a feature branch). This is a distinct run outcome, not a
   parked decision and not a step `FAILED`.
3. On any non-production branch the executor proceeds unchanged (commits and advances).
4. The four consumer-facing docs state the `main`/`dev` model (production vs.
   integration, feature-branch-per-REQ merged into integration with a plain merge,
   integration promoted to production via PR), and the stamped `config.yaml` ships the
   `git` section with defaults. `handbook/00-method.md`'s "the engine enforces them" claim
   is now true for branching.

## Notes

Non-goals (explicitly out of scope): auto-creating feature branches, opening PRs,
guarding the integration branch, any remote/push operations, and a config opt-out for the
guard. Detached HEAD is not the production branch, so it is allowed. Future work could
layer branch-management (decision 1) on top, but only behind its own REQ.
