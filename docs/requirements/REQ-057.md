## Context

Two documentation needs converge here, both surfaced by the REQ-047 trunk-based pivot and the
recovery-model work that followed it (REQ-053…056).

**Need 1 — the human handbook is stale.** The Quarto handbook (`devsteward/handbook/*.qmd`)
still describes the pre-REQ-047 world: feature branches, worktrees, engine-initiated switching,
and merge topology that no longer exists. Its recovery prose still names `steward recover` (a
verb REQ-054 renamed to `repeat`, deferring the prose to "a docs REQ"), has no `revalidate`
(REQ-055 deferred its docs here too), and predates REQ-056's "D/H aren't decisions" change. The
handbook now actively contradicts the shipped CLI. It needs a **complete revision** to
post-REQ-047 reality, with the recovery/forward-path model documented as one coherent section.

**Need 2 — there is no Claude-facing usage manual, so agents read the engine's source.** Peter
has repeatedly observed Claude, while driving DevSteward *from a consumer project* (FlowSteward),
parse the DevSteward package source to figure out how to use the tool and how to recover from
(often pre-REQ-047) states — e.g.:

> *"Let me check how the engine re-runs a failed step so I land this through its transaction
> rather than by hand."* → `sed -n '180,230p' devsteward/cli.py`

This is the wrong behaviour. **DevSteward should be treated like an encapsulated class that
hides its implementation**: a consumer (human or agent) interacts through the `steward` command
and its documented contract, never through the engine's internals. Reading `cli.py` couples the
consumer to private structure, surfaces dead pre-pivot code paths as if they were current, and
produces by-hand recoveries that bypass the engine's transaction boundary. The gap is concrete:
we ship a human-targeted handbook but **no concise, Claude-targeted usage manual for the
`steward` command**. The fix is to write that manual — the engine's *public interface* as an
agent reads it — ship it with the templates, stamp it into every new project, and point the
consumer `CLAUDE.md` at it so the agent reaches for the manual, not the source.

The two documents have different audiences and densities (a human reference guide vs. a terse
agent operating manual) but must agree on one thing: the current command surface. Both carry
`repeat` (replacing `recover`) and `revalidate`; and the bundled **skills'** prose — which
still says `recover` in `advance/SKILL.md` — is aligned to match (REQ-054 moved the `--repeat`
flag and code but left the verb-name prose to this REQ), preserving the skills↔template hardlink
discipline (`[[skills-hardlinked-to-templates]]`).

One behavioural fix rides along because documentation alone cannot close it. State F — a `manual`
acceptance criterion awaiting its human oracle — parks an async QA *decision* (REQ-034), but its
clear verb is `steward validate REQ`, not `decision answer`. If an agent runs `decision answer`
on that ticket (natural — it appears in `steward decision list`), the validate step flips to
`PENDING`, re-runs unattended, still cannot get the human, and **re-parks**: the same circular
trap REQ-056 removed for D/H. A guard refuses `decision answer` on a pending-validation ticket
and redirects to `steward validate`, so the documented path is also the only path.

black-box `steward` manual so it never needs to read the package source.

- The Quarto handbook is completely revised to post-REQ-047 reality (no feature-branch /
  worktree / switching / merge topology) and documents the recovery model as one coherent
  section: `repeat`, the `rework`-vs-`revalidate` root-cause choice, D/H → `repeat`, and the

  the recovery path out of every red/parked state without reference to DevSteward internals,

  not present `steward recover` as a live command.

## Notes

- **Why a manual rather than more handbook.** The human handbook is a reference guide; an agent
  needs a terse operating manual keyed to the command surface and the recovery verbs. They are
  separate documents with separate audiences — Peter's "two documents." Forcing the agent to
  read the human handbook (or worse, the source) is the leak this REQ closes.
- **Encapsulation is the principle, the manual is the mechanism.** DevSteward is an encapsulated
  unit; `steward` + its documented contract is the whole public interface. Reading `cli.py`
  couples consumers to private structure and resurrects dead pre-pivot paths. The Claude manual
  makes the black-box boundary real by giving the agent everything it needs on the public side.
- **Dogfooding.** The leak Peter observed is consumer-side (FlowSteward); when developing
  DevSteward *itself*, reading the engine source is legitimate. So the manual is primarily a
  consumer-facing template. If we want a live copy at the DevSteward repo root for dogfooding,
  the skills↔template hardlink pattern (`[[skills-hardlinked-to-templates]]`) is the maintenance
  approach; that copy is optional and not required by the acceptance.
- **State F vs REQ-056.** F stays a *decision* (it is a genuine human-present wait — a standing
  QA ticket belongs in `decision list`); only its wrong clear verb is guarded. This differs from
  D/H, which were not human-choice states at all and so came off decisions entirely (REQ-056).
- **Scope sizing.** This is a broad docs REQ (a full handbook revision + a new manual + template
  plumbing + skills + one guard). The develop phase may stage the deliverables, but they are one
  cohesive "make the documentation match the post-REQ-047 engine and give the agent a black-box
  interface" unit, so they land as one REQ per the owner's framing.
- **Process declarations:** fused develop, no concept phase, no lab. ACs 1–3 are `regression`
  (coupled oracles: the guard's behaviour, the stamping/reference, the verb strings); AC4 is
  `manual` (human oracle for revision completeness + black-box sufficiency), so the REQ has a
  System-Test phase but needs no owned lab asset (`process.lab: []`).
- **Localization:** the handbook, the Claude manual, CLAUDE.md, and skills are all English; no
  localized UI strings (house rule).
