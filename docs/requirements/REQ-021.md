## Context

Onboarding **memzy** onto the engine (plan
[0005-memzy-onboarding](../plans/0005-memzy-onboarding.md)) surfaced the one dialect
divergence the [[REQ-010]] gap table did not anticipate. The REQ-010 converter normalizes
memzy's 23 REQs cleanly — a trial run against memzy's **live** corpus lints down to exactly
**three problems, all one root cause**:

```
REQ-027.md: schema: depends_on.5: 'REQ-028p' does not match '^REQ-[0-9]{3}$'
REQ-028p.md: schema: id: 'REQ-028p' does not match '^REQ-[0-9]{3}$'
REQ-028p: missing a row in REQUIREMENTS_INDEX.md   (downstream of the same regex)
```

memzy deliberately authored `REQ-028p` (persistent cart) and `REQ-028s` (cart sharing) as
the two halves of an umbrella `REQ-028`, and planned `REQ-014a–d` the same way. The letter is
a **sub-part marker on an existing 3-digit number**, a real and reasonable way to split an
umbrella requirement after the fact without renumbering everything downstream of it. Only
`REQ-028p` is a live file today; the rest are roadmap entries.

DevSteward's format hard-codes `^REQ-[0-9]{3}$`, so it rejects the suffix outright. The
operator chose to **relax the format** rather than renumber memzy — renumbering would rewrite
memzy's references and break every `[[REQ-028p]]` backlink across its prose, imposing
DevSteward's numbering on a project that had its own coherent scheme. Widening the format is
the smaller, more honest change and is a legitimate generalization: "an umbrella REQ split
into lettered sub-parts" is a pattern worth supporting first-class, not a memzy quirk.

The relaxation is **purely lexical** (Decision 1): `REQ-028p` becomes a valid, *distinct*
id that merely shares a number prefix with `REQ-028`. The engine attaches **no** parent/child
meaning — no umbrella rollup, no family ordering, no lint that a `REQ-028` parent file exists.
That family-awareness would be a far larger change to sequencing and lint, and memzy does not
need it (the `REQ-028` umbrella file never exists; `028p`/`028s` stand alone). Pure-lexical is
the whole of this REQ.

The change surface is small because the codebase already treats ids opaquely: `reqfile.id`
reads the frontmatter string verbatim, `glob("REQ-*.md")` already matches lettered files,
`source.py` builds step ids as `f"{r.id}:{phase}"` and splits steps on `:` (suffix-safe), and
the **only** id-number regex in the engine is the index-row matcher `lint.py:_INDEX_ROW_RE`.
So the relaxation is three regexes plus guards proving the opaque paths really hold.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | **Purely lexical** suffix — `REQ-028p` is a distinct opaque id sharing a number prefix; the engine attaches no parent/child semantics (no rollup, no family ordering) | memzy needs only that the id validate and round-trip; family-awareness would touch sequencing + lint for no current consumer. Keep the format change minimal and the semantics unchanged |
| 2 | New id pattern `^REQ-[0-9]{3}[a-z]?$` — **one optional lowercase letter** | Exactly matches memzy's observed usage (`028p`, `028s`, `014a–d`); rejects `028ab`, `0281`, `028-2`. The letter is a suffix *on* the 3-digit number, never a replacement for it |
| 3 | Apply the pattern to **id**, **depends_on items**, and **supersedes** in both the package schema (`devsteward/schema/`, which `lint` loads) **and** the stamped template schema; widen `lint._INDEX_ROW_RE` to `(REQ-\d{3}[a-z]?)`. Leave the `SCN-` pattern untouched | These are the only three places the `REQ-NNN` format is enforced. The package + template copies must stay in sync or future `steward new` consumers get a narrower format than the engine. Scenarios are out of scope |
| 4 | **Step derivation is guarded, not changed** — add a test proving a reopened (active) lettered REQ yields `REQ-NNNx:design/build/land` and that a dependent's `depends_on` edge resolves to `REQ-NNNx:land` | `source.py` already uses `r.id` opaquely and splits on `:`, so no code change is expected — but the guarantee that a lettered REQ works *when reopened* must be pinned by a test, since memzy's lettered REQs land as `done` (no steps) and the path is otherwise unexercised |
| 5 | **Next-id allocation is an intake-skill instruction fix**, not a code change — both `intake/SKILL.md` copies gain "strip any trailing letter before taking the max" | The next-id rule lives in the skill markdown the model executes, not in a Python function. Without it, intake against memzy's lettered corpus could read `028p` as higher than `028` and skew numbering. The honest test for a skill-prose guarantee is a skill-content assertion, not a behavioral pytest |
| 6 | **Regression-pinned** — the existing dogfood lint and the REQ-010 memzy fixture corpus stay green, and a lettered-id fixture is added to that corpus | Widening a regex only *adds* matches, so every existing 3-digit id is unaffected; proving it against DevSteward's own corpus and an extended memzy fixture makes that explicit rather than assumed |

## Requirement

Relax DevSteward's REQ-id format to accept a single optional lowercase-letter suffix on the
3-digit number, purely lexically, with the engine's id-handling paths proven to tolerate it.

### Format change

- `^REQ-[0-9]{3}$` → `^REQ-[0-9]{3}[a-z]?$` for **id**, **depends_on** items, and
  **supersedes** in both `devsteward/schema/req.schema.json` and
  `devsteward/templates/docs/requirements/schema/req.schema.json`. The `SCN-` pattern is
  unchanged.
- `lint._INDEX_ROW_RE`: `(REQ-\d{3})` → `(REQ-\d{3}[a-z]?)`, so an index row for a lettered
  id is matched (clearing the "missing a row" false positive) and its status is sync-checked.

### Guards (pure-lexical paths proven, not changed)

- **Step derivation** — a reopened/active lettered REQ produces its three phase steps and
  cross-REQ dependency edges resolve. (`source.py` expected to need no change.)
- **Next-id allocation** — both `intake/SKILL.md` copies instruct stripping the letter suffix
  before computing the next id, so a lettered id never skews numbering.

### Out of scope

- **Family / umbrella semantics** — no parent-REQ rollup, no grouped ordering, no lint that a
  `REQ-NNN` umbrella exists for `REQ-NNNx`. Purely lexical (Decision 1).
- **Multi-letter or numeric suffixes** (`028ab`, `028-2`) — single `[a-z]` only (Decision 2).
- **The `SCN-` id format** and converting memzy's scenarios — unchanged / [[REQ-010]] scope.
- **Running the converter on memzy or seeding its ledger** — plan 0005 Pieces 2–5; separate
  acts after this REQ lands.

## Notes

- **Why this is honest, not a special case.** memzy's lettered scheme is a sound way to split
  an umbrella REQ; encoding it in the format (rather than renumbering one project to fit)
  generalizes DevSteward instead of bending memzy. The relaxation is strictly additive — every
  existing 3-digit id validates and behaves identically — so it cannot regress a native repo.
- **The change is small because the design was already opaque.** The audit found a single
  id-number regex in the whole engine (`_INDEX_ROW_RE`); ids otherwise flow as strings.
  Decisions 4–6 are guards that *prove* that opacity holds, not new machinery.
- **Generalization path.** Once landed, plan 0005 Piece 2 runs the [[REQ-010]] converter on
  memzy in place and lint goes green; Pieces 3–5 (ledger seed, scaffold stamp, CLAUDE.md
  reconciliation) complete the onboarding. The unbuilt ledger-seeder for already-finished
  corpora is a likely sibling REQ, not part of this one.
