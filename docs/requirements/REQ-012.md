## Context

`CswapAccountProvider` (REQ-008) was lifted from the `run_batch*.py` quota machinery and
assumes `cswap` is a *command wrapper*: `precheck()` calls `cswap status` and
`claude_argv()` builds `cswap exec claude …`. The installed **claude-swap 0.11.2 has no
such interface**. It is an *account switcher* — a flag-based CLI (`--switch-to N`,
`--slot N`, `--status`, `--list`) that mutates the active account in `~/.claude.json`,
after which you invoke plain `claude`. There is no `exec` subcommand and no `status`
positional.

The consequence is a silent, total breakage of unattended runs. The engine launches

```
cswap exec claude -p "/advance …" --output-format stream-json --verbose
```

which argparse rejects instantly (`exit 2`). `claude` never starts. The executor
classifies the non-zero exit as `Outcome.ERROR` and marks the step **failed** — with
`step_started` and `step_failed` stamped at the *same second* in `events.jsonl`, the
fingerprint of a launch that never happened. Dogfooding REQ-011 hit exactly this; the
only workaround today is pinning `accounts.provider: single`, which discards account
rotation. `precheck()`'s `cswap status` call also errors, but it is swallowed as
"proceeding", so the misconfiguration is invisible until a step falsely fails.

This REQ corrects the provider to the real cswap 0.11 contract and hardens the engine so
a wrapper that dies *before emitting any stream-json line* is no longer indistinguishable
from `claude` itself erroring mid-task.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | `claude_argv()` returns plain `["claude"]`; cswap never wraps the command | Matches the 0.11 switcher model — cswap mutates state, it does not exec |
| 2 | Account selection moves into `precheck()`: `--use N` ⇒ `cswap --switch-to N`; the gate is `cswap --status` (flag) | precheck is already the per-run seam and the only place a side effect (switching) is safe and observed |
| 3 | Target cswap ≥ 0.11 only; no probing for the legacy `exec` shape | We control the dependency; branching on a CLI nobody ships is dead code |
| 4 | Harden `claude._classify`: a runner that exits non-zero with **zero** stream-json events is a *launch/environment* failure, distinct from a mid-task error | A false "failed" step from a broken wrapper must be diagnosable, not silently fatal |
| 5 | Switching stays non-fatal: a failed `--switch-to`/`--status` degrades to "proceed", logged | Preserve REQ-008's degradation contract — never hard-fail on quota machinery |

## Requirement

`CswapAccountProvider` speaks the claude-swap 0.11 flag CLI:

- `claude_argv()` returns `["claude"]` whether or not cswap is present — cswap is not a
  command wrapper.
- `precheck()` runs `cswap --status` as a non-fatal gate; when `use` is set it activates
  the account with `cswap --switch-to <use>` before returning. Any non-zero exit, missing
  binary, or timeout degrades to `(True, <reason>)` — never a block.
- `steward run --use N` therefore selects account N by switching, not by argv injection.

`claude._classify` distinguishes a launch failure (non-zero return, no stream-json events
captured) from a genuine in-flight error, so the executor and report can name the cause
instead of recording an opaque false "failed".

```yaml acceptance
- id: AC1
  text: With cswap present and use=N, claude_argv() is plain ["claude"] (no "exec" token) and precheck switches the account via `cswap --switch-to N`.
  test: "python -m pytest tests/test_accounts.py::test_use_switches_account"
  status: pass
- id: AC2
  text: precheck uses `cswap --status` and degrades non-fatally (returns ok=True) on non-zero exit, missing binary, or timeout.
  test: "python -m pytest tests/test_accounts.py::test_precheck_status_non_fatal"
  status: pass
- id: AC3
  text: A runner that exits non-zero having emitted no stream-json events is classified as a launch failure, distinct from a mid-task ERROR.
  test: "python -m pytest tests/test_claude_classify.py::test_launch_failure_distinct"
  status: pass
```
