## Context

A downstream project (FlowSteward, 2026-06-29/30) shipped multiple REQs **regression-green**
whose user-visible feature still did not work — "built but unwired." Four concrete cases: an
INBOX→workflow entry gate, a state-machine advancement, a calendar-invite disposition, and a
phantom-mail exclusion helper. Each was built, unit-tested, and green — yet never *called* by
the live worker cadence / read path. The gates could not catch it because acceptance stopped at
the unit, never reaching the live entrypoint. The green was honest about the unit and silent
about the system.

Two distinct root causes surfaced:

1. **Wiring gap.** No acceptance criterion proved the unit was actually *reached* by the running
   system. "The unit is correct" and "the system invokes the unit" are different claims; only the
   first was tested.
2. **Premature acceptance.** For outcome- or risk-shaped REQs ("no stuck mail, no matter what"),
   intake was forced to *invent* system-level ACs before the causes / stuck-paths / seams were
   known. The ACs were guesses, and unknown causes slipped straight through them.

**Second trigger (2026-07-05, amendment):** the FlowSteward REQ-081 postmortem
(`docs/reports/2026-07-05-flowsteward-req081-concept-phase-scope-and-worktree-sweep-postmortem.md`,
copied into this repo as the record) exposed two more concept-phase doctrine gaps, both on the
same surfaces this REQ already owns:

3. **Mis-seeded concept-phase scope.** REQ-081's concept deliverable was a *live-data* report
   whose IMAP leg could only run inside the deployed production container — producing it is
   inherently commit→push→deploy→run→iterate. But `/advance` seeds *every* attended session with
   "exactly one checkpoint, leave the tree dirty, the engine commits once," and no surface says a
   concept phase may legitimately commit repeatedly with `steward checkpoint` as the *terminal*
   act. The `/advance` skill text is also stale on this exact point: it still says "Spikes are
   throwaway — never commit prototype code," which REQ-067 (committed-prototype bundle) already
   superseded.
4. **Uninterrogated phase model.** REQ-081 was authored `concept: true` + `develop: fused` even
   though its own Context said the target-model ACs were unknowable before the concept
   deliverable existed — so `concept: true` degraded into a label with no phase behind it in
   which to author them, and its AC6 imported the *downstream* REQ's acceptance bar ("sufficient
   basis to run the T2 curation session") onto an upstream inventory step whose Notes scoped all
   modeling out. Intake never asked. The pairing is *not* wrong per se — it is the legitimate
   REQ-039 default for spike-shaped concepts — which is why the fix is an interrogation rule,
   not a lint (Decision 6).

DevSteward already has the raw materials to prevent all of these: the concept phase (REQ-039/067)
is the attended, solution-aware session that *could* derive ACs once analysis exists; the
acceptance taxonomy (REQ-027/064/068) already pushes acceptance toward decoupled system-level
oracles. What is missing is **doctrine** that names these patterns, gives intake a crisp decision
rule, and makes "unwired" a criterion *failure* rather than an invisible omission. This REQ is
that doctrine — captured in the agent-facing manual (`STEWARD.md`), sharpened in the `/intake`
and `/advance` skill texts, and framed in the handbook (`_00-method`). It is **not** engine
enforcement: the engine already permits AC authoring during the concept phase, already tolerates
mid-phase commits (a terminal `steward checkpoint` over an already-clean tree records the step
over an effectively no-op commit — observed 2026-07-05, REQ-081), and the land gate is the
concept deliverable + `concept_refs`; no executor code changes.

This is a process-learning REQ in the lineage of REQ-064 (intake screens env-bound regression
ACs) and REQ-068 (the V-model `check:` lanes) — each codified a hard-won downstream lesson into
the intake doctrine and its surfaces.

## Requirement

Bake five doctrine rules, plus a unifying decision rule, into the doctrine surfaces. The text
must be present and mutually coherent across `STEWARD.md`, the `/intake` skill
(`.claude/skills/intake/SKILL.md` + its hardlinked template), the `/advance` skill
(`.claude/skills/advance/SKILL.md` + its hardlinked template), and
`devsteward/handbook/_00-method.qmd`.

1. **Concept-phase-as-functional-spec.** Frame intake→concept onto the V-model left arm: *intake*
   captures the solution-free **user** requirement plus the explicit decision that acceptance
   cannot yet be written; the attended **concept** phase analyzes causes / stuck-paths / seams and
   **derives** the acceptance criteria (the functional spec — where solution knowledge legitimately
   enters). **Decision rule:** set `concept: true` **when the acceptance criteria cannot be honestly
   written at intake.** Unify this with the existing UI/empirical-prototype use under one line:
   *"the concept phase is where you earn the ACs you can't yet write."* The concept deliverable is
   whatever earns them — a cause/path-analysis doc (outcome REQ) **or** a committed prototype
   (UI/empirical REQ, the bundle-directory form per REQ-067).

2. **Wire-through-the-live-entrypoint.** A *system-scoped* acceptance criterion must exercise the
   feature through its **real running entrypoint** (the cadence / scheduler, the served surface) —
   so a feature that is present and unit-tested but **unwired** *fails* the criterion. **Tests
   passing ≠ wired.** This sharpens the existing "drive acceptance to system level" guidance (§2a).

3. **Don't-scope-a-known-defect-out.** A *known defect* is either fixed in the current REQ or homed
   in a **named follow-on REQ** — never silently deferred. (Genuine non-goals may still be listed
   out-of-scope; this rule is specifically about known **defects**.) Silent deferral is how the
   wiring gaps stayed invisible.

4. **Concept-phase-iterates-until-frozen.** An *empirical* concept phase — one whose deliverable
   is frozen live data or a committed prototype that the session must gather/build from the real
   world — is legitimately **multi-commit**: it may commit, push, and deploy repeatedly during the
   attended develop session to produce its own inputs. **`steward checkpoint` is the *terminal*
   bookkeeping act once the deliverable is frozen — not the only commit.** A terminal checkpoint
   over an already-clean tree is sanctioned and records the step over an effectively no-op commit.
   The `/advance` skill must seed a `concept: true` session with *this* scope ("iterate until the
   deliverable is frozen; checkpoint last") instead of the blanket "one checkpoint, leave the tree
   dirty" frame, and must drop the stale "never commit prototype code" line that contradicts
   REQ-067. (Batch is unaffected: a `concept: true` develop step is attended-only — batch parks it.)

5. **Phase-model-placement.** Whenever `concept: true` is set *because the target ACs depend on
   the concept deliverable* (the rule-1 case), intake must also decide **where the post-freeze
   work lives** — and ask this explicitly: either `develop: split`, so a post-freeze develop
   phase iterates the analysis and authors the target ACs against the frozen deliverable, **or**
   a named downstream REQ owns the modeling — and then the upstream REQ must **never carry the
   downstream REQ's acceptance bar** (no "sufficient basis for phase-N+1"-style manual AC on an
   upstream inventory step whose own Notes scope that work out). `concept: true` +
   `develop: fused` remains the legitimate default for spike-shaped concepts whose ACs *are*
   writable at intake; either shape is fine alone — the unexamined combination is the defect.

The rules must read coherently with the existing taxonomy text (REQ-027/064/068 — `check:` lanes,
oracle coupling) and the concept-gate text (REQ-039/067) rather than duplicating or contradicting
it.

## Notes

- **Engine enforcement is deliberately out of scope** (Decisions 4, 6, 7): "wire through the live
  entrypoint" is a human-judgment rule a linter would largely false-positive on; the phase-model
  guard is an interrogation, not a lint, because `concept:true` + `fused` is the legitimate
  spike default. The REQ-081 commit-sweep defect (worktree-wide staging, no run lock —
  `devsteward/core/git.py` / `core/executor.py`) is **deliberately unfiled** per Peter, and the
  deterministic privacy-ignore recommendation is out of scope (consumer discipline); the copied
  postmortem
  (`docs/reports/2026-07-05-flowsteward-req081-concept-phase-scope-and-worktree-sweep-postmortem.md`)
  is the durable record of both, seeding any future intake.
- **Surfaces & sync:** the `/intake` and `/advance` SKILL.md files are each hardlinked to their
  template (one inode — edit once). `STEWARD.md` at the repo root is a **symlink** to
  `devsteward/templates/STEWARD.md` (one file — never double-edit); it is an engine-owned stamped
  artifact tracked by `steward sync` (REQ-066). The handbook chapter has no template twin.
- **Dogfooding chain:** this REQ has a `manual` AC, so it gets a `validate` step — run
  `steward validate REQ-071` from a plain terminal for the AC2 sign-off. The `regression` AC1
  alone going green would itself be "built but unwired-coherence," which is exactly the failure
  mode the REQ names.
- Lineage: REQ-064 (intake screens env-bound regression ACs), REQ-068 (V-model `check:` lanes),
  REQ-039/067 (concept phase + committed-prototype bundle), REQ-018 (checkpoint as the verifying
  bookkeeper — rule 4 documents its terminal/no-op-over-clean-tree semantics). This REQ is the
  doctrine that ties the concept gate to acceptance derivation and to the concept session's
  real workflow.
