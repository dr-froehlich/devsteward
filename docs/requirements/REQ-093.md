## Context

DevSteward's unit of work is the requirement, and a requirement is already solution-shaped.
By the time `/intake` finishes, an idea has been interrogated into scope boundaries,
dependencies, and acceptance criteria naming runnable tests. That is the point — it is what
lets the engine certify anything. But it leaves three gaps.

**There is no cheap way in.** The only door into the method is a full `/intake` interview.
A half-formed observation — *"the return button should be green and larger"*, *"I want a
printout for this panel"* — has nowhere to live and dies in a chat log. The prompt for this
REQ was a non-programmer running Claude Code who wired an "add to backlog" button into his
own application and fed it one-sentence needs; the entry cost was the whole reason it
worked.

**There is no user-language layer.** Every artifact in the system is written in solution
language. Nothing records the need in the words of the person who has it.

**Nothing checks the built thing against the need that motivated it.** A REQ closes when its
acceptance criteria go green — criteria written by the same session that designed the
solution, against a specification that session also wrote. The loop closes on itself. A
system built this way can pass every check it set for itself while drifting away from what
anyone asked for, and it does so invisibly, because no artifact survives that says what was
asked for. This is the observed failure mode: a set of self-sustaining rules and constraints
that no longer reflect the actual user requirements.

One consumer has already improvised the fix. DriveSteward's REQ-016 keeps a `docs/BACKLOG.md`
of needs in the operator's words, with a handle rather than a REQ id (*"an id in a table
reads as a commitment to build that thing, in that order"*), a rule that an item naming a
mechanism *"has already made a decision nobody asked it to make"*, and notes distinguishing
the operator's own words from items a session proposed and the operator then chose. That
file is the seed of this REQ, and its 15-item corpus is the proof surface.

The framing was checked against practice before being designed. It is not a Scrum layer
bolted onto a V-model; it is the second level of requirement that ISO/IEC/IEEE 29148 already
defines — the Stakeholder Requirements Specification, transformed by the System Requirements
Definition process into the SyRS that a REQ already is. DriveSteward's "no mechanism in an
item" rule is 29148's *implementation-free* quality attribute, derived independently. The
full assessment, including what the surrounding field is doing and what is deliberately not
being copied from Scrum, is the handbook's outlook chapter (`handbook/_05-outlook.qmd`).

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Two levels of requirement, not two systems: backlog item (StRS, user language) → REQ (SyRS, solution language), joined by an explicit translation at intake | The alternative — a Scrum layer above the V-model — treats them as separate machines needing a joint. 29148 already defines one transformation between two levels; there is nothing to join |
| 2 | Item acceptance is **advisory to the REQ and blocking to the item** | The engineering cycle must not be able to fail from the system-requirement level downward — verification stays absolute. But the owner may still withhold acceptance: *"exactly as specified"* and *"still not easy to use"* are both true at once, and today the system cannot hold them together |
| 3 | A denied item stays **open** in the backlog with an attempt record naming the REQ that tried and the stated reason; the REQ closes on its verification result | Mirrors Scrum: an unaccepted item returns to the product backlog, the sprint is not reopened. The recorded reason is what stops the next REQ repeating the attempt — without it a denied item is just an item that failed twice |
| 4 | The acceptance verdict is a **standalone command**, not a step inside the System-Test session | Acceptance belongs to the person with the need, not the tester; the honest verdict on something like *"easy to use"* often arrives only after living with the result; a future status server must be able to record one; and it keeps a backlog-linked REQ from acquiring a mandatory extra validation session |
| 5 | Verdicts are append-only events in a profile-owned `.devsteward/backlog.jsonl`; the backlog file stores **no status column** | The sequence of verdicts *is* the attempt record. A stored status would be a second copy with no writer at land — the defect REQ-083 subtracted from `ROADMAP.md`. Keeping it out of the core `events.jsonl` keeps the content-agnostic executor core content-agnostic |
| 6 | Take-up is derived from the REQ's `backlog_refs:`, never stored as an event or a column | One writer, at intake, in the same commit as the REQ and its index row — the existing same-commit discipline already covers it. Storing it anywhere else creates a second writer |
| 7 | Item acceptance criteria are authored at intake **before** the translation to a requirement | Criteria written knowing the solution get quietly bent to fit what was going to be built anyway — the failure this REQ exists to prevent, reappearing one level up. Capture stays frictionless; the discipline lands at intake |
| 8 | No sprint object, no time-box, no story points, no agent role-play, no worktrees | The REQ is the container; a sprint object would be a second status surface above the index. Points estimate human throughput. The product owner's value is that they are a person, not a simulation. Worktrees are machinery REQ-047 removed |
| 9 | Provenance is a field on the item, not a footnote | The distinction between the operator's words and a session's proposal the operator accepted is the actual guard against the system writing its own requirements and then satisfying them |
| 10 | The DriveSteward retrofit is a **develop obligation** of this REQ, with a committed corpus fixture for the mechanism and a human sign-off for the result | devsteward does not dogfood the backlog — it has no user-need queue — so the format would otherwise land proven only against fixtures it shaped itself. REQ-085 precedent: extend the machinery and drive the live conversion in one REQ, attended and fixable in place |
| 11 | `steward new` stamps the backlog; `backlog-add` creates it when missing; `sync` never touches it | Found during build: the REQ-086 seeding precedent does not transfer. `_templates/req.md` is *referenced by a stamped skill*, so its absence breaks `/intake`; a backlog's absence is a valid state. Seeding through `sync` would also hand **devsteward itself** a backlog, contradicting this REQ's own honor-when-present promise. The capture verb is the right creator — wanting to record a need is exactly when a project acquires a backlog |
| 13 | A fourth verdict, `held` — the need stands but is deliberately not being worked | Surfaced by the live corpus, not by design: DriveSteward had ruled one item "not withdrawn and not being worked … waiting on a reason to be believed rather than on a session". `open` would read as available and `retired` as withdrawn; both discard the owner's ruling, which is precisely the information this layer exists to keep. It reuses the same append-only machinery and, like a denial, yields to a live REQ taking the item up |
| 12 | An item's acceptance criteria live in the backlog file under `## Acceptance criteria`, one `###` section per handle | They are the *owner's* conditions of satisfaction, so they belong to the item, not to the REQ. The engine never grades them — it surfaces them when the verdict is given, and lints only that a section names a real item. Keeping them out of the REQ's `acceptance:` block is what stops them becoming blocking criteria and re-conflating the two verdicts |

## Requirement

### The backlog artifact

A project may keep a backlog of user needs at a path named by a new `backlog_file` config
seam (default `docs/BACKLOG.md`), following REQ-084: the layout is the consumer's. The whole
feature is **honor-when-present** — a project without the file lints green, and every backlog
command exits cleanly saying so. devsteward itself is such a project and stays one.

The file is a markdown table the engine parses and appends to, with surrounding prose
preserved across rewrites (the `REQUIREMENTS_INDEX.md` splice precedent). Columns are
`Handle | Need | Origin`:

- **Handle** — lowercase kebab-case, unique within the file, stable once minted. Not a REQ
  id: listing an item commits to nothing and schedules nothing.
- **Need** — the need in the user's words. Implementation-free: an item that names a
  mechanism has already made a decision nobody asked it to make.
- **Origin** — `operator` (their own words) or `proposed` (a session proposed it and the
  operator chose it from alternatives).

The file stores **no status column and no "taken up by" column**. Both are derived.

### Capture

`steward backlog-add "<need>" [--handle H] [--origin operator|proposed]` appends an item,
minting a unique handle from the text when none is given. It is the frictionless entry
point — usable by a person, by a session recording what the operator just said, or later by
a status server.

### Take-up at intake

A REQ declares the items it takes up in new frontmatter `backlog_refs: []`, alongside
`concept_refs` and `scenario_refs`. `/intake` gains a take-up step and one ordering rule:
when items are taken up, their acceptance criteria are authored **first, in user language**,
and only then translated into the requirement and its verification criteria. The stamped
skill and the repo's hardlinked copy carry the same text.

### The acceptance verdict

Three standalone commands, flat and discoverable per REQ-089:

- `steward backlog-accept <handle> [--note "…"]`
- `steward backlog-deny <handle> --reason "…"` — the reason is **mandatory**
- `steward backlog-hold <handle> --reason "…"` — the need stands but is deliberately not
  being worked; taking the item up lifts the hold
- `steward backlog-retire <handle> --reason "…"` — the owner no longer wants it

Each appends an event to `.devsteward/backlog.jsonl`; nothing is ever rewritten, so a second
verdict on the same item leaves the first readable. A denial does not close the item and
does not affect the REQ that attempted it.

### Derived status

`steward backlog-list` renders each item's state, computed from the REQ graph and the event
log with no stored copy anywhere:

| State | Derived from |
|---|---|
| `open` | no REQ references the handle, no verdict |
| `in-progress` | a REQ referencing it is not yet done |
| `attempted` | every referencing REQ is done, no verdict yet |
| `accepted` | latest verdict is an accept |
| `open (denied N×)` | latest verdict is a denial — still available to be taken up |
| `held` | latest verdict is a hold, and no live REQ has taken it up |
| `retired` | latest verdict is a retirement |

Each item also renders its attempt record: which REQs referenced it, and the reason given on
each denial.

### Lint

`steward lint` gains referential integrity only: every `backlog_refs` handle resolves to an
item, handles are unique within the file, and every verdict event names a known handle. It
does **not** enforce that an item be taken up, ordered, prioritized, or ever accepted — the
backlog commits to nothing.

### The item's acceptance criteria

The owner's conditions of satisfaction live in the backlog file's `## Acceptance criteria`
section, one `###` heading per handle followed by a bullet list, in the owner's own words.
`/intake` authors them **before** translating the need into a requirement. The engine never
grades them — acceptance is a human verdict — it surfaces them when a verdict is recorded and
lints only that a section names a real item. Parsing is scoped to that section and skips HTML
comments, so ordinary prose headings and a commented-out example are never read as content.

### How a project acquires a backlog

`steward new` stamps an empty backlog file with its grammar documented in place. In an
existing project, `steward backlog-add` **creates** the file from the same template when it
is missing and never overwrites one that exists. `steward sync` does **not** touch it: the
backlog is consumer *content*, not engine behaviour, so it never joins the tracked drift set
— the line REQ-036 Decision 1 already draws for `CLAUDE.md`.

### The DriveSteward retrofit

This REQ's develop session converts DriveSteward's existing 16-item backlog to the shipped
grammar, wires REQ-019's two taken-up items into `backlog_refs`, and iterates on whatever
the real prose turns up — attended, and fixable in place. The shapes that corpus actually
contains are captured as a committed fixture so the mechanism stays disconfirmable here.

### Out of scope

The **retrospective** and per-project governance loop (a separate REQ, deliberately: its
shape is not yet known). The **status server** — a small web surface showing projects, their
state, and backlog items with a way to tick them off — is a separate objective and a separate
REQ; Decision 4 is the constraint this REQ owes it. Ordering, priority and item types are not
built: they would be fields with no reader.

## Notes

**Vocabulary.** Three terms are routinely crossed where agile and V-model practice meet, and
this REQ fixes them in file formats that will outlive the confusion. Per the Scrum Guide, a
**Definition of Done** is a single product-wide quality checklist applied to every item —
never per-item; DevSteward already has one and it is the engine's land gate, so nothing is
invented here. **Acceptance criteria** are per-item, in user language, and belong to the
person with the need — hence the backlog item. **Verification criteria** are what a REQ's
`check: regression` / `check: live` entries already are.

**AC9 costs a validation session for this REQ.** That is deliberate and bounded: it proves
the live retrofit happened at all, which a develop obligation with no criterion cannot. It
does not generalize — Decision 4 exists precisely so that taking up a backlog item never
forces a validation session on an ordinary REQ.

**Cross-repo work.** The retrofit lands as commits in DriveSteward's own repository under its
own process, as the THermo conversion did for REQ-085. This REQ's own gate is the fixture
corpus; AC9 is the sign-off on the live result.

**Follow-ons.** The retrospective and per-project governance loop, and the status server, are
both named in *Out of scope* above and are not deferred defects — they are separate
objectives with their own shapes to settle.
