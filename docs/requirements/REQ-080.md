## Context

When a headless Claude session dies on a usage/budget limit mid-run, `steward run` stops
the whole run. The operator must notice, wait for the budget window to clear, and restart
by hand (`steward repeat REQ-NNN` + a fresh `steward run`). Observed during FlowSteward
REQ-116 development (2026-07-16): the run quit, and roughly two hours of otherwise-usable
unattended time were lost to a limit the engine could have waited out.

The REQ-116 trace exposes **two** distinct gaps behind that one user-visible failure:

1. **Misclassification.** The FlowSteward ledger recorded the budget-limit death as
   `step_failed` outcome `"error"` — not `usage_limit`. The session's ending did not match
   `_LIMIT_MARKERS` in `claude._classify` (REQ-016 matches only the runtime's out-of-band
   signal, correctly — but the marker list missed this ending's shape). An ERROR sets the
   step `FAILED`, a stopping state that demands the manual `steward repeat`; a correctly
   classified limit would merely have requeued it `PENDING`. Chasing every future wording
   of the limit signal is a losing game; the engine already has a budget **oracle** —
   `clauder gate` (REQ-058) — that can corroborate an ambiguous ERROR at the moment it
   happens.

2. **The run stops even on a correctly classified limit.** `Executor.run` breaks out of
   its loop on `RunOutcome.LIMIT`. Yet the machinery to wait already exists and is already
   trusted: `precheck` → `clauder gate` has a wait-and-re-gate loop (sleeps clauder's
   `wait_seconds`, re-gates, switches accounts when clauder says so, honors the stop
   signal during the wait). It only runs at *step start* — a mid-session limit never loops
   back into it. The fix is subtraction-shaped: stop treating LIMIT as a run-terminating
   outcome and let the next loop iteration's existing gate own the waiting.

A third, smaller defect rides along: a limit-interrupted step is requeued `PENDING` (not
`RECOVER`), so a relaunched session starts without the `--repeat` recovery signal despite
a dirty tree of partial edits from the killed session. The manual workflow accidentally
fixed this (`steward repeat` sets RECOVER); the automatic resume must fix it deliberately.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | One REQ covers both gaps (classification + resume loop) | They are one user-visible failure — "run quits on budget limit". Fixing only the loop leaves the REQ-116 shape (misclassified ERROR → FAILED) still stopping the run. |
| 2 | Corroborate an ambiguous ERROR via `clauder gate`, don't grow the marker list | The runtime signal (REQ-016) stays the primary classifier; clauder is the budget oracle the engine already trusts. A session death that misses the markers but coincides with a clauder-exhausted verdict is treated as a limit interruption. |
| 3 | Wait as long as clauder says — the run process stays alive | Unattended runs exist to ride out exactly these windows (possibly hours until a reset). The existing precheck gate loop already implements the wait/re-gate/switch; the stop signal (Ctrl-C) interrupts it gracefully. |
| 4 | Requeue a limit-interrupted step as `RECOVER`, not `PENDING` | The relaunched session must receive `--repeat` so it assesses the killed attempt's partial edits (mirrors what the manual `steward repeat` did; consistent with REQ-079's whole-tree doctrine). |
| 5 | Consecutive-limit guard: 3 immediate limit-deaths on the same step with no intervening gate wait or progress → requeue and stop as today | Guards the tight spin where clauder says "proceed" but sessions keep dying instantly (account-state mismatch). A real gate wait or a completed step resets the counter. |
| 6 | clauder absent / gate failure → stop as today | Auto-resume is a clauder-backed feature; without the oracle there is no honest signal for when the budget clears. No blind polling. |
| 7 | Regression-only acceptance (fake runner + fake clauder seams) | A real budget limit cannot be provoked on demand and owns no lab; the next natural occurrence in FlowSteward is informal confirmation, not a gating AC. |

Accepted risk (Decision 2): a genuine code error that happens to coincide with an
exhausted budget gets retried instead of failing immediately. The guard (Decision 5)
bounds it, and once the budget clears the genuine error re-surfaces as a plain FAILED.

## Requirement

A budget/usage limit that kills a headless session no longer terminates `steward run`.
The engine classifies the death honestly (runtime signal first, clauder corroboration for
the ambiguous ERROR shape), requeues the step with its recovery signal, and re-enters the
existing `clauder gate` loop — waiting out the window or switching accounts as clauder
directs — then relaunches the step and keeps working. The run stops only when: clauder is
unavailable (no oracle), clauder declares the budget unsatisfiable, the consecutive-limit
guard trips, or the operator sends the stop signal.

## Notes

- **Out of scope:** any clauder-side change (clauder is a separate project; the engine
  consumes `clauder gate` as-is per REQ-058), and attended `steward advance` semantics —
  it stays single-step and may still return LIMIT to a present human. The repair loop's
  LIMIT feeds the same run loop and benefits from the resume automatically; no separate
  repair-side machinery.
- All acceptance oracles are engine-internal (fake runner + fake clauder seams); the
  suite is self-contained in a clean checkout — no service, secret, or network required.
- The observed trace: FlowSteward `.devsteward/events.jsonl` REQ-116:develop,
  2026-07-16T13:40:05 `step_failed outcome=error` followed by a manual `step_recover` at
  13:41:53 — the misclassified shape this REQ closes.
