## Context

The owner's need, in the owner's words (backlog item `backlog-review-author`): *"I want to
review, author and modify backlog items for any of my projects."* Its criteria include *"I can
add an item, reword its need and its acceptance criteria, and change its origin."* REQ-097 took
the item up and delivered the dashboard's add and edit forms. The item has no verdict yet. The
owner's ruling at intake: *"My backlog item implied the functionality as working, not
defective, so this REQ is needed to close it."*

**What happened (2026-10-10).** The owner added `joint-project-tasks` through the dashboard's
add form and typed the need over three lines. A browser submits a textarea with CRLF line
breaks. `backlog._cell` (`devsteward/profiles/req/backlog.py`) escapes `|` and nothing else, so
`append_item` wrote the row with its line breaks intact and the row split over three lines.
`add()` does not read back what it writes, so the add reported success. The redirect to the
project page then parsed the file and failed: *"line 49: not a well-formed item row: '|
joint-project-tasks | Handover between projects works like that:'"*. From then on every
backlog read failed: `steward lint`, `steward backlog-list` and the dashboard's backlog
section. Nothing was lost. The row was joined by hand and committed (`70e1051`). The CLI has
the same gap: `steward backlog-add` with a quoted multi-line argument writes the same broken
row. The edit form and `backlog-edit` have it too.

**Three more holes in the same writer, verified at intake against the shipped code:**

- **Every line boundary breaks a row, not only CR and LF.** The reader splits the file with
  `str.splitlines()`, which also breaks on `\x0b`, `\x0c`, `\x1c`–`\x1e`, `\x85`, ` `
  and ` `. A need containing any of them fails the same way.
- **`|` drifts.** The writer escapes `|` to `\|`, but the reader never unescapes it. A need
  `a | b` reads back as `a \| b`, and every rewrite adds a backslash (`a \\| b`,
  `a \\\| b`, …). Every dashboard edit rewrites the row, because the form always sends need
  and origin, and the page shows the backslashes. REQ-097 AC5 says `backlog-edit`
  "round-trips through the parser", and its test passes only because no need in its fixture
  contains a `|`. No consumer backlog contained a `\|` at intake, so there is nothing to
  migrate.
- **`<!--` hides content.** `_live_lines` treats `<!--` anywhere in a line as the start of an
  HTML comment. A need containing it truncates its row, which fails with the same error. An
  acceptance criterion containing it is worse: the rest of that bullet and every criterion
  after it are dropped **silently**, with no error at all. A criterion passed to
  `backlog-edit --criterion` with an embedded line break also loses everything after the
  break without a word (`["line one\nline two", "next"]` reads back as
  `["line one", "next"]`).

`backlog.parse`'s own docstring names the stake: *"a dropped item is exactly the failure this
whole layer exists to prevent."* Here the writer is the one dropping content.

**The manual implies every REQ comes from a backlog item.** The owner reports that consumer
sessions keep asking them to add a backlog item after they have already intaken a REQ. Nothing on
record says every REQ needs an item, and nothing says a REQ without one is normal. What the
shipped text does say leans one way. STEWARD.md calls an item *"the stakeholder-level
requirement a REQ is translated from"* and says to run `steward backlog-list` *"at the start
of every `/intake`. If the project keeps a backlog, the intake probably starts from an
item."* `/intake` §1 says the same, and the handbook (`_01-format.qmd` §backlog) calls the
item *"the need in the user's words, which a REQ is translated from at intake."* Nothing
balances that wording, so a session reads it as "every REQ traces to an item". In the owner's
words: *"a backlog item drives a requirement or several, but my inner "V-Model" loop does not
require a backlog item for every REQ. Many requests, and especially defects need repairs and
are not driven [by] a new feature need."*

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | **Line breaks fold to one space on every write.** Each run of whitespace that contains a line boundary is replaced by a single space. A line boundary is any character `str.splitlines()` splits on, because that is what the reader splits on. The fold applies to a need and to an acceptance criterion, on add and edit, from the CLI and the dashboard alike. | Owner's choice of three: fold; store the breaks as `<br>` and decode them on read; refuse the input. The REQ-093 format is one item per table row and one row per line. Folding keeps every word and loses only the paragraph breaks. It adds no encode/decode pair that the parser would have to keep in step. The dashboard's criteria textarea is not affected: it already splits on lines, one criterion per line, which is its documented use. |
| 2 | **`|` round-trips: the writer escapes it and the reader unescapes it.** A need reads back exactly as typed, however many times it is rewritten. | Verified drift (Context). REQ-097 AC5's round-trip claim was never exercised with a `\|`. No consumer file holds `\|`, so nothing needs migrating. |
| 3 | **`<!--` and `-->` inside a need or a criterion round-trip.** They read back exactly, and no row or criterion after them is hidden or truncated. The encoding (escaping on write, or making the reader stop treating a marker inside a row or bullet as a comment) is the develop session's choice. Commented-out content stays documentation: the stamped template's commented example must still be ignored. | Verified at intake: the need case fails loudly, the criterion case loses content silently. The owner chose to include both in this REQ. The template constraint is the reason `_live_lines` exists (REQ-093). |
| 4 | **Check before write.** `add` and `edit` parse the text they are about to write and refuse with `BacklogError`, leaving the file untouched, unless it reads back with the item exactly as it will be stored (the folded need, its origin and its criteria). The dashboard flashes that error and no success. | Owner's call. In the observed failure the write succeeded, the user saw a success message, and then the file could not be read by anything. One check turns any encoding gap this REQ misses into a refused write that leaves the file intact. It is the REQ-063 shape: check before the irreversible act, never destroy what is there. |
| 5 | **The shipped manual says that a REQ does not require a backlog item.** The rule, as the owner approved it: *"A REQ does not require a backlog item. An item may drive one or more REQs, and a REQ the owner intakes directly, such as a defect repair or a change no recorded need asked for, is complete without one. At `/intake`, the session reads `steward backlog-list` itself and shows the owner only the items related to the idea, or says that none are."* It replaces the one-sided wording in STEWARD.md ("The backlog"), `/intake` §1 and §2d step 1, and handbook `_01-format.qmd` §backlog. | Owner's call; there is no recorded rationale either way (Context). **The rule makes the item optional and forbids nothing.** At intake the owner rejected two drafted sentences: *"[an item] is never derived from [a REQ]"*, which turned "not required" into "forbidden" and contradicted REQ-093's own `proposed` origin, and *"never suggest recording a backlog item for a REQ already intaken"*, which only made sense in that conversation and treats a symptom. With the optionality stated, nothing is left pushing toward the nagging. The `/intake` skill ships to every consumer (it is inode-shared with its template), and that is intended: the nagging happens in consumer projects. Showing only related items is the owner's improvement over listing the whole backlog. The accepted risk is that a session judges an item unrelated that the owner would have picked. |

Same commit as the code. | REQ-094: the fold is behaviour a consumer agent observes (what it typed is not byte-for-byte what is stored). |

No System-Test phase and no lab.** | Every criterion runs headless in a clean checkout, through the real dashboard routes (the Flask app, as REQ-097's tests do) and the click CLI. ## Requirement

### What the owner types is what the file holds

For every write to the backlog file, by `steward backlog-add`, `steward backlog-edit`, and the
dashboard's add and edit forms (all of which call `backlog.add` / `backlog.edit`, REQ-097):

- **Line breaks.** In a need and in an acceptance criterion, each run of whitespace containing
  a line boundary (any character `str.splitlines()` splits on, CRLF included) is stored as a
  single space. The item is one row on one line, and a criterion is one bullet on one line.
- **`|`.** A need containing `|` reads back exactly as typed, and stays exact across any number
  of rewrites. The dashboard shows `a | b`, never `a \| b`.
- **Comment markers.** A need or criterion containing `<!--`, `-->` or both reads back exactly
  as typed, and every row and criterion after it still parses. A genuine HTML comment block
  in the file, such as the stamped template's worked example, is still ignored.
- **Check before write.** If the text about to be written would not parse back with the item
  exactly as stored, the write is refused with `BacklogError` and the file is byte-unchanged.
  The CLI exits non-zero with the message, and the dashboard flashes it as an error. No
  success message is shown for a write that did not happen.

Everything else REQ-093 and REQ-097 guarantee is unchanged: every byte outside the written
row or criteria block is preserved, handles are never renamed, and the file stores no status.

### The manual: a REQ does not require a backlog item

STEWARD.md ("The backlog"), the bundled `/intake` skill (§1 and §2d step 1) and the handbook
(`_01-format.qmd` §backlog) state Decision 5's rule in place of the wording that says a REQ is
translated from an item and that an intake probably starts from one. The rule adds no
prohibition.

## Notes

**Out of scope, on purpose.** Keeping paragraph breaks inside a need (`<br>` encoding was
considered and declined, Decision 1). Changing the dashboard's Need box to a single-line
input: the textarea stays, because long needs wrap and the fold makes it safe. Recording the
owner's verdict on `backlog-review-author`: that is the owner's act, whenever they choose
(REQ-093 Decision 4). The `prose-converter-fidelity` and `backlog-commit-ui-changes` items
are separate needs and are not taken up here.

**Develop obligations.** Update STEWARD.md, `/intake` and the handbook in the same commit as
the code (Decisions 5 and 7, REQ-094). The `/intake` edit changes a shipped skill: edit either
inode-shared path once, never both. Consumers pick it up at their next `steward sync`; no hand
sweep is owed, because no consumer document repeats the changed wording.

**Risks.** (1) A need written by hand into the file with a literal `\|` now reads back as `|`.
That is the intended meaning, and no consumer file contained one at intake. (2) The
check-before-write compares the parsed item with the stored item. If the fold and the reader
disagree about whitespace, an honest write could be refused. AC1 drives every line-boundary
character through the real path, which is what proves they agree.
