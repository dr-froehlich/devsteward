## Context

REQ-053's forward-path audit (`docs/reports/2026-06-19-process-resilience-forward-path-audit.md`)
found one **correctness-of-fit** gap in the recovery surface — the only place a named path
makes a human redo *sound* work. When a validation goes red, the parked-decision brief
(`validate.py:_park_red`) steers the human unconditionally to `steward rework`, which re-opens
`develop` (`DONE → RECOVER`) and re-runs the build. That is the right move when develop was
**hollow** (an internal cause — the work was genuinely insufficient). But a red validation is
just as often caused by something **external to the work** — a broken lab fixture, a missing
credential, an IMAP host that was down — which the human then fixes. There the develop work
*stands*; the right move is to **re-run the validation only**, leaving develop `DONE`.

That re-validate-only path exists mechanically today but is **un-named and undocumented**:
`decision answer DEC` flips just the validate step `BLOCKED → PENDING` (develop stays `DONE`),
then `steward validate REQ` re-runs it. Because only `rework` is named and the brief points
only at it, a human who hit an external cause is pushed into a needless develop redo.

This REQ closes that gap with the missing symmetric verb — **`steward revalidate REQ`** — the
validate-layer counterpart of `rework`. It is `rework`'s mirror image: same precondition (an
in-flight REQ parked on a *red* validation), opposite action (leave `develop` `DONE`, re-arm
`validate`). It also fixes the red-validation brief to offer the **choice** between the two
edges instead of presuming the internal cause.

This is recommendation #2 + #3 of the audit, prioritised first because it is the sole
fit-correctness item. It is deliberately a *rename-and-name* move, not new recovery machinery
on a new premise: the action already exists; this gives it an honest name and an honest brief.
It is independent of REQ-054 (the `recover → repeat` rename) and does not depend on it.

## Requirement

Add a `steward revalidate REQ` operator verb and correct the red-validation brief so a human
parked on a red validation has both forward edges named and the external-cause path no longer
forces a develop redo.

- `lifecycle.revalidate(cfg, ledger, req_id)` re-arms a red-parked validation: on an in-flight
  REQ whose latest validation event is red (`ok:false`) and whose `validate` step is `BLOCKED`,
  it sets `REQ:validate` to `PENDING`, **leaves `REQ:develop` untouched at `DONE`**, answers any
  open decision parked on the validate step, and appends a `revalidate` event carrying the red
  validation's `evidence` path and failure `brief`. It touches neither git nor the REQ file.
- It refuses with a `LifecycleError` (CLI maps to non-zero) when there is no red validation to
  re-run: an unknown id, a `done` REQ (pointing at supersede), a REQ with no validate step, or a
  validate step not `BLOCKED` on a red — the same refusal taxonomy as `rework`.
- The red-validation parked-decision message (`_park_red`) names both `steward rework REQ`
  (develop was hollow — redo it) and `steward revalidate REQ` (an external lab/setup issue was
  fixed — the develop stands, re-run validation only), framed as a choice keyed on the root cause.
- `steward revalidate REQ` is registered on the CLI and wired through the same atomic,
  HEAD-agnostic transaction boundary as `recover`/`rework`, printing the `validate → pending`
  transition on success and a clean non-zero refusal otherwise.

## Notes

- **Why a new verb and not just documenting `decision answer`.** The audit weighed this: the
  re-validate path *is* reachable via `decision answer DEC` + `steward validate`, but it is
  two steps, undocumented, and the brief steers elsewhere. A named verb that mirrors `rework`
  makes the symmetric model legible and removes the misdirection — it fills a named hole rather
  than adding machinery on a new premise (the design-principle test).
- **Relationship to siblings.** REQ-054 renames `recover → repeat` (independent — this REQ uses
  today's verb names); REQ-056 carries the `--recover` resume signal through decision-answered
  dirty re-runs (states D/H — orthogonal to validate); REQ-057 documents the async-QA / state-F
  path and the verb's handbook entry. None blocks this one beyond REQ-033 (the `rework` edge it
  mirrors, which pulls in the REQ-030 validate phase) and REQ-047 (the un-divergeable state
  model).
- **Test harness.** Reuses `test_rework.py`'s `_seed_red` / `test_system_test_phase` harness —
  the same in-memory git topology and red-validation seeding where `rework` is tested, so the
  mirror verb is exercised against the identical wiring.
- **Process declarations:** defaults — fused develop, no concept phase, no lab. All ACs are
  `regression` (module-scope, coupled oracle); there is no artifact/manual check, so no
  System-Test phase. The `process:` block is omitted.
- **Localization:** all messages are operator-facing CLI/technical English; no localized UI
  strings.
