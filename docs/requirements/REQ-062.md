> Bringing an existing project under the engine is a *sequenced multi-REQ deployment*, not a
> single REQ. Build order: **REQ-023** (converter index splice) → **REQ-022** (`steward
> seed-ledger`) → **REQ-024** (`onboard` skill) → **REQ-062** (drive memzy live — the proof, this
> one). Foundations **REQ-010** (memzy converter) and **REQ-021** (lettered ids) are already
> DONE; the deferred **REQ-017** (legacy-prose converter) is the ExamEngineer-only path, off this

## Context

The onboarding machinery — [[REQ-010]] (convert), [[REQ-023]] (safe in-place index splice),
[[REQ-022]] (`steward seed-ledger`), [[REQ-024]] (the `onboard` skill that drives them) — is
proven only in unit tests and skill-content assertions until it is run, once, end-to-end against
a real project. A phase of machinery that goes `done` without ever being observed driving a live
migration is the hollow-green shape this engine exists to prevent (the same reasoning that made
[[REQ-031]] the first **lab** consumer after [[REQ-030]] built the validate phase).

This REQ is that proof. **memzy** is the first project retrofitted — chosen because it is recent
and low-stakes (the operator's call), **not** ExamEngineer, which stays a trusted pre-DevSteward
reference and migrates later (via [[REQ-017]]), if at all. memzy is a clean target: a
frontmatter-dialect corpus REQ-010 already converts (23 REQs validated clean against its live
corpus), a lettered id (`REQ-028p`) [[REQ-021]] handles, a richer index ([Planned] + Scenarios)
[[REQ-023]] preserves, and a `.claude/` + ~160-line domain `CLAUDE.md` the `onboard` skill must
**merge into, not overwrite**.

The deliverable that lands in *this* repo is the proof record (the plan + a short onboarding
report); the substance — memzy's converted corpus, seeded `.devsteward/` ledger, stamped
scaffold, reconciled `CLAUDE.md` — lands in **memzy's own git**, not here. DevSteward records that
it happened and a human signs it off.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | The proof is a **`manual` AC** a human signs off, exactly like [[REQ-031]] AC3 — there is no DevSteward-side regression test for "memzy is onboarded" (that state lives in memzy's repo). | The migration mutates another repo over live operator judgement; the honest oracle is a human inspecting memzy's result, not a pytest in this repo. The `manual` AC routes the REQ through the validate phase (REQ-030). |
| 2 | The live migration runs the **shipped `onboard` skill** ([[REQ-024]]) against memzy, gated at each step by `steward lint` / `steward status` — it does **not** re-implement or hand-do the pipeline. | This REQ exists to prove the skill drives the real thing; bypassing it would prove nothing. A red gate stops the run and surfaces a defect back to the machinery REQs. |
| 3 | memzy's repo changes are committed in **memzy's own git** (by the operator / memzy's own seeded `steward`); this REQ commits only the **proof record** (plan + onboarding report) on DevSteward's `dev`. | Cross-repo ledger writes are not a thing ([[REQ-031]] Decision 7). Each repo owns its own history; DevSteward owns the evidence that the onboarding succeeded. |
| 4 | **Scope is memzy only.** ExamEngineer and any other project are explicitly *not* part of this proof; each future onboarding is its own operator act (and, if it warrants a tracked proof, its own REQ). | Keeps the first proof small and real; generalization is asserted by the uniform pipeline, demonstrated once here. |

## Requirement

Drive memzy end-to-end under the steward engine using the shipped `onboard` skill, and have a
human sign off that memzy is correctly migrated:

- Run the `onboard` skill ([[REQ-024]]) against the memzy checkout: **convert** the REQ corpus in
  place ([[REQ-010]] + [[REQ-023]] splice), **seed** the ledger ([[REQ-022]]), **stamp** the
  scaffold (merging into memzy's existing `.claude/`), and **reconcile** memzy's `CLAUDE.md` —
  each step gated by `steward lint` / `steward status`, stopping on any red gate.
- Capture a short **onboarding report** (what ran, the gate results, anything that surfaced) as
  this REQ's develop deliverable in DevSteward; memzy's actual repo changes land in memzy's git.
- A human reviews memzy's post-onboard state and signs off (the `manual` AC).

### Out of scope

- Any project other than memzy (Decision 4); ExamEngineer is the deferred [[REQ-017]] path.
- Converting memzy's Scenarios / Planned table content (preserved, not converted — [[REQ-023]]).
- Fixing the machinery itself: a defect surfaced during the run is a red gate that routes back to
  [[REQ-022]]/[[REQ-023]]/[[REQ-024]] (rework), not patched inside this proof.

## Validation procedure (for whoever runs `steward validate REQ-062`)

1. From the **memzy** checkout root (`/home/peter/projects/memzy`), run `steward lint` — it must
   be clean (the converted corpus is schema-valid, the index synced).
2. Run `steward status` from memzy's root — it must report every historic REQ `done` and an
   **empty work queue** (a seeded, caught-up project; `advance` is a no-op until memzy's next
   `/intake`).
3. Confirm the stamp **merged**, did not overwrite: memzy's own `CLAUDE.md` domain guidance, its
   `.claude/settings.local.json`, and its richer `ROADMAP.md` / Scenarios are all intact, with the
   house conventions (same-commit discipline, the ledger contract, the co-author trailer) folded
   in.
4. Read the onboarding report captured under DevSteward's `docs/reports/`; confirm each pipeline
   step's gate was green and nothing was hand-forced past a red gate.
5. Sign off (or, on a defect, route the cause back to the machinery REQ via `steward rework`).
