## Context

Nine REQs were built green and were, in reality, hollow: code and tests shared one set of
hallucinated assumptions, so the tests confirmed the code's behaviour against itself rather
than against reality. The canonical specimen is FlowSteward REQ-003 AC1 — *"reads credentials
from config/.env and connects to a fixture IMAP server"* — marked `passing` while: (a) no
`.env` loading, entry point, or template exists; and (b) the "fixture IMAP server" is the
build agent's own in-memory double, authored in the same step as the code. In V-model terms
**verification of a narrow sub-claim passed; validation against the user requirement was never
attempted** — a module-level double was used to discharge a system-level acceptance criterion,
and nothing in the AC's wording or status revealed the mismatch.

The root cause is not "AI vs human." Every acceptance criterion in the *successful* legacy
corpus (ExamEngineer) was also Claude-authored, yet it stayed reliable. The difference is
**house style**: ExamEngineer's ACs are granular and bound to named, greppable artifacts
(`_extract_yaml_files()` extracts `.yaml` files; null answers are silently skipped), and its
strongest tests produce **observable artifacts with a decoupled oracle** (output that can be
hashed/compared, signed off once). DevSteward's hastily-seeded house style produced abstract,
artifact-less ACs whose only oracle was a self-authored mock. **A coupled oracle cannot
disconfirm.**

The leverage point is the **seed**: the `/intake` interview is the one moment a human shapes
the REQ before the headless Autobahn. If intake institutionalises system-level, artifact-bound
acceptance criteria and a machine-readable test classification, the downstream engine inherits
a house style that can fail honestly. This REQ fixes the seed and makes the classification
first-class — a **routing key** the engine can steer phases by, validated for *presence* by
lint and shaped for *quality* by intake. It deliberately does **not** build the System-Test
phase, its flow-routing, or any lab harness — those are the follow-on REQs this one enables.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Each acceptance criterion carries a required `check:` field, enum `regression \| artifact \| manual`. | One field, three values matching the test kinds actually observed in a working corpus (ExamEngineer). It is a **routing key**, not decoration: it tells the engine which phase validates the criterion. |
| 2 | The three values map to the **V-model** and steer the flow. `regression` = module/unit scope, coupled/mock oracle, headless → **Build phase** (verification). `artifact` = system scope, **decoupled durable** oracle (a captured/golden/hashable observable produced by the lab; the engine reads only its pass/fail **signal**), headless → **System-Test phase** (validation). `manual` = system-scope **human** oracle, a **decision stop** (usually lab-assisted) → **also the System-Test phase**. | The oracle's coupling — not a test's name — decides whether a test can disconfirm. Verification (build) and validation (system test) are the two sides of the V. A human review *is* validation, hence system-level, hence inside the system-test phase — a module test needing human interaction is rare, and human validation usually needs the same lab tooling the phase stands up. |
| 3 | An `artifact` (system) test compares an **observable, captured result** (a produced file/report/captured message, hashed or golden-compared) and the engine consumes only its **pass/fail signal** — it never inspects the lab's internals. | This decoupling is what made ExamEngineer's strongest tests powerful: "connect and find mails" becomes "fetch *this* captured mail and compare". Lint cannot tell whether the lab equipment works; only the runtime signal can. |
| 4 | The classification **steers phase existence**: a REQ with only `regression` ACs runs no System-Test phase; any `artifact` *or* `manual` AC makes the System-Test (validation) phase apply. | "If there are no system tests, we don't need a system-test phase." The formal distinction is exactly what lets the process be conditional. |
| 5 | `steward lint` validates only that every AC declares a **valid `check:`** (present + in enum). It does **not** police test quality, granularity, lab function, or scope. | Lint is static; the worth of an `artifact` test is a runtime signal lint can't see. Granularity and system-level discipline are enforced where a human is present — **intake** — not by a brittle lint heuristic. The over-broad "externally-facing" gate and its waiver are dropped: almost everything touches the filesystem, and lint cannot enforce honest deferral. |
| 6 | `/intake` is the leverage point and is rewritten to seed the house style: interrogate acceptance toward **end-to-end, system-level chains with measurable, captured deliverables**; classify each AC's `check:`; and decide, while the human is present, (a) whether an optional **concept phase** (risk buy-down / spike, where final test specs and lab needs are frozen) is warranted, (b) which **lab** assets the System-Test phase will require, and (c) whether the develop work runs **fused** (one design+build session — the default) or **split** with an attended design review, for genuinely risky REQs. | Intake is the only human-in-the-loop seed; fixing house style here propagates to every headless step. The music is in the intake skill. The fused/split call belongs here because it must be made *while a human is present* — defaulting fused, declaring the exception (2026-06-10 assessment, plan 0011). |
| 7 | The **lab** (shared, versioned fixtures/harness whose **provenance** — reality-derived, owned — defines a test's level) is an **owned asset built by its own REQ**, not an inline double. This REQ ships the `check:` contract and declares the model; building the **System-Test phase + its flow-routing**, the independent **System Tester skill**, and the **first lab (IMAP)** are named follow-on REQs. | Independence = context independence + reality-derived fixtures; a first-class owned lab is what gives `artifact` checks trustworthy provenance. Ship the seed first; the consumers of the taxonomy come next. |
| 8 | REQ-027 **dogfoods its own taxonomy**: its deliverables (a schema field, the intake skill, handbook prose) are honestly `regression`-checkable; it carries **no `artifact`** test (there is nothing to validate in a lab) and **one `manual`** check — a human confirming a real intake run produces system-level, correctly-classified ACs. | The REQ practises what it preaches: it does not fake a system test, and it records the one genuinely human-oracle check as `manual` rather than auto-passing it. |
| 9 | Lint enforces `check:` on **active** REQs only (open/in-progress/blocked), mirroring the existing test-id rule: drafts may be incomplete by definition, terminal REQs are history. **No backfill** — stale drafts gain `check:` at promotion; `done` REQs are untouched. | Mass-stamping `check: regression` onto twenty unexamined done REQs would be the exact hollow-seeding antipattern this REQ exists to kill. The rule fires when a REQ becomes active — exactly when the engine is on the hook for it. (Interview 2026-06-10.) |
| 10 | The three intake-time declarations live in one **optional `process:` frontmatter block** — `develop: fused\|split`, `concept: bool`, `lab: [REQ-ids]` — with defaults `fused` / `false` / `[]`, schema-validated; lint resolves `lab` references like `depends_on`. Absent block ⇒ defaults, so every existing REQ stays valid. | One structured block keeps what is conceptually a single process declaration together and machine-readable — REQ-029 (fused/split) and REQ-030 (lab routing) consume it mechanically instead of parsing prose. (Interview 2026-06-10.) |
| 11 | The existing land gate stays **blind** to `check:` in this REQ — verifier and step source untouched. An engine-driven land of a REQ carrying `artifact`/`manual` ACs fails **loudly** (the gate tries to run the test string) until REQ-029/030 build the routing. | Failing loudly is the conservative direction (a skip is not green); `steward run` is parked until plan 0011 step 4 anyway, and REQ-029 reworks this exact code path next. Building a slice of routing here would be redone twice. (Interview 2026-06-10.) |
| 12 | Until REQ-030's decision stop exists, a `manual` check is discharged by **hand-flip + provenance**: the human reviewer sets the AC's `status: pass` and the sign-off (date, reviewer, what was reviewed) is recorded in `verified_by`/Notes. | The human *is* the oracle of a `manual` check — recording the verdict by hand is the honest act, not a bypass. Leaving the taxonomy REQ itself `done`-with-pending-validation would weaken `done` from day one. (Interview 2026-06-10.) |

## Requirement

The acceptance schema/linter gains a required per-criterion `check:` field
(`regression | artifact | manual`). `steward lint` enforces only that every AC of an
**active** REQ declares a valid value — nothing about test quality, nothing on drafts or
terminal REQs (Decision 9). The three values are a routing key that maps
acceptance onto the V-model: `regression` → **Build phase** (verification); `artifact`
(decoupled, lab-produced, signal) and `manual` (human-oracle decision stop) → the
**System-Test phase** (validation), which a REQ runs only if it declares at least one such
criterion.

`/intake` is rewritten to seed this house style: its interrogation drives acceptance toward
measurable, system-level, end-to-end deliverables; it classifies each criterion's `check:`;
and it records, in an optional `process:` frontmatter block (Decision 10), whether an
optional **concept phase** is taken, which **lab** assets the System-Test phase will require
(`lab:` REQ references, lint-resolved), and whether develop runs **fused** (default) or
**split** with an attended design review. The handbook documents the taxonomy, the V-model
phase mapping, the oracle definition, and shows one fully-tagged example acceptance block.

Building the System-Test phase, its flow-routing (the conditional phase execution and the
`manual` decision stop), the independent System Tester skill, and the first lab harness are
explicitly **out of scope** — named follow-on REQs this one enables.

## Notes

- **Out of scope (own REQs this one enables):** the **System-Test (validation) phase** and its
  flow-routing (conditional phase execution + the `manual` decision stop); the independent
  **System Tester skill** (runs `artifact`/`manual` checks in a context that never sees Build's
  diff); the first **lab harness** (a real/recorded IMAP server + seed corpus for the FlowSteward
  channel) as an owned, versioned asset; full engine support for the optional **concept phase**
  beyond its intake-time declaration.
- **V-model mapping:** Build = verification (left side); System-Test = validation (right side /
  field level, the user in the loop). `manual` is validation, therefore system-level, therefore
  inside the system-test phase — not a stray module-level stop.
- **Fused vs split (Decision 6c):** like the concept phase, this REQ only adds the intake-time
  *declaration*; the engine mechanics that consume it (one fused `develop` step by default, an
  attended design review when split is declared) are REQ-029's.
- **Concept phase:** optional, decided at intake (human present) and recorded in the REQ; the
  risk-buy-down/spike where final test specs and lab needs are frozen before the headless
  Autobahn. This REQ only adds its intake-time *declaration*, not engine phase mechanics.
- **Deferred validation:** when intake classifies an AC as `artifact`/`manual` but the lab or
  System-Test phase is not built yet, the deferral is tracked through the recorded **lab
  dependency** (which names the follow-on REQ that owns the asset) — not a separate per-AC waiver.
- **Interim `manual` discharge (Decision 12):** until REQ-030, a human reviewer flips the AC's
  `status: pass` by hand and records the sign-off (date, reviewer, scope) in `verified_by`/Notes.
  REQ-030's decision-stop mechanics replace the hand-flip; the provenance convention survives.
- **Hazard window (Decision 11, accepted):** between this REQ and REQ-029/030, an
  *engine-driven* land of a REQ with `artifact`/`manual` ACs fails loudly because the gate
  cannot run their test strings. This is intentional — conservative failure, and the window is
  covered: `steward run` stays parked (plan 0011) and migration REQs land interactively.
- **Oracle (glossary):** the part of a test that decides correct vs incorrect — distinct from the
  fixture (inputs/environment) and the system under test. `regression` oracles are coupled to the
  code (mock assertions); `artifact` oracles are decoupled and durable (golden/hashed observable
  output); `manual` oracles are human judgment.
- **Localization:** all schema/lint/skill/handbook text is technical English; no user-facing
  localized strings introduced.
- **Surfaces touched:** the acceptance linter (`devsteward/lint.py`); the acceptance parser
  (`AcceptanceCheck` in `devsteward/core/model.py` + `devsteward/profiles/req/reqfile.py`, which
  gain the `check:` field); the frontmatter schema (`devsteward/schema/req.schema.json`, the
  optional `process:` block); the `/intake` SKILL.md (the repo's `.claude/skills/intake/` and
  the stamped `devsteward/templates/.claude/skills/intake/`, kept identical); and the handbook
  (`devsteward/handbook/01-format.md` / `03-workflow.md`). The verifier
  (`devsteward/profiles/req/verify.py`) and step source are explicitly **not** touched
  (Decision 11).
