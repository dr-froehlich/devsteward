## Context

`STEWARD.md` (the shipped manual, line 214) promises that a REQ's frontmatter `status:`
flip, its `REQUIREMENTS_INDEX.md` row edit, and the code that satisfies it move in the
**same commit** — "the engine does this for you on a checkpoint." FlowSteward observed the
engine break that promise twice back-to-back on 2026-07-09: `steward checkpoint REQ-098`
(commit `3a71b62`, hand-fixed in `ecb49d3`) and `steward checkpoint REQ-099` (commit
`070d8c3`) each landed the code + tests + ledger while leaving the `status: draft → done`
frontmatter flip and the index-row `DRAFT → DONE` edit **written to the worktree but
uncommitted** — silently, with no error. Both were caught only because a human ran `git
status` out of habit. Full writeup: `flowsteward/docs/postmortems/2026-07-09-checkpoint-omits-status-flip.md`.

The flip *is* produced — `ReqDoneFlipper` (`profiles/req/checkpoint.py`) runs as the
`on_verified` seam *before* the commit and writes `status: done` to the REQ file and `DONE`
to the index. What fails is **staging**, and the cause is now confirmed (not a suspect):
REQ-076's boundary-delta scoping. The FlowSteward land was **headless** (`steward advance`/
`run` — the `checkpoint` event records `driver: headless`, so the postmortem's "steward
checkpoint" is the operation-generically, not the interactive verb), which goes through the
*scoped* commit path. `GitCli._stage_code(baseline)` rebuilds the index from `HEAD` and stages
only `dirty_paths() - baseline`; when the REQ file or the index is in the boundary set,
`on_verified`'s subsequent flip to those same paths is subtracted back out and left unstaged.
Reproduced at the seam in a throwaway repo: with `REQ-NNN.md` dirty at the boundary, the
commit omits it, the committed status stays `open`, and the worktree is left `M REQ-NNN.md`.

The heuristic's blind spot is **structural, not an edge case**. REQ-076 answers "which dirty
files belong in this commit?" by *timing* — dirty-at-boundary means "someone else's." But the
`REQUIREMENTS_INDEX.md` row-flip is written by **every** REQ's land; the shared index is
neither the session's code delta nor a concurrent session's foreign work — it is a *third
category*, the engine's own bookkeeping, that the timing model has no slot for. And it
**cascades**: REQ-098's land drops its index-flip → the index is left dirty → at REQ-099's
boundary the index is *still* dirty, so it lands in REQ-099's baseline → REQ-099's index-flip
is subtracted too. Once seeded, a `steward run` drops the flip of every subsequent step and
never self-heals — which is exactly why two REQs failed back-to-back with no concurrency.

**The fix corrects a category error rather than reverting or re-guessing** (decided with the
owner against reverting REQ-076 and against a ledger-level serialize). The timing scope exists
only to exclude a *concurrent session's code*; it must never see the engine's **own** writes.
The engine authors the flip (REQ frontmatter + index row) with full knowledge of those paths,
so it stages them **by knowledge, always** — outside the `dirty_paths() - baseline`
subtraction. REQ-076's disjoint-code sweep protection (REQ-081→REQ-090) is preserved
untouched; only the engine's own bookkeeping stops being guessed about.

Two guards failed to catch it. First, nothing asserts a clean tree after the land returns
success (REQ-032 promises "every terminal step outcome leaves a clean tree" but does not
verify it at the checkpoint tail). Second, the marker↔ledger reconciliation lint (REQ-028
AC5, `lint.py` rule 7) is **one-directional**: it fires only when frontmatter is `done` but
the ledger is not (marker-ahead) — line 177 `continue`s past every REQ whose frontmatter
is not `done`, so the *opposite* drift (ledger `done`, committed marker still `draft`) is
structurally invisible. And it reads the *working tree*, where the uncommitted flip makes
everything look consistent, so it cannot see a committed-HEAD-vs-worktree gap at all. This
same reconciliation was the top corrective action of the 2026-06-09 REQ-003a postmortem;
it landed (REQ-028) but only in the direction that postmortem's failure took.

If a checkpoint's dirty leftover is ever discarded (a `git clean`, a stash drop, a branch
tidy) before the human notices, the REQ silently reverts to reading `draft`/`DRAFT` in the
committed docs while the ledger and the shipped code say `done` — an unreconciled false
`draft` with no writer to correct it.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | **Correct REQ-076's category error** — the engine's own bookkeeping (REQ frontmatter flip + index row) is staged **by knowledge, always**, outside the `dirty_paths() - baseline` timing subtraction; the timing scope applies only to the session's genuinely-unknown code delta. | The heuristic can never classify a file many steps must write (the shared index). Rather than revert (loses the REQ-081 sweep protection) or serialize at the ledger (more machinery), the minimal root fix is to stop guessing about the engine's *own* writes. `on_verified` returns the paths it wrote; the commit force-includes them. |
| 2 | Cover **both** land tails through the shared `_land_checked` — headless `mechanical_land` (scoped, the confirmed cause) and interactive `checkpoint` (`baseline is None`, already whole-tree). | One correction serves both; the interactive path gets a regression guard even though its whole-tree stage was already immune. |
| 3 | Add a **post-land clean-tree assertion**: after the code commit, anything left dirty beyond the pre-boundary/concurrent set (`baseline − flip_paths`) fails loudly and rolls back, never returns DONE. | Strengthens REQ-032 from a promise into a checked invariant, and would have **stopped the cascade at REQ-098** — turning a silent, self-propagating drift into a loud halt. The backstop a human's `git status` habit was standing in for. |
| 4 | Make the marker↔ledger lint guard **symmetric** and read **committed HEAD**: hard-error when the ledger's delivering step is DONE but HEAD's frontmatter/index still read not-done, alongside the existing marker-ahead case. | The durable detector the 2026-06-09 postmortem asked for, in this drift's direction. Reading HEAD (not the worktree) is the only source that catches a flip written-but-not-committed — a worktree read looks consistent and misses it. |
| 5 | Do **not** revert REQ-076, add new git topology, or make a second commit. | House rule: prefer subtraction and don't solve information-flow with git topology. REQ-076's disjoint-code protection stands; the one commit is right — this makes it *complete* by keeping the engine's own writes out of the guess. |

## Requirement

After a green `steward checkpoint REQ-NNN develop` (and the headless `mechanical_land`
equivalent) on a REQ whose develop step lands:

- The **one authoritative code commit** at `HEAD` contains the REQ frontmatter `status: done`
  flip **and** the `REQUIREMENTS_INDEX.md` row `DONE` edit, together with the code/tests —
  never written to the worktree as an after-the-fact, uncommitted side effect.
- The working tree is **clean** (`git status --porcelain` empty apart from the trailing
  `.devsteward/` ledger commit the engine makes itself). A land that would leave the flip (or
  any tracked edit) unstaged **fails loudly** — it does not report success with a dirty tree.
- `steward lint` **hard-errors** when the ledger records a REQ's delivering step (`develop`,
  or legacy `land`) as DONE but the REQ's **committed** frontmatter status / index row still
  read not-`done` — the symmetric complement of the existing marker-ahead rule — reading
  committed HEAD so a written-but-uncommitted flip in the worktree cannot mask the drift.

## Notes

- **Every AC is `regression`:** the oracle is `git` and the engine's own recorded state —
  decoupled from any mock, runs headless in every develop gate, no lab and no live service.
  There is no `artifact`/`manual` check, so this REQ has no System-Test phase.
- **Root cause is confirmed** (headless scoped path + the shared-index cascade, reproduced at
  the seam), so the fix is precise: the engine's flip paths are staged unconditionally
  (`GitCli._stage_code` gains an `include` set fed from `on_verified`'s returned paths). AC2 is
  the reproduction (REQ file + index dirty at the boundary); AC1 guards the already-immune
  interactive path against regression.
- **Interaction with REQ-063's pre-commit capture gate:** `on_verified` runs after
  `_capture_gap` and before `_commit`; the fix must not perturb the capture-gate tree (the gate
  checks pure code, and the flip is not a source/test file the named tests read) — the clean-tree
  assertion runs on the *certified* land tail, not the gap path (a gap already sets FAILED and
  leaves the ledger-close commit as the only write).
- **Out of scope:** any new commit, branch, or worktree; the `.devsteward/` ledger's own
  trailing commit (unchanged, REQ-032/048); the `commit_deferred` (validate-pending) path, which
  intentionally does not flip — only the *landing* tail is in scope.
