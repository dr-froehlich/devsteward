## Context

REQ-011 enforced *one* edge of the branching model — the engine refuses to autocommit on the
production branch — and explicitly scoped the rest out (its Decision 3: "committing on the
integration branch is allowed"). So the `dev`↔feature seam was never specified, and the
documents that *do* speak to it push the wrong rule: the **intake skill** says "branch
first," and **CLAUDE.md** says REQ-sized work "is never typed directly onto `dev`." Read
literally, those send a *requirement declaration* onto a feature branch.

That is the bug, and it is not theoretical — it was just observed end-to-end. Filing two
REQs on two feature branches produced: (1) a merge conflict in `REQUIREMENTS_INDEX.md` and
`ROADMAP.md` (both branches appended rows to the same shared registry); (2) an id-allocation
race (REQ-017 was reserved on an unmergeable branch, forcing the next id to REQ-018); and
(3) a ledger with no obvious branch home, left dirty for the whole session. None of these are
execution mistakes — they are what *must* happen when shared, integration-level bookkeeping
is forked.

The error is a category confusion. A **requirement spec is a registry entry**, the
**roadmap is a shared plan**, and the **ledger is a global cursor** — none of these is
behavior to isolate and merge. You branch to *change behavior*, not to *declare intent*. The
real seam is **declaration vs. implementation**, not "REQ-sized work vs. everything else."

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | **Declaration lives on the integration branch**: intake (REQ frontmatter, index row, roadmap, scenarios) is committed directly on `dev`, never on a feature branch | Serializes id allocation, eliminates registry merge conflicts, and makes the backlog visible immediately. A draft REQ belongs on the integration/beta branch, not hidden on a branch |
| 2 | **Only implementation branches**: code + acceptance tests + the status-flip to `done` + the index `DONE`-sync go on a feature branch → plain merge into `dev` | This is the only artifact that changes behavior and benefits from isolated, atomic verification. The land-time index edit touches one row, so registry conflicts shrink from "every intake fights" to "rare, trivial" |
| 3 | **Plans are declaration by default**: a `docs/plans/NNNN` may live on `dev` (especially when planning more than one REQ to compare) **or** be committed alongside the implementation on the feature branch | A plan is a thinking artifact, not behavior. The "two plans in parallel" case *requires* `dev`; the "plan then immediately build" case is cleaner bundled with the code |
| 4 | **The ledger's home is `dev`, at rest** | The cursor is a single global pointer and `events.jsonl` is append-only. During a batch run the engine necessarily advances the ledger *on the feature branch* (it commits code + ledger together) and it reconciles on merge — so "current on `dev`" holds between runs, not mid-flight. Concurrent *implementation* of two REQs is out of scope (one cursor) |
| 5 | **Enforce it, don't just document it** — extend the REQ-011 guard so the executor refuses **build** and **land** steps on the integration branch (naming the fix: create a feature branch), while **design** is allowed there (plans may live on `dev`); intake needs no engine change because the engine never runs intake | REQ-011's own lesson: a branching rule asserted only in prose is a doc/reality gap. The symmetric partner to the production-branch guard is an integration-branch guard on the steps that *implement* |

## Requirement

Make "declaration on the integration branch, implementation on a feature branch" both the
documented house rule and an engine-enforced one.

### Conventions (declaration — amended on `dev` as part of this change)

1. The **intake skill** no longer says "branch first." It commits intake on the current
   integration branch (frontmatter + index row + roadmap together, co-author trailer).
2. **CLAUDE.md** (and the consumer `CLAUDE.md.tmpl`) state the declaration/implementation
   seam: intake, roadmap, plans, and the ledger live on `dev`; only implementation branches.
3. **`handbook/03-workflow.md`** describes the same seam.

### Enforcement (implementation — to be built on a feature branch)

4. The executor, before running a step, refuses a **`build`** or **`land`** step when the
   current branch is the configured `integration_branch` — it invokes no `claude`, commits
   nothing, leaves the step `PENDING`, and prints a guard message naming the branch and the
   fix (create a feature branch). A **`design`** step proceeds on the integration branch.
5. On a feature branch (neither production nor integration) every step proceeds unchanged.
   The existing production-branch refusal (REQ-011) is untouched.

### Out of scope

- Auto-creating feature branches or opening PRs (REQ-011 Decision 1 still holds — the engine
  guards, it does not manage git topology).
- Concurrent implementation of two REQs against one ledger (single cursor — Decision 4).
- Moving the ledger entirely off feature branches (would need `steward checkpoint`,
  [[REQ-018]]) — a separate, optional refinement.

## Notes

- **Why this is REQ-011's missing half.** REQ-011 closed the `dev`→`main` edge and deferred
  the `dev`↔feature edge by decision. This REQ closes that edge with the same philosophy
  (enforce, don't merely assert) and the same mechanism (a precheck branch refusal).
- **Self-demonstrating:** this REQ was intaked **on `dev`, with no feature branch** — the
  first artifact produced under the rule it specifies. The convention amendments (1–3) ride
  with the declaration on `dev`; the engine guard (4–5) is the implementation that branches.
- **The id race is the clearest tell.** Allocating `REQ-NNN` is reading-and-incrementing a
  shared counter; doing it on a fork is reading a stale counter. Serializing intake on `dev`
  removes the race by construction.
