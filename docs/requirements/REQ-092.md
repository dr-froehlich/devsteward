## Context

The handbook states the method's second rule plainly: *"REQ-001 is a frozen north star.
Direction changes by **superseding** it with a new REQ, never by quietly weakening it"*
(`devsteward/handbook/_00-method.qmd`). `steward lint` then refuses exactly that move —
rule 6 (`devsteward/lint.py:166-169`) is unconditional:

```python
north = next((r for r in reqs if r.id == "REQ-001"), None)
if north is not None and north.status in ("dropped", "superseded"):
    problems.append("REQ-001 (north star) must not be dropped or superseded")
```

So the engine forbids its own documented direction change. The rule's *intent* is sound
and worth keeping — a project must never be left with no compass — but its *mechanism* is
wrong: it pins the compass to the literal id `REQ-001` forever, which conflates "the
project has a north star" with "REQ-001 is the north star". Those come apart the first
time a project's direction actually changes.

It has now come apart in the field. DriveSteward's REQ-016 is a written, concept-phase
north star that supersedes its REQ-001 after fifteen REQs of evidence — a widened
audience, whole-drive automation, a history that outlives the run. Its own land step must
flip REQ-001 to `superseded` and move CLAUDE.md's pointer; `steward checkpoint REQ-016
develop` cannot complete because lint refuses the flip. The REQ is blocked on the engine,
not on its own work. Every consumer shares one pipx editable engine, so the same wall
stands in front of memzy, THermo, FlowSteward and every future project the day its
direction changes — which is the one moment this rule is guaranteed to be hit.

The fix is subtraction of the wrong half: keep "never lose the compass", drop "the compass
is REQ-001". Lint follows the `supersedes` chain from REQ-001 and refuses only when the
walk ends without a live heir that claims the role.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | **The rule becomes "the project always has a live compass", not "REQ-001 is live"** | The intent lint was reaching for. Pinning the id was never the invariant anyone wanted; it was the cheapest thing to write when no project had yet changed direction. Operator's ruling, 2026-08-22 |
| 2 | **An heir must both declare `supersedes: REQ-001` (transitively) and carry `north-star` in `tags:`** | Two claims, deliberately conjoined: the chain says *which* REQ replaces it, the tag says the replacement is *the compass* rather than a narrow REQ that happens to retire the old one. A supersede alone is too loose — a REQ can supersede the north star for a scoped reason without becoming the project's direction. Operator's choice over the simpler chain-only rule; devsteward's own REQ-001 and DriveSteward's REQ-016 already carry the tag, so the convention is observed, not invented |
| 3 | **The chain is walked transitively** | 001 → 016 → 042 is the normal shape of a project that changes direction twice. A one-hop rule would refuse the second supersede for no reason |
| 4 | **Any non-terminal status counts as live — `draft` included; only `dropped`/`superseded` heirs do not** | Operator's ruling. The rule names the compass, it does not adjudicate whether the compass has been adopted; requiring `open` would trap an operator who retires REQ-001 in the same commit that writes its replacement, and the refusal message would be the only place that trap is documented. A project that prefers to keep REQ-001 live until its heir is activated (DriveSteward REQ-016's own doctrine) is free to — the engine does not impose it |
| 5 | **One status-agnostic rule: `dropped` and `superseded` are treated alike** | Operator's ruling. What matters is whether REQ-001 has left live status leaving nothing behind, not by which verb. One rule, one refusal message, no second branch to keep in step |
| 6 | **The refusal message names the cure** | The reader is a session or an operator hitting a hard stop mid-land, with no reason to know what a "north-star tag" is. The message states both conditions an heir must meet |
| 7 | **`/intake` and `/bootstrap` learn to follow the chain; the handbook is left alone** | Operator's scoping. The intake skill today tells a session to read `REQ-001.md` as the north star — after a supersede that is the *retired* compass, and every intake downstream would be steered by it. The handbook's rule 2 already says the right thing; it needed the engine to catch up, not rewording |
| 8 | **No schema change** | `tags:` is already a free-form unique string array, and `supersedes:` already accepts a string or a list. The rule is a lint check over data the format holds today |
| 9 | **Proof is devsteward-side regression only; no cross-repo touch** | Operator's ruling. The rule is decidable from a set of REQ files, so synthetic requirement dirs disconfirm it completely and headlessly. DriveSteward's unblock is the operator's own `steward checkpoint REQ-016 develop` after this lands, not an acceptance criterion of this REQ |

## Requirement

### The rule

`steward lint` rule 6 is replaced. Given the loaded REQ set:

- If `REQ-001` is absent, or its status is anything other than `dropped`/`superseded`,
  the rule is silent (today's behaviour for a live compass).
- If `REQ-001`'s status is `dropped` or `superseded`, lint walks the `supersedes` graph
  outward from `REQ-001`: a REQ is an **heir** when its `supersedes` (a string or a list)
  contains `REQ-001`, or contains a REQ that is itself an heir. The walk terminates on
  cycles.
- The rule is **silent** when at least one heir is *live* — its status is not `dropped`
  and not `superseded` — **and** carries `north-star` in `tags:`.
- Otherwise lint reports one problem naming both conditions an heir must satisfy.

The docstring's numbered list of checks is updated to state the rule as implemented, so
the module's contract and its code do not diverge the way the handbook and the code did.

### The skills

`/intake` and `/bootstrap` are taught that the north star is *the live compass*, not
literally `REQ-001`: orientation follows the `supersedes` chain from `REQ-001` to the
live north-star-tagged heir and reads that, and a session that supersedes the compass
knows the heir must carry the `north-star` tag or the land will be refused. The repo
skills and their stamped templates are one inode each (`.claude/skills/<name>/SKILL.md` ↔
`devsteward/templates/.claude/skills/<name>/SKILL.md`) — edited once, never twice.


## Notes

**What each criterion is worth.** AC1 is the disconfirmable one: the rule is a pure
function of a REQ set, so synthetic dirs exercise every branch including the ones no real
project has reached yet (the two-hop chain, the dead heir). AC2 is mixed and filed
honestly — the self-lint half genuinely disconfirms (a rewrite that breaks the live-REQ-001
path turns the engine's own repo red), while the skill-surface half has a coupled oracle,
the same session writing the sentence and the test that looks for it. It is kept because
the *hardlink* assertion inside it catches a real, repeatedly-hit failure — a template
edited apart from its repo twin — and because `tests/test_req071_doctrine_surfaces.py` is
the established precedent for doctrine-surface checks in this repo.

**Not in scope.** No change to `devsteward/handbook/` (Decision 7). No change to
`req.schema.json` (Decision 8) — the `north-star` tag stays a convention lint reads, not a
schema-required field, so no existing project's REQs become invalid. No change to
`devsteward/templates/tests/test_project_initialized.py`: it asserts REQ-001 exists and
that its index row matches its frontmatter, both of which stay true after a supersede —
it never asserted a status. No change to `steward activate`'s refusal to reopen a
`superseded` REQ (`devsteward/lifecycle.py`): retiring the compass and reopening a
finished REQ are different questions and the latter is unaffected. No cross-repo work in
DriveSteward (Decision 9).

**Required environment:** none — the acceptance tests build their own requirement
directories in tmp paths and read no service, secret or network.

**Why this is not a `live` or `artifact` check.** The oracle is a lint problem list over
files the test writes itself; there is no system-scope surface to observe and no lab
asset. It is unit-scoped verification and belongs in the develop gate.
