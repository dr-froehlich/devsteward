## Context

[REQ-016](REQ-016.md)'s backlog opens with the need this REQ takes up: *"the default
operation is a fully automatic smart refresh, which improves the drive's read performance
based on measurements before and after, with a target to achieve the best possible read
performance for that particular drive across the mapped part of the drive and within safe
operating parameters"* (`auto-smart-refresh`), and beside it *"a drive's true parameters are
determined during probing and/or the refresh process itself"* (`drive-true-parameters`).

The tool can already do each half. It cannot do them together, and this REQ is about why
that matters more than it looks.

### What the current shape costs, measured

Today a refresh is a pipeline of separate whole-device acts: three coarse passes → a fine
pass over nominated extents → a threshold from a crisp anchor → a work list → `refresh
--from-scan` → read-back verification → **a second whole-device scan** → `compare`. On the
Dell (`session-c2`, `Micron_M550_mSATA_512GB`, 1 000 215 216 blocks) that came to a before
scan of **5 876.0 s**, a refresh of 368 blocks in **0.27 s**, and an after scan of
**5 405.0 s**. Three hours of work, of which the writing is nine parts in ten million.

Chunking does not reduce the reading — every extent is still read once per persistence pass.
What it removes is the second whole-device sweep, because the read-back the invariant already
requires *is* the after-measurement. That is roughly half the wall clock of every run the tool
will ever make, and it is the least interesting of the three reasons to do it.

### The work list goes stale, and the direction is not the one anybody assumed

REQ-012 finding 34 recorded that the flagged population on the worn `SKHynix_HFM512GD3HX015N`
barely reproduces between scans. **Recomputed for this intake from the committed Session B
captures** — the per-block, per-pass latencies in `fine.weak_blocks` of
`session-b-scan-{before,mid}.json`, each written LBA of `session-b-wave1.jsonl` mapped to its
4096-byte rewrite unit — the picture is sharper than finding 34 stated, and it points the
other way:

| between the before and mid scans, 37 minutes apart | any pass ≥ 15 ms | slow in **all three** passes |
|---|---|---|
| slow before | 1 601 | 390 |
| slow at mid | 885 | 254 |
| still slow | 292 | **2** |
| **left the slow state** | 1 309 | 388 |
| … of those **not** inside a rewrite unit wave 1 wrote | **0** | **0** |
| **newly slow at mid** | 593 | 252 |
| … of those inside a rewrite unit wave 1 wrote | **0** | 7 |

Two things follow, and only the second was suspected.

**Nothing has ever been observed getting better on its own.** Every block that left the
~20 ms state was inside a unit the refresh reprogrammed — zero exceptions, under either
reading of "slow". The improvement tracks the write exactly. (REQ-012 finding 21, which reads
like spontaneous recovery, is not: those 40 Lenovo blocks sat at 0.2554 ms and moved to
0.2489 ms — **2.6 %** — and merely crossed a bar. That is threshold reshuffling of a marginal
population, a different phenomenon from a block leaving a 20 ms state, and this REQ keeps the
two apart.)

**Blocks acquire the state, unbidden, in tens of minutes.** 593 blocks that were fine in all
three passes of the before scan read ≥ 15 ms 37 minutes later, and **not one of them was
inside a unit anything had written**. Under the strict reading the turnover is near total: of
the 254 persistently-slow blocks at mid, **2** had been persistently slow before.

So the ~20 ms state is not a property of a block. It is a state the flash moves into and out
of, on a timescale shorter than a single run of this tool.

That is not, on its own, an argument that a work list "goes stale" — it is an argument that
**there is no fixed truth about the drive for an open-loop plan to be a plan about.** A
process that measures once, decides once and then executes cannot know whether its writes
landed on the right cells, whether they helped, or whether the drive moved underneath it while
it worked. Reference values derived at the start are the drive's state at the start. Every one
of those gaps is closed by measuring the effect of each write while there is still a run left
to act on what the measurement says (Decision 3).

### The instrument is not what causes it — the Lenovo says so

|  | before scan | after scan |
|---|---|---|
| whole device, 3 passes | 1 146 s | 1 145 s |
| max block latency seen | **0.433 ms** | **0.413 ms** |
| blocks ≥ 5 ms | **0** | **0** |
| flagged | 88 | 104 (48 in common) |

Same code, same read pattern, two whole-device sweeps 47 minutes apart, on
`SAMSUNG MZVL21T0HCLR-00BL7`: the ~20 ms tier **does not occur at all**. That refutes read
disturb from the tool's own fine pass as a general mechanism — the reads do not manufacture
the effect. It cannot refute disturb on already-marginal media, because the Lenovo has none;
but that residual claim is much weaker, and if it were true the tool would be surfacing cells
that are close to the edge and then refreshing them.

The Lenovo's own turnover is entirely the marginal kind — everything under 0.44 ms against a
0.069 ms anchor. **These are two populations, not one**, and the tool currently applies one
rule to both. [REQ-013](REQ-013.md) anticipated exactly this when it built the magnitude bar
beside the persistence bar and recorded `flagged_by` per block, *"so a later REQ can ask
whether the two populations respond differently to a rewrite."* This is that REQ.

### The drive cannot be asked to exonerate a reading — checked, not assumed

The operator's requirement, given at this intake, is that the algorithm be able to rule out
spurious effects such as the drive's own housekeeping. The obvious first move is to ask the
drive. It does not work, and the captures say why.

**NVMe.** Across Session B, Data Units Written moved **+34** and **+56** against the 33.5 and
55.5 units DriveSteward itself asked for — half a unit of slack. That proves less than it
appears: NVMe defines Data Units Written as units *the host* wrote, so internal relocation is
excluded by specification. The counter cannot see housekeeping even in principle.

**SATA.** Across `session-c2` — two whole-device scans, ~1.5 TB read, 368 blocks written:

```
Hardware_ECC_Recovered    15 → 15
Reported_Uncorrect        14 → 14
Wear_Leveling_Count      217 → 217
Total_LBAs_Written  ...254 → ...622      (exactly +368)
```

Nothing moved but the host write counter, by exactly what was asked for. But
`Total_LBAs_Written` is host-only too, and `Wear_Leveling_Count` is average P/E cycles — far
too coarse to register a session. Vendor logs that do see NAND-side writes (OCP's physical
media units written) are not present on consumer drives.

**Standard SMART, on both transports, counts host traffic and gross wear and is blind to
background relocation at session timescales.** Ruling out spurious effects therefore cannot be
delegated to a counter. It has to be built into how the algorithm reads, and every mechanism
that can do it is affordable only because the work is chunked — in the two-scan shape each one
would cost another whole-device pass.

### What is not available, and is said plainly

The `SKHynix_HFM512GD3HX015N` — the only drive this project has ever met that exhibits the
~20 ms tier — was borrowed, was refreshed, and went home. **This project currently has no
weak specimen.** The Micron flags 368 blocks at the frozen rule and has never produced a
reading above 5 ms; the Lenovo produces nothing at all. The operator is looking for one.

That constrains this REQ and does not block it. The loop, its discriminators, its resume
behaviour and its parameter measurement are all disconfirmable against [REQ-003](REQ-003.md)
corpora and against the two drives in hand. What cannot be proved without a susceptible drive
is how the loop behaves on the tier it was designed for, and whether a refresh holds. Those
are named in Notes as owed rather than quietly filed under a synthetic fixture — because a
loop device's latency does not respond to being written, so no corpus this project can build
is able to stand in for the answer.

## Requirement

### The loop

A new verb walks the mapped part of the device in chunks and, for each chunk, **reads,
discriminates, decides, writes, verifies, re-measures and acts on what it measured** before it
reports and moves on. The last stage is what makes it a loop rather than a plan in small
pieces, and it is what Decision 3 asks for. Each stage is stated as behaviour, not as an
implementation:

- **Reads** the chunk at the probed read unit, in an order that does not correlate slowness
  with position, and again after a pipeline lag, so that the persistence rule
  [REQ-013](REQ-013.md) froze is evaluated across genuinely separated readings.
- **Discriminates** candidates from artefacts *before* spending a write: a reading at or below
  the drive's measured cache-hit floor did not reach the media and is not evidence of
  anything; a candidate that stops being slow after a quiescent interval, with nothing
  written, was not the media; a candidate whose repeated readings do not reproduce is not a
  candidate. Each discrimination is recorded with what it decided and why.
- **Decides** against a crisp anchor formed from flash this run has itself programmed, with a
  stated bootstrap for the first chunk and a stated rule that keeps the anchor tracking the
  drive's present state rather than the run's position on it.
- **Writes** whole rewrite units, aligned, byte-identical, journalled before the write, and
  refuses anything that is not — the check REQ-012 built at the write path, now guarding a
  work list this tool composed rather than one it read from a file.
- **Verifies** by read-back and hash, unchanged.
- **Re-measures** the written units, and the units adjacent to them that it did not write,
  after the lag that makes the reading a media reading — so that *did this rewrite work* and
  *did it disturb anything* are both answered during the run and not an hour later.
- **Acts** on the answer, which is the stage that closes the loop:
  - a unit that did not come back crisp is retried, up to a bounded number of attempts, and a
    unit that survives them is recorded as **unresponsive** rather than quietly counted as
    refreshed — the distinction `rewrite-response-health` will be built on;
  - a unit that was not written and got **worse** is recorded as disturbed, and is itself a
    candidate for the next chunk;
  - the reference values the next chunk decides against are re-derived from the units this
    chunk programmed, so the run's own writes calibrate it as it goes;
  - and when the answers say the run is not helping — writes that do not improve, writes that
    fail, or disturbance that outruns repair — the run **stops and says so**, rather than
    spending the rest of the drive's endurance proving it. A tool that can find itself doing
    harm has to be able to put the tools down, which is REQ-016's invariant applied to the
    tool's own effect rather than to a single write.

The whole of it is resumable. An interruption at any point leaves every block byte-identical
to what it held before, and a resumed run does not have to redo work whose decision and write
both survived.

### What the operator sees while it runs

Progress and running efficacy appear on **stderr** as the run proceeds — blocks completed
against blocks planned, the position reached, and per chunk what was flagged, what was
discriminated away, what was written and what came back crisp. stdout stays the report's
channel and `--json` stays a machine contract, per [REQ-011](REQ-011.md) Decision 3 and
[REQ-018](REQ-018.md): no prompt, no progress and no prose on stdout, ever.

### The drive's true parameters, measured while working

The run resolves and records, each with its provenance in the manner REQ-012 established
(`probed`, `given`, `fallback`, `floor`, `not-determined`):

- **the cache-hit floor** — the cost of an answer that did not reach the media;
- **the cache-miss floor** — the crisp cost of an answer that did;
- **the read unit**, as REQ-013 probes it today;
- **the rewrite unit**, floored at the indirection unit as REQ-012 Decision 14 requires;
- **the program page**, where the opportunistic neighbourhood probe of Decision 8 can fire,
  and `not-determined` where it cannot.

A capture states which of these were measured on this drive in this run and which were
inherited or defaulted, so that no reader has to guess whether a number came from the drive.

### What the run may claim

The report distinguishes what the run improved from what it merely observed, and says what it
could not rule out. Where the witness units moved, where the discriminators were inconclusive,
or where the drive's own state changed under the run, the report says so rather than
presenting a clean improvement. **"Nothing improved" and "this run cannot tell you" both
remain first-class answers** (REQ-016 Decision 10).

## Notes

**Develop-session obligations, performed attended and deliberately not routed to the
System-Test phase** (Decision 12). A fresh System Tester never sees the diff and cannot fix
what it finds, so these belong in the session that can iterate on them:

- **The concept phase measures on hardware.** The cache floors, the quiescent behaviour, the
  eviction distance that sets the pipeline lag, and the in-flight crisp anchor against
  REQ-013's frozen one, on both drives in hand — `LENOVO 20XW005VGE` /
  `SAMSUNG MZVL21T0HCLR-00BL7` (NVMe, healthy) and the operator's Dell /
  `Micron_M550_mSATA_512GB` (SATA, 368 blocks flagged at the frozen rule). Booted from the
  REQ-010 stick, as every hardware session in this project is.
- **The post-freeze develop phase runs the loop end to end on the Micron**, which is the
  operator's own drive, is writable, is the transport this project supports worst, and is
  where a procedural problem costs an evening rather than a favour (REQ-012 Decision 10).

**What this REQ cannot prove, and where it is owed.** The `SKHynix_HFM512GD3HX015N` went home
refreshed and this project has no drive that exhibits the ~20 ms tier. Three things therefore
stay unproven when this REQ lands, and none of them is being quietly filed under a synthetic
fixture:

- how the loop behaves on the tier it was designed for;
- whether a refresh **holds** — the late-revisit measurement the loop makes possible, which is
  the question `rewrite-response-health` in REQ-016's backlog will need answered;
- the program page, where Decision 8's neighbourhood probe needs weak neighbours to fire.

**A REQ-003 corpus cannot stand in for any of them**, and that limit is worth stating so that
nobody later builds a fixture that appears to close them: a loop device's latency is injected
by `dm-delay` and does not respond to being written, so a synthetic corpus can prove the
loop's control flow, its discrimination, its alignment and its crash behaviour, and can never
prove that a rewrite repaired anything. The evidence that it does is REQ-012 finding 31 on
real hardware — 840 blocks at 20.414 ms before, 0.068 ms after — and it stays that.

The same limit is what makes Decision 3(b) and 3(c) testable today, which is worth saying
because it looks like a coincidence and is not. On a corpus, **no rewrite ever helps** — so the
case the tool must survive without a specimen, a drive that does not respond to being
refreshed, is the corpus's default behaviour rather than a fixture anyone has to contrive
(AC10). Disturbance is the other way round and is honest about it: the harness simulates the
*observation* while no loop device can produce the physics, so AC11 tests that the tool looks
at what it did not write, not that program disturb is real.

These are **owed to a session with a susceptible drive**, which the operator is looking for.
They are not homed in a named follow-on REQ because no such REQ should be allocated before the
specimen exists — an id in the index reads as a commitment to build a thing in an order, which
is what REQ-016 Decision 3 and the backlog's own preamble reject.

**What this REQ takes up from the backlog.** `auto-smart-refresh` — the algorithm, not yet the
default operation, which is a later change of default (Decision 2) and depends on the boot menu
`boot-to-menu` describes. `drive-true-parameters` — the cache floors and, opportunistically,
the program page. It **supplies the measurement** `rewrite-response-health` will need without
taking that item up: the loop produces the response data, and the health model built on it is
downstream and needs the specimen this project does not have.

**Explicitly out of scope.** No dashboard, no graphics, no history, no cross-run drive
identity — `performance-dashboard`, `live-dashboard`, `session-record-on-stick`,
`history-manager` and `drive-recognised` are separate needs and this REQ only owes them a
stream of data that is fit to render. No change to `--full` or to `full-rewrite-option`. No
change to REQ-006's hazard register or to any refusal it makes. No causal attribution of the
improvement (Decision 5). No change to REQ-013's frozen multipliers: the concept phase compares
its in-flight anchor against them and a disagreement is argued in the REQ that owns the number,
not folded in here.
